파이썬에는 `pip`, Rust에는 `cargo`가 있지만 C++에는 [정해진 패키지 관리자가 없습니다](#/read/basics/package-managers). 어려운 까닭은 [ABI](#/read/cpp-stl/impl-abi)입니다. 컴파일된 라이브러리는 컴파일러, 표준 라이브러리, 빌드 종류가 맞아야 섞을 수 있어서 "바이너리 하나를 내려받는다"로 끝나지 않습니다. C++의 패키지 관리자는 **내 설정에 맞는 바이너리를 찾아 주거나, 없으면 그 설정으로 빌드해 주는** 도구입니다.

## 길 넷

| 길 | 어디서 오는가 | 버전을 고정하는 법 |
| --- | --- | --- |
| OS 패키지 (`apt`) | 배포판이 빌드해 둔 것 | 배포판의 판에 묶인다 |
| `FetchContent` | 소스를 내려받아 내 프로젝트와 함께 빌드 | 태그나 커밋 |
| vcpkg | 포트(빌드 조리법)를 따라 내 컴퓨터에서 빌드 | 기준선(포트 모음의 커밋) |
| Conan | 조리법, 그리고 설정별로 미리 빌드된 바이너리 | 버전과 리비전, 잠금 파일 |

어느 길로 오든 프로젝트의 `CMakeLists.txt`는 `find_package`와 타깃 이름만 압니다. 앞 페이지의 `station`은 손으로 설치한 `sensorkit`과 아래의 Conan 패키지를 **같은 파일로** 썼습니다.

## Conan: 설정이 바이너리의 이름이다

Conan은 "무엇으로 어떻게 빌드하는가"를 프로파일에 적습니다.

```ini
[settings]
os=Linux
arch=x86_64
compiler=gcc
compiler.version=14
compiler.cppstd=23
compiler.libcxx=libstdc++11
build_type=Release

[buildenv]
CC=gcc-14
CXX=g++-14
```

패키지를 만드는 쪽은 조리법(`conanfile.py`)을 씁니다. [앞 페이지](#/read/cpp-advanced/tool-cmake)의 `sensorkit`에 붙였습니다.

```python
# conanfile.py: sensorkit을 Conan 패키지로 만드는 조리법
from conan import ConanFile
from conan.tools.cmake import CMake, cmake_layout


class SensorkitRecipe(ConanFile):
    name = "sensorkit"
    version = "1.2.0"
    settings = "os", "compiler", "build_type", "arch"   # 다르면 다른 바이너리
    generators = "CMakeToolchain"
    exports_sources = ("CMakeLists.txt", "cmake/*", "include/*", "src/*", "apps/*",
                       "tests/*")

    def layout(self):
        cmake_layout(self)

    def build(self):
        cmake = CMake(self)
        cmake.configure()
        cmake.build()

    def package(self):
        CMake(self).install()

    def package_info(self):
        self.cpp_info.libs = ["sensorkit"]
        self.cpp_info.defines = ["SENSORKIT_MAX_TAPS=8"]
        self.cpp_info.set_property("cmake_target_name", "sensorkit::sensorkit")
```

```text nocheck
$ conan create . --profile gcc14.profile
Package 'd01c869d3652bb2e91f06fcd21506b4f20d90fce' created
```

끝의 긴 수가 **패키지 ID**입니다. 이름과 버전이 아니라 `settings`의 값들에서 계산됩니다. 쓰는 쪽은 필요한 것만 적습니다.

```ini
[requires]
sensorkit/1.2.0

[generators]
CMakeDeps
CMakeToolchain

[layout]
cmake_layout
```

```text nocheck
$ conan install . --profile gcc14.profile
sensorkit/1.2.0: Already installed! (1 of 1)
$ cmake --preset conan-release && cmake --build --preset conan-release
$ ./build/Release/station
1.5 (sensorkit 1.2.0)
```

`conan install`이 `find_package`가 읽을 파일과 CMake 프리셋을 만들어 줍니다. 이제 같은 것을 디버그로 달라고 해 봅니다.

```text nocheck
$ conan install . --profile gcc14.profile -s build_type=Debug
ERROR: Missing binary: sensorkit/1.2.0:758ebddaeb56b2e4a9cecc51090c635e29a14f21
$ conan install . --profile gcc14.profile -s build_type=Debug --build=missing
Package '758ebddaeb56b2e4a9cecc51090c635e29a14f21' created
```

설정 하나가 바뀌자 ID가 달라졌고, 그 ID의 바이너리가 없으니 조리법으로 새로 빌드했습니다. 릴리스와 디버그, GCC 13과 14, x86-64와 ARM의 바이너리가 한 저장소에 나란히 있을 수 있는 까닭입니다. [섞으면 안 되는 것](#/read/cpp-stl/impl-abi)을 도구가 이름으로 갈라 둡니다.

버전은 잠금 파일로 고정합니다. `conan lock create .`가 만든 `conan.lock`에는 버전만이 아니라 조리법의 리비전까지 적힙니다.

```text nocheck
"sensorkit/1.2.0#d9a8311a7822575a27caf4fb7b6f1e16%1795233224.6053972"
```

<Note>
여기서는 바깥 저장소 없이(`--no-remote`) 직접 만든 패키지로만 돌렸습니다. 공개 저장소(ConanCenter)의 라이브러리를 쓰는 일도 `[requires]`에 한 줄을 적는 같은 절차입니다. 그쪽은 이 책의 환경에서 돌려 보지 못했습니다.
</Note>

## vcpkg: 포트와 기준선

vcpkg는 프로젝트에 `vcpkg.json`을 두고, CMake의 툴체인 파일 자리에 vcpkg의 것을 넣습니다. 그러면 설정할 때 vcpkg가 빠진 의존을 빌드해 프로젝트 폴더 아래(`vcpkg_installed`)에 놓습니다.

```json
{
    "name": "station",
    "version": "0.1.0",
    "dependencies": [
        "fmt",
        { "name": "nlohmann-json", "version>=": "3.11.0" }
    ],
    "builtin-baseline": "<vcpkg 저장소의 커밋 해시 40자>"
}
```

```sh
cmake -S . -B build \
    -DCMAKE_TOOLCHAIN_FILE=$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake
cmake --build build
```

| | vcpkg | Conan |
| --- | --- | --- |
| 기본 동작 | 소스에서 빌드하고 결과를 캐시한다 | 맞는 바이너리를 받고, 없으면 빌드한다 |
| 버전의 기준 | 기준선 하나가 모든 포트의 판을 정한다 | 패키지마다 버전, 잠금 파일 |
| 대상 플랫폼 | 트리플릿 (`x64-linux`, `arm64-linux`) | 프로파일의 `settings` |
| 조리법의 말 | CMake 스크립트 | 파이썬 |

기준선은 "포트 모음 전체의 어느 날 모습"을 가리키는 커밋입니다. 올리면 모든 의존이 함께 올라갑니다. 하나만 다르게 하려면 `overrides`에 적습니다. 다른 CPU용으로 빌드할 때는 트리플릿을 고르고, 내 [툴체인 파일](#/read/cpp-advanced/tool-cmake)은 `VCPKG_CHAINLOAD_TOOLCHAIN_FILE`로 넘깁니다.

<Note kind="warn">
이 절은 돌려 보지 못했습니다. vcpkg를 내려받아 실행하는 일이 이 책의 환경에서 막혀 있습니다. 파일의 모양과 옵션은 2026년 11월의 공식 문서를 따랐습니다.
</Note>

## 어느 쪽이든 지킬 것

- **버전을 고정하고 저장소에 넣습니다.** `conan.lock`이든 기준선이든, 오늘 빌드한 것과 반년 뒤에 빌드한 것이 같아야 합니다. [CI](#/read/cpp-advanced/tool-ci)가 그 파일로 빌드합니다.
- **`CMakeLists.txt`에 패키지 관리자를 적지 않습니다.** `find_package`와 타깃까지만 적고, 어디서 찾을지는 프리셋과 툴체인 파일이 정합니다. 그래야 배포판 패키지로도, 다른 관리자로도 빌드됩니다.
- **가져온 코드는 내 컴퓨터에서 실행됩니다.** 조리법은 빌드할 때 도는 프로그램입니다. 의존 하나를 더하는 일은 그 코드와 그것이 다시 끌어오는 코드를 모두 믿는 일입니다. 꼭 필요한 것만 더합니다.

## 정리

- C++의 패키지 관리자는 내 컴파일러와 설정에 맞는 바이너리를 구해 주는 도구다. Conan은 설정에서 패키지 ID를 계산한다
- 디버그로 바꾸자 ID가 달라져 `Missing binary`가 났고, `--build=missing`으로 조리법에서 새로 빌드했다
- 버전은 잠금 파일이나 기준선으로 고정하고, `CMakeLists.txt`는 `find_package`와 타깃만 알게 한다
