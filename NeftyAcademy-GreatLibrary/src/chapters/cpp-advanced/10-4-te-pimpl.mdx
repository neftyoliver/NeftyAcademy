export const summary = 'pimpl이 막아 주는 다시 컴파일과 치르는 호출 값을 재고, const 전파와 힙 없는 변형을 만든다';

pimpl의 모양과 소멸자를 `.cpp`에 두는 까닭은 [「전방 선언과 pimpl」](#/read/cpp-syntax/mod-pimpl)에서 봤습니다. 거기서는 "다시 컴파일하지 않는다", "포인터를 한 번 거친다"고만 했습니다. 여기서는 그 둘을 **재고**, 흔한 두 가지 약점인 `const`와 힙 할당을 고친 변형을 봅니다. pimpl도 타입 지우기의 한 갈래입니다. 지우는 대상이 여러 타입이 아니라 **구현 하나**일 뿐입니다.

## 방화벽이 막아 주는 것

`std::regex`, `std::map`, `std::vector<std::string>`를 `private` 멤버로 가진 `Parser` 클래스와, 그것을 쓰는 파일 20개로 된 프로젝트를 두 벌 만들었습니다. 한 벌은 멤버를 헤더에 두고, 한 벌은 pimpl입니다. GCC 14 `-O2`로 한 파일씩 컴파일한 시간입니다.

| | 멤버를 헤더에 | pimpl |
| --- | --- | --- |
| 쓰는 파일 하나의 컴파일 | 0.92초 | 0.74초 |
| `private` 멤버 하나를 더한 뒤 다시 빌드 | 19.3초. 21개를 다시 컴파일한다 | 3.3초. 1개만 |
| 멤버를 더하기 전과 후의 `sizeof(Parser)` | 104바이트에서 112바이트로 | 8바이트 그대로 |

첫 줄의 차이는 크지 않습니다. `<regex>`를 읽기만 하고 쓰지 않으면 값이 작고, `<string>`과 `<memory>`만으로도 전처리한 결과가 7만 9천 줄이기 때문입니다. pimpl의 값은 **둘째 줄**에 있습니다. 구현을 고칠 때마다 쓰는 쪽 전부를 다시 컴파일하는가, 한 파일만 하는가입니다.

셋째 줄은 컴파일 시간과 다른 이야기입니다. 클래스의 크기가 바뀌면 옛 헤더로 컴파일해 둔 쪽은 틀린 크기로 객체를 만듭니다. 라이브러리만 새것으로 바꿔 끼우는 배포에서는 그것이 곧 깨짐입니다. pimpl은 크기를 포인터 하나로 고정합니다. 이 이야기는 [「ABI 안정성」](#/read/cpp-advanced/iop-abi-stable)에서 잇습니다.

## 치르는 값

`long` 하나를 더하는 `add()`를 2억 번 부르는 루프와, 객체를 만들고 없애는 루프입니다. x86-64, GCC 14입니다.

| | 헤더에 정의 | pimpl | pimpl에 `-flto` |
| --- | --- | --- | --- |
| `add()` 한 번 | 0.25 ns | 1.6 ns | 0.29 ns |
| 만들고 없애기 | 사라진다 | 12 ns | 사라진다 |

pimpl의 `add()`는 다른 파일에 있어 인라인되지 않고, 부를 때마다 포인터를 읽습니다. 만들 때는 `malloc`이 듭니다. Clang 20에서도 1.7 ns와 14 ns였습니다.

셋째 열이 흥미롭습니다. 링크할 때 최적화(`-flto`)를 켜면 컴파일러가 파일의 경계를 넘어 인라인하고, 할당까지 없앴습니다. **컴파일의 방화벽은 그대로 두고 실행 시간의 값만 지운** 셈입니다. 다만 링크가 느려지고, 라이브러리를 따로 배포하는 경계에서는 쓸 수 없습니다.

## const가 새지 않게

[`const` 멤버 함수 안에서도 `impl_->x = 1`이 컴파일된다](#/read/cpp-syntax/mod-pimpl)는 약점이 있었습니다. `const`인 것은 포인터이지 가리키는 것이 아니어서입니다. 포인터를 한 겹 싸면 막을 수 있습니다.

```cpp
#include <experimental/propagate_const>
#include <memory>
#include <print>

class Gauge {
public:
    Gauge() : impl_(std::make_unique<Impl>()) {}
    int read() const
    {
        // ++impl_->reads;   // 이제 컴파일 오류다
        return impl_->value;
    }
    void set(int v) { impl_->value = v; }

private:
    struct Impl {
        int value = 0;
        int reads = 0;
    };
    std::experimental::propagate_const<std::unique_ptr<Impl>> impl_;
};

int main()
{
    Gauge gauge;
    gauge.set(7);
    std::println("{} / 크기 {}바이트", gauge.read(), sizeof(gauge));
}
```

```text
7 / 크기 8바이트
```

주석을 풀면 GCC 14는 `increment of member 'Gauge::Impl::reads' in read-only object`라고 합니다. `propagate_const`는 `const`인 자기를 통해서는 `const Impl&`만 내줍니다. 크기는 늘지 않습니다.

이 타입은 표준이 아니라 라이브러리 기초 기술 명세(`<experimental/…>`)의 것입니다. libstdc++ 14와 libc++ 20에 모두 있었습니다. C++26 초안에는 `std::indirect<T>`가 있습니다. 힙의 값 하나를 가지면서 `const`를 전하고, 복사하면 속까지 복사되는 타입이라 pimpl에 그대로 맞습니다. 이 책의 두 컴파일러에는 아직 없습니다.

## 힙 없는 pimpl

할당이 아까운 타입에는 `Impl`을 **객체 안의 버퍼에** 만드는 변형이 있습니다. [작은 버퍼](#/read/cpp-advanced/te-sbo)와 같은 생각입니다. 한 파일에 적었지만 주석으로 나눈 대로 두 파일에 놓입니다.

```cpp
#include <cstddef>
#include <new>
#include <print>
#include <string>
#include <utility>

// ---- sensor.h 에 놓일 부분 ----
class Sensor {
public:
    explicit Sensor(std::string name);
    ~Sensor();
    Sensor(const Sensor&) = delete;
    Sensor& operator=(const Sensor&) = delete;

    void feed(double sample);
    double average() const;

private:
    struct Impl;
    Impl* impl();
    const Impl* impl() const;

    // 크기와 정렬만 헤더에 드러난다. 속은 여전히 숨어 있다
    alignas(8) std::byte storage_[48];
};

// ---- sensor.cpp 에 놓일 부분 ----
struct Sensor::Impl {
    std::string name;
    double sum = 0;
    long count = 0;
};

Sensor::Impl* Sensor::impl()
{
    return std::launder(reinterpret_cast<Impl*>(storage_));
}
const Sensor::Impl* Sensor::impl() const
{
    return std::launder(reinterpret_cast<const Impl*>(storage_));
}

Sensor::Sensor(std::string name)
{
    // 헤더에 적은 숫자가 맞는지 여기서 확인한다
    static_assert(sizeof(Impl) <= sizeof(storage_), "storage_가 작다");
    static_assert(alignof(Impl) <= alignof(Sensor), "정렬이 모자란다");
    ::new (storage_) Impl{std::move(name)};
}
Sensor::~Sensor() { impl()->~Impl(); }
void Sensor::feed(double sample)
{
    impl()->sum += sample;
    ++impl()->count;
}
double Sensor::average() const
{
    return impl()->count ? impl()->sum / impl()->count : 0;
}

int main()
{
    Sensor sensor("thermo");
    sensor.feed(20);
    sensor.feed(23);
    std::println("평균 {} / Sensor {}바이트", sensor.average(), sizeof(Sensor));
}
```

```text
평균 21.5 / Sensor 48바이트
```

| 얻는 것 | 치르는 것 |
| --- | --- |
| 힙 할당이 없다. 속은 객체와 붙어 있다 | **크기와 정렬이 헤더로 샌다.** 구현이 커지면 헤더의 48을 고쳐야 하고, 그러면 다 다시 컴파일한다 |
| 구현의 타입과 헤더는 여전히 숨는다 | 크기가 환경마다 다르다. 이 `Impl`은 libstdc++에서 48바이트, libc++에서 40바이트였다 |
| | 소멸, 이동, 복사를 모두 손으로 쓴다 |

`static_assert`가 이 변형의 안전장치입니다. 버퍼를 40으로 줄이면 GCC 14는 `static assertion failed: storage_가 작다`로 멈춥니다. 여유를 두고 잡되, 크기가 ABI의 일부가 되었다는 것은 잊지 않습니다.

<Note kind="warn">
`impl()`을 클래스 안에서 정의하면 Clang 20은 컴파일하지 않습니다. `std::launder`가 완전한 타입을 요구하는데 그 자리에서 `Impl`은 선언만 되어 있기 때문입니다. GCC 14는 통과시켰습니다. 예제처럼 `Impl`의 정의 뒤에서 정의합니다.
</Note>

## 고르기

| 상황 | 쓰는 것 |
| --- | --- |
| 라이브러리의 바깥 얼굴. 구현이 자주 바뀌고, 무겁거나 플랫폼 전용인 헤더를 쓴다 | pimpl |
| 그런데 수없이 만들어지는 작은 객체다 | 힙 없는 pimpl, 또는 pimpl을 쓰지 않는다 |
| 구현이 여럿이고 실행 중에 고른다 | [추상 클래스와 생성 함수](#/read/cpp-syntax/inh-abstract) |
| 프로그램 안쪽의 평범한 클래스 | 아무것도 하지 않는다. 숨길 것이 없으면 값을 치를 까닭이 없다 |

[모듈](#/read/cpp-syntax/mod-modules)은 헤더를 거듭 읽는 값을 줄여 주지만 pimpl을 대신하지는 않습니다. 내보낸 클래스의 `private` 멤버는 여전히 인터페이스에 있어서, 고치면 가져다 쓰는 쪽이 다시 컴파일되고 크기도 바뀝니다. 이 부분은 재 보지 않았고, 모듈의 규칙에서 따라 나오는 이야기입니다.

## 정리

- pimpl의 값은 구현을 고칠 때 한 파일만 다시 컴파일하는 것과, 클래스의 크기가 고정되는 것이다. 예제에서 19초가 3초가 됐다
- 호출은 0.25 ns가 1.6 ns로, 만들기는 `malloc` 한 번이 든다. `-flto`를 켜면 실행 시간의 값은 사라진다
- `const`는 `propagate_const`로 전하고, 할당이 아까우면 버퍼에 만들되 크기가 헤더로 샌다는 것을 안다
