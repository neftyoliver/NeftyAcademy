설정, 경로표, 캐시처럼 **읽기는 잦고 쓰기는 드문** 자료가 있습니다. 읽기만 하는 스레드끼리는 서로를 막을 까닭이 없습니다. `std::shared_mutex`는 잠금을 두 가지로 나눠서, 읽는 쪽은 여럿이 함께 들어오고 쓰는 쪽은 혼자 들어오게 합니다.

## 읽는 쪽은 함께, 쓰는 쪽은 혼자

```cpp
#include <latch>
#include <map>
#include <mutex>
#include <optional>
#include <print>
#include <shared_mutex>
#include <string>
#include <thread>

class Registry {
public:
    std::optional<int> find(const std::string& name) const
    {
        std::shared_lock lock(guard_);          // 읽는 쪽: 여럿이 함께 들어온다
        auto it = ports_.find(name);
        if (it == ports_.end()) return std::nullopt;
        return it->second;
    }

    void set(const std::string& name, int port)
    {
        std::unique_lock lock(guard_);          // 쓰는 쪽: 혼자 들어온다
        ports_[name] = port;
    }

    // 없으면 만들어 넣는다
    int find_or_add(const std::string& name, int port)
    {
        {
            std::shared_lock lock(guard_);
            if (auto it = ports_.find(name); it != ports_.end()) return it->second;
        }                                       // 읽는 잠금을 놓는다
        // 그 사이에 다른 스레드가 넣었을 수 있다
        std::unique_lock lock(guard_);
        // 그래서 다시 확인한다
        return ports_.try_emplace(name, port).first->second;
    }

private:
    mutable std::shared_mutex guard_;           // const 함수에서도 잠그므로 mutable
    std::map<std::string, int> ports_;
};

int main()
{
    Registry registry;
    registry.set("http", 80);
    std::println("{} {}", registry.find("http").value_or(-1),
                 registry.find("ssh").value_or(-1));
    int first_try = registry.find_or_add("ssh", 22);
    int second_try = registry.find_or_add("ssh", 2222);
    std::println("{} {}", first_try, second_try);

    // 읽는 잠금 둘이 함께 들어와 있는 동안 쓰는 잠금은 들어오지 못한다
    std::shared_mutex guard;
    std::latch both_inside(2);
    std::latch checked(1);
    bool writer_got_in = true;
    {
        auto reader = [&] {
            std::shared_lock lock(guard);
            both_inside.count_down();           // 둘 다 여기까지 와야 넘어간다
            both_inside.wait();
            checked.wait();
        };
        std::jthread first(reader);
        std::jthread second(reader);
        both_inside.wait();
        writer_got_in = guard.try_lock();
        checked.count_down();
    }
    std::println("읽는 쪽 둘이 함께 들어온 동안 쓰는 쪽은 {}",
                 writer_got_in ? "들어왔다" : "못 들어왔다");
}
```

```text
80 -1
22 22
읽는 쪽 둘이 함께 들어온 동안 쓰는 쪽은 못 들어왔다
```

읽는 함수는 [`std::shared_lock`](#/read/cpp-advanced/sync-locks)을, 고치는 함수는 `std::unique_lock`이나 `std::lock_guard`를 씁니다. 읽는 잠금을 쥐고 자료를 **고치면** 컴파일러는 막지 못하고 경합이 됩니다. 읽는 함수를 `const`로 두면 그 실수를 타입이 잡아 줍니다.

`find_or_add`가 이 뮤텍스의 함정을 보여 줍니다. 읽는 잠금을 쓰는 잠금으로 **올리는 방법은 없습니다.** 두 스레드가 읽는 잠금을 쥔 채 동시에 올리려 하면 서로가 놓기를 기다리는 [교착](#/read/cpp-advanced/sync-deadlock)이 되기 때문입니다. 놓고 다시 잠가야 하고, 그 틈에 다른 스레드가 먼저 넣었을 수 있으므로 **다시 확인**합니다. `try_emplace`가 그 확인입니다. 둘째 줄의 출력이 `22 22`인 까닭입니다.

## 이득이 나는 조건

| 읽기만 하는 스레드들 | 스레드 1개 | 2개 | 4개 |
| --- | --- | --- | --- |
| 짧은 읽기(18 ns), `std::mutex` | 73 ms | 480 ms | 1,050 ms |
| 짧은 읽기, `std::shared_mutex` | 84 ms | 530 ms | 985 ms |
| 긴 읽기(5.6 µs), `std::mutex` | 590 ms | 2,600 ms | 3,800 ms |
| 긴 읽기, `std::shared_mutex` | 560 ms | 800 ms | 1,180 ms |

x86-64 서버 VM(코어 2개), GCC 14 `-O2`에서 잰 값입니다. 스레드마다 같은 횟수를 읽으므로 스레드가 늘면 일도 늡니다. 긴 읽기에서는 `shared_mutex`가 두 코어를 다 씁니다. 짧은 읽기에서는 **아무 이득이 없습니다.** 읽는 잠금도 "지금 몇이 들어와 있는가"를 뮤텍스 안에 적어야 하고, 그 숫자를 두 코어가 번갈아 고치는 값이 읽기 자체보다 크기 때문입니다. 혼자 쓸 때는 [`mutex`보다 느리기까지 합니다](#/read/cpp-advanced/sync-mutex).

`shared_mutex`는 잠근 채로 하는 일이 **잠금의 값보다 훨씬 길 때**만 고릅니다. 맵에서 값 하나를 꺼내는 정도면 `std::mutex`가 낫습니다.

## 쓰는 쪽이 굶는다

읽는 스레드 넷이 200 µs씩 걸리는 읽기를 쉬지 않고 되풀이하는 동안, 쓰는 스레드 하나가 잠금을 얻으려 했습니다.

| 표준 라이브러리 | 쓰는 쪽이 기다린 시간 |
| --- | --- |
| GCC 14의 libstdc++ | 998 ms. 읽는 스레드들을 멈출 때까지 **한 번도** 들어가지 못했다 |
| Clang 20의 libc++ | 0.1 ms |

읽는 잠금들이 겹쳐서 이어지면 "아무도 읽지 않는 순간"이 오지 않습니다. 쓰려는 쪽이 기다리고 있을 때 새로 온 읽는 쪽을 들여보낼지는 표준이 정하지 않았고, 두 구현이 반대로 골랐습니다. libstdc++는 리눅스의 읽기-쓰기 잠금을 기본 설정으로 쓰는데 그 기본이 읽는 쪽 먼저입니다. 설정이 제때 반영되어야 하는 프로그램이라면 이 차이가 버그입니다.

## 스냅숏으로 바꾸기

읽기가 훨씬 잦은 자료는 잠금으로 지키는 대신 **통째로 갈아 끼울** 수 있습니다. 자료를 바꿀 수 없는 것(`const`)으로 만들어 [`shared_ptr`](#/read/cpp-advanced/sp-shared)에 담고, 읽는 쪽은 포인터만 복사해 들고 나갑니다.

```cpp
using Table = std::vector<int>;

class Snapshot {
public:
    // 읽는 쪽: 잠근 동안에는 포인터 하나만 복사한다
    std::shared_ptr<const Table> get() const
    {
        std::lock_guard lock(guard_);
        return current_;
    }

    // 쓰는 쪽: 새 표를 잠금 밖에서 다 만든 뒤 포인터만 바꾼다
    void set(Table next)
    {
        auto fresh = std::make_shared<const Table>(std::move(next));
        std::lock_guard lock(guard_);
        current_ = std::move(fresh);
    }

private:
    mutable std::mutex guard_;
    std::shared_ptr<const Table> current_ = std::make_shared<const Table>();
};
```

| | `shared_mutex` | 스냅숏 |
| --- | --- | --- |
| 긴 읽기, 스레드 2개 / 4개 | 800 ms / 1,180 ms | 610 ms / 1,200 ms |
| 읽는 동안 쓰는 쪽은 | 기다린다 (굶을 수 있다) | 기다리지 않는다 |
| 읽는 쪽이 보는 것 | 늘 최신 | 들고 나온 시점의 것. 읽는 동안 바뀌지 않는다 |
| 쓰기 한 번의 값 | 고친 만큼 | 전체를 새로 만든다 |

읽는 속도는 같고, 굶는 문제가 사라집니다. 읽는 쪽이 쥔 표는 다른 스레드가 새 표로 바꿔도 **마지막 읽는 쪽이 놓을 때까지** 살아 있습니다. 값은 쓰기입니다. 원소 하나를 고치려 해도 전체를 복사해야 하므로, 쓰기가 드물 때의 방법입니다. 포인터를 바꾸는 잠금까지 없애는 방법은 [「락 없는 자료 구조의 기초」](#/read/cpp-advanced/atm-lockfree)에서 봅니다.

<Note>
`shared_mutex`에도 재귀는 없습니다. 읽는 잠금을 쥔 스레드가 같은 뮤텍스를 한 번 더 읽는 잠금으로 잠그는 것도 정의되지 않은 동작입니다. 쓰려는 스레드가 사이에 끼어 기다리고 있으면, 구현에 따라 둘째 읽는 잠금이 그 뒤에 줄을 서서 자기 자신을 기다리게 됩니다.
</Note>

## 정리

- `shared_lock`은 여럿이 함께, `unique_lock`은 혼자 들어온다. 읽는 잠금을 쓰는 잠금으로 올릴 수는 없으니 놓고 다시 잠근 뒤 다시 확인한다
- 짧은 읽기에서는 `std::mutex`와 차이가 없다. 잠근 채로 하는 일이 길 때만 이득이다
- 쓰는 쪽을 들여보내는 차례는 구현마다 다르다. 읽기가 훨씬 잦으면 바꿀 수 없는 스냅숏을 갈아 끼우는 편이 낫다
