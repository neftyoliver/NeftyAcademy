[「디버그 모드와 경화 모드」](#/read/cpp-stl/impl-debug)에서 범위 검사를 켜는 스위치와 기본적인 값을 봤습니다. 여기서는 세 가지를 더 봅니다. 표준이 무엇을 검사하라고 정했는지, 오늘의 구현이 그것을 얼마나 채우는지, 검사가 정말로 값이 드는 자리가 어디인지입니다.

## 표준이 정한 것

C++26 초안(N5050)은 라이브러리 함수의 전제 조건 가운데 일부를 **경화된 전제 조건**으로 따로 표시합니다. 구현이 스스로를 경화된 구현이라고 정하면 그 조건을 어긴 호출은 [계약 위반](#/read/cpp-advanced/safe-contracts)이 되어 프로그램이 끝나고, 아니면 지금처럼 정의되지 않은 동작입니다. 초안의 소스를 세어 보니 그 표시가 70곳에 있었습니다.

| 대상 | 경화된 전제 조건이 붙은 것 |
| --- | --- |
| `vector`, `array`, `deque`, `string`, `list` 등 | `a[n]`, `front()`, `back()`, `pop_front()`, `pop_back()` |
| `span`, `mdspan` | `[]`, `front`, `back`, `first`, `last`, `subspan`, 길이가 정해진 `span`의 생성자 |
| `string_view` | `[]`, `front`, `back`, `remove_prefix`, `remove_suffix` |
| `optional`, `expected` | `*`, `->`, `error()` |
| `bitset`, `valarray`, `shared_ptr<T[]>` | `[]` |
| 그 밖 | `common_iterator`, `counted_iterator`, 뷰의 `front`와 `back`, `stacktrace` |

**컨테이너의 반복자와 알고리즘은 목록에 없습니다.** 싸게 확인할 수 있는 것만 골랐기 때문입니다. 코드가 물어볼 수 있게 `__cpp_lib_hardened_vector` 같은 매크로 19개도 정해 두었는데, GCC 14와 libc++ 20은 검사를 켜도 이 매크로를 정의하지 않았습니다. 초안보다 먼저 나온 구현입니다.

<Note>
2026년 11월 21일 현재 C++26은 [아직 승인되지 않았습니다](#/read/cpp-syntax/ver-26). 경화가 계약의 말로 적혀 있어서 계약을 둘러싼 다툼에 함께 묶여 있습니다. 아래의 스위치는 표준이 어떻게 정리되든 지금 쓸 수 있습니다.
</Note>

## 오늘의 구현

어기는 호출 스물네 가지를 돌려 봤습니다. libstdc++ 14는 `-D_GLIBCXX_ASSERTIONS`, libc++ 20은 `fast` 모드입니다.

| 어긴 것 | 초안의 목록 | libstdc++ 14 | libc++ 20 |
| --- | --- | --- | --- |
| `vector`·`array`·`deque`·`string`의 `[]`, `front`, `pop_back` | 있다 | 멈춘다 | 멈춘다 |
| `span`·`string_view`의 `[]`, `first`, `remove_prefix` | 있다 | 멈춘다 | 멈춘다 |
| 빈 `optional`·`expected`의 `*`, `error()` | 있다 | 멈춘다 | 멈춘다 |
| `bitset`의 `[]`, 빈 `list`의 `front()` | 있다 | **지나친다** | 멈춘다 |
| 널인 `unique_ptr`·`shared_ptr`의 `*` | 없다 | 멈춘다 | 검사하지 않는다 |
| 위아래가 뒤집힌 `std::clamp` | 없다 | 멈춘다 | 검사하지 않는다 |
| `*v.end()`, `v.begin()[n]`, 무효가 된 반복자 | 없다 | 지나친다 | 지나친다 |
| 작은 벡터를 향한 `std::copy` | 없다 | 지나친다 | 지나친다 |

- **목록의 것은 libc++가 모두 잡았고 libstdc++ 14는 둘을 놓쳤습니다.** 대신 libstdc++는 목록 밖의 널 포인터와 `clamp`까지 봅니다. libc++는 `clamp`를 `extensive` 모드부터 보고, 널 포인터는 검사 없이 읽다가 세그먼트 오류로 죽었습니다.
- **아래 두 줄은 어느 쪽 경화도 보지 못합니다.** libstdc++의 디버그 모드만 넷을 다 잡았습니다. 반복자와 알고리즘의 실수는 [새니타이저](#/read/cpp-advanced/tool-sanitizers)와 테스트의 몫입니다.
- **멈추는 모양이 다릅니다.** libstdc++는 헤더의 줄과 조건을 찍고 `abort`합니다. libc++의 `fast`는 메시지 없이 잘못된 명령 신호로 죽습니다. 최적화한 빌드에서는 여러 검사의 함정이 명령 하나로 합쳐져서, 디버거가 44번 줄의 잘못을 66번 줄이라고 가리켰습니다. `-O0`으로 다시 빌드하자 `operator[]`와 44번 줄이 나왔습니다.

## 검사의 값

원소 4,096개짜리 `int` 벡터로 루프 여섯 가지를 쟀습니다. 원소 하나에 드는 시간(ns)이고 다섯 번 가운데 가장 작은 값입니다.

| 루프 | GCC `-O3` | 단언을 켜면 | Clang, 끔 → `fast` |
| --- | --- | --- | --- |
| `i < v.size()`로 읽기 | 0.13 | 0.13 | 0.13 → 0.14 |
| 범위 `for`로 읽기 | 0.13 | 0.13 | 0.14 → 0.14 |
| 길이 `n`을 따로 받아 읽기 | 0.13 | **0.26** | 0.13 → 0.14 |
| 읽어서 다른 벡터에 쓰기 | 0.07 | **0.26** | 0.06 → 0.06 |
| 두 벡터를 곱해 더하기 | 0.27 | 0.34 | 0.32 → 0.26 |
| 섞인 번호를 따라 읽기 | 0.26 | 0.27 | 0.27 → 0.28 |

- **루프 조건이 그 벡터의 `size()`면 검사는 사라집니다.** 번호가 범위 안이라는 것을 컴파일러가 이미 압니다.
- **조건이 다른 것을 말하면 검사가 남습니다.** GCC 14에서는 남은 검사가 [벡터화](#/read/cpp-advanced/perf-simd)를 풀어서 두 배에서 네 배가 됐습니다. 벡터화가 없는 `-O2`에서는 0.21이 0.27이 된 것이 가장 큰 차이였습니다.
- **Clang 20에서는 여섯 루프 모두 차이가 없었습니다.** libstdc++의 단언을 켜도 같았습니다. 검사를 루프 밖으로 몰아내고 벡터화를 지킵니다.

Google은 2024년에 서버 전체를 경화된 libc++로 바꾸고 평균 0.30%가 들었다고 밝혔습니다. 위의 표와 맞는 숫자입니다. 값이 드는 곳은 뜨거운 루프 몇 개이고, 거기서는 범위를 먼저 잘라 검사를 한 번으로 만듭니다.

```cpp
#include <span>
#include <vector>

// 고치기 전: 번호마다 out의 범위를 검사한다
void scale(const std::vector<int>& in, std::vector<int>& out)
{
    for (std::size_t i = 0; i < in.size(); ++i) out[i] = in[i] * 3;
}

// 고친 뒤: first가 길이를 한 번 검사하고, 루프 안의 검사는 사라진다
void scale(std::span<const int> in, std::span<int> out)
{
    out = out.first(in.size());
    for (std::size_t i = 0; i < in.size(); ++i) out[i] = in[i] * 3;
}
```

GCC `-O3`에 단언을 켠 채로 0.26이 0.07로 돌아왔습니다. `out`이 짧으면 여전히 멈춥니다. 멈추는 자리가 루프 안에서 `first`로 옮겨 갔을 뿐입니다.

## 경화가 보지 않는 것

경화는 라이브러리 타입의 함수 안에서 **수 둘을 견줄 뿐**입니다. 다음 셋은 두 라이브러리의 검사를 모두 켠 채로 조용히 지나갔습니다.

| 코드 | 지나친 까닭 | 잡는 것 |
| --- | --- | --- |
| 사라진 벡터를 가리키는 `span`의 `s[1]` | 번호는 범위 안이다 | ASan, [수명 검사](#/read/cpp-advanced/safe-profiles) |
| C 배열의 `raw[3]` | 라이브러리의 타입이 아니다 | UBSan. `std::array`로 바꾸면 경화도 본다 |
| `v.data()`로 꺼낸 포인터의 `p[3]` | 검사할 함수를 거치지 않는다 | ASan, Clang의 `-Wunsafe-buffer-usage` |

## 섞어 빌드하면

단언은 [타입의 생김새를 바꾸지 않아서](#/read/cpp-stl/impl-debug) 켠 파일과 끈 파일을 함께 링크할 수 있습니다. 그런데 링크가 된다는 것과 검사가 남는다는 것은 다릅니다. `v[3]`을 읽는 함수를 두 파일에 하나씩 두고, 한 파일만 단언을 켜서 빌드했습니다.

| 빌드 | 링크 순서 | 켠 파일의 함수 | 끈 파일의 함수 |
| --- | --- | --- | --- |
| `-O0` | 켠 파일이 먼저 | 멈춘다 | **멈춘다** |
| `-O0` | 끈 파일이 먼저 | **지나친다** | 지나친다 |
| `-O2` | 어느 쪽이든 | 멈춘다 | 지나친다 |

`-O0`에서는 `operator[]`가 펼쳐지지 않고 두 목적 파일에 같은 이름으로 들어갑니다. 링커는 [그 가운데 하나만 남기므로](#/read/cpp-syntax/fn-inline) 먼저 온 쪽이 프로그램 전체의 답이 됩니다. 검사를 켰다고 믿은 파일이 조용히 지나치는 것이 둘째 줄입니다.

<Note kind="warn">
그래서 경화는 파일마다가 아니라 **프로그램 전체에** 겁니다. [프리셋](#/read/cpp-advanced/tool-ci)의 플래그나 GCC의 `-fhardened`처럼 한곳에 적고, 미리 빌드해 가져오는 라이브러리도 [같은 설정으로 빌드된 것](#/read/cpp-advanced/tool-packages)을 씁니다.
</Note>

## 정리

- C++26 초안은 `[]`, `front`, `*optional` 같은 70곳을 경화된 전제 조건으로 정했다. libc++ 20의 `fast`는 시험한 것을 모두 잡았다. 반복자, 알고리즘, 수명, 맨 포인터는 경화가 보지 않는다
- 검사는 루프 조건이 범위를 말해 주면 사라진다. 남으면 GCC 14에서 벡터화가 풀려 최대 네 배였고 Clang 20에서는 차이가 없었다. 범위를 먼저 자르면 되돌아온다
- 켠 파일과 끈 파일을 섞으면 링크 순서가 검사를 정한다. 프로그램 전체를 같은 설정으로 빌드한다
