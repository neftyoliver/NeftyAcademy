[테스트](#/read/cpp-advanced/tool-testing)도 [새니타이저](#/read/cpp-advanced/tool-sanitizers)도 [정적 분석](#/read/cpp-advanced/tool-static)도 돌려야 쓸모가 있는데, 바쁜 사람은 돌리지 않습니다. 지속적 통합(CI)은 커밋이 올라올 때마다 깨끗한 기계에서 같은 검사를 대신 돌리는 장치입니다. 앞에서 테스트를 붙인 온도 조절기 프로젝트에 그 장치를 답니다.

## 한 줄로 도는 검사

CI 설정 파일에 빌드 명령을 길게 적어 두면, CI에서만 깨지는 빌드를 내 자리에서 다시 만들 수가 없습니다. 그래서 검사 하나를 **내 자리에서도 똑같이 도는 명령 한 줄**로 만들고 CI는 그 줄만 부르게 합니다. [프리셋](#/read/cpp-syntax/mod-cmake)에는 설정뿐 아니라 빌드, 테스트, 그리고 셋을 차례로 도는 워크플로도 적을 수 있습니다.

```json
{
    "version": 6,
    "configurePresets": [
        {
            "name": "base",
            "hidden": true,
            "generator": "Ninja",
            "binaryDir": "build/${presetName}",
            "cacheVariables": {
                "CMAKE_CXX_COMPILER_LAUNCHER": "ccache",
                "CMAKE_COMPILE_WARNING_AS_ERROR": "ON"
            }
        },
        {
            "name": "asan",
            "inherits": "base",
            "cacheVariables": {
                "CMAKE_CXX_COMPILER": "g++-14",
                "CMAKE_BUILD_TYPE": "Debug",
                "CMAKE_CXX_FLAGS":
                    "-fsanitize=address,undefined -fno-sanitize-recover=all"
            }
        }
    ],
    "buildPresets": [{ "name": "asan", "configurePreset": "asan" }],
    "testPresets": [
        {
            "name": "asan",
            "configurePreset": "asan",
            "output": { "outputOnFailure": true },
            "execution": { "timeout": 60 }
        }
    ],
    "workflowPresets": [
        {
            "name": "asan",
            "steps": [
                { "type": "configure", "name": "asan" },
                { "type": "build", "name": "asan" },
                { "type": "test", "name": "asan" }
            ]
        }
    ]
}
```

```text nocheck
$ cmake --workflow --preset asan
Executing workflow step 1 of 3: configure preset "asan"
Executing workflow step 2 of 3: build preset "asan"
[2/2] Linking CXX executable test_thermostat
Executing workflow step 3 of 3: test preset "asan"
100% tests passed, 0 tests failed out of 4
```

`tsan`은 플래그를 `-fsanitize=thread`로 바꾼 것이고, `clang`은 컴파일러를 `clang++-20`, 빌드 종류를 `Release`로 바꾸고 [clang-tidy가 읽을](#/read/cpp-advanced/tool-static) `CMAKE_EXPORT_COMPILE_COMMANDS`를 켠 것입니다. 경고 옵션 `-Wall -Wextra`는 `CMakeLists.txt`에 있고, 경고를 오류로 바꾸는 줄은 프리셋에만 있습니다. 다른 버전의 컴파일러로 빌드하는 사람까지 새 경고 하나에 막히지 않게 하려는 것입니다.

## 무엇을 돌릴까

| 일 | 명령 | 잡는 것 | 걸린 시간 |
| --- | --- | --- | --- |
| `asan` | `cmake --workflow --preset asan` | 메모리 오류, 정의되지 않은 동작 | 4.4초 |
| `tsan` | `cmake --workflow --preset tsan` | 데이터 경합 | 3.5초 |
| `clang` | `cmake --workflow --preset clang` | 다른 컴파일러의 경고, 최적화 빌드의 버그 | 3.6초 |
| 모양 | `clang-format --dry-run --Werror` | 어긋난 모양 | 0.02초 |
| 정적 분석 | `run-clang-tidy -p build/clang` | 돌리지 않고 찾는 버그 | 23초 |

코어가 둘인 이 책의 장비에서 빈 폴더로 시작해 잰 시간입니다.

- **새니타이저 빌드도 둘, 컴파일러도 둘입니다.** [한 빌드에 함께 켤 수 없는 것](#/read/cpp-advanced/tool-sanitizers)이 있고, [도구마다 잡는 버그가 달랐기](#/read/cpp-advanced/tool-static) 때문입니다.
- **가장 느린 것은 정적 분석입니다.** 테스트 파일 하나에 23초였고 그중 17초가 `clang-analyzer-*`였습니다. gmock을 쓰지 않는 테스트 파일은 4초였습니다. 줄 수가 아니라 끌려오는 헤더가 시간을 정합니다. 빠른 일이 먼저 답하도록 일을 따로 둡니다.
- **[교차 빌드](#/read/cpp-advanced/tool-cmake)도 같은 꼴입니다.** 프리셋에 `toolchainFile` 한 줄을 넣자, 센서 라이브러리를 ARM용으로 빌드해 에뮬레이터로 테스트하는 일이 3.9초에 돌았습니다.

## 캐시

CI 기계는 매번 빈 폴더에서 시작하므로 늘 전부 컴파일합니다. ccache는 컴파일러 앞에 서서, 소스와 옵션과 컴파일러가 지난번과 같으면 저장해 둔 목적 파일을 돌려줍니다. 프리셋의 `CMAKE_CXX_COMPILER_LAUNCHER`가 그 연결입니다. [파일 스물한 개짜리 프로젝트](#/read/cpp-advanced/tool-cmake)의 빌드 폴더를 지우고 다시 빌드하며 쟀습니다.

| 지난 빌드와 달라진 것 | 걸린 시간 |
| --- | --- |
| 캐시가 비어 있다 | 8.3초 |
| 없다 | 0.1초 |
| 파일 하나의 끝에 주석을 달았다 | 0.2초 |
| 파일 하나를 고쳤다 | 0.8초 |

주석만 단 파일은 다시 컴파일되지 않았습니다. ccache는 파일이 달라졌으면 전처리한 결과를 견주는데, 주석은 거기서 사라지기 때문입니다. 위 표의 세 일도 4초 안팎에서 0.5~0.6초가 됐습니다.

<Note kind="warn">
[모듈 살피기](#/read/cpp-advanced/tool-cmake)가 켜져 있으면 GCC에서는 캐시가 듣지 않습니다. CMake 3.28이 컴파일 명령에 `-fmodules-ts`를 붙이는데, ccache 4.9는 그 옵션이 있으면 저장하지 않습니다. 같은 프로젝트가 8.2초에서 8.0초가 됐을 뿐이고 `ccache -s`에는 `Unsupported compiler option: 42 / 42`가 찍혔습니다. Clang에서는 0.6초로 줄었습니다. 모듈을 쓰지 않으면 `CMAKE_CXX_SCAN_FOR_MODULES`를 끕니다.
</Note>

## 워크플로 파일

GitHub Actions라면 저장소에 이 파일을 둡니다. 다른 서비스도 꼴은 같습니다.

```yaml
# .github/workflows/ci.yml
name: ci
on:
  push:
    branches: [main]
  pull_request:

concurrency:                # 새 커밋이 오면 앞의 실행은 그만둔다
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-24.04   # ubuntu-latest는 움직이는 이름이다
    timeout-minutes: 15     # 적지 않으면 360분
    strategy:
      fail-fast: false      # 하나가 실패해도 나머지를 끝까지 돌린다
      matrix:
        preset: [asan, tsan, clang]
    steps:
      - uses: actions/checkout@v6
      - name: 도구 깔기
        run: |
          sudo apt-get update
          sudo apt-get install -y cmake ninja-build ccache g++-14 clang-20 \
            libgtest-dev libgmock-dev
      - uses: actions/cache@v6
        with:
          path: ~/.cache/ccache
          key: ccache-${{ matrix.preset }}-${{ github.sha }}
          restore-keys: ccache-${{ matrix.preset }}-
      - run: cmake --workflow --preset ${{ matrix.preset }}
```

- **이름에 버전을 적습니다.** GitHub는 `ubuntu-latest`를 2026년 10월 19일부터 11월 19일 사이에 24.04에서 26.04로 옮긴다고 알렸습니다. 컴파일러도 `g++`이 아니라 `g++-14`로 부릅니다. 고정해 둔 것은 내가 정한 날에 올립니다.
- **캐시 키에 커밋을 넣습니다.** 한 번 저장된 키의 내용은 바꿀 수 없습니다. 키가 늘 새것이어야 일이 성공할 때마다 저장되고, 꺼낼 때는 `restore-keys`와 앞머리가 맞는 것 중 가장 최근 것이 옵니다.
- **[잠금 파일](#/read/cpp-advanced/tool-packages)이 있으면 그것으로 받습니다.** 워크플로 앞에 `conan install . --lockfile=conan.lock`을 둡니다. 잠금 파일과 요구가 어긋나자 `not in lockfile` 오류와 종료 코드 1이 나왔습니다.
- **모양 검사와 정적 분석**은 `jobs` 아래에 일을 하나 더 적어 표의 명령을 부릅니다.

<Note>
이 파일은 GitHub에서 돌려 보지 못했습니다. 안에 든 명령과 패키지 이름은 같은 Ubuntu 24.04에서 돌려 확인했고, 러너 이름과 액션의 버전(`checkout`과 `cache` 모두 6), 360분은 2026년 11월 21일에 문서로 확인했습니다. 이것들도 움직이므로 쓰기 전에 다시 봅니다.
</Note>

## 제대로 실패하기

CI는 출력을 읽지 않고 **종료 코드**만 봅니다. 문제가 있어도 0을 돌려주는 검사는 없는 것과 같습니다.

- **UBSan**은 [알리고 계속 가므로](#/read/cpp-advanced/tool-sanitizers) 프리셋에 `-fno-sanitize-recover=all`을 넣었습니다.
- **경고**는 종료 코드를 바꾸지 않습니다. 쓰지 않는 변수를 하나 넣자 프리셋 빌드는 1로 끝났고, 프리셋 없는 빌드는 0이었습니다.
- **멈춘 테스트**는 일 전체를 붙잡습니다. `ctest -VV`가 알려 준 기본 제한은 10,000,000초였습니다. 오지 않는 답을 기다리는 테스트를 넣어 봤습니다.

```text nocheck
$ cmake --workflow --preset asan
5/5 Test #5: Uplink.WaitsForReply .......................***Timeout  60.06 sec
80% tests passed, 1 tests failed out of 5
$ echo $?
8
```

프리셋의 `"timeout": 60`이 끊었습니다. 없었다면 일의 제한 15분까지, 그것도 없었다면 360분까지 갔을 것입니다.

## 가끔 실패하는 테스트

```cpp nocheck
TEST(Stats, CountsFromTwoThreads)
{
    int hits = 0;                       // 버그: 두 스레드가 같이 고친다
    auto work = [&] { for (int i = 0; i < 100; ++i) ++hits; };
    std::thread a(work), b(work);
    a.join();
    b.join();
    EXPECT_EQ(hits, 200);
}
```

[경합](#/read/cpp-advanced/atm-atomic)이 있는 테스트입니다. 네 가지로 돌렸습니다.

| 돌린 방법 | 결과 |
| --- | --- |
| 새니타이저 없는 빌드로 1,800번 | 8번 실패 |
| `ctest --repeat until-pass:3`으로 1,800번 | 0번 실패 |
| `ctest --repeat until-fail:200`을 15번 | 10번 찾음 |
| `tsan` 프리셋으로 70번 | 70번 실패 |

- **통과할 때까지 다시 돌리면 버그가 초록 불을 받습니다.** `until-pass`는 급한 불을 끄는 옵션이지 고치는 옵션이 아닙니다.
- **찾을 때는 거꾸로 돌립니다.** `until-fail`은 실패할 때까지 되풀이합니다. 그래도 열다섯 번 중 다섯 번은 200번을 다 통과했습니다.
- **TSan 일은 운에 기대지 않습니다.** 합이 200으로 맞아 gtest가 `OK`를 찍은 실행에서도 `data race`와 줄 번호를 내고 종료 코드를 바꿨습니다.

## 정리

- 검사를 프리셋의 워크플로로 만들어 `cmake --workflow --preset 이름` 한 줄로 돌린다. CI는 그 줄만 부르고, 내 자리에서도 같은 줄이 돈다
- ccache로 4초가 0.5초, 8.3초가 0.1초가 됐다. 모듈 살피기가 켜진 GCC 빌드에서는 듣지 않는다
- CI는 종료 코드만 본다. 경고는 오류로, UBSan은 멈추게, 테스트에는 시간 제한을 둔다. 가끔 실패하는 테스트는 다시 돌려 덮지 않는다
