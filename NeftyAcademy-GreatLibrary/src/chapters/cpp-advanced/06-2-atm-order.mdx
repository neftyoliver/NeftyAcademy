[원자적 연산](#/read/cpp-advanced/atm-atomic)마다 생략해 온 인자가 하나 있습니다. `store(v)`는 `store(v, std::memory_order_seq_cst)`입니다. 이 인자는 "이 연산이 **다른 연산들과 어떤 순서로** 보여야 하는가"를 정합니다. 기본값이 가장 강하고 가장 비쌉니다.

## 쓰기는 늦게 보인다

두 스레드가 각자 자기 변수에 1을 쓰고 상대의 변수를 읽습니다. 누가 먼저든 적어도 한쪽은 1을 읽어야 할 것 같습니다.

```cpp
#include <atomic>
#include <print>
#include <thread>

// 두 스레드가 "내 것을 쓰고, 상대 것을 읽는다". 둘 다 0 을 읽는 판이 있는가?
template <std::memory_order Store, std::memory_order Load>
long both_zero(int rounds)
{
    std::atomic<int> x{0}, y{0};
    // 몇 번째 판인가. 상대는 이것을 보고 출발한다
    std::atomic<int> round{0};
    std::atomic<int> answered{0};       // 상대가 몇 번째 판까지 끝냈는가
    int r1 = 0, r2 = 0;
    long count = 0;

    std::jthread other([&] {
        for (int i = 1; i <= rounds; ++i) {
            while (round.load() != i) {}
            y.store(1, Store);
            r2 = x.load(Load);
            answered.store(i);
        }
    });
    for (int i = 1; i <= rounds; ++i) {
        x.store(0);
        y.store(0);
        round.store(i);                 // 출발
        x.store(1, Store);
        r1 = y.load(Load);
        while (answered.load() != i) {}
        if (r1 == 0 && r2 == 0) ++count;
    }
    return count;
}

int main()
{
    using std::memory_order;
    const int rounds = 1'000'000;
    std::println("seq_cst          {}",
                 both_zero<memory_order::seq_cst, memory_order::seq_cst>(rounds));
    std::println("release/acquire  {}",
                 both_zero<memory_order::release, memory_order::acquire>(rounds));
    std::println("relaxed          {}",
                 both_zero<memory_order::relaxed, memory_order::relaxed>(rounds));
}
```

```text nocheck
seq_cst          0
release/acquire  133976
relaxed          159373
```

x86-64 서버 VM(코어 2개)에서 GCC 14 `-O2`로 백만 판을 돌린 결과입니다. 약한 순서에서는 **둘 다 0을 읽은 판**이 열에 한 번 넘게 나옵니다. 돌릴 때마다 12만에서 18만 사이로 달라지지만, `seq_cst`에서는 한 번도 나오지 않습니다.

코어는 쓰기를 바로 캐시에 내보내지 않습니다. 자기만 보는 버퍼에 넣어 두고 다음 명령으로 넘어갑니다. 두 코어가 각자 쓰기를 버퍼에 넣은 채로 상대의 변수를 읽으면 둘 다 옛 값을 봅니다. `seq_cst`의 쓰기는 그 버퍼를 비울 때까지 다음으로 넘어가지 않습니다. 그래서 모든 스레드가 **하나의 순서**에 동의할 수 있고, 그만큼 느립니다.

## 순서 인자

| 인자 | 쓰는 연산 | 약속 |
| --- | --- | --- |
| `relaxed` | 모두 | 이 연산이 쪼개지지 않는다. 그것뿐이다 |
| `release` | 쓰기 | 이 쓰기보다 **앞서 한 내 쓰기들**이, 이 값을 `acquire`로 읽은 쪽에게 보인다 |
| `acquire` | 읽기 | 위의 짝. 읽은 값을 쓴 쪽이 그 전에 한 쓰기들이 보인다 |
| `acq_rel` | 읽고 쓰는 연산 (`fetch_add`, `exchange`, 비교 후 교환) | 둘 다 |
| `seq_cst` | 모두 | 위에 더해, 모든 `seq_cst` 연산이 모든 스레드에게 같은 순서로 보인다 |

`consume`도 있지만 어느 컴파일러도 뜻대로 구현하지 않았고 `acquire`로 다룹니다. 쓰지 않습니다.

## 넘겨주기와 세기

약한 순서가 맞는 자리는 두 가지 꼴로 거의 다 덮입니다.

```cpp
#include <atomic>
#include <print>
#include <thread>
#include <vector>

struct Config {
    int port = 0;
    int workers = 0;
};

Config config;                              // 보통 변수다
std::atomic<bool> ready = false;
std::atomic<long> requests = 0;             // 세기만 하는 값

int main()
{
    Config seen;
    {
        std::jthread reader([&] {
            // acquire: true 를 봤다면, 그 store 보다 앞서 쓰인 것들도 보인다
            while (!ready.load(std::memory_order_acquire))
                std::this_thread::yield();
            seen = config;
        });
        config = {8080, 4};                             // 1. 자료를 다 채우고
        ready.store(true, std::memory_order_release);   // 2. 그 뒤에 알린다
    }
    std::println("{} {}", seen.port, seen.workers);

    {
        std::vector<std::jthread> workers;
        for (int i = 0; i < 4; ++i) {
            workers.emplace_back([] {
                // relaxed: 이 값으로 다른 자료를 넘겨주지 않는다.
                // 더해지기만 하면 된다
                for (int n = 0; n < 100'000; ++n)
                    requests.fetch_add(1, std::memory_order_relaxed);
            });
        }
    }   // join 이 끝난 뒤에 읽으므로 모든 덧셈이 보인다
    std::println("{}", requests.load());
}
```

```text
8080 4
400000
```

| 꼴 | 순서 | 까닭 |
| --- | --- | --- |
| **넘겨주기**: 보통 자료를 다 만든 뒤 원자적 변수로 "됐다"고 알린다 | 쓰는 쪽 `release`, 읽는 쪽 `acquire` | 알림을 본 쪽에게 자료가 보여야 한다. [한 번만 만들기](#/read/cpp-advanced/sync-once)의 포인터도 이 꼴이다 |
| **세기**: 통계, 진행 정도 | `relaxed` | 값 자체만 맞으면 된다. 그 값을 보고 다른 자료를 읽지 않는다 |

`config`는 원자적이 아닌데 두 스레드가 건드립니다. 경합이 아닌 까닭은 `release`와 `acquire`가 "쓰기가 먼저, 읽기가 나중"이라는 순서를 만들어 주기 때문입니다. 여기서 `ready`를 `relaxed`로 읽으면 그 순서가 사라지고 `config`는 경합이 됩니다. 맨 처음의 실험처럼 **두 변수를 서로 엇갈려 보고 판단하는** 코드는 `seq_cst`가 아니면 틀립니다.

## 기계마다 다른 값

| 연산 | x86-64 | AArch64 |
| --- | --- | --- |
| 읽기 `relaxed` | `mov` | `ldr` |
| 읽기 `acquire`, `seq_cst` | `mov` | `ldar` |
| 쓰기 `relaxed` | `mov` | `str` |
| 쓰기 `release` | `mov` | `stlr` |
| 쓰기 `seq_cst` | `xchg` | `stlr` |
| 더하기 `relaxed` | `lock xadd` | `ldadd` |
| 더하기 `seq_cst` | `lock xadd` | `ldaddal` |

GCC 14 `-O2`가 만든 명령입니다(AArch64는 `-march=armv8.2-a`). x86-64에서는 **`seq_cst` 쓰기 하나만** 다릅니다. 보통의 `mov`가 이미 `release`와 `acquire`만큼 강해서, 약한 인자를 줘도 같은 명령이 나옵니다. 그 쓰기 하나의 차이는 5.8 ns와 0.4 ns입니다. AArch64는 단계마다 명령이 다릅니다. 기계가 약속하는 것이 적어서 필요한 만큼을 명령으로 골라야 합니다.

<Note kind="warn">
이 표가 함정입니다. x86-64에서는 `release`가 필요한 자리에 `relaxed`를 써도 같은 명령이 나오므로 **틀린 코드가 맞게 돕니다.** 같은 코드를 라즈베리 파이에서 돌리면 가끔 틀립니다. ThreadSanitizer도 이 차이는 잡지 못합니다. PC에서 시험을 통과했다는 것이 약한 순서가 맞다는 증거는 되지 못합니다.
</Note>

## 고르는 법

1. 기본값(`seq_cst`)으로 쓴다. 대부분의 코드에서 차이는 보이지 않는다
2. 재어 보니 그 연산이 정말 뜨거운 자리에 있고, 위의 두 꼴 가운데 하나에 정확히 들어맞으면 약한 순서를 쓴다
3. 왜 그 순서로 충분한지를 주석으로 적는다. 적을 수 없으면 `seq_cst`로 되돌린다

x86-64에서 얻는 것은 `seq_cst` 쓰기를 `release`로 바꿀 때의 5 ns가 전부입니다. 읽기와 더하기는 무엇을 적든 같습니다. ARM에서는 얻는 것이 더 있지만 틀릴 길도 그만큼 많습니다.

## 정리

- 쓰기는 코어의 버퍼를 거쳐 늦게 보인다. `seq_cst`만이 모든 스레드에게 하나의 순서를 약속한다
- 자료를 넘겨줄 때는 `release`로 쓰고 `acquire`로 읽는다. 세기만 하는 값은 `relaxed`로 충분하다
- x86-64는 약한 순서의 버그를 숨긴다. 기본값을 쓰고, 바꿀 때는 까닭을 적는다
