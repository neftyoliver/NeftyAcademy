표준 라이브러리의 헤더는 백 개가 넘습니다. 외울 것은 아니고, 어떤 일이 어느 헤더에 있는지 한 번 훑어 두면 찾는 시간이 줄어듭니다.

## 분야별 지도

| 분야 | 헤더 | 이 책 |
| --- | --- | --- |
| 문자열과 글 | `<string>` `<string_view>` `<charconv>` `<format>` `<print>` `<regex>` | 2장 |
| 컨테이너 | `<vector>` `<array>` `<deque>` `<list>` `<span>` `<map>` `<set>` `<unordered_map>` `<flat_map>` `<stack>` `<queue>` | 3–5장 |
| 반복자, 알고리즘 | `<iterator>` `<algorithm>` `<numeric>` `<execution>` `<ranges>` | 6–8장 |
| 어휘 타입 | `<utility>` `<tuple>` `<optional>` `<variant>` `<any>` `<expected>` `<functional>` `<bitset>` | 9장 |
| 메모리 | `<memory>` `<memory_resource>` `<new>` | 10장 |
| 입출력, 파일 | `<iostream>` `<fstream>` `<sstream>` `<iomanip>` `<filesystem>` | 11–12장 |
| 시간 | `<chrono>` | 13장 |
| 수 | `<random>` `<bit>` `<numbers>` `<cmath>` `<complex>` `<ratio>` `<mdspan>` | 14장 |
| 오류 | `<stdexcept>` `<exception>` `<system_error>` `<source_location>` `<stacktrace>` | 15장 |
| 동시성 | `<thread>` `<mutex>` `<future>` `<atomic>` `<stop_token>` | 16장 |
| 타입 도구 | `<type_traits>` `<concepts>` | 17장 |

이름이 엉뚱한 곳에 있는 것이 몇 개 있습니다. 자주 헷갈리는 것만 적습니다.

| 찾는 것 | 있는 곳 |
| --- | --- |
| `std::move`, `std::forward`, `std::pair`, `std::swap` | `<utility>` |
| `std::accumulate`, `std::iota`, `std::gcd` | `<numeric>` (`<algorithm>`이 아니다) |
| `std::unique_ptr`, `std::shared_ptr` | `<memory>` |
| `std::function`, `std::hash`, `std::ref` | `<functional>` |
| `std::size_t`, `std::byte`, `std::nullptr_t` | `<cstddef>` |
| `std::uint8_t`, `std::int32_t` | `<cstdint>` |

## 쓰는 것은 직접 포함한다

표준 헤더는 속에서 다른 표준 헤더를 포함합니다. 그래서 `<algorithm>`을 빼먹어도 `<vector>`가 우연히 끌고 들어와 컴파일되는 일이 생깁니다. 어떤 헤더가 무엇을 끌고 오는지는 표준이 정하지 않으므로, 컴파일러를 바꾸거나 판을 올리면 깨집니다.

```cpp nocheck
#include <string>

std::uint8_t flags = 0;     // <cstdint> 를 포함하지 않았다

int main() { return flags; }
```

```text
error: 'uint8_t' in namespace 'std' does not name a type; did you mean 'wint_t'?
```

GCC 14의 결과입니다. 이 코드는 GCC 12까지는 컴파일되었습니다. GCC 13이 `<string>` 안의 포함 관계를 정리하면서 깨졌고, 그때 많은 프로젝트가 같은 오류를 만났습니다. 코드가 틀렸던 것이고 컴파일러가 틀린 것이 아닙니다.

규칙은 하나입니다. **그 파일에서 이름을 쓴 것의 헤더는 그 파일에서 직접 포함합니다.** 내 헤더가 `<vector>`를 포함하고 있더라도, `.cpp`에서 `std::vector`를 쓰면 `.cpp`에도 적습니다.

<Note kind="warn">
알고리즘 문제 풀이에서 보이는 `#include <bits/stdc++.h>`는 GCC의 내부 헤더입니다. 표준이 아니어서 MSVC와 libc++에는 없고, 헤더 전부를 읽으므로 컴파일도 느립니다. 제품 코드에는 쓰지 않습니다. 모든 것을 한 번에 가져오는 표준 방법은 [「C++20 모듈」](#/read/cpp-syntax/mod-modules)의 `import std;`입니다.
</Note>

## C 헤더의 두 이름

C의 헤더는 이름이 둘입니다. `<stdio.h>`는 `printf`를 전역에 두고, `<cstdio>`는 `std::printf`로 둡니다. C++ 코드에서는 `<c이름>` 꼴을 포함하고 `std::`를 붙여 부릅니다.

| 포함한 것 | 반드시 되는 이름 | 될 수도 있는 이름 |
| --- | --- | --- |
| `<cstdio>` | `std::printf` | `printf` |
| `<stdio.h>` | `printf` | `std::printf` |

"될 수도 있는" 쪽은 구현이 허락받았을 뿐 약속된 것이 아닙니다. 그 틈에서 조용한 버그가 나옵니다.

```cpp
#include <cmath>
#include <print>

int main()
{
    std::println("abs(-2.5)      = {}", abs(-2.5));
    std::println("std::abs(-2.5) = {}", std::abs(-2.5));
}
```

```text
abs(-2.5)      = 2
std::abs(-2.5) = 2.5
```

GCC 14의 결과이고 `-Wall -Wextra`에서도 경고가 없습니다. `std::` 없는 `abs`는 전역에 있던 C의 `int abs(int)`로 갔고, -2.5가 -2로 잘린 뒤 2가 되었습니다. 같은 코드가 libc++에서는 2.5를 찍습니다. `std::abs`라고 적으면 어디서나 `double`용이 골라집니다.

## 기능이 있는지 묻기

"이 컴파일러의 라이브러리에 `std::expected`가 있는가"는 판 번호로 알 수 없습니다. 같은 `-std=c++23`이어도 라이브러리마다 구현한 범위가 다릅니다. `<version>` 헤더가 기능마다 매크로를 하나씩 정의해 둡니다.

```cpp
#include <print>
#include <version>

int main()
{
    std::println("__cplusplus          {}", __cplusplus);
    std::println("__cpp_lib_print      {}", __cpp_lib_print);
    std::println("__cpp_lib_expected   {}", __cpp_lib_expected);
    std::println("__cpp_lib_generator  {}", __cpp_lib_generator);
#ifdef __cpp_lib_flat_map
    std::println("__cpp_lib_flat_map   {}", __cpp_lib_flat_map);
#else
    std::println("__cpp_lib_flat_map   없음");
#endif
#ifdef __cpp_lib_mdspan
    std::println("__cpp_lib_mdspan     {}", __cpp_lib_mdspan);
#else
    std::println("__cpp_lib_mdspan     없음");
#endif
}
```

```text
__cplusplus          202302
__cpp_lib_print      202211
__cpp_lib_expected   202211
__cpp_lib_generator  202207
__cpp_lib_flat_map   없음
__cpp_lib_mdspan     없음
```

GCC 14의 출력입니다. 값은 그 기능이 표준에 들어간 해와 달이고, 매크로가 없으면 기능이 없습니다. 같은 프로그램을 Clang 20과 libc++로 컴파일하면 `flat_map`과 `mdspan`이 202207로 나옵니다. 이 책의 예제는 GCC 14에서 돌려 확인했고, GCC 14에 없는 것은 그 자리에서 따로 밝힙니다.

헤더 자체가 있는지는 `__has_include`로 묻습니다.

```cpp nocheck
#if __has_include(<flat_map>)
#  include <flat_map>
template <typename K, typename V> using Table = std::flat_map<K, V>;
#else
#  include <map>
template <typename K, typename V> using Table = std::map<K, V>;
#endif
```

## 운영체제가 없는 곳

리눅스가 도는 라즈베리파이는 표준이 "호스트 환경"이라 부르는 곳이고, 위의 헤더가 모두 있습니다. 운영체제 없이 도는 마이크로컨트롤러는 "프리스탠딩 환경"이고, 표준이 보장하는 헤더가 훨씬 적습니다.

| 판 | 프리스탠딩에서 보장되는 것 |
| --- | --- |
| C++20까지 | `<cstddef>` `<cstdint>` `<limits>` `<new>` `<type_traits>` `<concepts>` `<compare>` `<bit>` `<atomic>` `<initializer_list>` `<source_location>` 등 |
| C++23에서 더해진 것 | `<utility>` `<tuple>` `<ratio>` 전부, `<memory>` `<iterator>` `<ranges>`의 일부 |

보장이 그렇다는 것이고, 실제 툴체인은 대개 이보다 많이 줍니다. 힙과 예외와 파일에 기대지 않는 `<array>`, `<span>`, `<algorithm>`, `<optional>`은 마이크로컨트롤러에서도 흔히 그대로 씁니다. 무엇을 피하는지는 임베디드 C++ 책의 [「쓰지 않는 기능」](#/read/cpp-embedded/why-avoid)에서 다룹니다.

## 정리

- 이름을 쓴 파일에서 그 헤더를 직접 포함한다. 다른 헤더가 끌고 와 준 것에 기대지 않는다
- C 헤더는 `<c이름>` 꼴로 포함하고 `std::`를 붙여 부른다
- 기능이 있는지는 `<version>`의 `__cpp_lib_...` 매크로와 `__has_include`로 확인한다
