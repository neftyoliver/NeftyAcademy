`std::unordered_map`과 `std::unordered_set`은 해시 표입니다. [`map`](#/read/cpp-stl/assoc-map)이 열쇠를 **견주어** 자리를 찾는다면, 이쪽은 열쇠로 **숫자를 계산해** 자리로 바로 갑니다. 그래서 찾기가 평균 O(1)이고, 그 값으로 순서를 잃습니다.

## 버킷

열쇠를 해시 함수에 넣으면 큰 정수가 나옵니다. 그것을 버킷 개수로 나눈 나머지가 그 원소가 들어갈 버킷입니다. 같은 버킷에 떨어진 원소들은 사슬로 이어집니다.

```text
버킷   [0] [1] [2] [3] [4] ...
        │       │
        ▼       ▼
      led=17  fan=4 ─▶ button=22
```

쓰는 법은 `map`과 같습니다. `[]`, `insert`, `try_emplace`, `find`, `contains`, `erase`가 모두 있습니다. 없는 것은 순서에 기대는 `lower_bound`와 `upper_bound`입니다.

원소가 늘어 버킷이 붐비면 버킷을 늘리고 원소를 다시 나눠 담습니다. 이것이 **다시 해싱**(rehash)입니다.

```cpp
#include <print>
#include <unordered_map>

int main()
{
    std::unordered_map<int, int> m;
    std::println("처음 버킷 {}, 버킷당 최대 원소 {}", m.bucket_count(),
                 m.max_load_factor());

    std::size_t last = m.bucket_count();
    for (int i = 0; i < 300; ++i) {
        m[i] = i;
        if (m.bucket_count() != last) {
            std::println("원소 {:3}개에서 버킷 {:3} -> {:3}", m.size(), last,
                         m.bucket_count());
            last = m.bucket_count();
        }
    }
    std::println("버킷당 평균 {:.2f}개", m.load_factor());

    std::unordered_map<int, int> prepared;
    prepared.reserve(300);          // 300개가 들어가도 다시 해싱하지 않게
    std::println("reserve(300) 뒤 버킷 {}", prepared.bucket_count());
}
```

```text
처음 버킷 1, 버킷당 최대 원소 1
원소   1개에서 버킷   1 ->  13
원소  14개에서 버킷  13 ->  29
원소  30개에서 버킷  29 ->  59
원소  60개에서 버킷  59 -> 127
원소 128개에서 버킷 127 -> 257
원소 258개에서 버킷 257 -> 541
버킷당 평균 0.55개
reserve(300) 뒤 버킷 313
```

GCC 14의 결과입니다. 버킷당 평균 원소 수(`load_factor`)가 `max_load_factor`(기본 1)를 넘으려 하면 버킷을 두 배 남짓으로 늘립니다. [`vector`의 다시 할당](#/read/cpp-stl/ov-complexity)과 같은 상각 구조이고, 약점도 같습니다. 다시 해싱하는 그 한 번은 모든 원소를 건드리는 O(n)입니다. 들어갈 개수를 알면 `reserve(n)`으로 미리 잡습니다.

## 순서가 없다

```cpp
#include <print>
#include <unordered_set>

int main()
{
    std::unordered_set<int> ids = {3, 1, 4, 15, 9, 2, 6};
    for (int id : ids)
        std::print("{} ", id);
    std::println("");

    for (int id = 100; id < 110; ++id)      // 더 넣으면 다시 해싱된다
        ids.insert(id);
    for (int id : ids)
        std::print("{} ", id);
    std::println("");
}
```

```text nocheck
6 9 2 15 4 1 3
109 108 107 106 3 1 105 4 2 9 100 6 101 15 102 103 104
```

GCC 14의 결과입니다. 넣은 순서도, 크기 순서도 아닙니다. 더 넣었더니 앞서 있던 원소들의 순서까지 바뀌었습니다. 이 순서는 구현마다 다르고 같은 구현에서도 판마다 달라질 수 있으므로, **도는 순서에 기대는 코드를 쓰면 안 됩니다.** 출력 파일의 줄 순서, 테스트의 기대값, 통신으로 보내는 항목의 순서가 여기에 걸리면 컴파일러를 올린 날 깨집니다. 순서가 필요하면 `map`을 쓰거나, 꺼낸 뒤에 정렬합니다.

## 무효화 규칙

| 연산 | 반복자 | 포인터와 참조 |
| --- | --- | --- |
| 넣기, 다시 해싱이 일어남 | 전부 죽는다 | 모두 산다 |
| 넣기, 다시 해싱이 없음 | 모두 산다 | 모두 산다 |
| 지우기 | 지운 원소의 것만 | 지운 원소의 것만 |
| `rehash`, `reserve` | 전부 죽는다 | 모두 산다 |

원소는 노드에 따로 살고 버킷은 노드를 가리키기만 합니다. 다시 해싱은 버킷 배열만 새로 짜므로 원소의 주소는 그대로입니다.

```cpp
#include <cstdint>
#include <print>
#include <string>
#include <unordered_map>

int main()
{
    std::unordered_map<std::string, int> pins = {{"led", 17}, {"button", 22}};
    const int* led = &pins.at("led");
    const auto before = reinterpret_cast<std::uintptr_t>(led);
    const std::size_t buckets_before = pins.bucket_count();

    for (int i = 0; i < 1000; ++i)
        pins["pin" + std::to_string(i)] = i;

    const auto after = reinterpret_cast<std::uintptr_t>(&pins.at("led"));
    std::println("버킷 {} -> {}", buckets_before, pins.bucket_count());
    std::println("원소는 제자리인가: {}, 값 {}", before == after, *led);
}
```

```text
버킷 13 -> 1109
원소는 제자리인가: true, 값 17
```

값을 가리키는 포인터는 들고 있어도 되고, 반복자는 넣는 일이 끼면 다시 `find`로 얻습니다.

## 최악의 경우

"평균 O(1)"은 원소가 버킷에 고르게 퍼질 때의 이야기입니다. 모두 한 버킷에 몰리면 사슬 하나를 처음부터 훑는 O(n)이 됩니다. 모든 열쇠에 0을 돌려주는 해시로 재 봅니다.

```cpp nosan
#include <chrono>
#include <cstddef>
#include <print>
#include <unordered_set>

struct BadHash {
    std::size_t operator()(int) const { return 0; }     // 전부 같은 버킷으로
};

template <typename Set>
long long fill_ms(int n)
{
    const auto start = std::chrono::steady_clock::now();
    Set s;
    for (int i = 0; i < n; ++i)
        s.insert(i);
    const auto took = std::chrono::steady_clock::now() - start;
    return std::chrono::duration_cast<std::chrono::milliseconds>(took).count();
}

int main()
{
    for (int n : {5'000, 10'000, 20'000})
        std::println("n = {:5}: 기본 해시 {}ms, 나쁜 해시 {}ms", n,
                     fill_ms<std::unordered_set<int>>(n),
                     fill_ms<std::unordered_set<int, BadHash>>(n));
}
```

```text nocheck
n =  5000: 기본 해시 0ms, 나쁜 해시 33ms
n = 10000: 기본 해시 0ms, 나쁜 해시 131ms
n = 20000: 기본 해시 0ms, 나쁜 해시 526ms
```

x86-64 서버, `-O2`의 값입니다. 개수가 두 배가 되면 시간이 네 배가 됩니다. 해시 함수의 질이 이 컨테이너의 전부이고, [「해시 함수 만들기」](#/read/cpp-stl/assoc-hash)에서 다룹니다.

<Note kind="warn">
바깥에서 들어온 값을 열쇠로 쓰는 서버는 이 최악의 경우를 **공격으로** 당할 수 있습니다. 같은 버킷에 떨어지는 열쇠를 골라 수만 개 보내면 요청 하나가 서버를 멈춥니다. 표준 라이브러리의 해시에는 실행마다 바뀌는 씨앗이 없어서 막아 주지 않습니다. 믿을 수 없는 입력에는 `map`을 쓰거나 씨앗이 있는 해시를 직접 넣습니다.
</Note>

## map과 고르기

| | `map` | `unordered_map` |
| --- | --- | --- |
| 찾기 | O(log n) | 평균 O(1), 최악 O(n) |
| 열쇠에 필요한 것 | `<` | 해시 함수와 `==` |
| 도는 순서 | 열쇠 순 | 정해지지 않음 |
| 범위로 찾기 | 된다 | 안 된다 |
| 넣을 때 걸리는 시간 | 고르다 | 다시 해싱할 때 한 번 튄다 |

무작위 `int` 열쇠로 찾기 한 번에 걸린 시간을 재면 원소 100개에서는 `map` 5ns, `unordered_map` 4ns로 비슷했고, 1만 개에서 82ns와 11ns, 100만 개에서 1,400ns와 50ns로 벌어졌습니다(x86-64 서버, GCC 14 `-O2`). 원소가 많고 순서가 필요 없으면 `unordered_map`이 맞습니다. 원소가 수십 개라면 무엇을 써도 되고, 그때는 [정렬된 `vector`](#/read/cpp-stl/assoc-flat)가 메모리를 가장 덜 씁니다.

## 정리

- 해시로 버킷을 골라 바로 간다. 평균 O(1)이고 순서가 없다. 도는 순서에 기대지 않는다
- 붐비면 다시 해싱한다. 반복자는 죽고 원소의 주소는 산다. 개수를 알면 `reserve`
- 해시가 나쁘거나 공격받으면 O(n)이 된다. 믿을 수 없는 열쇠에는 조심한다
