부모 포인터가 가리키는 객체가 실제로 무엇인지 실행 중에 물을 수 있습니다. 이 기능을 **RTTI**(run-time type information)라고 하고, `dynamic_cast`와 `typeid`가 그 창구입니다.

## dynamic_cast

```cpp
#include <memory>
#include <print>
#include <typeinfo>
#include <vector>

class Sensor {
public:
    virtual ~Sensor() = default;
    virtual double read() const = 0;
};

class Thermometer : public Sensor {
public:
    double read() const override { return 23.5; }
    void calibrate(double offset) { std::println("보정 {:+}", offset); }
};

class Barometer : public Sensor {
public:
    double read() const override { return 1013.2; }
};

int main()
{
    std::vector<std::unique_ptr<Sensor>> all;
    all.push_back(std::make_unique<Thermometer>());
    all.push_back(std::make_unique<Barometer>());

    for (const auto& s : all) {
        if (auto* t = dynamic_cast<Thermometer*>(s.get()))
            t->calibrate(-0.5);                 // 온도계일 때만 들어온다
        else
            std::println("온도계가 아니다");

        const Sensor& ref = *s;
        std::println("{}", typeid(ref) == typeid(Barometer));
    }
}
```

```text
보정 -0.5
false
온도계가 아니다
true
```

`dynamic_cast<Thermometer*>(p)`는 `p`가 가리키는 객체가 정말 `Thermometer`(또는 그 자식)일 때만 포인터를 돌려주고, 아니면 `nullptr`을 돌려줍니다.

| 꼴 | 실패하면 |
| --- | --- |
| `dynamic_cast<T*>(pointer)` | `nullptr` |
| `dynamic_cast<T&>(reference)` | `std::bad_cast` 예외 |

- 가상 함수가 하나라도 있는 타입(다형적 타입)에만 쓸 수 있다. 타입 정보가 가상 함수 표 옆에 놓이기 때문이다
- 부모에서 자식으로 내려갈 때뿐 아니라, [다중 상속](#/read/cpp-syntax/inh-multiple)에서 한 부모로부터 **옆의 부모로** 건너갈 때도 쓴다
- `if (auto* t = dynamic_cast<…>(…))` 꼴로 쓰면 성공했을 때만 `t`가 보인다

## static_cast로 내려가면

```cpp nocheck
auto* t = static_cast<Thermometer*>(s.get());   // 확인하지 않는다
t->calibrate(-0.5);     // s가 Barometer였다면 정의되지 않은 동작
```

`static_cast`도 내려가기를 해 주지만 **확인하지 않습니다.** 비용이 없는 대신 틀리면 정의되지 않은 동작입니다. 실제 타입을 다른 방법으로 이미 확실히 알 때만 씁니다.

## typeid

`typeid(식)`은 그 식의 타입을 나타내는 `std::type_info`를 돌려줍니다(`<typeinfo>`).

| 쓰임 | 결과 |
| --- | --- |
| `typeid(ref) == typeid(Barometer)` | 실제 타입이 **정확히** `Barometer`인가. 자식은 다르다고 나온다 |
| `typeid(ref).name()` | 타입의 이름. 구현마다 꼴이 다르다 |
| `typeid(int)` | 타입을 직접 줄 수도 있다. 이때는 컴파일할 때 정해진다 |

`name()`이 돌려주는 글자는 표준이 정하지 않습니다. GCC와 Clang은 `11Thermometer` 같은 맹글링된 이름을, MSVC는 `class Thermometer`를 줍니다. 로그에 찍는 용도일 뿐 비교나 저장에 쓰면 안 됩니다.

## 비용과 끄기

| 항목 | 내용 |
| --- | --- |
| 크기 | 다형적 클래스마다 타입 정보(이름 문자열 포함)가 실행 파일에 들어간다 |
| 시간 | `dynamic_cast`는 상속 그래프를 따라가며 견준다. 가상 함수 호출보다 훨씬 느리다 |
| 끄기 | `-fno-rtti`로 통째로 끌 수 있다. `dynamic_cast`와 `typeid`를 쓰면 컴파일 오류가 된다 |

플래시가 작은 마이크로컨트롤러 프로젝트와 일부 큰 코드베이스(LLVM, 크로뮴 등)는 RTTI를 끄고 씁니다. 라즈베리 파이 급에서는 켜 두어도 부담이 없습니다.

## 먼저 물을 것

`dynamic_cast`가 자꾸 필요하다면 설계가 보내는 신호입니다. "타입을 물어보고 갈라서 처리"하는 코드는 타입이 하나 늘 때마다 모든 갈래를 찾아 고쳐야 합니다.

| 대안 | 언제 |
| --- | --- |
| [가상 함수](#/read/cpp-syntax/inh-virtual)를 하나 더 둔다 | 모든 자식에게 뜻이 있는 동작일 때. 대부분 이것이 답이다 |
| 더 좁은 인터페이스로 나눈다 | 일부 자식만 가진 능력일 때 (`Calibratable`) |
| `std::variant`와 `std::visit` | 타입의 종류가 정해져 있고 닫혀 있을 때. 빠뜨린 갈래를 컴파일러가 잡는다 |

<Note>
그래도 쓸 자리는 있습니다. 플러그인처럼 바깥에서 온 객체가 **선택 사항인 인터페이스**를 구현했는지 묻는 경우가 그렇습니다. "이 장치가 `Calibratable`이기도 한가?"는 `dynamic_cast`가 정직하게 답하는 질문입니다.
</Note>

## 정리

- `dynamic_cast`는 확인하고 내려간다. 포인터는 `nullptr`, 참조는 예외로 실패를 알린다
- `typeid`는 정확한 타입을 견준다. `name()`의 글자는 구현마다 다르다
- 자주 필요하면 가상 함수나 `std::variant`로 풀 수 있는지 먼저 본다
