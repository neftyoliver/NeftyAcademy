C++은 C의 빌드 방식을 그대로 물려받았습니다. `.cpp` 파일 하나하나를 **서로 모르는 채로** 컴파일하고, 링커가 나중에 이어 붙입니다. 헤더는 그 사이에서 "서로에 대해 알아야 할 것"을 글자째로 복사해 넣는 장치입니다.

## 번역 단위

`.cpp` 파일 하나에 `#include`한 헤더를 모두 펼쳐 넣은 것이 **번역 단위**입니다. 컴파일러가 실제로 보는 것은 이것입니다.

| `#include` 한 줄 | 전처리 뒤의 줄 수 (GCC 14, `-std=c++23`) |
| --- | --- |
| `<cstdio>` | 1,079 |
| `<vector>` | 27,941 |
| `<string>` | 33,578 |
| `<print>` | 66,000 |
| `<iostream>` | 68,977 |

`std::println` 한 줄을 쓰는 파일도 6만 줄을 컴파일합니다. `.cpp`가 백 개면 그 6만 줄을 백 번 읽습니다. C++ 빌드가 느린 가장 큰 까닭이고, [모듈](#/read/cpp-syntax/mod-modules)이 풀려는 문제입니다. `g++ -H`는 어떤 헤더가 어떤 헤더를 끌고 오는지 나무로 보여 줍니다.

## 한 번 정의 규칙

여러 번역 단위가 같은 이름을 쓸 때의 규칙이 **ODR**(One Definition Rule)입니다. [「inline과 하나의 정의 규칙(ODR)」](#/read/cpp-syntax/fn-inline)에서 본 것을 정리하면 이렇습니다.

| 종류 | 규칙 |
| --- | --- |
| 보통 함수, 전역 변수 | 프로그램 전체에 정의가 **하나**. 둘이면 링크 오류 |
| 클래스, 열거형, 템플릿, `inline` 함수와 변수 | 번역 단위마다 하나씩 있어도 된다. 단, **모두 똑같아야** 한다 |

둘째 줄의 "똑같아야 한다"는 컴파일러도 링커도 **확인하지 않습니다.** 어기면 정의되지 않은 동작이고, 표준은 진단을 요구하지 않습니다.

## 어기면

서로 다른 두 파일이 우연히 같은 이름의 구조체와 함수를 가졌습니다.

```cpp nocheck
// sensor.cpp
struct Reading {
    int value = 1;
};

inline int scale(Reading r) { return r.value * 10; }

int from_sensor() { return scale(Reading{}); }
```

```cpp nocheck
// display.cpp
struct Reading {                // 같은 이름, 다른 내용
    double value = 2.5;
    int unit = 3;
};

inline int scale(Reading r) { return static_cast<int>(r.value * 100) + r.unit; }

int from_display() { return scale(Reading{}); }
```

```cpp nocheck
// main.cpp
#include <print>

int from_sensor();
int from_display();

int main()
{
    std::println("{} {}", from_sensor(), from_display());
}
```

기대하는 출력은 `10 253`입니다. 실제로는 이렇게 나옵니다(GCC 14, x86-64 리눅스).

```text
$ g++ -std=c++23 -O0 sensor.cpp display.cpp main.cpp && ./a.out
10 30
$ g++ -std=c++23 -O2 sensor.cpp display.cpp main.cpp && ./a.out
10 253
```

두 `scale(Reading)`은 링커가 보기에 **같은 이름**입니다. `inline` 함수는 여러 곳에 있어도 되므로 링커는 하나만 남기고 나머지를 버립니다. `-O0`에서는 `display.cpp`가 `sensor.cpp`의 `scale`을 부르게 되었고, `-O2`에서는 호출이 각자 인라인되어 우연히 맞았습니다. 파일을 적는 순서를 바꾸면 결과가 또 바뀝니다.

경고는 없습니다. **디버그 빌드에서만 나는 버그**, 혹은 그 반대가 이렇게 만들어집니다.

## 막는 법

| 방법 | 내용 |
| --- | --- |
| 파일 안에서만 쓰는 것은 [이름 없는 네임스페이스](#/read/cpp-syntax/ns-basic)에 | `namespace { struct Reading { … }; }` 다른 파일의 같은 이름과 충돌하지 않는다 |
| 여러 파일이 쓰는 것은 **헤더 하나**에서만 정의 | 복사해 붙여 넣은 구조체가 두 벌 있으면 언젠가 어긋난다 |
| 프로젝트의 것은 네임스페이스 안에 | 다른 라이브러리와의 충돌을 막는다 |
| 모든 파일을 **같은 옵션**으로 컴파일 | `-DDEBUG`로 멤버가 늘어나는 구조체, `-fpack-struct`, 표준 라이브러리의 디버그 모드가 파일마다 다르면 같은 사고가 난다 |

`-flto -Wodr`로 빌드하면 GCC가 번역 단위들을 견줘 일부를 찾아 줍니다. 가상 함수가 있는 클래스의 어긋남은 잡았고, 위 예제는 잡지 못했습니다. 도구보다 위의 습관이 먼저입니다.

## 헤더에 두는 것

| 헤더 (`.h`, `.hpp`) | 소스 (`.cpp`) |
| --- | --- |
| 함수의 선언 | 함수의 정의 |
| 클래스 정의 (멤버 함수의 선언 포함) | 멤버 함수의 정의 |
| 템플릿 (정의까지) | 그 파일에서만 쓰는 도우미 (이름 없는 네임스페이스) |
| `inline` 함수, `constexpr` 함수와 상수 | 전역 변수의 정의 |
| `enum`, `using` 별칭, `extern` 선언 | |

## 헤더 쓰는 법

| 지침 | 까닭 |
| --- | --- |
| 맨 위에 `#pragma once` (또는 `#ifndef` 가드) | 같은 헤더가 두 번 펼쳐져 클래스가 재정의되는 것을 막는다 |
| 헤더는 **혼자서도** 컴파일되어야 한다 | 쓰는 것은 스스로 `#include`한다. 남이 먼저 포함해 주기를 기대하지 않는다 |
| 헤더에 `using namespace`를 쓰지 않는다 | 포함한 모든 파일에 퍼진다 |
| 필요한 것만 포함한다 | 헤더의 `#include` 하나는 그것을 쓰는 모든 파일의 컴파일 시간이 된다 |
| 가리키기만 하면 [전방 선언](#/read/cpp-syntax/mod-pimpl)으로 | 포함 자체를 없앤다 |
| `.cpp`에서는 **자기 헤더를 맨 먼저** 포함한다 | 헤더가 혼자 컴파일되는지를 매번 확인하게 된다 |

`#pragma once`는 표준이 아니지만 GCC, Clang, MSVC가 모두 지원하고, 가드 이름이 겹치는 실수가 없어 널리 씁니다.

<Note>
`static` 전역 함수와 이름 없는 네임스페이스의 것은 **내부 연결**이라서 번역 단위마다 따로 있습니다. 링커에게 보이지 않으므로 ODR 충돌이 없습니다. 반대로 이런 것을 **헤더에** 두면 포함한 파일마다 사본이 생깁니다. 헤더의 상수에는 `inline constexpr`을 씁니다.
</Note>

## 정리

- `.cpp`마다 따로 컴파일되고, 헤더는 글자째로 복사된다. 그래서 느리다
- 같은 이름의 클래스나 `inline` 함수가 번역 단위마다 다르면 경고 없이 깨진다
- 파일 전용은 이름 없는 네임스페이스에, 공유하는 것은 헤더 하나에, 옵션은 모두 같게
