표준 콘셉트로 모자라면 직접 만듭니다. 콘셉트는 "타입이 갖춰야 할 것"에 이름을 붙인 `bool` 상수식입니다.

## 콘셉트 정의

```cpp
#include <concepts>
#include <print>
#include <string_view>

template <typename T>
concept Sensor = requires(const T& s) {
    { s.read() } -> std::convertible_to<double>;
    { s.name() } -> std::convertible_to<std::string_view>;
};

struct Thermometer {
    double read() const { return 23.5; }
    std::string_view name() const { return "temp"; }
};

struct Counter {
    int read() const { return 42; }
    const char* name() const { return "count"; }
};

void report(const Sensor auto& s)
{
    std::println("{} = {}", s.name(), static_cast<double>(s.read()));
}

static_assert(Sensor<Thermometer>);
static_assert(!Sensor<int>);

int main()
{
    report(Thermometer{});
    report(Counter{});
}
```

```text
temp = 23.5
count = 42
```

`Thermometer`와 `Counter`는 **아무것도 상속하지 않았습니다.** `Sensor`라는 말도 모릅니다. `read()`와 `name()`이 있고 결과가 알맞게 바뀌기만 하면 `Sensor`입니다. 남이 만든 타입, 고칠 수 없는 타입도 조건만 맞으면 그대로 쓸 수 있습니다.

`static_assert(Sensor<Thermometer>);`를 타입 옆에 적어 두면 "이 타입은 `Sensor`여야 한다"는 뜻이 코드에 남고, 어긋나는 순간 그 줄에서 오류가 납니다.

## 쌓아 올리기

콘셉트는 다른 콘셉트로 만들 수 있습니다. `&&`로 이으면 [더 좁은 콘셉트](#/read/cpp-syntax/con-requires)가 됩니다.

```cpp nocheck
template <typename T>
concept Resettable = requires(T& t) { t.reset(); };

template <typename T>
concept ManagedSensor = Sensor<T> && Resettable<T> && std::movable<T>;

void run(const Sensor auto& s);             // (1)
void run(const ManagedSensor auto& s);      // (2) 둘 다 맞으면 이쪽이 뽑힌다
```

## 가상 함수와 견주기

[가상 함수](#/read/cpp-syntax/inh-virtual)와 템플릿은 "여러 타입을 같은 코드로 다룬다"는 같은 문제의 두 가지 답입니다.

| | 가상 함수 | 템플릿 + 콘셉트 |
| --- | --- | --- |
| 타입이 정해지는 때 | 실행 중 | 컴파일할 때 |
| 타입이 갖출 것 | 부모 클래스를 상속 | 조건만 만족 |
| 호출 | vptr을 거친 간접 호출 | 직접 호출. 인라인이 된다 |
| 여러 타입을 한 컨테이너에 | 된다 (`vector<unique_ptr<Base>>`) | 안 된다 (타입마다 다른 함수다) |
| 코드 크기 | 함수 하나 | 타입마다 하나씩 |
| 컴파일 | 본문을 `.cpp`에 숨길 수 있다 | 본문이 헤더에 있어야 한다 |
| 실행 중에 바꿔 끼우기 | 된다 (플러그인, 설정에 따라) | 안 된다 |

고르는 기준은 "**어떤 타입이 올지 언제 아는가**"입니다.

- 설정 파일을 읽어야 어느 센서인지 안다, 종류가 다른 것들을 한 목록에 담는다 → 가상 함수
- 이 보드에는 이 센서라는 것을 컴파일할 때 안다, 안쪽 루프라서 호출 비용이 아깝다 → 템플릿

둘을 섞기도 합니다. 바깥 경계는 [인터페이스](#/read/cpp-syntax/inh-abstract)로 두고, 그 구현 안의 뜨거운 부분은 템플릿으로 씁니다.

## 좋은 콘셉트

| 지침 | 까닭 |
| --- | --- |
| 문법이 아니라 **뜻**에 이름을 붙인다 | `HasPlus`(`+`가 있다)보다 `Number`. `std::string`도 `+`가 있지만 수가 아니다 |
| 연산 하나짜리 콘셉트를 피한다 | 뜻이 있는 개념은 대개 연산 여러 개와 그 사이의 관계로 이루어진다 |
| 표준 콘셉트를 재료로 쓴다 | `std::regular<T> && …`. 이름이 익숙하고 포함 관계가 맞물린다 |
| 필요한 만큼만 요구한다 | 본문이 쓰지 않는 것을 요구하면 쓸 수 있는 타입을 까닭 없이 막는다 |
| 본문이 쓰는 것은 다 요구한다 | 빠뜨리면 제약은 통과하고 본문에서 옛날식 긴 오류가 난다 |

마지막 둘이 어긋나는지는 컴파일러가 봐 주지 않습니다. 콘셉트를 겨우 만족하는 **가장 가난한 타입**을 하나 만들어 템플릿을 인스턴스화해 보는 것이 시험 방법입니다.

<Note kind="warn">
콘셉트는 **문법만** 확인합니다. `read()`가 있다는 것은 보지만 그것이 정말 "읽는" 함수인지, 같은 값을 돌려주는지는 모릅니다. `std::regular_invocable`과 `std::invocable`이 문법상 똑같은 것처럼, 뜻에 대한 약속은 문서와 이름으로만 전해집니다.
</Note>

## 클래스 템플릿에도

```cpp nocheck
template <Sensor S>
class Logger {
public:
    explicit Logger(S sensor) : sensor_(std::move(sensor)) {}
    void tick() { std::println("{}", sensor_.read()); }

private:
    S sensor_;          // 포인터가 아니라 값으로 품는다. 힙 할당이 없다
};

Logger logger{Thermometer{}};       // Logger<Thermometer>
```

가상 함수 판이라면 `std::unique_ptr<Sensor>`를 멤버로 두었을 자리입니다. 템플릿 판은 센서를 **통째로 품고**, `tick()` 안의 `read()`는 인라인됩니다.

## 정리

- `template <typename T> concept 이름 = 조건;`. 상속 없이 조건만 맞으면 만족한다
- 타입을 컴파일할 때 알면 템플릿, 실행 중에 정해지면 가상 함수
- 콘셉트는 뜻에 이름을 붙이고, 본문이 쓰는 만큼만 요구한다
