[「우리 프로그램이 작동하는 방식」](#/read/basics/code-runs)에서 CPU는 프로그램 카운터가 가리키는 명령 하나를 실행하고 다음으로 넘어가는 일만 되풀이한다고 했습니다. 이 쪽에서는 그 되풀이를 실제 x86-64 기계어 바이트로 따라가 보고, 지금의 CPU가 이 단순한 순서를 어떻게 겹쳐서 빠르게 하는지 봅니다.

## 세 단계

| 단계 | 하는 일 |
| --- | --- |
| 가져오기(fetch) | 프로그램 카운터가 가리키는 주소에서 명령의 바이트를 읽는다. 프로그램 카운터를 다음 명령으로 옮긴다 |
| 해석(decode) | 바이트를 보고 무슨 명령인지, 어느 레지스터를 쓰는지 알아낸다 |
| 실행(execute) | 연산 장치가 계산하고, 결과를 레지스터나 메모리에 쓴다 |

x86-64에서 프로그램 카운터의 이름은 `rip`, ARM64에서는 `pc`입니다([「CPU와 레지스터」](#/read/basics/arch-cpu)). 반복과 조건은 모두 이 칸의 값을 바꾸는 **점프 명령**으로 만들어집니다.

## 기계어 바이트로 따라가기

1부터 n까지 더하는 C 함수입니다.

```c
int sum_to(int n)
{
    int s = 0;
    for (int i = 1; i <= n; i++)
        s += i;
    return s;
}
```

`gcc -O1 -c`로 컴파일한 뒤 `objdump -d -M intel`로 풀어 본 결과입니다. 왼쪽부터 함수 안에서의 위치(16진수), 명령의 실제 바이트, 사람이 읽는 이름입니다.

```text
   0:  f3 0f 1e fa         endbr64
   4:  85 ff               test   edi,edi
   6:  7e 24               jle    2c
   8:  83 c7 01            add    edi,0x1
   b:  b8 01 00 00 00      mov    eax,0x1
  10:  ba 00 00 00 00      mov    edx,0x0
  15:  (11바이트짜리 아무 일도 안 하는 명령)
  20:  01 c2               add    edx,eax
  22:  83 c0 01            add    eax,0x1
  25:  39 f8               cmp    eax,edi
  27:  75 f7               jne    20
  29:  89 d0               mov    eax,edx
  2b:  c3                  ret
  2c:  ba 00 00 00 00      mov    edx,0x0
  31:  eb f6               jmp    29
```

n이 3일 때 CPU가 하는 일을 따라가 봅니다. `edi`에 n이, `eax`에 i가, `edx`에 합 s가 들어 있습니다.

1. `rip`가 4일 때 `85 ff`를 가져옵니다. 명령이 2바이트이므로 `rip`는 6이 됩니다. 해석해 보니 `test edi,edi`, n이 0 이하인지 보는 명령입니다
2. `7e 24`는 "0 이하이면 점프"입니다. n은 3이라 점프하지 않고 `rip`는 8로 갑니다
3. 8~10번에서 n에 1을 더해 4로 만들고(끝 표시), i를 1, s를 0으로 둡니다
4. 20번부터가 반복입니다. s에 i를 더하고, i에 1을 더하고, i와 4를 비교합니다
5. 27번의 `75 f7`이 핵심입니다. `75`는 "같지 않으면 점프", `f7`은 점프할 거리입니다. `f7`은 [2의 보수](#/read/basics/math-integers)로 −9이고, 이 명령 다음 주소인 29에서 9를 빼면 20입니다. 그래서 `rip`가 20으로 돌아가 반복합니다
6. i가 4가 되면 점프하지 않고 29로 넘어가, 합을 결과 레지스터 `eax`로 옮기고 `ret`으로 돌아갑니다

C의 `for`는 기계어에서 "비교하고, 조건이 맞으면 `rip`를 뒤로 돌리는 점프"가 됐습니다. `if`, `while`, 함수 호출도 모두 이런 점프의 조합입니다.

<Note>
15번 자리의 11바이트는 아무 일도 하지 않는 명령(nop)입니다. 반복이 시작되는 20번을 16의 배수 주소에 맞춰 두면 CPU가 명령을 가져오기 편해서, 컴파일러가 빈자리를 채워 넣었습니다.
</Note>

## 파이프라인

세 단계를 명령 하나씩 차례로 하면, 연산 장치는 가져오기와 해석을 하는 동안 놀게 됩니다. 그래서 CPU는 공장의 조립 라인처럼 단계를 **겹칩니다.** 명령 1을 실행하는 동안 명령 2를 해석하고 명령 3을 가져옵니다.

| 박자 | 가져오기 | 해석 | 실행 |
| --- | --- | --- | --- |
| 1 | 명령 1 | | |
| 2 | 명령 2 | 명령 1 | |
| 3 | 명령 3 | 명령 2 | 명령 1 |
| 4 | 명령 4 | 명령 3 | 명령 2 |

라인이 차고 나면 박자마다 명령 하나가 끝납니다. 지금의 CPU는 단계를 열몇 개로 더 잘게 나누고, 라인을 여러 줄 두어서 한 박자에 명령 여러 개를 끝냅니다.

## 분기 예측

파이프라인에는 약점이 있습니다. 27번의 `jne`를 아직 실행하지 않았는데 그다음 명령을 미리 가져와야 합니다. 20으로 돌아갈지 29로 갈지는 비교가 끝나야 압니다. 그래서 CPU는 **어느 쪽일지 짐작해서** 그쪽 명령을 먼저 진행합니다. 짐작이 맞으면 그대로 이어 가고, 틀리면 미리 해 둔 일을 버리고 다시 시작합니다. 버리는 데 박자가 십여 번 듭니다.

CPU는 지난번에 어느 쪽으로 갔는지를 기억해서 짐작합니다. 반복문처럼 규칙적인 갈림길은 거의 다 맞힙니다. 규칙이 없으면 절반쯤 틀립니다. 아래 프로그램으로 그 차이를 재 봅니다. 0~255 사이의 무작위 값 100만 개 가운데 128 이상인 것만 더하는데, 한 번은 섞인 채로, 한 번은 정렬한 뒤에 합니다.

```c flags=-O1,-fno-if-conversion,-fno-if-conversion2
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

enum { N = 1 << 20, ROUNDS = 50 };

static int cmp(const void *a, const void *b)
{
    return *(const unsigned char *)a - *(const unsigned char *)b;
}

// 128 이상인 값만 더한다. 조건 하나에 따라 갈림길이 생긴다
static double run(const unsigned char *v, long *out)
{
    struct timespec a, b;
    long total = 0;
    timespec_get(&a, TIME_UTC);
    for (int r = 0; r < ROUNDS; r++)
        for (int i = 0; i < N; i++)
            if (v[i] >= 128)
                total += v[i];
    timespec_get(&b, TIME_UTC);
    *out = total;
    double ns = (b.tv_sec - a.tv_sec) * 1e9 + (b.tv_nsec - a.tv_nsec);
    return ns / ((double)N * ROUNDS);
}

int main(void)
{
    unsigned char *v = malloc(N);
    for (int i = 0; i < N; i++)
        v[i] = (unsigned char)(rand() & 0xff);

    long t1, t2;
    double mixed = run(v, &t1);
    qsort(v, N, 1, cmp);
    double sorted = run(v, &t2);
    printf("뒤섞인 배열  %.2f ns/칸  합 %ld\n", mixed, t1);
    printf("정렬된 배열  %.2f ns/칸  합 %ld\n", sorted, t2);
    free(v);
    return 0;
}
```

`gcc -O1 -fno-if-conversion -fno-if-conversion2`로 컴파일해 검사 기계에서 돌린 결과입니다.

```text nocheck
뒤섞인 배열  3.50 ns/칸  합 5026738600
정렬된 배열  0.30 ns/칸  합 5026738600
```

같은 값을 같은 개수만큼 더해서 합도 같은데, 섞인 쪽이 열 배 넘게 느립니다. 정렬하면 앞쪽 절반은 늘 "아니다", 뒤쪽 절반은 늘 "그렇다"여서 CPU의 짐작이 거의 다 맞습니다. 섞여 있으면 절반쯤 틀리고, 틀릴 때마다 파이프라인을 비웁니다.

<Note kind="tip">
컴파일 옵션에 붙인 두 `-fno-if-conversion`은 실험을 위해 컴파일러의 꾀를 막은 것입니다. 그냥 `gcc -O2`로 컴파일하면 컴파일러가 갈림길을 "조건에 따라 값을 고르는" 명령으로 바꿔 없애 버려서, 두 배열 모두 0.30ns 안팎이 나옵니다. 갈림길을 없애는 것도 분기 예측 실패를 피하는 방법입니다.
</Note>

## 정리

- CPU는 프로그램 카운터가 가리키는 명령을 가져오고, 해석하고, 실행하는 일을 되풀이하며, 반복과 조건은 프로그램 카운터를 바꾸는 점프 명령이다
- 파이프라인은 여러 명령의 단계를 겹쳐 박자마다 명령 하나 이상을 끝낸다
- 갈림길의 방향을 미리 짐작하는 분기 예측이 틀리면 미리 한 일을 버리므로, 규칙 없는 갈림길은 같은 계산을 열 배 느리게 만들 수 있다
