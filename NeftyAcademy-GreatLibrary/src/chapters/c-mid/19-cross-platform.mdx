## 다른 부분을 한 칸에 가두기

가장 중요한 원칙은 **운영체제마다 다른 코드를 한곳에 모으는 것**입니다. `#ifdef`가 프로그램 곳곳에 흩어지면 고치기 어려워집니다. 작은 플랫폼 층을 만들고, 나머지 코드는 그 층의 함수만 부르게 합니다.

```c flags=-D_POSIX_C_SOURCE=200809L
#include <stdint.h>
#include <stdio.h>
#include <string.h>

// ---- 운영체제마다 다른 부분은 이 칸 안에만 ----
#if defined(_WIN32)
  #define WIN32_LEAN_AND_MEAN
  #include <windows.h>
  #define PLAT_NAME "Windows"
  #define PATH_SEP '\\'
static uint64_t now_ns(void)
{
    LARGE_INTEGER f, c;
    QueryPerformanceFrequency(&f);
    QueryPerformanceCounter(&c);
    return (uint64_t)((double)c.QuadPart * 1e9 / (double)f.QuadPart);
}
static void sleep_ms(unsigned ms) { Sleep(ms); }
#else
  #include <time.h>
  #if defined(__APPLE__)
    #define PLAT_NAME "macOS"
  #elif defined(__linux__)
    #define PLAT_NAME "Linux"
  #else
    #define PLAT_NAME "다른 POSIX"
  #endif
  #define PATH_SEP '/'
static uint64_t now_ns(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);    // 시계를 돌려도 뒤로 안 감
    return (uint64_t)t.tv_sec * 1000000000u + (uint64_t)t.tv_nsec;
}
static void sleep_ms(unsigned ms)
{
    struct timespec t = {ms / 1000, (long)(ms % 1000) * 1000000L};
    nanosleep(&t, nullptr);
}
#endif
// ---- 여기부터는 모든 운영체제에서 같은 코드 ----

static void path_join(char *out, size_t n, const char *a, const char *b)
{
    snprintf(out, n, "%s%c%s", a, PATH_SEP, b);
}

int main(void)
{
    printf("운영체제 %s, 포인터 %zu바이트\n", PLAT_NAME, sizeof(void *));
    char p[128];
    path_join(p, sizeof p, "saves", "slot1.dat");
    printf("경로 %s\n", p);

    uint64_t t0 = now_ns();
    sleep_ms(50);
    double ms = (double)(now_ns() - t0) / 1e6;
    printf("50ms 잠들기: %s\n", ms >= 50.0 && ms < 200.0 ? "맞음" : "이상함");
    return 0;
}
```

```text
운영체제 Linux, 포인터 8바이트
경로 saves/slot1.dat
50ms 잠들기: 맞음
```

- 위 칸만 운영체제마다 다르고, `main`은 한 글자도 다르지 않습니다. 실제 프로젝트에서는 이 칸을 `plat_win.c`, `plat_posix.c`처럼 파일로 나누고 빌드 시스템이 하나를 고르게 합니다([「CMake와 Ninja」](#/read/c-mid/build-cmake)의 `if(WIN32)`)
- 시간 재기는 벽시계가 아니라 **단조 시계**(`CLOCK_MONOTONIC`, 윈도의 `QueryPerformanceCounter`)를 씁니다. 사용자가 시계를 바꾸거나 NTP가 맞춰도 뒤로 가지 않습니다
- 같은 파일을 MinGW-w64(`x86_64-w64-mingw32-gcc`)로 컴파일하니 경고 없이 윈도용 `.exe`가 나왔고, 가져오는 DLL은 `KERNEL32.dll`과 `msvcrt.dll`이었습니다. 이 검사용 컴퓨터에서는 Wine이 동작하지 않아 윈도에서 실행해 보지는 못했습니다

## 어느 운영체제인지 아는 법

컴파일러는 대상에 따라 매크로를 미리 정의해 둡니다. `gcc -dM -E - < /dev/null`로 전부 볼 수 있습니다.

| 매크로 | 뜻 |
| --- | --- |
| `_WIN32` | 윈도(32비트와 64비트 모두). 64비트면 `_WIN64`도 |
| `__APPLE__` | 애플 운영체제. macOS인지 iOS인지는 `TargetConditionals.h`로 |
| `__linux__` | 리눅스(안드로이드 포함, 안드로이드는 `__ANDROID__`도) |
| `__unix__` | 대부분의 유닉스류. macOS에는 정의되지 않는다 |

마지막 줄이 흔한 함정입니다. "유닉스면 POSIX"라는 생각으로 `__unix__`만 검사하면 macOS가 빠집니다. 위 예제처럼 윈도를 먼저 가르고 나머지를 POSIX로 보는 편이 안전합니다. 위 표의 리눅스와 MinGW 매크로는 이 컴퓨터의 gcc-14와 MinGW gcc에서 직접 확인했습니다.

## 크기의 함정: long

| 모델 | `long` | 포인터 | 쓰는 곳 |
| --- | --- | --- | --- |
| LP64 | 8 | 8 | 64비트 리눅스, macOS |
| LLP64 | 4 | 8 | 64비트 윈도 |

두 모델 모두 `int`는 4바이트입니다.

64비트 윈도의 `long`은 **4바이트**입니다. MinGW로 `static_assert(sizeof(long) == 4)`를, 리눅스 gcc로 `sizeof(long) == 8`을 컴파일해 둘 다 통과하는 것을 확인했습니다. 파일 크기나 포인터를 `long`에 담는 코드는 윈도에서 조용히 잘립니다. 크기가 중요하면 `int64_t`, `uint32_t`, `size_t`, `intptr_t`처럼 `stdint.h`의 이름을 씁니다. 파일이나 네트워크로 나가는 구조체는 [「TCP」](#/read/c-mid/net-tcp)에서처럼 엔디언과 크기를 정해 한 바이트씩 짜 넣습니다.

## 경로, 줄 끝, 글자

- **경로**: 윈도는 `\`와 드라이브 글자(`C:`), 나머지는 `/`. 윈도 API도 대부분 `/`를 받아 주지만, 사용자에게 보여 주는 경로는 그 운영체제의 모양으로 만듭니다
- **줄 끝**: 윈도의 글자 파일은 `\r\n`. `fopen`의 `"r"`/`"w"`(글자 모드)는 윈도에서 이것을 바꿔 주므로, 바이트가 그대로여야 하는 파일은 반드시 `"rb"`/`"wb"`로 엽니다
- **글자**: 리눅스·macOS의 API와 터미널은 UTF-8입니다. 윈도 API는 UTF-16(`wchar_t`, 이름 끝이 `W`인 함수)이 기본이고, 콘솔에 UTF-8 한글을 바로 찍으면 깨질 수 있습니다. 프로그램 안에서는 UTF-8로 통일하고, 윈도 API를 부를 때만 `MultiByteToWideChar`로 바꾸는 방식이 흔합니다. 콘솔 출력은 `SetConsoleOutputCP(CP_UTF8)`을 먼저 부릅니다

<Note>
모든 것을 손으로 감쌀 필요는 없습니다. 창·입력·소리는 SDL이나 GLFW, 네트워크와 비동기 입출력은 libuv, 그 밖의 기본 기능은 GLib처럼, 이미 여러 운영체제를 감싸 둔 라이브러리가 많습니다([「C 생태계의 네 층」](#/read/c-mid/c-ecosystem), [「자주 쓰이는 C 생태계 라이브러리」](#/read/c-mid/common-libraries)). 그리고 어디서 돈다고 말하려면 그 운영체제에서 실제로 빌드하고 시험해야 합니다. ## 정리

- 운영체제마다 다른 코드는 작은 플랫폼 층 한곳에 가두고, 나머지 코드는 그 층의 함수만 부르게 한다
- `_WIN32`, `__APPLE__`, `__linux__`로 대상을 가르되 `__unix__`에는 macOS가 없으며, 64비트 윈도의 `long`은 4바이트이므로 크기가 중요하면 `stdint.h`의 이름을 쓴다
- 경로 구분자, 글자·바이트 모드, UTF-8과 UTF-16의 차이를 챙기고, 지원한다고 말하는 모든 운영체제에서 CI로 빌드하고 시험한다
