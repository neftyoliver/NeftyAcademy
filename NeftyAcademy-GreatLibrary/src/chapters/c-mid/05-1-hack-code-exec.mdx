[「튜링 기계와 폰 노이만 구조」](#/read/basics/history-turing-von-neumann)에서 프로그램과 자료가 같은 메모리에 있다는 것이 컴퓨터의 힘이자 위험이라고 했습니다. 이 쪽은 그 위험이 실제로 어떻게 드러나는지를 봅니다. 목표는 공격법을 익히는 것이 아니라, **왜 C에서 길이 확인 하나가 그렇게 중요한지** 몸으로 아는 것입니다. 예제는 모두 작은 장난감이고, 검사 기계 안에서만 돌렸습니다.

## 옆 칸을 덮어쓰기

```c
#include <stdio.h>
#include <string.h>

struct login {
    char name[8];       // 이름 칸: 7글자 + 끝 표시
    int is_admin;       // 바로 뒤에 붙은 권한 칸
};

static void try_login(const char *input)
{
    struct login l = {.is_admin = 0};
    strcpy(l.name, input);              // 길이를 확인하지 않는다
    printf("%-12s → is_admin = %d %s\n", input, l.is_admin,
           l.is_admin ? "(관리자!)" : "");
}

int main(void)
{
    try_login("nefty");
    try_login("AAAAAAAAB");
    return 0;
}
```

`gcc-14 -O0 -fno-stack-protector -D_FORTIFY_SOURCE=0`으로, 곧 아래에서 볼 방어 장치를 모두 끄고 컴파일해 돌린 결과입니다.

```text nocheck
nefty        → is_admin = 0
AAAAAAAAB    → is_admin = 66 (관리자!)
```

`name`은 8바이트인데 `"AAAAAAAAB"`는 끝 표시까지 10바이트입니다. `strcpy`는 길이를 확인하지 않고 끝 표시(`\0`)가 나올 때까지 복사하므로, 넘친 `B`(0x42 = 66)와 `\0`이 바로 뒤의 `is_admin` 칸에 들어갔습니다. 사용자가 입력한 **글자 하나로 권한이 바뀌었습니다.** 메모리에서 [구조체](#/read/c-basic/struct)의 필드가 붙어 있고, [바이트에 타입이 없다](#/read/basics/math-integers)는 것이 그대로 드러난 결과입니다. C에서는 이것이 정의되지 않은 동작이라, 컴파일러와 옵션에 따라 결과가 다를 수 있습니다.

## 돌아갈 주소를 덮어쓰기

함수를 부르면 CPU는 **일을 마치고 돌아갈 주소**를 스택에 적어 두고, 함수의 지역 변수도 그 근처에 둡니다. 지역 배열이 넘치면 그 주소까지 덮어쓸 수 있습니다.

```c nocheck
static void copy_name(const char *input)
{
    char buf[8];
    strcpy(buf, input);                 // 8바이트 칸에 40바이트를 쓴다
    printf("%.8s\n", buf);
}
```

이 함수에 `A` 40개를 넘기고 스택 보호를 끈 채(`-fno-stack-protector`) 돌리면 프로그램이 죽습니다.

```text nocheck
Segmentation fault      ./smash0
```

함수가 끝나고 돌아가려는 순간, 적어 둔 주소가 `A`(0x41)로 덮여 `0x4141414141414141`이라는 엉뚱한 곳으로 뛰었기 때문입니다. 여기서 위험이 시작됩니다. `A` 대신 **공격자가 고른 주소**를 넣으면 프로그램은 죽지 않고 그 주소의 코드를 실행합니다. 입력으로 들어온 자료가 프로그램의 흐름을 빼앗는 것, 이것이 "의도하지 않은 코드 실행"의 뼈대입니다. 1988년의 모리스 웜부터 지금까지 수많은 공격이 이 원리를 썼습니다.

## 막는 장치들

지금의 컴파일러와 OS는 이런 일을 여러 겹으로 막습니다. 같은 예제가 기본 설정에서 어떻게 되는지 봅니다.

**스택 보호(canary).** 우분투의 GCC는 기본으로 `-fstack-protector-strong`을 켭니다. 함수에 들어갈 때 돌아갈 주소 앞에 무작위 값 하나를 놓아 두고, 나갈 때 그 값이 그대로인지 봅니다. 위의 `copy_name`을 스택 보호만 켠 채 돌리면 돌아가기 전에 멈춥니다.

```text nocheck
*** stack smashing detected ***: terminated
Aborted                 ./smash
```

**길이를 아는 복사(FORTIFY).** 우분투의 GCC는 최적화를 켜면(`-O2`) `_FORTIFY_SOURCE`도 켭니다. 컴파일러가 복사할 곳의 크기를 아는 경우 `strcpy`를 크기를 확인하는 판으로 바꿉니다. 첫 예제(`struct login`)를 그냥 `gcc-14 -O2`로 컴파일하면 넘치는 순간 멈춥니다.

```text nocheck
*** buffer overflow detected ***: terminated
```

**ASan.** 개발 중에 쓰는 [AddressSanitizer](#/read/c-mid/cc-llvm)는 배열 밖 쓰기 대부분을 잡지만, 첫 예제는 놓쳤습니다. `name`에서 넘친 바이트가 **같은 구조체 안의** `is_admin`으로 들어가서, ASan이 보기에는 정상적인 메모리였기 때문입니다. 도구마다 보는 곳이 다르니 한 가지에만 기대면 안 됩니다.

| 장치 | 막는 것 | 어디서 |
| --- | --- | --- |
| 스택 보호 | 돌아갈 주소 덮어쓰기를 함수가 끝날 때 알아챈다 | 컴파일러 |
| FORTIFY | 크기를 아는 버퍼에 넘치게 복사하기 | 컴파일러 + C 라이브러리 |
| 쓰기와 실행 나누기(NX) | 자료로 들어온 바이트를 기계어로 실행하기 | CPU + OS |
| 주소 흩어 놓기(ASLR) | 공격자가 뛸 곳의 주소를 미리 알기 | OS |

아래 두 줄은 [「메모리를 숨기고 보호하기」](#/read/c-mid/sec-memory)에서 자세히 봅니다.

<Note kind="warn">
방어 장치는 마지막 그물이지 해결책이 아닙니다. 스택 보호는 함수가 끝날 때야 알아채므로 그 전에 덮인 함수 포인터는 막지 못하고, FORTIFY는 크기를 모르는 포인터에는 소용이 없습니다. 진짜 해결은 **처음부터 넘치지 않게 쓰는 것**입니다. `strcpy` 대신 길이를 받는 함수를 쓰고(`snprintf(l.name, sizeof l.name, "%s", input)`), 입력의 길이를 먼저 확인합니다.
</Note>

## 정리

- 길이를 확인하지 않는 복사는 버퍼 뒤의 변수를 덮어써 권한 같은 값을 바꿀 수 있다
- 지역 배열이 넘쳐 돌아갈 주소가 덮이면, 공격자가 고른 주소로 프로그램의 흐름이 넘어간다
- 스택 보호, FORTIFY, NX, ASLR이 여러 겹으로 막지만 모두 그물일 뿐이고, 길이를 확인하는 코드가 진짜 방어다
