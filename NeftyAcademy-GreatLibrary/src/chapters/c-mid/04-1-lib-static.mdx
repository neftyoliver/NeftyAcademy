[「Makefile」](#/read/c-mid/build-make)에서 `util.c`를 `util.o`로 컴파일해 `main.o`와 함께 링크했습니다. `util.c` 같은 파일이 수십 개가 되고 여러 프로그램이 함께 쓴다면, 목적 파일을 하나하나 넘기는 대신 **한 파일로 묶어** 두는 것이 편합니다. 그 묶음이 정적 라이브러리입니다. 링크할 때 필요한 기계어를 실행 파일 안에 **복사해 넣는다**는 점에서, 실행할 때 빌려 오는 [「동적 라이브러리」](#/read/c-mid/lib-dynamic)와 다릅니다.

## 만들기

정적 라이브러리는 목적 파일 여러 개를 담은 상자입니다. 리눅스에서는 `ar`(archive)로 만들고, 이름은 `lib이름.a`로 짓는 관례가 있습니다.

```sh
gcc-14 -O2 -c util.c extra.c          # util.o, extra.o
ar rcs libutil.a util.o extra.o       # 둘을 묶는다
ar t libutil.a                        # 안에 든 것 보기
```

```text nocheck
util.o
extra.o
```

`rcs`는 넣고(`r`), 없으면 만들고(`c`), 심볼 색인을 붙이라(`s`)는 뜻입니다. 색인은 링커가 "`clamp`는 어느 조각에 있나"를 빨리 찾게 해 줍니다. `nm libutil.a`로 보면 조각마다 무엇이 정의돼 있는지 나옵니다.

```text nocheck
util.o:
0000000000000000 T clamp

extra.o:
0000000000000000 T triple
```

`extra.c`에는 `triple`이라는 함수 하나를 넣어 두었습니다. `main.c`는 이것을 쓰지 않습니다.

## 쓰기

```sh
gcc-14 -O2 main.c -L. -lutil -o app
./app
```

```text nocheck
0 42 100
```

| 옵션 | 뜻 |
| --- | --- |
| `-L.` | 라이브러리를 이 폴더(`.`)에서도 찾아라 |
| `-lutil` | `libutil`을 붙여라. 앞의 `lib`과 뒤의 `.a`(또는 `.so`)는 링커가 붙인다 |

수학 함수를 쓸 때 붙이는 `-lm`도 같은 규칙으로 `libm`을 뜻합니다. 같은 이름의 `.so`(동적)와 `.a`(정적)가 함께 있으면 링커는 동적 쪽을 먼저 고릅니다. 정적으로 붙이려면 `-static`을 주거나 `libutil.a` 파일 이름을 직접 넘깁니다.

## 필요한 조각만 가져온다

만든 실행 파일에 무엇이 들어갔는지 봅니다.

```text nocheck
$ nm app | grep -E "clamp|triple"
00000000000011c0 T clamp
```

`clamp`는 있고 `triple`은 없습니다. 링커는 라이브러리를 통째로 넣지 않고, **아직 정의를 못 찾은 심볼이 들어 있는 조각(목적 파일)만** 꺼내 넣습니다. `main.o`가 `clamp`를 찾고 있으니 `util.o`를 꺼냈고, 아무도 `triple`을 찾지 않으니 `extra.o`는 두고 왔습니다.

이 단위는 함수가 아니라 **목적 파일**입니다. `clamp`와 `triple`이 같은 `.c` 파일에 있었다면 `triple`도 함께 딸려 왔을 것입니다. 그래서 C 라이브러리들은 함수 하나에 파일 하나씩 두기도 합니다. 컴파일할 때 `-ffunction-sections`, 링크할 때 `-Wl,--gc-sections`를 주면 함수 단위로 버릴 수도 있습니다.

## 링크 순서의 함정

라이브러리를 소스보다 앞에 적으면 이렇게 됩니다.

```text nocheck
$ gcc-14 -O2 -L. -lutil main.c -o app2
main.c:(.text.startup+0x17): undefined reference to `clamp'
```

`libutil.a`에 `clamp`가 분명히 있는데도 못 찾았습니다. GNU 링커는 명령 줄을 **왼쪽부터 한 번만** 훑습니다. `-lutil`을 만났을 때는 아직 `main.o`를 읽기 전이라 찾는 심볼이 하나도 없었고, 그래서 아무 조각도 꺼내지 않고 지나갔습니다. 그 뒤에 `main.o`가 `clamp`를 찾지만 라이브러리는 이미 지나간 뒤입니다.

규칙은 하나입니다. **쓰는 쪽을 먼저, 쓰이는 쪽을 나중에.** 라이브러리끼리 서로 기댈 때도 같아서, `liba`가 `libb`를 쓰면 `-la -lb` 순서로 적습니다. 서로가 서로를 쓰는 경우에는 `-Wl,--start-group … -Wl,--end-group`으로 묶어 여러 번 훑게 할 수 있습니다. [「CMake와 Ninja」](#/read/c-mid/build-cmake)의 `target_link_libraries`를 쓰면 CMake가 순서를 맞춰 줍니다. 참고로 LLVM의 링커 lld와 맥의 링커는 순서와 관계없이 찾아 줍니다.

<Note kind="tip">
윈도우에서는 정적 라이브러리가 `util.lib`이고, MSVC의 `lib.exe`로 만듭니다(`lib /OUT:util.lib util.obj extra.obj`). 그런데 DLL을 쓸 때 링크하는 "가져오기 라이브러리"도 같은 `.lib` 확장자라서 헷갈리기 쉽습니다. 파일 크기가 작고 안에 기계어가 없다면 가져오기 라이브러리입니다.
</Note>

## 정적 링크의 장단점

| | 정적 라이브러리 |
| --- | --- |
| 좋은 점 | 실행 파일 하나만 옮기면 돈다. 실행할 때 찾는 시간이 없다 |
| 나쁜 점 | 실행 파일이 커진다. 라이브러리의 버그를 고치려면 쓰는 프로그램을 모두 다시 빌드해야 한다 |
| 함께 생각할 것 | 라이선스. LGPL 라이브러리를 정적으로 넣으면 받는 사람이 다시 링크할 수 있게 해 줘야 한다 |

[「교차 컴파일: PC에서 라즈베리파이용으로」](#/read/c-mid/build-cross)에서 glibc까지 정적으로 넣었더니 70KB가 700KB가 된 것이 앞의 두 줄을 보여 줍니다. 라이선스는 [「소프트웨어의 갈래」](#/read/basics/software-kinds)에서 봤습니다.

## 정리

- 정적 라이브러리(`lib이름.a`)는 `ar rcs`로 목적 파일을 묶은 것이고, `-L폴더 -l이름`으로 링크한다
- 링커는 아직 정의를 못 찾은 심볼이 든 목적 파일만 꺼내 실행 파일에 복사해 넣으므로, 쓰지 않는 파일은 들어가지 않는다
- GNU 링커는 왼쪽부터 한 번만 훑으므로 라이브러리는 그것을 쓰는 소스와 목적 파일보다 뒤에 적어야 한다
