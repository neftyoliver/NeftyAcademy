[「정적 라이브러리」](#/read/c-mid/lib-static)는 링크할 때 기계어를 실행 파일에 복사해 넣었습니다. 동적 라이브러리는 실행 파일에 "이 라이브러리의 이 함수가 필요하다"는 **쪽지만** 남기고, 프로그램을 실행할 때 OS의 로더가 라이브러리를 찾아 메모리에 올려 이어 줍니다. 리눅스에서는 `.so`(shared object), 윈도우에서는 `.dll`, 맥에서는 `.dylib`입니다. [「ELF」](#/read/c-mid/exe-elf)에서 본 `NEEDED: libc.so.6`이 바로 그 쪽지였습니다.

## 만들기

같은 `util.c`, `extra.c`를 동적 라이브러리로 만듭니다. 이름은 `libclamp`로 했습니다(까닭은 아래 Note에 있습니다).

```sh
gcc-14 -O2 -fPIC -shared -Wl,-soname,libclamp.so.1 \
       util.c extra.c -o libclamp.so.1.0.0
ln -s libclamp.so.1.0.0 libclamp.so.1
ln -s libclamp.so.1 libclamp.so
```

| 옵션 | 뜻 |
| --- | --- |
| `-fPIC` | 어느 주소에 올려도 돌아가는 코드로 컴파일한다. 여러 프로그램이 같은 라이브러리를 각자 다른 주소에 올리기 때문이다 |
| `-shared` | 실행 파일이 아니라 공유 라이브러리를 만든다 |
| `-Wl,-soname,libclamp.so.1` | 링커(`-Wl,`)에게 이 라이브러리의 공식 이름(soname)을 알린다 |

이름이 셋인 까닭은 아래 "soname과 버전"에서 봅니다. 링크하는 방법은 정적 라이브러리와 같습니다.

```sh
gcc-14 -O2 main.c -L. -lclamp -o app-dyn
./app-dyn
```

```text nocheck
./app-dyn: error while loading shared libraries: libclamp.so.1:
cannot open shared object file: No such file or directory
```

컴파일과 링크는 됐는데 실행이 안 됩니다. `-L.`은 **링크할 때** 링커에게만 알려 준 것이고, **실행할 때** 라이브러리를 찾는 로더는 그것을 모르기 때문입니다.

<Note kind="warn">
처음에는 이 라이브러리를 `libutil`이라고 지었다가 이상한 오류를 만났습니다. `cannot open shared object` 대신 `symbol lookup error: undefined symbol: clamp`가 났습니다. glibc가 예전부터 같은 이름의 `/lib/x86_64-linux-gnu/libutil.so.1`을 갖고 있어서, 로더가 그쪽을 찾아 불러온 것입니다. 라이브러리 이름은 시스템 것과 겹치지 않게 지어야 합니다.
</Note>

## 로더가 찾는 길

리눅스의 로더(`ld-linux-x86-64.so.2`)는 대략 이 순서로 찾습니다.

| 차례 | 찾는 곳 |
| --- | --- |
| 1 | 실행 파일에 적힌 RUNPATH(링크할 때 `-Wl,-rpath,…`로 적는다) |
| 2 | 환경 변수 `LD_LIBRARY_PATH`의 폴더들 |
| 3 | `/etc/ld.so.cache`(`ldconfig`가 만든 목록. `/usr/lib` 같은 시스템 폴더) |

시험 삼아 돌릴 때는 `LD_LIBRARY_PATH=. ./app-dyn`처럼 환경 변수를 주면 됩니다. 프로그램과 라이브러리를 한 폴더에 담아 나눠 줄 때는 `$ORIGIN`(실행 파일이 있는 폴더)을 RUNPATH에 적어 두는 방법을 많이 씁니다.

```sh
gcc-14 -O2 main.c -L. -lclamp -Wl,-rpath,'$ORIGIN' -o app-rp
ldd app-rp
```

```text nocheck
    linux-vdso.so.1
    libclamp.so.1 => /tmp/lib/./libclamp.so.1
    libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
    /lib64/ld-linux-x86-64.so.2
```

`ldd`는 이 프로그램을 실행하면 어떤 라이브러리가 어디서 불려 올지 보여 줍니다. 라이브러리를 시스템에 설치할 때는 `/usr/local/lib` 같은 곳에 넣고 `sudo ldconfig`로 목록을 새로 만듭니다. [「apt와 저장소」](#/read/basics/apt)로 까는 라이브러리 패키지가 이 일을 대신 해 줍니다.

## soname과 버전

세 이름은 각자 쓰임이 있습니다.

| 이름 | 누가 쓰나 |
| --- | --- |
| `libclamp.so.1.0.0` | 실제 파일. 고칠 때마다 끝의 숫자가 바뀐다 |
| `libclamp.so.1` | soname. 실행 파일의 `NEEDED`에 적히고, 로더가 찾는 이름 |
| `libclamp.so` | 링크할 때 `-lclamp`가 찾는 이름. 개발용 패키지(`-dev`)에만 있다 |

soname의 숫자 `1`은 "이 번호가 같으면 서로 바꿔 끼워도 된다"는 약속입니다. 함수를 지우거나 인자를 바꿔 옛 프로그램과 맞지 않게 되면 `libclamp.so.2`로 올립니다. 그러면 `.so.1`을 쓰는 옛 프로그램과 `.so.2`를 쓰는 새 프로그램이 한 기계에서 함께 돕니다.

## 다시 빌드하지 않고 고치기

동적 라이브러리의 가장 큰 장점은 라이브러리만 바꿔 **쓰는 프로그램을 모두 고칠 수 있다**는 것입니다. 범위를 거꾸로 준 경우를 다루지 못하던 `clamp`를 고쳐 `libclamp.so.1.0.1`을 만들고, `libclamp.so.1` 링크만 새 파일로 돌렸습니다. 프로그램(`clamp(50, 100, 0)`을 찍는 `rev`)은 다시 링크하지 않았습니다.

```text nocheck
$ ./rev          # libclamp.so.1 → 1.0.0
100
$ ln -sf libclamp.so.1.0.1 libclamp.so.1
$ ./rev          # libclamp.so.1 → 1.0.1
50
```

보안 업데이트가 이렇게 동작합니다. OpenSSL에 구멍이 나면 OpenSSL 라이브러리만 새로 깔면 그것을 쓰는 수백 개의 프로그램이 한꺼번에 고쳐집니다. [「업데이트를 통한 보안」](#/read/c-mid/sec-updates)에서 이어집니다.

## 실행 중에 열기: dlopen

라이브러리를 프로그램이 원할 때 직접 열 수도 있습니다. 플러그인을 불러오는 프로그램이 이렇게 합니다. `dlopen`은 POSIX 함수입니다.

```c nocheck
#include <dlfcn.h>
#include <stdio.h>

typedef int (*triple_fn)(int);

int main(void)
{
    void *lib = dlopen("./libclamp.so.1", RTLD_NOW);   // 실행 중에 연다
    if (lib == NULL) {
        printf("열기 실패: %s\n", dlerror());
        return 1;
    }
    triple_fn triple;
    *(void **)&triple = dlsym(lib, "triple");          // POSIX가 권하는 꼴
    if (triple == NULL) {
        printf("찾기 실패: %s\n", dlerror());
        return 1;
    }
    printf("triple(14) = %d\n", triple(14));
    dlclose(lib);
    return 0;
}
```

```text nocheck
triple(14) = 42
```

`-D_POSIX_C_SOURCE=200809L`로 컴파일해 라이브러리가 있는 폴더에서 돌린 결과입니다(이 프로그램은 링크할 때 `-lclamp`가 필요 없습니다). 라이브러리를 치우고 돌리면 `열기 실패: ./libclamp.so.1: cannot open shared object file`이 나옵니다. `dlsym`이 돌려주는 `void *`를 함수 포인터로 바로 바꾸면 ISO C에서는 경고가 나서([함수 포인터](#/read/c-basic/ptr-function)와 자료 포인터는 다른 것으로 보기 때문), POSIX 문서가 권하는 `*(void **)&` 꼴을 썼습니다.

## 정리

- 동적 라이브러리는 `-fPIC -shared`로 만들고, 실행 파일에는 필요하다는 쪽지(`NEEDED`)만 남아 실행할 때 로더가 찾아 이어 준다
- 로더는 RUNPATH, `LD_LIBRARY_PATH`, `ldconfig`의 목록 순으로 찾으며, 링크할 때의 `-L`은 실행할 때 쓰이지 않는다
- soname이 같은 동안은 라이브러리만 바꿔 끼워 쓰는 프로그램을 모두 고칠 수 있고, `dlopen`으로 실행 중에 라이브러리를 열 수도 있다
