[「안전과 인증」](#/read/cpp-industrial/land-safety)에서 안전 관련 소프트웨어는 코드와 함께 요구 사항, 설계, 시험 기록이 산출물이 된다고 했습니다. 평가하는 사람이 보는 것은 무엇을 만들어야 했고, 어떻게 만들었고, 정말 그렇게 되었는지의 기록과, 그 기록들이 빈틈없이 이어져 있다는 증거입니다. 이 쪽에서는 작은 인터록 하나로 그 기록을 따라가 봅니다.

## V 모델

IEC 61508-3은 소프트웨어 개발을 V 모양으로 그립니다. 왼쪽으로 내려가며 요구를 잘게 나누어 설계하고, 맨 아래에서 코드를 쓴 뒤, 오른쪽으로 올라가며 같은 높이의 문서를 기준으로 시험합니다.

| 왼쪽: 만드는 단계 | 오른쪽: 짝이 되는 시험 |
| --- | --- |
| 소프트웨어 안전 요구 사항 명세 | 확인 시험 |
| 아키텍처 | 통합 시험 |
| 모듈 설계 | 모듈 시험 |
| 코딩 | 코드 검토, 정적 분석 |

오른쪽의 활동은 두 가지입니다. **검증**(verification)은 각 단계의 결과가 그 단계에 주어진 요구를 만족하는지(제대로 만들었나), **확인**(validation)은 완성된 소프트웨어가 안전 요구 사항 명세를 만족하는지(맞는 것을 만들었나) 봅니다. 명세가 틀리면 검증을 다 통과해도 위험하므로, 명세는 위험성 평가에서 이어져 나오고 그 자체도 검토를 받습니다. 목표와 요구를 모두 만족하면 다른 수명 주기를 써도 됩니다.

## 추적성

문서들을 잇는 실이 **추적성**입니다. 요구마다 `REQ-S1` 같은 번호를 붙이고, 설계, 코드, 시험이 자기가 다루는 요구 번호를 적습니다. 앞으로(요구 → 시험) 보면 시험이 없는 요구가, 뒤로(코드·시험 → 요구) 보면 아무도 시키지 않은 코드나 빠진 요구의 흔적이 드러납니다.

아래는 기계 문 인터록의 요구 세 개와 구현입니다. 문이 열린 채로 정비하려면 정비 키를 돌리고 인에이블 스위치(가운데까지 눌러 쥐는 동안만 움직임을 허락하는 손잡이 스위치)를 잡아야 합니다. 프로그램은 시험 묶음마다 추적, 결정 커버리지, MC/DC를 보고하고, 인에이블 검사를 빠뜨린 틀린 판이 걸리는지도 봅니다. 실제 기계에서는 인증된 안전 장치가 맡는 기능이지만, 검증 기록을 만드는 방식은 같습니다.

```cpp
#include <array>
#include <cstdio>
#include <cstring>
#include <string>
#include <vector>

struct Req { const char* id; const char* text; };
const std::vector<Req> reqs = {
    {"REQ-S1", "비상 정지가 눌리면 움직이지 않는다"},
    {"REQ-S2", "문이 닫히고 비상 정지가 정상이면 움직인다"},
    {"REQ-S3", "문이 열리면 정비 키와 인에이블이 모두 있어야 움직인다"},
};

// 구현한 요구: REQ-S1, REQ-S2, REQ-S3
// e 비상 정지 정상, g 문 닫힘, k 정비 키, h 인에이블 스위치
bool may_move(bool e, bool g, bool k, bool h) {
    return e && (g || (k && h));
}
bool forgot_enable(bool e, bool g, bool k, bool) {   // 일부러 틀린 판
    return e && (g || k);
}

using In = std::array<bool, 4>;
struct Test { const char* id; const char* req; In in; bool expect; };
using Fn = bool (*)(bool, bool, bool, bool);
bool run(Fn f, const In& x) { return f(x[0], x[1], x[2], x[3]); }

std::vector<Test> suiteA = {
    {"T1", "REQ-S1", {0, 1, 0, 1}, false},
    {"T2", "REQ-S2", {1, 1, 0, 1}, true},
    {"T3", "REQ-S3", {1, 0, 0, 1}, false},
};

void report(const char* name, const std::vector<Test>& s) {
    std::printf("== 묶음 %s: 시험 %zu개\n추적", name, s.size());
    for (const Req& r : reqs) {                       // 요구 → 시험
        std::string ids;
        for (const Test& t : s)
            if (std::strcmp(t.req, r.id) == 0) ids += std::string(" ") + t.id;
        std::printf("  %s:%s", r.id, ids.empty() ? " 시험 없음!" : ids.c_str());
    }
    for (const Test& t : s) {                         // 시험 → 요구
        bool known = false;
        for (const Req& r : reqs) known |= std::strcmp(t.req, r.id) == 0;
        if (!known) std::printf("  %s: 요구 없음!", t.id);
    }
    std::vector<bool> out;
    int pass = 0, yes = 0;
    for (const Test& t : s) {
        out.push_back(run(may_move, t.in));
        pass += out.back() == t.expect;
        yes += out.back();
    }
    std::printf("\n결과  %d/%zu 통과, 결정은 참 %d번 거짓 %zu번\nMC/DC",
                pass, s.size(), yes, s.size() - yes);
    std::string shown, missed;
    for (int c = 0; c < 4; ++c) {     // c만 다르고 결과가 다른 시험 짝이 있나
        bool found = false;
        for (size_t a = 0; a < s.size(); ++a)
            for (size_t b = 0; b < s.size(); ++b) {
                int diff = 0;
                for (int i = 0; i < 4; ++i) diff += s[a].in[i] != s[b].in[i];
                found |= diff == 1 && s[a].in[c] != s[b].in[c] && out[a] != out[b];
            }
        (found ? shown : missed) += std::string(" ") + "egkh"[c];
    }
    std::printf(" 보임:%s", shown.c_str());
    if (!missed.empty()) std::printf("  못 보임:%s", missed.c_str());
    const char* caught = nullptr;
    for (const Test& t : s)
        if (!caught && run(forgot_enable, t.in) != t.expect) caught = t.id;
    if (caught) std::printf("\n틀린 판: %s에서 실패 -> 잡음\n", caught);
    else std::printf("\n틀린 판: 모두 통과 -> 놓침\n");
}

int main(int argc, char** argv) {
    std::string only = argc > 1 ? argv[1] : "";
    std::vector<Test> suiteB = suiteA;
    suiteB.push_back({"T4", "REQ-S3", {1, 0, 1, 1}, true});
    suiteB.push_back({"T5", "REQ-S3", {1, 0, 1, 0}, false});
    if (only != "B") report("A", suiteA);
    if (only != "A") report("B", suiteB);
}
```

```text
== 묶음 A: 시험 3개
추적  REQ-S1: T1  REQ-S2: T2  REQ-S3: T3
결과  3/3 통과, 결정은 참 1번 거짓 2번
MC/DC 보임: e g  못 보임: k h
틀린 판: 모두 통과 -> 놓침
== 묶음 B: 시험 5개
추적  REQ-S1: T1  REQ-S2: T2  REQ-S3: T3 T4 T5
결과  5/5 통과, 결정은 참 2번 거짓 3번
MC/DC 보임: e g k h
틀린 판: T5에서 실패 -> 잡음
```

- **A의 겉모습**: 요구마다 시험이 있고 모두 통과했으며, `return`의 식은 참과 거짓이 다 나왔으므로 문장·결정 커버리지도 100%입니다
- **MC/DC가 본 빈틈**: 그런데 k나 h 하나만 바꿨더니 결과가 바뀐 시험 짝이 없습니다. 정비 키와 인에이블이 결과를 가르는지 보인 적이 없으니, 인에이블을 빠뜨린 코드도 A를 다 통과합니다
- **B**: 키와 인에이블을 함께 잡은 T4, 키만 돌린 T5를 더하자 네 조건이 다 보였고 틀린 판은 T5에서 걸렸습니다

## MC/DC

**MC/DC**(modified condition/decision coverage)는 결정의 모든 결과가 나오고, 결정 안의 조건 하나하나가 다른 조건을 그대로 둔 채 혼자서 결과를 바꿀 수 있음을 시험으로 보이라는 기준입니다. 조건이 N개면 시험이 적어도 N+1개 필요하고 이 식은 딱 5개로 되므로, 조합 16개를 다 시험하지 않고도 위의 실수를 잡습니다. IEC 61508-3은 100% 분기 커버리지를 SIL 3과 4에서, MC/DC를 SIL 4에서 강력 권장합니다. ISO 26262-6은 ASIL D에서 MC/DC를 강력 권장하고, 항공의 DO-178C는 가장 높은 레벨 A에서 요구합니다.

GCC 14부터는 `-fcondition-coverage`로 빌드하면 MC/DC를 재고 `gcov --conditions`로 보여 줍니다. 위 프로그램은 인자로 `A`나 `B`를 주면 그 묶음만 돌립니다.

```text nocheck
$ g++-14 -std=c++20 --coverage -fcondition-coverage interlock.cpp -o interlock
$ ./interlock A > /dev/null && gcov-14 --conditions interlock.cpp > /dev/null
$ grep -A3 '   17:' interlock.cpp.gcov
       3*:   17:    return e && (g || (k && h));
condition outcomes covered 5/8
condition  2 not covered (true)
condition  3 not covered (true false)

$ rm interlock.gcda && ./interlock B > /dev/null
$ gcov-14 --conditions interlock.cpp > /dev/null
$ grep -A1 '   17:' interlock.cpp.gcov
        5:   17:    return e && (g || (k && h));
condition outcomes covered 8/8
```

gcov는 조건에 0부터 번호를 붙이고(0=e, 1=g, 2=k, 3=h) 참과 거짓을 따로 셉니다. A에서 k는 거짓으로 결과를 가른 것(T3)만 보였고, h는 k가 늘 거짓이라 단락 평가로 평가조차 되지 않았습니다. GCC가 재는 것은 마스킹 MC/DC라는 변형인데, B는 이것도 다 채웁니다.

커버리지는 목표가 아니라 요구에서 뽑은 시험의 빈틈을 재는 자입니다. 빈틈이 보이면 시험을 끼워 넣기 전에 빠진 요구인지, 빠진 시험인지, 필요 없는 코드인지 따지고, 끝내 닿지 않는 방어 코드 같은 곳은 이유를 적어 둡니다.

## 안전 케이스

이렇게 쌓인 기록을 하나의 주장으로 묶은 것이 **안전 케이스**(safety case)입니다. "이 용도에 충분히 안전하다"는 주장을 작은 주장으로 나누고 각각에 증거를 답니다. 이 구조를 그리는 표기로 GSN(Goal Structuring Notation)이 널리 쓰이는데, 글로만 옮기면 이런 모양입니다.

```text nocheck
G1  인터록 소프트웨어 v2.4.1은 SIL 2 안전 기능에 쓰기에 충분히 안전하다
    맥락: 위험성 평가 HA-03, 안전 요구 사항 명세 SRS-07 3판
    전략: 위험 → 요구 → 시험의 사슬과 개발 방법을 차례로 보인다
  G2  안전 요구가 위험을 모두 다룬다 (증거: 위험-요구 추적표, 명세 검토)
  G3  요구마다 시험으로 검증되었다 (증거: 추적 행렬, 시험 보고서)
  G4  시험이 정한 구조 커버리지를 채웠다 (증거: 커버리지 보고서)
  G5  코딩 지침을 지켰다 (증거: 정적 분석 보고서, 승인된 일탈 기록)
  G6  쓴 도구를 믿을 근거가 있다 (증거: 도구 분류와 검증 기록)
```

[「IEC 61508」](#/read/cpp-industrial/safe-iec61508)의 SIL과 도구 등급, [「MISRA C++」](#/read/cpp-industrial/safe-misra)의 일탈 기록, [「정적 분석」](#/read/cpp-industrial/safe-analysis)의 보고서가 증거 칸을 채웁니다. 모든 증거는 같은 판을 가리켜야 합니다. v2.4.0의 시험 보고서는 v2.4.1의 증거가 아니므로 문서마다 판과 커밋을 적고, 코드를 바꾸면 영향 분석으로 닿는 요구와 시험을 찾아 다시 검증합니다([「업데이트」](#/read/cpp-industrial/depl-update)). 이것을 따지는 기능 안전 평가는 SIL이 높을수록 더 독립된 사람, 부서, 조직이 맡습니다.

<Note>
커버리지 측정 도구는 잘못돼도 결함을 놓칠 뿐 실행 코드를 바꾸지 않으므로 T2, 실행 코드를 만드는 컴파일러는 T3이며, T3 도구에는 명세대로 동작한다는 증거(오래 써 온 실적이나 도구 검증)가 있어야 합니다. 또 커버리지는 계측한 빌드에서 재므로, 같은 시험이 출하할 빌드에서도 통과하는지 따로 확인합니다.
</Note>

## 정리

- 만드는 단계마다 짝이 되는 시험을 두고, 요구 번호로 요구, 설계, 코드, 시험을 앞뒤로 이어 빠진 시험과 시키지 않은 코드를 찾는다
- 문장과 결정 커버리지가 100%여도 조건마다 결과를 가르는지는 모를 수 있고, MC/DC는 그것을 적은 시험으로 보이며 GCC 14의 `-fcondition-coverage`로 잴 수 있다
- 안전 케이스는 "충분히 안전하다"는 주장을 목표, 전략, 증거로 나누어 보이며, 모든 증거는 출하하는 같은 판을 가리켜야 한다
