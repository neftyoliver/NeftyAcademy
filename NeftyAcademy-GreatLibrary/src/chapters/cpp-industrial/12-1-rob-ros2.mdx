**ROS 2**(Robot Operating System 2)는 이름과 달리 운영 체제가 아니라, 로봇 소프트웨어를 여러 프로그램(노드)으로 나누어 서로 이어 주는 미들웨어와 도구, 라이브러리의 묶음입니다. 연구실에서 시작했지만 지금은 이동 로봇과 로봇 팔의 연구와 제품에 널리 쓰이고, 성능이 필요한 노드는 C++ API인 rclcpp로 씁니다. 배포판은 해마다 5월에 나오고 짝수 해의 판이 5년 지원판(LTS)입니다. 2026년 5월에 나온 Lyrical Luth는 2031년 5월까지, Jazzy Jalisco는 2029년 5월까지, Humble Hawksbill은 2027년 5월까지 지원됩니다.

## 노드와 통신

- **토픽**: 발행자와 구독자가 이름 붙은 통로로 메시지를 흘려보냅니다. 센서 값, 로봇 상태처럼 계속 흐르는 데이터에 씁니다
- **서비스**: 요청을 보내고 응답을 받습니다. 짧게 끝나는 질문이나 설정에 씁니다
- **액션**: 목표를 보내면 중간 경과를 받다가 결과를 받고, 도중에 취소할 수도 있습니다. 팔을 어떤 자세로 옮기는 일처럼 오래 걸리는 일에 씁니다
- **파라미터**: 노드마다 이름 붙은 설정값을 두고 밖에서 읽고 바꿉니다

밑에서는 산업용 발행·구독 표준인 DDS가 노드를 찾아 잇고 메시지를 나르며, 기본 구현은 Fast DDS입니다. 같은 망에서 같은 도메인 번호(`ROS_DOMAIN_ID`)를 쓰는 노드는 따로 설정하지 않아도 서로를 찾습니다. rclcpp로 쓴 노드는 이렇습니다. 이 책의 검사 환경에는 ROS 2가 없어 이 코드는 문서와 대조만 했습니다.

```cpp nocheck
// rclcpp 노드: 온도는 센서 QoS로, 상태는 늦게 온 구독자도 받게, 명령은 기본 QoS로
#include <chrono>
#include <memory>
#include <rclcpp/rclcpp.hpp>
#include <std_msgs/msg/float64.hpp>
#include <std_msgs/msg/string.hpp>

using namespace std::chrono_literals;
using std_msgs::msg::Float64;
using std_msgs::msg::String;

class Cell : public rclcpp::Node {
public:
    Cell() : Node("cell") {
        temp_ = create_publisher<Float64>("temperature", rclcpp::SensorDataQoS());
        auto latched = rclcpp::QoS(1).transient_local();
        state_ = create_publisher<String>("state", latched);
        cmd_ = create_subscription<String>("command", 10, [this](const String& m) {
            RCLCPP_INFO(get_logger(), "명령: %s", m.data.c_str());
        });
        timer_ = create_wall_timer(100ms, [this] {
            Float64 t;
            t.data = 42.0;                       // 실제로는 센서에서 읽는다
            temp_->publish(t);
        });
        String s;
        s.data = "ready";
        state_->publish(s);
    }

private:
    rclcpp::Publisher<Float64>::SharedPtr temp_;
    rclcpp::Publisher<String>::SharedPtr state_;
    rclcpp::Subscription<String>::SharedPtr cmd_;
    rclcpp::TimerBase::SharedPtr timer_;
};

int main(int argc, char** argv) {
    rclcpp::init(argc, argv);
    rclcpp::spin(std::make_shared<Cell>());
    rclcpp::shutdown();
}
```

`rclcpp::spin`이 타이머와 구독의 콜백을 차례로 부릅니다. 돌고 있는 노드는 `ros2 topic list`로 토픽을 보고, `ros2 topic info -v /temperature`로 끝마다의 QoS를 확인합니다.

## QoS

토픽마다 메시지를 어떻게 나를지 **QoS** 정책으로 정합니다. 신뢰성(잃은 것을 다시 보내는 reliable, 보내고 잊는 best effort), 지속성(늦게 온 구독자에게 남겨 둔 메시지를 주는 transient local, 주지 않는 volatile), 기록 깊이, 마감 같은 것들입니다. 기본값은 reliable, volatile, 깊이 10이고, 센서용 `SensorDataQoS`는 best effort에 깊이 5입니다. 발행자와 구독자는 구독자가 요청한 것을 발행자가 제공할 때만 연결됩니다. 아래는 이 규칙과 동작을 흉내 낸 것입니다. 출력의 신뢰와 최선은 reliable과 best effort, 지속과 휘발은 transient local과 volatile입니다.

```cpp
#include <algorithm>
#include <cstdio>
#include <string>
#include <vector>

enum class Rel { BestEffort, Reliable };
enum class Dur { Volatile, TransientLocal };
struct QoS { Rel rel; Dur dur; int depth; int deadline_ms = 0; };  // 0: 마감 없음

const char* text(Rel r) { return r == Rel::Reliable ? "신뢰" : "최선"; }
const char* text(Dur d) { return d == Dur::TransientLocal ? "지속" : "휘발"; }

// 구독자가 요청한 것을 발행자가 제공해야 연결된다 (요청과 제공)
std::string mismatch(const QoS& pub, const QoS& sub) {
    if (sub.rel == Rel::Reliable && pub.rel == Rel::BestEffort) return "신뢰성";
    if (sub.dur == Dur::TransientLocal && pub.dur == Dur::Volatile) return "지속성";
    if (sub.deadline_ms && (!pub.deadline_ms || pub.deadline_ms > sub.deadline_ms))
        return "마감";
    return "";
}

struct Sub { std::string name; QoS qos; bool late = false; };  // late: 나중에 옴

void topic(const std::string& name, const QoS& pub, int count, bool lossy,
           const std::vector<Sub>& subs) {
    std::printf("%s  발행: %s, %s, 깊이 %d, 메시지 %d개%s\n", name.c_str(),
                text(pub.rel), text(pub.dur), pub.depth, count,
                lossy ? ", 와이파이" : "");
    for (const Sub& s : subs) {
        std::printf("  %s: ", s.name.c_str());
        std::string bad = mismatch(pub, s.qos);
        if (!bad.empty()) {
            std::printf("연결 안 됨 (맞지 않는 정책: %s)\n", bad.c_str());
            continue;
        }
        int got = 0, lost = 0, resent = 0;
        if (s.late) {
            // 둘 다 지속을 약속했으면 발행자가 남겨 둔 깊이만큼 받는다
            if (pub.dur == Dur::TransientLocal && s.qos.dur == Dur::TransientLocal)
                got = std::min(count, pub.depth);
        } else {
            bool reliable = pub.rel == Rel::Reliable && s.qos.rel == Rel::Reliable;
            for (int i = 1; i <= count; ++i) {
                bool dropped = lossy && i % 4 == 0;     // 네 번에 한 번 잃는 망
                if (!dropped) ++got;
                else if (reliable) { ++resent; ++got; } // 다시 보내 받는다
                else ++lost;
            }
        }
        std::printf("%d/%d 받음", got, count);
        if (lost) std::printf(", 잃음 %d", lost);
        if (resent) std::printf(", 다시 보냄 %d", resent);
        std::printf("\n");
    }
}

int main() {
    QoS sensor{Rel::BestEffort, Dur::Volatile, 5};       // SensorDataQoS와 비슷
    QoS normal{Rel::Reliable, Dur::Volatile, 10};        // 기본값
    QoS latched{Rel::Reliable, Dur::TransientLocal, 1};  // 늦게 와도 마지막 것
    QoS strict = normal;
    strict.deadline_ms = 100;                            // 100ms마다 오라고 요청

    topic("/camera", sensor, 20, true, {{"viewer", sensor}, {"logger", normal}});
    topic("/odom", normal, 20, true, {{"planner", normal}, {"plotter", sensor}});
    topic("/robot_description", latched, 1, false,
          {{"rviz", latched, true}, {"monitor", normal, true}});
    topic("/cmd_vel", normal, 10, false, {{"base", normal}, {"safety", strict}});
}
```

```text
/camera  발행: 최선, 휘발, 깊이 5, 메시지 20개, 와이파이
  viewer: 15/20 받음, 잃음 5
  logger: 연결 안 됨 (맞지 않는 정책: 신뢰성)
/odom  발행: 신뢰, 휘발, 깊이 10, 메시지 20개, 와이파이
  planner: 20/20 받음, 다시 보냄 5
  plotter: 15/20 받음, 잃음 5
/robot_description  발행: 신뢰, 지속, 깊이 1, 메시지 1개
  rviz: 1/1 받음
  monitor: 0/1 받음
/cmd_vel  발행: 신뢰, 휘발, 깊이 10, 메시지 10개
  base: 10/10 받음
  safety: 연결 안 됨 (맞지 않는 정책: 마감)
```

- **연결되지 않는 짝**: best effort로 내보내는 카메라를 reliable로 구독한 logger는 아무것도 받지 못했습니다. 프로그램은 멀쩡히 돌고 메시지만 오지 않으므로 ROS 2에서 가장 흔히 겪는 문제입니다. 이때 ROS 2는 맞지 않는 정책을 경고 로그로 남기므로 먼저 로그를 봅니다
- **잃는 망에서**: 둘 다 reliable인 planner는 잃은 다섯 개를 다시 받아 모두 받았고, reliable 발행자를 best effort로 구독한 plotter는 그냥 잃었습니다. 다시 보내는 동안 뒤 메시지가 밀리므로, 최신 값만 중요한 센서는 best effort가 낫습니다
- **늦게 온 구독자**: 로봇 모델처럼 한 번만 내보내는 것은 transient local로 남겨 둡니다. 둘 다 지속을 약속한 rviz는 나중에 와도 받았고, volatile로 구독한 monitor는 받지 못했습니다
- **마감**: safety는 100ms마다 와야 한다고 요청했는데 발행자가 마감을 약속하지 않아 연결되지 않았습니다

## 공장에서 쓸 때

ROS 2의 통신은 실시간을 보장하지 않습니다. 그래서 1ms 단위의 관절 제어는 실시간 커널 위의 제어 루프에 두고, ROS 2는 그보다 느린 계획, 인식, 감시를 맡기는 것이 보통입니다. 하드웨어와 제어 루프를 잇는 틀이 ros2_control이고([「로봇 컨트롤러와 잇기」](#/read/cpp-industrial/rob-controller)), 팔의 경로 계획에는 MoveIt 2, 이동 로봇의 주행에는 Nav2를 많이 씁니다.

<Note>
DDS는 같은 망의 노드를 멀티캐스트로 찾기 때문에, 공장 망에서는 찾는 범위부터 좁힙니다. 도메인 번호를 셀마다 나누고, `ROS_AUTOMATIC_DISCOVERY_RANGE`로 찾는 범위를 한 기계 안이나 같은 서브넷으로 제한하며, 로봇 셀은 [「보안」](#/read/cpp-industrial/depl-security)의 구역 하나로 묶습니다. 노드 사이의 인증과 암호화가 필요하면 DDS 보안을 켜는 SROS2를 씁니다.
</Note>

## 정리

- ROS 2는 노드를 토픽, 서비스, 액션, 파라미터로 잇는 미들웨어이며, 밑에서는 DDS가 노드를 찾고 메시지를 나르고, C++ 노드는 rclcpp로 쓴다
- QoS는 신뢰성, 지속성, 깊이, 마감 등을 정하며, 구독자가 요청한 것을 발행자가 제공할 때만 연결되므로 맞지 않는 짝은 메시지를 하나도 받지 못한다
- 공장에서는 빠른 제어를 실시간 루프에 두고 ROS 2에는 계획과 감시를 맡기며, 찾는 범위를 좁히고 셀을 보안 구역으로 묶는다
