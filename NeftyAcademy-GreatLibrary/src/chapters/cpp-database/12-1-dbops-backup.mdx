데이터는 디스크 고장만이 아니라 잘못 실행한 `DELETE`나 `UPDATE`, 버그 있는 마이그레이션, 랜섬웨어로도 사라집니다. 백업을 설계할 때는 최근 얼마 동안의 데이터까지 잃어도 되는지(**RPO**, 복구 시점 목표)와 되살리기까지 얼마나 걸려도 되는지(**RTO**, 복구 시간 목표)를 먼저 정합니다. 하루에 한 번 덤프를 뜨면 RPO는 최대 하루입니다.

## 쓰는 중인 SQLite 복사하기

SQLite는 파일 하나라서 그냥 복사하고 싶어집니다. 아래 프로그램은 WAL 모드로 만 행을 넣고 연결을 연 채로 네 가지 방법으로 복사한 뒤, 복사본을 열어 확인하고 하나를 메모리로 되살립니다.

```cpp flags=-lsqlite3
#include <sqlite3.h>
#include <unistd.h>
#include <cstdio>
#include <filesystem>
#include <string>

namespace fs = std::filesystem;

std::string one(sqlite3* db, const char* sql) {
    sqlite3_stmt* st;
    if (sqlite3_prepare_v2(db, sql, -1, &st, nullptr) != SQLITE_OK)
        return sqlite3_errmsg(db);
    std::string v;
    if (sqlite3_step(st) == SQLITE_ROW)
        v = reinterpret_cast<const char*>(sqlite3_column_text(st, 0));
    sqlite3_finalize(st);
    return v;
}

// 온라인 백업: 한 번에 페이지 n개씩 옮기며 남은 페이지를 보인다
bool backup(sqlite3* src, const std::string& path, int n,
            sqlite3* other = nullptr) {
    sqlite3* dst;
    sqlite3_open(path.c_str(), &dst);
    sqlite3_backup* b = sqlite3_backup_init(dst, "main", src, "main");
    int rc, step = 0;
    while ((rc = sqlite3_backup_step(b, n)) == SQLITE_OK || rc == SQLITE_BUSY ||
           rc == SQLITE_LOCKED) {
        std::printf("  %d단계: 전체 %d페이지 중 %d페이지 남음\n", ++step,
                    sqlite3_backup_pagecount(b), sqlite3_backup_remaining(b));
        if (other && step == 1)                 // 백업 도중에 다른 연결이 쓴다
            sqlite3_exec(other, "INSERT INTO parts (name) VALUES ('끼어든 행')",
                         nullptr, nullptr, nullptr);
    }
    std::printf("  %d단계: %s\n", ++step,
                rc == SQLITE_DONE ? "끝" : sqlite3_errstr(rc));
    sqlite3_backup_finish(b);
    sqlite3_close(dst);
    return rc == SQLITE_DONE;
}

void check(const std::string& path) {            // 백업은 열어서 확인해야 백업이다
    sqlite3* db;
    sqlite3_open_v2(path.c_str(), &db, SQLITE_OPEN_READONLY, nullptr);
    std::printf("  %s: integrity_check → %s, count(*) → %s\n",
                fs::path(path).filename().c_str(),
                one(db, "PRAGMA integrity_check").c_str(),
                one(db, "SELECT count(*) FROM parts").c_str());
    sqlite3_close(db);
}

int main() {
    fs::path dir = fs::temp_directory_path() / ("bk_" + std::to_string(getpid()));
    fs::create_directories(dir);
    std::string live = (dir / "live.db").string();
    sqlite3 *db, *other;
    sqlite3_open(live.c_str(), &db);
    sqlite3_exec(db, "PRAGMA journal_mode = WAL;"
                     "CREATE TABLE parts (id INTEGER PRIMARY KEY, name TEXT);"
                     "WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL "
                     "SELECT i + 1 FROM n WHERE i < 10000) "
                     "INSERT INTO parts (name) "
                     "SELECT printf('부품-%05d', i) FROM n",
                 nullptr, nullptr, nullptr);
    sqlite3_open(live.c_str(), &other);

    std::printf("파일만 복사: live.db %ju바이트, live.db-wal %ju바이트\n",
                fs::file_size(live), fs::file_size(live + "-wal"));
    fs::copy_file(live, dir / "naive.db");      // 쓰는 중인 DB의 파일만 복사한다

    std::printf("백업 API, 20페이지씩\n");
    backup(db, (dir / "copy1.db").string(), 20);
    std::printf("도중에 다른 연결이 쓰면 처음부터 다시\n");
    backup(db, (dir / "copy2.db").string(), 20, other);
    std::printf("VACUUM INTO\n");
    std::string q = "VACUUM INTO '" + (dir / "copy3.db").string() + "'";
    sqlite3_exec(db, q.c_str(), nullptr, nullptr, nullptr);
    std::printf("확인\n");
    for (const char* f : {"naive.db", "copy1.db", "copy2.db", "copy3.db"})
        check((dir / f).string());

    sqlite3* restored;                           // 되살리기: 백업 파일에서 메모리로
    sqlite3_open(":memory:", &restored);
    sqlite3* file;
    sqlite3_open((dir / "copy3.db").c_str(), &file);
    sqlite3_backup* b = sqlite3_backup_init(restored, "main", file, "main");
    sqlite3_backup_step(b, -1);                  // -1: 한 번에 전부
    sqlite3_backup_finish(b);
    std::printf("되살린 메모리 DB: %s행\n",
                one(restored, "SELECT count(*) FROM parts").c_str());
    for (sqlite3* d : {file, restored, other, db}) sqlite3_close(d);
    fs::remove_all(dir);
}
```

```text
파일만 복사: live.db 4096바이트, live.db-wal 218392바이트
백업 API, 20페이지씩
  1단계: 전체 51페이지 중 31페이지 남음
  2단계: 전체 51페이지 중 11페이지 남음
  3단계: 끝
도중에 다른 연결이 쓰면 처음부터 다시
  1단계: 전체 51페이지 중 31페이지 남음
  2단계: 전체 51페이지 중 31페이지 남음
  3단계: 전체 51페이지 중 11페이지 남음
  4단계: 끝
VACUUM INTO
확인
  naive.db: integrity_check → ok, count(*) → no such table: parts
  copy1.db: integrity_check → ok, count(*) → 10000
  copy2.db: integrity_check → ok, count(*) → 10001
  copy3.db: integrity_check → ok, count(*) → 10001
되살린 메모리 DB: 10001행
```

- **파일만 복사**: WAL 모드에서는 커밋한 트랜잭션이 체크포인트 전까지 `-wal` 파일에 쌓입니다. 만 행이 모두 `-wal`에 있었으므로 본 파일만 복사한 `naive.db`는 무결성 검사를 통과하는 빈 데이터베이스입니다. 쓰는 도중에 복사하면 여러 트랜잭션의 페이지가 섞여 깨지기도 하므로, 파일 복사는 모든 연결이 닫힌 뒤에만 합니다
- **백업 API**: `sqlite3_backup_step(b, n)`은 페이지 n개를 옮기는 동안만 원본에 읽기 잠금을 겁니다. 그 사이에 다른 연결이 쓰면 다음 단계에서 처음부터 다시 복사하므로(2단계에서 다시 31페이지 남음) `copy2.db`에는 끼어든 행도 있습니다. 백업하는 그 연결로 쓴 변경은 다시 시작하지 않고 대상에 반영됩니다. 쓰기가 잦아 끝나지 않으면 `-1`로 한 번에 옮기는데, 롤백 저널 모드에서는 그동안 쓰기가 막힙니다
- **VACUUM INTO**(3.27부터): 문장 하나로 일관된 스냅숏을 새 파일에 씁니다. 빈 페이지와 지운 데이터의 흔적이 없어 작지만 백업 API보다 CPU를 더 씁니다
- **열어서 확인**: `naive.db`처럼 `integrity_check`를 통과해도 데이터가 없을 수 있으니 행 수 같은 값을 함께 봅니다. 되살리기는 백업 파일을 원본으로 둔 같은 API입니다

다른 기계로는 보통의 `rsync` 대신 `sqlite3_rsync`(3.47부터, 실험적)로 SSH를 거쳐 일관된 사본을 보냅니다.

## PostgreSQL: 논리 백업

`pg_dump`는 데이터베이스 하나를 SQL이나 자체 형식으로 내보내는 **논리 백업**입니다. 트랜잭션 하나의 스냅숏으로 읽어 다른 연결이 쓰는 중에도 일관되고, 새 판의 서버로도 옮길 수 있습니다.

```sh
pg_dump -Fc -f shop.dump shop            # 사용자 정의 형식: 압축, 골라 되살리기
pg_dumpall --globals-only > globals.sql
createdb shop_check                      # 되살려 보기는 새 데이터베이스에
pg_restore -d shop_check -j 4 shop.dump  # 연결 4개로 나눠 되살린다
psql -d shop_check -Atc "SELECT count(*) FROM parts"
```

`pg_dump`는 데이터베이스 하나만 담으므로 역할과 테이블스페이스는 `pg_dumpall`로 따로 뜹니다. 되살릴 때는 데이터를 다 넣은 뒤 기본 키와 인덱스를 만들어, 행마다 인덱스를 고치는 것보다 빠릅니다. `-t`로 테이블 하나만 되살릴 수도 있습니다.

## PostgreSQL: 물리 백업과 시점 복구

논리 덤프는 뜬 순간까지만 담고 큰 데이터베이스는 되살리기가 느립니다. **물리 백업** 도구 `pg_basebackup`은 도는 서버의 데이터 디렉터리를 파일째 뜨고, 복사하는 동안의 변경은 WAL로 받아 맞춥니다. WAL을 계속 보관해 두면 베이스 백업에 WAL을 다시 적용해 원하는 시각으로 되살리는 **시점 복구**(PITR)가 됩니다. 같은 주 판, 같은 CPU 구조에서만 쓸 수 있습니다.

```ini
# 운영 서버: 다 찬 WAL 파일을 보관소로
archive_mode = on
archive_command = 'test ! -f /backup/wal/%f && cp %p /backup/wal/%f'

# 되살릴 서버: 베이스 백업을 풀고 recovery.signal을 만든 뒤
restore_command = 'cp /backup/wal/%f %p'
recovery_target_time = '2026-11-22 14:59:00+09'
```

서버는 목표 시각 뒤의 첫 커밋 앞에서 멈추고 기본값(`recovery_target_action = pause`)대로 기다리며, 확인한 뒤 `pg_wal_replay_resume()`을 부르면 쓰기를 받습니다. WAL은 16MB 세그먼트가 다 차야 보관되므로 목표 시각 뒤의 기록이 보관소에 아직 없을 수 있고, 그러면 PostgreSQL 13부터는 목표에 닿지 못했다는 오류로 멈춥니다. `archive_timeout`으로 보관 간격에 상한을 두거나 `pg_receivewal`로 WAL을 실시간으로 받아 RPO를 줄입니다. 17부터는 `summarize_wal = on`이면 `pg_basebackup --incremental`로 바뀐 블록만 뜨고 `pg_combinebackup`으로 합쳐 되살립니다. 일정과 보존, 검증은 pgBackRest, Barman, WAL-G 같은 도구가 맡습니다.

## MySQL과 MariaDB

`mysqldump`(MariaDB는 `mariadb-dump`)는 `--single-transaction`이면 InnoDB 테이블을 스냅숏 하나로 덤프합니다(MyISAM은 일관되지 않습니다). `--source-data`(MySQL 8.0.26부터, MariaDB는 `--master-data`)로 덤프 시점의 binlog 위치를 적어 두면, 되살린 뒤 그 뒤의 binlog를 `mysqlbinlog`로 재생해 시점 복구를 합니다. 큰 데이터베이스는 Percona XtraBackup이나 `mariadb-backup` 같은 물리 백업 도구를 씁니다.

## 어디에, 몇 벌

흔히 **3-2-1 규칙**을 따릅니다. 원본을 포함해 세 벌을, 두 가지 저장 매체에, 한 벌은 다른 장소에 둡니다. 랜섬웨어에 대비해 한 벌은 지우거나 덮어쓸 수 없는 곳에 두기도 합니다. 실수로 실행한 `DROP TABLE`도 곧바로 복제되므로 복제 서버는 백업이 아닙니다([「복제」](#/read/cpp-database/dbops-replica)). 백업은 암호화하고 열쇠는 따로 둡니다.

<Note>
2017년 1월 GitLab.com은 운영 데이터베이스의 파일을 실수로 지운 뒤에야, 매일 돌던 pg_dump 백업이 계속 실패해 왔다는 것을 알았습니다. 서버는 9.6인데 9.2판 pg_dump가 돌았고(pg_dump는 자기보다 새 판의 서버를 덤프하지 못합니다), 실패 알림 메일은 수신 서버에서 걸러졌습니다. 결국 다른 용도로 여섯 시간 전에 떠 둔 디스크 스냅숏으로 되살려 그 사이의 데이터를 잃었습니다. 정기적으로 되살려 보며 걸리는 시간(RTO)을 재고, 백업 파일의 크기와 나이를 감시합니다.
</Note>

## 정리

- 쓰는 중인 파일을 그대로 복사하면 WAL의 변경을 놓치거나 깨진 사본이 나오므로, SQLite는 백업 API나 VACUUM INTO로 일관된 스냅숏을 뜬다
- PostgreSQL은 pg_dump 논리 백업과 pg_basebackup에 WAL 보관을 더한 시점 복구를, MySQL은 --single-transaction 덤프와 binlog 재생을 쓴다
- 백업은 되살려 행 수까지 확인해야 백업이고, 3-2-1로 나눠 두며, 복제 서버는 백업이 아니다
