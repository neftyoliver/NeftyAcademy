따로 컴파일한 두 조각이 함께 돌아가려면 "인자는 어디에 담고, 결과는 어디서 꺼내는가"를 똑같이 알고 있어야 합니다. 그 약속이 <strong>ABI</strong>(Application Binary Interface)입니다.

## API와 ABI

| | 누구와의 약속 | 예 |
| --- | --- | --- |
| API | 소스 코드 수준. 사람이 읽는다 | `int add(int a, int b);` |
| ABI | 기계어 수준. 컴파일러가 지킨다 | "첫 인자는 `rdi`, 결과는 `rax`" |

API가 같아도 ABI가 다르면 함께 링크할 수 없습니다. 헤더는 API만 알려 줍니다. ABI는 운영체제와 CPU의 조합마다 문서로 정해져 있고, 컴파일러가 알아서 따릅니다.

## 호출 규약

함수를 부르는 쪽과 불리는 쪽의 약속을 <Term tip="calling convention. 인자와 반환값의 위치, 레지스터 보존 책임 등">호출 규약</Term>이라고 합니다. ABI에서 가장 자주 마주치는 부분입니다.

| | 리눅스·맥 x86-64 (System V) | 윈도우 x64 | ARM64 (AAPCS64) |
| --- | --- | --- | --- |
| 정수·포인터 인자 | `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` | `rcx`, `rdx`, `r8`, `r9` | `x0` ~ `x7` |
| 실수 인자 | `xmm0` ~ `xmm7` | `xmm0` ~ `xmm3` | `v0` ~ `v7` |
| 반환값 | `rax` | `rax` | `x0` |
| 넘치는 인자 | 스택 | 스택 | 스택 |

앞 챕터의 디버거 화면에서 `lea rdi, …` 다음에 `call puts`가 온 이유가 이 표의 첫 줄입니다. 글자열의 주소가 첫 인자라서 `rdi`에 넣었습니다.

## 누가 레지스터를 지키는가

함수를 부르고 돌아오면 레지스터 값이 바뀌어 있을 수 있습니다. 그래서 레지스터를 둘로 나눕니다.

| | 뜻 | System V x86-64 |
| --- | --- | --- |
| 부르는 쪽이 지킨다 (caller-saved) | 불린 함수가 마음대로 써도 된다. 필요하면 부르기 전에 저장해 둔다 | `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8` ~ `r11` |
| 불린 쪽이 지킨다 (callee-saved) | 쓰려면 저장했다가 돌아가기 전에 되돌려 놓아야 한다 | `rbx`, `rbp`, `r12` ~ `r15` |

`-O0` 어셈블리의 첫 줄 `push rbp`와 끝의 `pop rbp`가 이 약속을 지키는 코드입니다. 그 밖에 `call` 직전에는 스택 포인터가 16바이트의 배수여야 한다는 규칙도 있습니다.

## 타입의 크기와 배치도 ABI

같은 C 코드라도 플랫폼에 따라 타입의 크기가 다릅니다.

| 타입 | 리눅스·맥 64비트 (LP64) | 윈도우 64비트 (LLP64) |
| --- | --- | --- |
| `int` | 4바이트 | 4바이트 |
| `long` | **8바이트** | **4바이트** |
| `long long` | 8바이트 | 8바이트 |
| 포인터 | 8바이트 | 8바이트 |

구조체 안에서 멤버가 놓이는 위치도 ABI가 정합니다.

```c
#include <stddef.h>
#include <stdio.h>

struct a { char c; int i; };
struct b { char c; double d; char e; };
struct c { double d; char c; char e; };

int main(void)
{
    printf("%zu %zu\n", sizeof(struct a), offsetof(struct a, i));  // 8 4
    printf("%zu %zu\n", sizeof(struct b), sizeof(struct c));       // 24 16
    return 0;
}
```

`char` 하나와 `int` 하나인데 5바이트가 아니라 8바이트입니다. `int`는 4의 배수 주소에 놓여야 해서 사이에 3바이트의 빈칸(<strong>패딩</strong>)이 들어갑니다. `struct b`와 `struct c`는 멤버가 같아도 순서 때문에 크기가 다릅니다. 큰 타입을 앞에 두면 빈칸이 줄어듭니다.

## 왜 알아야 하는가

- **다른 언어와 붙일 때**: 파이썬이나 러스트에서 C 함수를 부를 수 있는 것은 C의 ABI를 따르기 때문이다
- **파일과 네트워크**: 구조체를 통째로 파일에 쓰거나 보내면, 받는 쪽의 ABI가 다를 때 깨진다. `long` 대신 `int32_t`처럼 크기가 정해진 타입을 쓰고 패딩을 조심한다
- **라이브러리를 갈아 끼울 때**: 구조체에 멤버를 하나 더하면 API는 그대로 보여도 ABI는 깨진다. 예전에 컴파일한 프로그램이 새 라이브러리와 맞지 않게 된다
- **시스템 콜**: 커널에 일을 시키는 방법(어느 레지스터에 번호를 넣는가)도 ABI의 일부다

<Note>
보통은 컴파일러가 ABI를 알아서 지키므로 신경 쓸 일이 없습니다. 어셈블리를 직접 쓰거나, 서로 다른 언어·컴파일러·기기 사이에서 바이트를 주고받을 때 필요해집니다. IoT에서는 마지막 경우가 자주 옵니다.
</Note>

## 정리

- ABI는 기계어 수준의 약속: 호출 규약, 타입 크기, 구조체 배치
- 인자는 정해진 레지스터에, 결과는 `rax`(ARM64는 `x0`)에
- 기기 사이에 주고받는 데이터에는 크기가 고정된 타입을 쓴다
