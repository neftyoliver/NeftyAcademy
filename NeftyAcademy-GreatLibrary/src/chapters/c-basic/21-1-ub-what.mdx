C 표준에는 "이렇게 하면 무슨 일이 일어날지 정하지 않는다"고 적힌 곳이 많습니다. 이것을 <strong>정의되지 않은 동작</strong>(undefined behavior, UB)이라고 합니다. C를 안전하게 쓰려면 반드시 이해해야 하는 개념입니다.

## 표준이 정하지 않는 세 단계

| 종류 | 뜻 | 예 |
| --- | --- | --- |
| 구현이 정하는 동작 | 컴파일러마다 다르지만, 문서에 적어 둬야 한다 | `int`의 크기, `char`의 부호 |
| 명시되지 않은 동작 | 몇 가지 가운데 하나지만, 어느 것인지 말해 주지 않아도 된다 | `f(a(), b())`에서 `a`와 `b` 중 무엇을 먼저 부르는가 |
| 정의되지 않은 동작 | **아무 제한이 없다** | 배열 밖 접근, 부호 있는 정수의 넘침, 널 따라가기 |

앞의 둘은 "어느 플랫폼에서는 이렇다"고 말할 수 있습니다. 셋째는 그럴 수 없습니다. 프로그램에 UB가 있으면 표준은 그 프로그램 **전체에 대해** 아무것도 보장하지 않습니다.

## "아무 일이나"의 뜻

UB의 결과는 운에 따라 다릅니다.

- 기대한 대로 동작한다 (가장 나쁜 경우. 문제가 숨는다)
- 바로 죽는다 (가장 좋은 경우)
- 엉뚱한 값이 나온다
- 내 컴퓨터에서는 되고 다른 컴퓨터에서는 안 된다
- `-O0`에서는 되고 `-O2`에서는 안 된다
- 컴파일러를 새 버전으로 올렸더니 안 된다

## 컴파일러는 UB가 없다고 가정한다

UB가 위험한 진짜 이유는 최적화에 있습니다. 컴파일러는 "이 프로그램에는 UB가 없다"는 전제에서 코드를 다듬습니다.

```c
bool will_overflow(int x)
{
    return x + 1 < x;       // 넘치면 음수가 될 테니 참이 되겠지?
}
```

`-O0`으로 컴파일하면 쓴 그대로 더하고 비교합니다.

```asm
will_overflow:
    …
    add     eax, 1
    cmp     eax, dword ptr [rbp - 4]
    setl    al
    …
```

`-O2`에서는 이렇게 됩니다.

```asm
will_overflow:
    xor     eax, eax        ; 언제나 0(거짓)을 돌려준다
    ret
```

컴파일러의 추론은 이렇습니다. "부호 있는 정수의 넘침은 UB다. UB는 일어나지 않는다. 그러면 `x + 1`은 언제나 `x`보다 크다. 따라서 이 식은 언제나 거짓이다." 넘침을 검사하려던 코드가 통째로 사라졌습니다.

하나 더 봅니다.

```c
int read_value(int *p)
{
    int v = *p;             // 먼저 따라가고
    if (p == nullptr)       // 나중에 널을 확인한다
        return -1;
    return v;
}
```

```asm
read_value:
    mov     eax, dword ptr [rdi]
    ret
```

널 검사가 사라졌습니다. "`*p`를 했으니 `p`는 널이 아니다(널이면 UB인데 UB는 없으니까). 그러면 아래의 검사는 언제나 거짓이다."

<Note kind="warn">
UB는 "그 줄에서 이상한 값이 나온다"로 끝나지 않습니다. 컴파일러가 그 줄을 근거로 **앞뒤의 다른 코드까지** 바꿉니다. 그래서 증상이 원인과 멀리 떨어진 곳에 나타납니다.
</Note>

## 왜 이렇게 만들었나

- **빠르게**: 배열 접근마다 범위를 검사하고 덧셈마다 넘침을 검사하면 느려진다. C는 "프로그래머가 알아서 지킨다"고 믿고 검사를 생략한다
- **어느 기계에서나**: C는 온갖 CPU에서 돌아야 했다. 넘쳤을 때의 동작이 CPU마다 달랐으므로 하나로 정하지 않았다
- **최적화의 여지**: "이런 일은 없다"는 가정이 있어야 위와 같은 단순화가 가능하다

C는 속도와 자유를 주고, 대가로 규칙을 지킬 책임을 프로그래머에게 넘겼습니다.

## 막는 법

| 방법 | 잡아 주는 것 |
| --- | --- |
| `-Wall -Wextra` | 초기화 안 한 변수, 서식 불일치, 빠진 `return` 등 컴파일할 때 보이는 것 |
| `-fsanitize=undefined` (UBSan) | 정수 넘침, 잘못된 시프트, 널 따라가기 등을 실행 중에 |
| `-fsanitize=address` (ASan) | 배열 밖 접근, 해제 후 사용, 두 번 해제 |
| 디버그와 릴리스 빌드 모두 시험하기 | 최적화에 따라 달라지는 동작 |

```sh
clang -std=c23 -g -fsanitize=undefined ub.c -o ub
./ub
```

```text
ub.c:7:7: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
```

도구는 **실행된 경로**의 UB만 잡습니다. 그래서 어떤 것이 UB인지 알고 처음부터 쓰지 않는 것이 먼저입니다. 다음 챕터에서 자주 나오는 것들을 모읍니다.

## 정리

- UB가 있는 프로그램에는 표준이 아무것도 보장하지 않는다
- 컴파일러는 UB가 없다고 가정하고, 그 가정으로 주변 코드까지 바꾼다
- "내 컴퓨터에서 되니까 괜찮다"는 통하지 않는다. 경고와 새니타이저를 켠다
