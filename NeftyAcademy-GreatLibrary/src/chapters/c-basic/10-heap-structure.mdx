[`malloc`](#/read/c-basic/dyn-malloc)은 마법이 아니라 C로 짠 평범한 함수입니다. 안에서 무슨 일을 하는지 알면 `free`에 크기를 안 넘겨도 되는 이유, 배열을 넘겨 쓰면 프로그램이 한참 뒤에 죽는 이유가 보입니다.

## 프로세스의 메모리 지도

프로그램 하나가 받는 주소 공간은 대략 이렇게 나뉩니다(리눅스 기준, 낮은 주소부터).

| 영역 | 들어 있는 것 |
| --- | --- |
| 코드 | 기계어. 읽기와 실행만 된다 |
| 데이터 | 초깃값이 있는 전역 변수, 글자열 상수 |
| BSS | 0으로 시작하는 전역 변수 |
| 힙 | `malloc`이 나눠 주는 곳. 위쪽으로 자란다 |
| (빈 공간) | 공유 라이브러리와 큰 메모리 덩어리가 이 사이에 놓인다 |
| 스택 | 지역 변수, 돌아갈 주소. 아래쪽으로 자란다 |

## malloc은 도매상

운영체제는 메모리를 <strong>페이지</strong>(보통 4096바이트) 단위로만 줍니다. `malloc(10)`을 할 때마다 운영체제에 부탁하면 느리고 낭비가 큽니다. 그래서 `malloc`은 운영체제에게서 큰 덩어리를 받아 두고(리눅스에서는 `brk`와 `mmap` 시스템 콜), 그것을 잘게 잘라 나눠 줍니다. 돌려받은 조각은 목록에 모아 두었다가 다시 내줍니다.

## 직접 재 보기

```c
#include <malloc.h>
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    char *a = malloc(1);
    char *b = malloc(1);
    char *c = malloc(25);
    char *d = malloc(100);

    printf("a %p\nb %p\nc %p\nd %p\n", (void *)a, (void *)b, (void *)c, (void *)d);
    printf("쓸 수 있는 크기: %zu %zu %zu\n",
           malloc_usable_size(a), malloc_usable_size(c), malloc_usable_size(d));

    free(b);
    char *e = malloc(1);
    printf("e %p\n", (void *)e);

    free(a);
    free(c);
    free(d);
    free(e);
    return 0;
}
```

리눅스(glibc, 64비트)에서 실행한 결과입니다. 주소는 매번 다르지만 간격은 같습니다.

```text
a 0x5590d50862a0
b 0x5590d50862c0
c 0x5590d50862e0
d 0x5590d5086310
쓸 수 있는 크기: 24 40 104
e 0x5590d50862c0
```

세 가지를 읽을 수 있습니다.

- 1바이트를 달라고 했는데 `a`와 `b`의 간격이 **32바이트**입니다
- 1바이트를 빌려도 실제로는 24바이트를 쓸 수 있습니다
- `b`를 해제한 뒤 새로 빌린 `e`는 **`b`와 같은 주소**입니다

## 조각마다 붙는 머리표

`malloc`은 돌려주는 주소 **바로 앞 8바이트**에 그 조각의 크기를 적어 둡니다.

`0x21`은 크기 `0x20`(32바이트)에 깃발 비트 하나가 더해진 값입니다. 조각의 크기는 16의 배수로 맞춰지고(어떤 타입을 넣어도 정렬이 맞도록), 가장 작은 조각이 32바이트입니다. 그래서 1바이트를 빌려도 32바이트가 나갑니다.

이 머리표 덕분에 `free(p)`는 크기를 묻지 않습니다. `p` 바로 앞을 읽으면 되기 때문입니다.

## 그래서 생기는 일들

| 현상 | 이유 |
| --- | --- |
| 빌린 크기를 넘겨 쓰면 한참 뒤 `malloc`이나 `free`에서 죽는다 | 다음 조각의 머리표를 덮어썼고, 그 조각을 다룰 때 드러난다 |
| 해제한 메모리를 읽어도 옛 값이 보이곤 한다 | `free`는 내용을 지우지 않고 목록에 올려 둘 뿐이다 |
| 해제한 뒤 새로 빌리면 같은 주소가 나온다 | 방금 돌려받은 조각부터 다시 내준다 |
| `free`해도 프로세스의 메모리 사용량이 안 줄 수 있다 | 운영체제에 바로 돌려주지 않고 다음 요청에 쓰려고 들고 있다 |
| 작은 것을 아주 많이 빌리면 생각보다 많이 든다 | 조각마다 머리표와 정렬 여백이 붙는다 |
| 빈 메모리는 충분한데 큰 요청이 실패한다 | 빈 조각이 잘게 흩어져 있다(<strong>단편화</strong>) |

마지막 줄은 메모리가 작은 장치에서 중요합니다. 오래 도는 프로그램이 크기가 제각각인 메모리를 빌리고 돌려주기를 반복하면 힙이 조각납니다. 그래서 마이크로컨트롤러 펌웨어에서는 `malloc`을 아예 쓰지 않거나, 시작할 때 한 번만 빌리고 끝까지 들고 가는 방식을 택합니다.

<Note>
여기서 본 숫자(8바이트 머리표, 32바이트 최소 조각)는 리눅스의 glibc 이야기입니다. 윈도우, 맥, musl, jemalloc은 구조가 다릅니다. "관리 정보가 조각 가까이에 있고, 돌려받은 조각을 다시 쓴다"는 큰 그림은 같습니다.
</Note>

## 정리

- `malloc`은 운영체제에서 크게 받아 잘게 나눠 주는 관리자다
- 조각 앞에 크기를 적은 머리표가 있어서 `free`가 크기를 안다
- 넘겨 쓰기는 머리표를 망가뜨리고, 잦은 할당과 해제는 힙을 조각낸다
