게임 세상의 "물건"을 코드로 어떻게 표현할까요? 병사, 포탑, 새, 상자는 저마다 조금씩 겹치는 성질을 가집니다. 이 문제에 대한 답이 엔진의 **객체 모델**이고, 크게 세 가지 흐름이 있었습니다. 이 장(5장)은 그중 지금 많이 쓰는 **ECS**(엔티티·컴포넌트·시스템)를 만들어 가는데, 이 쪽은 먼저 셋을 견줍니다.

## 세 가지 모델

| 모델 | 물건은 | 동작은 |
| --- | --- | --- |
| 상속 계층 | `GameObject`에서 내려온 클래스의 객체 | 가상 함수 `update()` |
| 컴포넌트 묶음 | 컴포넌트 목록을 가진 객체 | 컴포넌트마다의 가상 함수 |
| ECS | 그냥 번호(엔티티) | 컴포넌트 배열을 훑는 시스템 함수 |

**상속 계층**은 `GameObject → Actor → Pawn → Character`처럼 성질을 위에서 물려받습니다. 처음엔 자연스럽지만, 성질이 겹치는 물건이 생기면 무너집니다. "날아다니는 포탑"은 `Turret` 아래에 둘까요, `FlyingThing` 아래에 둘까요? 다중 상속을 쓰거나, 공통 성질을 자꾸 위로 끌어올리다 맨 위 클래스가 모든 것을 다 아는 거대한 클래스가 됩니다.

**컴포넌트 묶음**은 "무엇이다" 대신 "무엇을 가졌다"로 생각합니다. 객체는 `Mover`, `Gun`, `Flyer` 같은 컴포넌트를 골라 담습니다. 조합은 자유로워지지만, 컴포넌트가 객체마다 따로 할당되고 가상 함수로 불려 메모리가 흩어집니다.

**ECS**는 거기서 한 걸음 더 갑니다. 엔티티는 번호일 뿐이고, 같은 종류의 컴포넌트는 한 배열에 모이며, 동작은 컴포넌트에 붙지 않고 "Position과 Velocity를 가진 것을 모두 움직인다" 같은 **시스템** 함수에 있습니다.

## 조합의 자유

```cpp
#include <cstdint>
#include <print>
#include <string>
#include <vector>

// 컴포넌트마다 비트 하나
enum : std::uint32_t { POS = 1, VEL = 2, GUN = 4, FLY = 8, AI = 16 };

struct Entities {
    std::vector<std::string> name;
    std::vector<std::uint32_t> mask;           // 어떤 컴포넌트를 가졌나
    int add(std::string n, std::uint32_t m)
    {
        name.push_back(std::move(n));
        mask.push_back(m);
        return static_cast<int>(name.size()) - 1;
    }
    // "이 컴포넌트들을 모두 가진 개체"를 고른다: 시스템이 하는 질문
    std::vector<int> query(std::uint32_t need) const
    {
        std::vector<int> out;
        for (std::size_t i = 0; i < mask.size(); ++i)
            if ((mask[i] & need) == need) out.push_back(static_cast<int>(i));
        return out;
    }
};

int main()
{
    Entities es;
    es.add("병사", POS | VEL | GUN | AI);
    es.add("포탑", POS | GUN | AI);
    es.add("새", POS | VEL | FLY);
    es.add("나는 포탑", POS | VEL | GUN | AI | FLY);   // 상속이면 어디에 둘까?
    es.add("상자", POS);

    auto show = [&](const char* sys, std::uint32_t need) {
        std::print("{:<14}:", sys);
        for (int i : es.query(need)) std::print(" {}", es.name[i]);
        std::println();
    };
    show("이동 시스템", POS | VEL);
    show("사격 시스템", POS | GUN | AI);
    show("비행 시스템", POS | VEL | FLY);
}
```

```text
이동 시스템   : 병사 새 나는 포탑
사격 시스템   : 병사 포탑 나는 포탑
비행 시스템   : 새 나는 포탑
```

"나는 포탑"은 새 클래스 없이 비트 다섯 개의 조합으로 만들어졌고, 이동·사격·비행 시스템이 저마다 필요한 컴포넌트를 가진 개체만 골라 처리합니다. 디자이너가 에디터에서 컴포넌트를 붙였다 떼며 새로운 물건을 만들 수 있다는 것이 이 방식의 가장 큰 장점입니다. 실제 ECS는 매번 모든 개체를 훑지 않고, 같은 조합끼리 모아 두어 질문에 바로 답합니다([「아키타입과 희소 집합」](#/read/cpp-game-engine/ecs-storage)).

## 속도

같은 일, 곧 20만 개 중 절반을 움직이는 일을 세 모델로 100프레임 돌려 봤습니다.

```cpp norun
#include <chrono>
#include <memory>
#include <print>
#include <vector>

// 1) 상속 계층: 모든 것이 GameObject에서 내려온다
struct GameObject {
    float x = 0, vx = 1;
    virtual ~GameObject() = default;
    virtual void update(float dt) { x += vx * dt; }
};
struct Enemy : GameObject {};
struct Turret : GameObject { void update(float) override {} };   // 움직이지 않음

// 2) 컴포넌트 묶음: 객체가 컴포넌트 목록을 가진다
struct Component {
    virtual ~Component() = default;
    virtual void update(float dt, float& x) = 0;
};
struct Mover : Component {
    float vx = 1;
    void update(float dt, float& x) override { x += vx * dt; }
};
struct Entity2 {
    float x = 0;
    std::vector<std::unique_ptr<Component>> comps;
};

// 3) ECS: 개체는 번호, 컴포넌트는 칸별 배열, 시스템은 그 배열을 훑는 함수
struct World {
    std::vector<float> x, vx;                 // Position, Velocity
};
void move_system(World& w, float dt)
{
    for (std::size_t i = 0; i < w.x.size(); ++i) w.x[i] += w.vx[i] * dt;
}

int main()
{
    constexpr int N = 200'000, FRAMES = 100;
    using clk = std::chrono::steady_clock;
    auto per = [&](auto d) {
        return std::chrono::duration<double, std::nano>(d).count() / (N * FRAMES);
    };

    std::vector<std::unique_ptr<GameObject>> objs;
    for (int i = 0; i < N; ++i)
        objs.push_back(i % 2 ? std::unique_ptr<GameObject>(new Enemy)
                             : std::unique_ptr<GameObject>(new Turret));
    std::vector<Entity2> ents(N);
    for (int i = 0; i < N; i += 2)
        ents[i].comps.push_back(std::make_unique<Mover>());
    World w;
    w.x.assign(N / 2, 0);
    w.vx.assign(N / 2, 1);

    auto t0 = clk::now();
    for (int f = 0; f < FRAMES; ++f)
        for (auto& o : objs) o->update(0.016f);
    auto t1 = clk::now();
    for (int f = 0; f < FRAMES; ++f)
        for (auto& e : ents)
            for (auto& c : e.comps) c->update(0.016f, e.x);
    auto t2 = clk::now();
    for (int f = 0; f < FRAMES; ++f) move_system(w, 0.016f);
    auto t3 = clk::now();

    std::println("상속 계층   {:.2f}ns/객체", per(t1 - t0));
    std::println("컴포넌트    {:.2f}ns/객체", per(t2 - t1));
    std::println("ECS         {:.2f}ns/객체", per(t3 - t2));
    std::println("검산: {:.2f} {:.2f} {:.2f}", objs[1]->x, ents[0].x, w.x[0]);
}
```

```text nocheck
상속 계층   1.50ns/객체
컴포넌트    2.31ns/객체
ECS         0.17ns/객체
검산: 1.60 1.60 1.60
```

GCC 14 `-O2`로 세 번 돌려 거의 같았고, Clang 20에서는 ECS가 0.05ns까지 내려갔습니다(나머지 둘은 비슷). 시간은 전체 20만 개로 나눈 값입니다.

- 상속과 컴포넌트는 객체마다 **포인터를 따라가** 흩어진 메모리를 읽고, 가상 함수를 부릅니다. 컴포넌트 묶음은 포인터를 한 번 더 따라가서 상속보다도 느렸습니다
- ECS는 움직이는 것들의 `x`와 `vx`가 각각 한 배열에 나란히 있어서, 반복문이 메모리를 앞에서부터 쭉 읽고, 컴파일러가 [「SIMD로 빠르게」](#/read/cpp-game-engine/math-simd)처럼 여러 개를 한 번에 처리하는 코드로 바꿀 수 있습니다. 상속 계층보다 9배쯤 빨랐습니다
- 또 ECS는 움직이지 않는 포탑을 아예 훑지 않습니다. 상속 계층은 포탑의 빈 `update()`까지 부릅니다

## 무엇을 고르나

속도만 보면 ECS가 압도적이지만, 모든 것을 ECS로 할 필요는 없습니다. UI, 게임 흐름(메뉴, 레벨 전환), 수가 적고 복잡한 것(보스 하나의 행동)은 평범한 객체가 더 읽기 쉽습니다. 많은 엔진이 **수가 많고 단순한 것은 ECS로, 적고 복잡한 것은 객체로** 섞어 씁니다. 「C++ 고급」의 [「가상 함수, 템플릿, variant 견주기」](#/read/cpp-advanced/te-compare)에서 본 것처럼, 가상 함수가 나쁜 것이 아니라 "수만 개를 매 프레임 하나씩 부를 때" 비싼 것입니다.

<Note>
"데이터 지향 설계"라는 말과 함께 ECS가 널리 알려졌지만, ECS를 쓴다고 저절로 빨라지는 것은 아닙니다. 시스템이 컴포넌트 여러 개를 띄엄띄엄 조회하거나, 개체마다 맵에서 찾아오면 위의 상속 계층보다 느려질 수도 있습니다. 빨라지는 까닭은 어디까지나 **같은 일을 하는 데이터를 나란히 두고 한 번에 훑는 것**입니다.
</Note>

## 정리

- 상속 계층은 성질이 겹치는 물건에서 무너지고, 컴포넌트 묶음은 조합이 자유롭지만 메모리가 흩어진다
- ECS는 엔티티를 번호로, 같은 컴포넌트를 한 배열에, 동작을 시스템 함수에 두어 조합과 속도를 함께 얻는다
- 측정에서 ECS는 상속보다 9배쯤 빨랐지만, 수가 적고 복잡한 것은 객체로 두고 섞어 쓰는 것이 보통이다
