많은 게임 엔진이 `std::vector`와 `std::unordered_map`을 쓰지 않거나, 같은 일을 하는 자기 컨테이너를 따로 둡니다(EA의 EASTL이 유명합니다). 표준 컨테이너가 틀려서가 아니라, 게임에서 중요한 것이 **언제, 몇 번 할당하나**와 **메모리에 어떻게 놓이나**이기 때문입니다. 이 쪽은 그 차이를 직접 세고 재 봅니다.

## 할당을 세어 보기

전역 `operator new`를 바꿔 할당 횟수를 셌습니다.

```cpp
#include <cstdint>
#include <cstdlib>
#include <new>
#include <print>
#include <unordered_map>
#include <vector>

static std::size_t g_allocs = 0;             // 전역 new를 세어 본다
void* operator new(std::size_t n)
{
    ++g_allocs;
    if (void* p = std::malloc(n)) return p;
    throw std::bad_alloc{};
}
void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }

// 열린 주소법 해시 표: 칸을 한 배열에 두고, 부딪히면 다음 칸으로
class FlatMap {
public:
    explicit FlatMap(std::size_t cap) : keys_(cap, kEmpty), vals_(cap) {}
    void insert(std::uint32_t k, int v)
    {
        std::size_t i = hash(k);
        while (keys_[i] != kEmpty && keys_[i] != k)
            i = (i + 1) & (cap() - 1);
        keys_[i] = k;
        vals_[i] = v;
    }
    const int* find(std::uint32_t k) const
    {
        for (std::size_t i = hash(k); keys_[i] != kEmpty;
             i = (i + 1) & (cap() - 1))
            if (keys_[i] == k) return &vals_[i];
        return nullptr;
    }

private:
    static constexpr std::uint32_t kEmpty = 0xFFFFFFFF;
    std::size_t cap() const { return keys_.size(); }   // 2의 거듭제곱
    std::size_t hash(std::uint32_t k) const
    {
        return (k * 2654435761u) & (cap() - 1);   // 곱셈 해시
    }
    std::vector<std::uint32_t> keys_;
    std::vector<int> vals_;
};

int main()
{
    constexpr int N = 1000;

    std::size_t a0 = g_allocs;
    std::vector<int> grow;
    for (int i = 0; i < N; ++i) grow.push_back(i);
    std::size_t a1 = g_allocs;
    std::vector<int> reserved;
    reserved.reserve(N);
    for (int i = 0; i < N; ++i) reserved.push_back(i);
    std::size_t a2 = g_allocs;
    std::println("vector {}개: 그냥 {}번 할당, reserve하면 {}번", N,
                 a1 - a0, a2 - a1);

    std::size_t b0 = g_allocs;
    std::unordered_map<std::uint32_t, int> um;
    for (int i = 0; i < N; ++i) um[i * 7] = i;
    std::size_t b1 = g_allocs;
    FlatMap fm(2048);
    for (int i = 0; i < N; ++i) fm.insert(i * 7, i);
    std::size_t b2 = g_allocs;
    std::println("해시 표 {}개: unordered_map {}번 할당, 열린 주소법 {}번", N,
                 b1 - b0, b2 - b1);
    std::println("찾기: {} {} / 없는 키 {}", um.at(700), *fm.find(700),
                 fm.find(701) == nullptr);

    // 순서가 상관없으면: 지울 것을 끝 원소와 바꾸고 끝을 뺀다
    std::vector<char> live = {'a', 'b', 'c', 'd', 'e'};
    std::size_t kill = 1;                     // 'b'를 지운다
    live[kill] = live.back();
    live.pop_back();
    std::print("바꿔 빼기 뒤:");
    for (char c : live) std::print(" {}", c);
    std::println();
}
```

```text
vector 1000개: 그냥 11번 할당, reserve하면 1번
해시 표 1000개: unordered_map 1007번 할당, 열린 주소법 2번
찾기: 100 100 / 없는 키 true
바꿔 빼기 뒤: a e c d
```

- **vector**: 하나씩 넣으면 용량이 모자랄 때마다 더 큰 덩어리로 옮겨 1000개에 11번 할당했습니다. 몇 개가 들어갈지 알면 `reserve`로 한 번에 끝납니다. 게임 루프 안에서는 "프레임 중 할당 0번"을 목표로, 크기를 미리 잡아 두거나 [「프레임 할당자와 스택 할당자」](#/read/cpp-game-engine/mem-frame)를 씁니다
- **unordered_map**: 원소 하나마다 노드를 따로 할당해서 1000개에 1007번(libc++ 20에서는 1010번)이었습니다. 표준이 "원소의 주소가 바뀌지 않는다"는 약속을 하기 때문에 생기는 구조입니다(「C++ STL」의 [「unordered_map과 unordered_set」](#/read/cpp-stl/assoc-unordered))
- **열린 주소법**: 키와 값을 큰 배열 두 개에 바로 넣고, 자리가 차 있으면 다음 칸으로 갑니다. 할당은 배열 두 개뿐입니다. 대신 원소의 주소가 고정되지 않고, 지우기가 조금 까다롭습니다(빈칸으로 만들면 뒤에 밀려 들어간 키를 못 찾게 되므로 "지워짐" 표시를 둡니다)

## 찾는 속도

10만 개를 넣고 각 키를 20번씩 찾았습니다.

```cpp norun
#include <chrono>
#include <cstdint>
#include <print>
#include <unordered_map>
#include <algorithm>
#include <random>
#include <vector>

int main()
{
    constexpr std::uint32_t N = 100'000, CAP = 1 << 18;
    std::unordered_map<std::uint32_t, int> um;
    std::vector<std::uint32_t> keys(CAP, 0xFFFFFFFF);
    std::vector<int> vals(CAP);
    auto h = [](std::uint32_t k) { return (k * 2654435761u) & (CAP - 1); };
    for (std::uint32_t i = 0; i < N; ++i) {
        um[i * 7] = int(i);
        auto j = h(i * 7);
        while (keys[j] != 0xFFFFFFFF) j = (j + 1) & (CAP - 1);
        keys[j] = i * 7;
        vals[j] = int(i);
    }
    std::vector<std::uint32_t> order(N);           // 찾는 순서를 섞는다
    for (std::uint32_t i = 0; i < N; ++i) order[i] = i;
    std::ranges::shuffle(order, std::mt19937{42});
    using clk = std::chrono::steady_clock;
    long long s1 = 0, s2 = 0;
    auto t0 = clk::now();
    for (int r = 0; r < 20; ++r)
        for (std::uint32_t i : order) s1 += um.find(i * 7)->second;
    auto t1 = clk::now();
    for (int r = 0; r < 20; ++r)
        for (std::uint32_t i : order) {
            auto j = h(i * 7);
            while (keys[j] != i * 7) j = (j + 1) & (CAP - 1);
            s2 += vals[j];
        }
    auto t2 = clk::now();
    auto ns = [](auto d) {
        return std::chrono::duration<double, std::nano>(d).count() / (20.0 * N);
    };
    std::println("unordered_map {:.1f}ns, 열린 주소법 {:.1f}ns (합 {})",
                 ns(t1 - t0), ns(t2 - t1), s1 == s2);
}
```

```text nocheck
unordered_map 11.5ns, 열린 주소법 3.0ns (합 true)
```

**찾는 순서를 섞었을 때**의 결과입니다(GCC 14, 세 번 모두 비슷, Clang 20 + libc++는 10.5ns 대 3.0ns). 그런데 섞지 않고 넣은 순서대로 찾으면 2.9ns 대 2.2ns로 거의 차이가 없었습니다. 노드들이 넣은 순서대로 메모리에 나란히 할당되어서, 같은 순서로 따라가면 캐시가 잘 맞기 때문입니다. 실제 게임에서는 찾는 순서가 넣은 순서와 상관없는 경우가 대부분이라, 노드를 따라 메모리를 건너뛰는 비용이 그대로 드러납니다. 성능을 잴 때는 **실제와 같은 접근 순서**로 재야 한다는 교훈도 함께 얻었습니다(「C++ 고급」의 [「캐시와 자료 배치」](#/read/cpp-advanced/perf-cache)).

## 순서가 상관없으면 바꿔 빼기

배열 가운데의 원소를 지우면 뒤의 원소를 모두 한 칸씩 당겨야 해서 O(n)입니다. 순서가 중요하지 않다면 **지울 칸에 끝 원소를 옮기고 끝을 빼면** O(1)입니다. 위 예제에서 `b`를 지우자 끝의 `e`가 그 자리로 왔습니다. 총알, 입자, 화면의 적처럼 "모두 훑기만 하고 순서는 상관없는" 목록에 늘 씁니다. 대신 원소의 칸 번호가 바뀌므로, 밖에서 칸 번호를 들고 있으면 안 됩니다. 칸 번호를 들고 있어야 한다면 [「핸들과 세대 인덱스」](#/read/cpp-game-engine/mem-handles)처럼 한 번 거치는 표를 둡니다. 이 둘을 합친 것이 [「아키타입과 희소 집합」](#/read/cpp-game-engine/ecs-storage)의 희소 집합입니다.

## 엔진이 컨테이너를 따로 두는 까닭

| 바람 | 표준 컨테이너 | 엔진 컨테이너가 흔히 하는 것 |
| --- | --- | --- |
| 할당자를 고르고 싶다 | 할당자 타입이 컨테이너 타입에 붙는다(pmr로 일부 해결) | 할당자를 실행 중에 넘긴다 |
| 작으면 할당하지 않기 | 문자열의 SSO 정도 | 원소 몇 개는 안에 품는 작은 벡터 |
| 디버그 빌드도 빨라야 | 디버그 검사로 몇 배 느려진다 | 검사를 따로 켜고 끈다 |
| 해시 표를 빠르게 | 노드 기반 | 열린 주소법(플랫) 해시 표 |

요즘은 표준에도 이런 바람을 일부 받아 주는 것들이 생겼습니다. `std::pmr` 컨테이너(「C++ 고급」의 [「pmr 메모리 자원」](#/read/cpp-advanced/mm-pmr)), C++23의 `std::flat_map`, C++26의 `std::inplace_vector`가 그렇습니다. 엔진을 처음 만든다면 표준 컨테이너로 시작하고, 프로파일러가 가리키는 곳만 바꾸는 순서가 좋습니다.

<Note>
열린 주소법 해시 표를 직접 만들 때는 **해시 함수의 품질**이 중요합니다. 위 예제의 곱셈 해시는 정수 키에 간단히 쓰기 좋지만, 문자열이나 공격자가 고를 수 있는 키(네트워크로 들어온 이름)에는 맞지 않습니다. 실전에서는 검증된 구현(Abseil의 `flat_hash_map`, Boost의 `unordered_flat_map` 등)을 쓰는 경우가 많습니다.
</Note>

## 정리

- 게임에서는 컨테이너의 할당 횟수와 메모리 배치가 중요하며, 크기를 알면 `reserve`로 미리 잡고 프레임 중 할당을 피한다
- `unordered_map`은 원소마다 노드를 할당해 무작위 순서로 찾을 때 느리고, 열린 주소법 해시 표는 배열 두 개로 몇 배 빠르다
- 순서가 상관없는 목록은 바꿔 빼기로 O(1)에 지우고, 엔진 컨테이너는 할당자·작은 크기·디버그 속도·플랫 해시를 위해 따로 둔다
