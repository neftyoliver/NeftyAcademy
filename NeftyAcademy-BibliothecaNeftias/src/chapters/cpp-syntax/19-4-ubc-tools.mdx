export const summary = 'ASan, UBSan, TSan이 잡는 것과 값, 표준 라이브러리의 검사 켜기, 경고 옵션, 정적 분석';

정의되지 않은 동작은 눈으로 찾기 어렵습니다. 다행히 도구가 좋습니다. 컴파일러에 옵션 하나를 더하면 실행 중에 **그 줄에서** 멈춰 알려 줍니다.

## 새니타이저

| 이름과 옵션 | 잡는 것 | 값 |
| --- | --- | --- |
| ASan (AddressSanitizer) `-fsanitize=address` | 범위 밖 읽기·쓰기(힙, 스택, 전역), 해제 뒤 사용, 반환 뒤 사용, 두 번 해제, 메모리 누수 | 시간 약 2배, 메모리 2~3배 |
| UBSan `-fsanitize=undefined` | 부호 있는 정수의 넘침, 잘못된 시프트, 널 포인터 읽기, 정렬 어긋남, 배열 인덱스, 잘못된 `bool`·`enum` 값 | 작다 |
| TSan (ThreadSanitizer) `-fsanitize=thread` | 데이터 경쟁, 잠금 순서 뒤집힘 | 시간 5~15배. ASan과 함께 못 쓴다 |
| MSan (MemorySanitizer) `-fsanitize=memory` | 초기화하지 않은 값 읽기 | Clang 전용. 표준 라이브러리까지 계측해야 한다 |

ASan과 UBSan은 함께 켭니다. **디버그 빌드와 테스트의 기본값**으로 삼습니다.

```sh
g++ -std=c++23 -g -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp
```

`-g`가 있어야 보고에 파일과 줄 번호가 나옵니다. [CMake 프리셋](#/read/cpp-syntax/mod-cmake)에 넣어 두면 잊지 않습니다.

## UBSan이 하는 말

```cpp nocheck
#include <climits>
#include <print>

int main(int argc, char**)
{
    int big = INT_MAX;
    int sum = big + argc;                   // 1. 부호 있는 정수의 넘침

    int shift = 31 + argc;
    int shifted = 1 << shift;               // 2. 폭 이상으로 밀기

    int table[4] = {1, 2, 3, 4};
    int picked = table[3 + argc];           // 3. 배열 범위 밖

    int* null = argc > 5 ? &sum : nullptr;
    int deref = *null;                      // 4. 널 포인터 읽기

    std::println("{} {} {} {}", sum, shifted, picked, deref);
}
```

```text
ub.cpp:7:19: runtime error: signed integer overflow: 2147483647 + 1
             cannot be represented in type 'int'
ub.cpp:10:21: runtime error: shift exponent 32 is too large for 32-bit type 'int'
ub.cpp:13:32: runtime error: index 4 out of bounds for type 'int [4]'
ub.cpp:16:17: runtime error: load of null pointer of type 'int'
```

UBSan은 기본으로는 알리고 **계속 실행합니다.** 테스트에서는 `-fno-sanitize-recover=all`을 더해 첫 오류에서 멈추고 0이 아닌 값으로 끝나게 합니다. 그래야 [`ctest`](#/read/cpp-syntax/mod-cmake)가 실패로 셉니다.

ASan의 보고는 무슨 일인지, 어디서 읽었는지, 그 메모리가 어디서 할당되고 해제되었는지를 세 덩어리의 호출 스택으로 보여 줍니다. 첫 줄의 종류(`heap-use-after-free`, `stack-buffer-overflow`, `stack-use-after-return` 등)와 **내 코드가 나오는 첫 줄**을 봅니다.

## 한계

- **실행된 줄만** 검사한다. 테스트가 지나가지 않는 경로의 버그는 모른다
- [별칭 규칙 위반](#/read/cpp-syntax/ubc-aliasing), [ODR 위반](#/read/cpp-syntax/mod-headers)의 대부분은 잡지 못한다
- 느리고 메모리를 많이 쓴다. 배포하는 빌드에는 넣지 않는다
- ASan으로 빌드한 것과 아닌 것을 섞어 링크하면 놓치는 것이 생긴다

64비트 ARM 리눅스(64비트 라즈베리 파이 OS)는 ASan, UBSan, TSan 모두의 지원 대상입니다. 메모리가 작은 보드에서는 ASan의 메모리 사용이 부담이므로, 로직 테스트는 PC에서 새니타이저와 함께 돌리고 보드에서는 하드웨어에 닿는 부분만 시험하는 구성이 흔합니다. [로직을 라이브러리로 떼어 두는](#/read/cpp-syntax/mod-cmake) 까닭이기도 합니다.

## 표준 라이브러리의 검사

`v[10]`은 범위를 검사하지 않습니다. 매크로 하나로 켤 수 있습니다.

| 옵션 | 효과 | 값 |
| --- | --- | --- |
| `-D_GLIBCXX_ASSERTIONS` | `operator[]`, `front()`, `back()`, `*optional`, 빈 `unique_ptr` 등의 사전 조건을 검사하고 어기면 `abort` | 작다. **배포 빌드에도 켤 만하다** |
| `-D_GLIBCXX_DEBUG` | 위에 더해 [무효가 된 반복자](#/read/cpp-syntax/ubc-invalidation), 정렬되지 않은 범위에 대한 이진 탐색 등 | 크다. 프로그램 전체를 같은 옵션으로 빌드해야 한다 |
| `-D_FORTIFY_SOURCE=3` | `memcpy`, `strcpy`, `snprintf` 등 C 함수의 버퍼 크기 검사 (`-O1` 이상) | 작다 |
| `-fhardened` (GCC 14부터) | 위의 가벼운 것들과 스택 보호 옵션을 한꺼번에 켠다 | 작다 |

```text
$ g++ -std=c++23 -D_GLIBCXX_ASSERTIONS main.cpp && ./a.out
/usr/include/c++/14/bits/stl_vector.h:1130: … operator[](size_type) …:
Assertion '__n < this->size()' failed.
Aborted
```

`std::vector<int> v{1, 2, 3};`의 `v[3]`을 읽는 프로그램입니다. 검사 없이 빌드하면 0을 찍고 정상 종료했습니다. 조용히 틀린 값으로 모터를 돌리는 것보다 그 자리에서 멈추는 편이 낫습니다. C++26은 이런 검사를 표준의 일부로 만듭니다([「C++26」](#/read/cpp-syntax/ver-26)). libc++(Clang)에서는 `-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST`가 같은 역할입니다.

## 경고

[처음에 정한](#/read/cpp-syntax/from-c-compile) `-Wall -Wextra -Wpedantic` 위에, 이 책에서 본 것들을 더합니다.

| 옵션 | 잡는 것 | 본 곳 |
| --- | --- | --- |
| `-Wconversion`, `-Wsign-conversion` | 값을 잃는 암시적 변환 | [암시적 변환](#/read/cpp-syntax/cast-implicit) |
| `-Wshadow` | 안쪽 변수가 바깥 변수를 가린다 | |
| `-Wnon-virtual-dtor` | 가상 함수는 있는데 소멸자가 가상이 아니다 | [가상 소멸자](#/read/cpp-syntax/inh-dtor) |
| `-Woverloaded-virtual` | 자식의 함수가 부모의 가상 함수를 가린다 | [virtual](#/read/cpp-syntax/inh-virtual) |
| `-Wold-style-cast` | C 방식 변환 | [static_cast](#/read/cpp-syntax/cast-static) |
| `-Wnull-dereference`, `-Wduplicated-cond`, `-Wlogical-op` | 널 읽기, 같은 조건의 반복, 수상한 `&&`·`\|\|` | |
| `-Wformat=2` | `printf` 계열의 서식 실수 | |
| `-Werror` | 경고를 오류로 | CI에서만. 컴파일러를 올릴 때 빌드가 깨지지 않게 |

새 프로젝트는 처음부터 모두 켭니다. 경고가 0인 상태를 지키는 것이 요령입니다. 경고가 수백 개 쌓여 있으면 새로 생긴 하나가 보이지 않습니다.

## 정적 분석

실행하지 않고 코드를 읽어 찾는 도구들입니다. 테스트가 지나가지 않는 경로도 봅니다.

| 도구 | 특징 |
| --- | --- |
| clang-tidy | 검사 수백 가지. `bugprone-*`, `cppcoreguidelines-*`, `modernize-*`, `performance-*`. 옛 문법을 새 문법으로 **고쳐 주기도** 한다. `compile_commands.json`을 읽는다 |
| `g++ -fanalyzer` | 함수를 넘나드는 경로 분석. C에 맞춰 만들어져 C++에서는 아직 약하다 |
| cppcheck | 빌드 설정 없이 돌릴 수 있다. 가볍다 |
| Valgrind | 정적 분석이 아니라 실행 도구. **다시 컴파일하지 않고** 메모리 오류를 찾는다. 수십 배 느리다 |

GCC로 빌드하는 프로젝트라도 clang-tidy를 따로 돌릴 수 있습니다. 편집기(clangd)에 물려 두면 쓰는 동안 밑줄로 보여 줍니다.

<Note kind="tip">
권하는 구성: 디버그 프리셋에는 `-fsanitize=address,undefined`와 `-D_GLIBCXX_ASSERTIONS`, 릴리스 프리셋에는 `-O2 -D_GLIBCXX_ASSERTIONS`, 그리고 모든 테스트를 디버그 프리셋으로 한 번 돌리는 것. 여기까지가 한 시간이면 되는 일이고, 이 책에서 본 정의되지 않은 동작의 대부분이 걸러집니다.
</Note>

## 정리

- 디버그 빌드와 테스트는 `-fsanitize=address,undefined`로. 실행된 줄만 검사하므로 테스트가 넓어야 한다
- `-D_GLIBCXX_ASSERTIONS`는 싸다. 표준 라이브러리의 범위 검사를 켠다
- 경고는 넉넉히 켜고 0으로 유지한다. clang-tidy가 그 위를 덮는다
