템플릿은 아무 타입이나 받고, 맞지 않으면 [본문 깊숙한 곳에서](#/read/cpp-syntax/tpl-lookup) 오류가 납니다. C++20의 **제약**(constraint)은 "이 템플릿은 이런 타입만 받는다"를 서명에 적는 방법입니다. 맞지 않는 타입은 본문에 들어가기 전에 걸러집니다.

## 제약으로 오버로드 고르기

```cpp
#include <concepts>
#include <print>
#include <string>

template <std::integral T>
T half(T value) { return value / 2; }               // 정수 타입만

double half(std::floating_point auto value)         // 실수 타입만
{
    return value / 2;
}

template <typename T>
    requires requires(T t) { t.size(); }            // size()가 있는 타입만
auto half(const T& container)
{
    return container.size() / 2;
}

int main()
{
    std::println("{}", half(7));
    std::println("{}", half(7.0));
    std::println("{}", half(std::string("abcdef")));
    // half("text");    // 오류: 셋 가운데 어느 제약도 만족하지 않는다
}
```

```text
3
3.5
3
```

이름이 같은 템플릿 셋이 있고, 인자의 타입이 **만족하는 제약**에 따라 하나가 뽑혔습니다. 제약을 만족하지 않는 템플릿은 후보에서 조용히 빠집니다.

`std::integral`과 `std::floating_point`는 `<concepts>`에 있는 [표준 콘셉트](#/read/cpp-syntax/con-standard)입니다. **콘셉트**는 타입에 대한 조건에 이름을 붙인 것이고, 타입을 넣으면 컴파일할 때 `true`나 `false`가 됩니다.

## 네 가지 적는 법

아래 넷은 뜻이 같습니다.

```cpp nocheck
template <std::integral T>                  // 1. typename 자리에
T twice(T v);

template <typename T>                       // 2. requires 절
    requires std::integral<T>
T twice(T v);

template <typename T>                       // 3. 뒤에 붙는 requires 절
T twice(T v) requires std::integral<T>;

auto twice(std::integral auto v);           // 4. auto 앞에
```

| 꼴 | 맞는 자리 |
| --- | --- |
| 1 | 조건이 콘셉트 하나일 때. 가장 흔하다 |
| 2 | 조건이 여럿이거나(`A<T> && B<T>`) 인자 둘의 관계일 때 |
| 3 | 클래스 템플릿의 멤버 함수 하나에만 조건을 걸 때 |
| 4 | 짧은 함수. `T`라는 이름이 필요 없을 때 |

## requires 식

`requires(T t) { … }`는 "중괄호 안의 것들이 **컴파일되는가**"를 묻는 식입니다. 실행되지 않고 `bool` 상수가 됩니다. 위 예제의 `requires requires`는 앞의 것이 절(조건을 거는 자리), 뒤의 것이 식(조건 그 자체)입니다.

안에 적을 수 있는 요구는 네 가지입니다.

```cpp nocheck
template <typename T>
concept Readable = requires(T dev, int address) {
    dev.open();                                     // 1. 이 식이 컴파일되어야 한다
    typename T::value_type;                         // 2. 이 타입이 있어야 한다
    { dev.read(address) } -> std::convertible_to<int>;  // 3. 결과의 타입까지 본다
    { dev.close() } noexcept;                       //    예외를 던지지 않아야 한다
    requires sizeof(T) <= 64;                       // 4. 이 조건이 참이어야 한다
};
```

| 요구 | 꼴 | 묻는 것 |
| --- | --- | --- |
| 단순 | `식;` | 식이 올바른가 |
| 타입 | `typename 이름;` | 그 타입이 있는가 |
| 복합 | `{ 식 } -> 콘셉트;` | 식이 올바르고, 결과 타입이 콘셉트를 만족하는가 |
| 중첩 | `requires 조건;` | 조건이 참인가 |

<Note kind="warn">
`requires` 식 안에 `sizeof(T) <= 64;`라고만 쓰면 "이 식이 컴파일되는가"를 묻게 되어 **늘 참**입니다. 값을 검사하려면 앞에 `requires`를 한 번 더 붙여 중첩 요구로 만들어야 합니다. 가장 흔한 실수입니다.
</Note>

## 오류가 달라진다

`half("text")`의 오류는 이렇게 나옵니다(GCC 14, 첫 후보에 대한 부분만 추림).

```text
error: no matching function for call to 'half(const char [5])'
note: candidate: 'template<class T>  requires  integral<T> T half(T)'
note: constraints not satisfied
  required for the satisfaction of 'integral<T>' [with T = const char*]
note: the expression 'is_integral_v<_Tp> [with _Tp = const char*]'
      evaluated to 'false'
```

본문 속의 엉뚱한 줄이 아니라 **부른 자리**에서, **어느 조건이 왜 거짓인지**가 나옵니다. 후보가 셋이므로 같은 설명이 세 번 되풀이됩니다. 제약은 문서이기도 합니다. 서명만 읽어도 무엇을 넘겨야 하는지 알 수 있습니다.

## 더 좁은 제약이 이긴다

두 템플릿이 모두 맞을 때, 한쪽의 제약이 다른 쪽의 제약을 **포함하면** 더 좁은 쪽이 뽑힙니다.

```cpp nocheck
void show(std::integral auto v);            // (1)
void show(std::signed_integral auto v);     // (2)

show(3);        // (2): signed_integral은 integral을 포함하므로 더 좁다
show(3u);       // (1): unsigned는 (2)를 만족하지 않는다
```

컴파일러는 콘셉트의 정의를 따라 들어가 `&&`로 이어진 조각들을 견줍니다. 그래서 조건을 콘셉트로 이름 붙여 쌓아 두는 편이 `requires` 절에 식을 길게 늘어놓는 것보다 낫습니다.

## 값에도 건다

제약은 `bool` 상수식이면 무엇이든 됩니다. [타입이 아닌 템플릿 인자](#/read/cpp-syntax/tpl-nontype)의 범위를 거는 데도 씁니다.

```cpp nocheck
template <int Pin>
    requires (Pin >= 0 && Pin <= 27)
struct Led;

Led<17> ok;
Led<40> bad;        // 오류: constraints not satisfied
```

## 정리

- 제약은 템플릿이 받을 타입의 조건. 만족하지 않으면 후보에서 빠지고, 오류는 부른 자리에서 난다
- `template <콘셉트 T>`, `requires` 절, `콘셉트 auto` 가운데 편한 것으로 적는다
- `requires(…) { … }` 식은 "이것이 컴파일되는가"를 묻는다. 값의 조건은 `requires`를 한 번 더 붙인다
