하드웨어와 통신 프로토콜을 다루면 "이 4바이트를 `float`로", "이 구조체를 바이트 열로" 읽어야 할 때가 옵니다. C에서는 포인터 변환이나 `union`으로 했습니다. C++에는 **정의된 방법**이 따로 있습니다.

## 정의된 방법들

```cpp
#include <bit>
#include <cstddef>
#include <cstdint>
#include <print>
#include <span>

struct Header {
    std::uint16_t id;
    std::uint16_t length;
};

int main()
{
    float f = 1.0f;
    auto bits = std::bit_cast<std::uint32_t>(f);        // 비트를 그대로 옮긴다
    std::println("{:#010x}", bits);

    Header h{0x1234, 8};
    auto bytes = std::as_bytes(std::span{&h, 1});       // 객체를 바이트 열로 본다
    for (std::byte b : bytes)
        std::print("{:02x}", std::to_integer<int>(b));
    std::println("");

    std::uint32_t value = 0x11223344;
    std::println("{:#x}", std::byteswap(value));        // 바이트 순서 뒤집기
    std::println("{}", std::endian::native == std::endian::little);

    auto address = reinterpret_cast<std::uintptr_t>(&h);    // 포인터 → 정수
    std::println("{}", address % alignof(Header) == 0);
}
```

```text
0x3f800000
34120800
0x44332211
true
true
```

| 하려는 일 | 도구 | 헤더 |
| --- | --- | --- |
| 같은 크기의 다른 타입으로 비트를 옮긴다 | `std::bit_cast<To>(from)` | `<bit>` (C++20) |
| 객체를 바이트 열로 읽는다 | `std::as_bytes(span)`, `std::as_writable_bytes(span)` | `<span>` |
| 바이트 열을 객체로 만든다 | `std::memcpy(&object, bytes, sizeof object)` | `<cstring>` |
| 바이트 순서를 뒤집는다 | `std::byteswap(v)` | `<bit>` (C++23) |
| 이 기계의 바이트 순서를 안다 | `std::endian::native` | `<bit>` (C++20) |

둘째 줄 `34120800`은 메모리에 `34 12 08 00` 순서로 놓였다는 것, 곧 이 기계가 리틀 엔디언이라는 뜻입니다. 라즈베리 파이와 x86 PC가 모두 그렇습니다. 네트워크 프로토콜은 대개 빅 엔디언이므로 보낼 때 `std::byteswap`으로 뒤집습니다.

## bit_cast

`std::bit_cast<To>(from)`은 `from`의 비트를 `To` 타입의 **새 값**으로 복사합니다.

- 두 타입의 크기가 같아야 하고, 둘 다 [`memcpy`로 복사해도 되는 타입](#/read/cpp-syntax/ct-assert)이어야 한다. 아니면 컴파일 오류
- `constexpr`이다. 컴파일할 때도 쓸 수 있다
- 최적화하면 `memcpy`도 함수 호출도 남지 않고 레지스터 사이의 이동 한 번이 된다

C++20 이전에는 같은 일을 `std::memcpy(&bits, &f, sizeof bits);`로 했습니다. 지금도 정의된 방법이고, 컴파일러가 똑같이 최적화합니다.

## 하면 안 되는 방법

```cpp nocheck
float f = 1.0f;
auto bits = *reinterpret_cast<std::uint32_t*>(&f);  // 정의되지 않은 동작

union { float f; std::uint32_t u; } pun;
pun.f = 1.0f;
auto bits2 = pun.u;         // C에서는 되지만 C++에서는 정의되지 않은 동작
```

첫째는 `float` 객체를 `uint32_t` 포인터로 읽어서 [엄격한 별칭 규칙](#/read/cpp-syntax/ubc-aliasing)을 어깁니다. 컴파일러는 "타입이 다른 두 포인터는 같은 곳을 가리키지 않는다"고 믿고 최적화하므로, `-O2`에서 읽은 값이 틀리게 나올 수 있습니다. 둘째의 `union` 방식은 C99에서는 허용되지만 C++ 표준은 허용하지 않습니다. GCC는 확장으로 받아 주지만 기댈 것은 아닙니다.

## reinterpret_cast

`reinterpret_cast`는 비트를 건드리지 않고 **타입만 바꿔 부르는** 변환입니다. 변환 자체는 되지만, 결과를 **써도 되는 경우**는 좁습니다.

| 쓰임 | 정의되어 있는가 |
| --- | --- |
| 포인터 → `std::uintptr_t` → 같은 타입의 포인터 | 그렇다 |
| 객체 포인터 → `char*`, `unsigned char*`, `std::byte*`로 읽기 | 그렇다. 이 셋은 무엇이든 가리켜도 된다 |
| 정수 주소 → 하드웨어 레지스터 포인터 | 구현이 정한다. 실제로는 다들 이렇게 쓴다 |
| 객체 포인터 → 관계없는 타입의 포인터로 읽고 쓰기 | **아니다** |
| 함수 포인터 → 다른 함수 포인터 → 원래대로 되돌려 부르기 | 그렇다. 되돌리지 않고 부르면 아니다 |

레지스터를 직접 만지는 코드에서 정당하게 쓰입니다.

```cpp nocheck
// /dev/gpiomem을 mmap해서 얻은 주소 base (또는 베어메탈에서의 고정 주소)
auto* gpset0 = reinterpret_cast<volatile std::uint32_t*>(base + 0x1C);
*gpset0 = 1u << 17;         // GPIO 17을 올린다
```

`volatile`은 "이 메모리는 읽고 쓰는 것 자체가 효과를 낸다"는 표시입니다. 컴파일러가 읽기나 쓰기를 합치거나 없애지 못하게 합니다. 이런 줄은 프로그램 전체에서 **한두 곳**에 모아 두고, 나머지 코드는 그 위에 얹은 타입 있는 함수를 쓰게 합니다.

## 바이트에서 구조체로

받은 패킷을 구조체로 읽을 때 흔히 `reinterpret_cast<const Header*>(buffer)`를 씁니다. 두 가지가 문제입니다.

| 문제 | 내용 |
| --- | --- |
| 정렬 | `buffer + 3` 같은 주소는 `Header`의 [정렬](#/read/cpp-syntax/life-alignment)에 맞지 않을 수 있다. ARM에서는 느려지거나 죽는다 |
| 별칭 | 그 자리에 `Header` 객체가 만들어진 적이 없다 |

`memcpy`로 지역 변수에 복사하는 것이 둘 다를 피하는 길입니다. 비용은 없습니다.

```cpp nocheck
Header read_header(std::span<const std::byte> buffer)
{
    Header h;
    std::memcpy(&h, buffer.data(), sizeof h);       // 정렬도 별칭도 문제없다
    return h;
}
```

<Note>
`std::byte`(`<cstddef>`)는 "글자도 숫자도 아닌 그냥 바이트"를 나타내는 타입입니다. 산술 연산이 없고 비트 연산만 됩니다. 숫자로 꺼내려면 `std::to_integer<int>(b)`를 씁니다. 날것의 메모리를 다루는 인터페이스에서 `char*`나 `unsigned char*` 대신 씁니다.
</Note>

## 정리

- 비트를 다른 타입으로 읽을 때는 `std::bit_cast`. 포인터를 바꿔 읽거나 `union`으로 읽지 않는다
- 객체를 바이트로 볼 때는 `std::as_bytes`, 바이트를 객체로 만들 때는 `memcpy`
- `reinterpret_cast`는 레지스터 주소 같은 좁은 자리에만, 한곳에 모아서
