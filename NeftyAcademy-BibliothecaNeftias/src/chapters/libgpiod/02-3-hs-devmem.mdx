sysfs가 느리던 시절에 라즈베리파이에서 널리 쓰인 라이브러리들은 커널을 건너뛰었습니다. SoC의 GPIO 레지스터를 프로그램의 메모리에 붙여 놓고 직접 읽고 썼습니다. WiringPi, pigpio, RPi.GPIO가 그렇게 만들어졌습니다. 빨랐지만 커널이 해 주던 것을 모두 내려놓았고, 5에서는 그 방식이 통하지 않게 되었습니다. 옛 프로젝트를 옮기려면 그 라이브러리들이 무엇을 하고 있었는지를 알아야 합니다.

## 어떻게 하는가

- **`/dev/mem`**: 컴퓨터의 물리 메모리 전체를 파일로 보여 주는 장치입니다. 주변 장치의 레지스터도 그 안에 있습니다. 무엇이든 고칠 수 있으므로 root만 엽니다
- **`/dev/gpiomem`**: 라즈베리파이의 커널이 2015년에 더한 장치로, GPIO 레지스터의 묶음만 보여 줍니다. `gpio` 그룹이면 root가 아니어도 엽니다
- **`mmap`**: 그 파일의 한 구간을 프로그램의 주소에 붙입니다. 그 뒤로는 메모리에 쓰는 것이 곧 핀을 움직이는 것입니다. 시스템 호출이 끼지 않습니다

아래 예제는 그 라이브러리들이 GPIO 17을 출력으로 바꾸고 HIGH로 올릴 때 하는 계산을, 진짜 레지스터 대신 배열을 놓고 따라 합니다.

```c
// 레지스터를 직접 만지는 라이브러리가 하는 일을 가짜 레지스터 묶음으로 따라 해 본다
#include <stdint.h>
#include <stdio.h>

// BCM2835 계열의 GPIO 레지스터가 묶음 안에서 놓인 자리
enum { GPFSEL0 = 0x00, GPSET0 = 0x1c, GPCLR0 = 0x28, GPLEV0 = 0x34 };

static uint32_t block[41];                   // 진짜라면 mmap으로 얻은 주소다

// 핀의 기능을 고른다: 레지스터 하나에 핀 열 개, 핀마다 세 비트 (000 입력, 001 출력)
static void select_function(int gpio, uint32_t function) {
    int reg = GPFSEL0 + gpio / 10 * 4;
    int shift = gpio % 10 * 3;
    uint32_t value = block[reg / 4];
    value &= ~(UINT32_C(7) << shift);        // 이웃 핀의 비트는 건드리지 않는다
    value |= function << shift;
    block[reg / 4] = value;
    printf("GPFSEL%d(+0x%02x)의 %d~%d번 비트 = %u, 레지스터 전체는 0x%08x\n",
           gpio / 10, (unsigned)reg, shift, shift + 2, (unsigned)function,
           (unsigned)value);
}

// 출력을 올린다: 올릴 핀의 비트만 1로 쓴다
static void set_high(int gpio) {
    block[GPSET0 / 4] = UINT32_C(1) << gpio;
    printf("GPSET0(+0x%02x)에 쓰는 값: 0x%08x\n", (unsigned)GPSET0,
           (unsigned)block[GPSET0 / 4]);
}

int main(void) {
    select_function(17, 1);
    set_high(17);

    // 이 묶음이 메모리의 어디에 있는지는 SoC마다 다르다
    struct {
        const char* board;
        uint32_t peripherals;
    } const boards[] = {
        {"1, Zero", 0x20000000}, {"2, 3, Zero 2 W", 0x3f000000}, {"4", 0xfe000000},
    };
    printf("레지스터 묶음의 물리 주소\n");
    for (size_t i = 0; i < sizeof boards / sizeof boards[0]; ++i)
        printf("  0x%08x  %s\n", (unsigned)(boards[i].peripherals + 0x200000),
               boards[i].board);
}
```

```text
GPFSEL1(+0x04)의 21~23번 비트 = 1, 레지스터 전체는 0x00200000
GPSET0(+0x1c)에 쓰는 값: 0x00020000
레지스터 묶음의 물리 주소
  0x20200000  1, Zero
  0x3f200000  2, 3, Zero 2 W
  0xfe200000  4
```

- **기능은 세 비트씩**: 레지스터 하나가 핀 열 개의 기능을 담고, 000이 입력이고 001이 출력입니다. 이웃 핀의 비트를 지키려면 읽어서 고친 다음 다시 써야 합니다. 두 프로그램이 같은 때에 이렇게 하면 한쪽이 고친 것이 지워질 수 있습니다
- **값은 비트 하나**: 올리는 레지스터와 내리는 레지스터가 따로 있고, 1을 쓴 비트의 핀만 바뀝니다
- **주소는 SoC마다 다르다**: 같은 묶음이 보드에 따라 세 군데에 있습니다. 라이브러리는 어떤 보드인지 알아낸 다음 주소를 골라야 했고, 새 보드가 나올 때마다 고쳐야 했습니다
- **5에는 이 묶음이 없다**: 5의 헤더는 RP1이 맡고, RP1의 레지스터는 생김새가 다릅니다. 위의 계산이 통째로 맞지 않습니다([「라즈베리파이 5에서 깨진 것들」](#/read/libgpiod/hs-pi5))

## 빠른 대신 잃는 것

- **임자가 없다**: 커널은 누가 어느 핀을 움직이는지 모릅니다. 요청도 `EBUSY`도 없고, `gpioinfo`에도 쓰는 중이라고 나오지 않습니다. 커널의 드라이버가 I2C나 SPI로 쓰고 있는 핀을 바꿔 버려도 막는 것이 없습니다
- **기다리지 못한다**: 메모리를 읽는 것으로는 핀이 바뀌는 순간에 깨어날 수 없습니다. 계속 읽거나 다른 길을 빌려야 합니다. RPi.GPIO의 문제 보고에는 이 모듈이 sysfs의 파일을 여는 흔적이 보입니다
- **권한이 통째다**: `/dev/gpiomem`을 열 수 있으면 모든 핀의 레지스터를 고칠 수 있습니다. 줄 하나만 맡기는 길이 없습니다
- **칩에 묶인다**: 브로드컴의 그 레지스터에 맞춘 코드라서 다른 보드에서는 돌지 않습니다

## 세 라이브러리의 지금

| 라이브러리 | 어떤 것인가 | 5에서 |
| --- | --- | --- |
| WiringPi | 2013년쯤 시작한 C 라이브러리. 만든 이가 손을 뗀 뒤 다른 모임이 이어받았다 | 된다. 5를 지원하도록 고쳤다 |
| pigpio | DMA로 시각을 맞추는 C 라이브러리. GPIO 0~27을 초당 100만 번까지 읽는다 | 아직 안 된다 |
| RPi.GPIO | 파이썬 모듈 | 안 된다 |

- **백서의 권고**: 라즈베리파이의 GPIO 백서는 pigpio를 새 프로젝트에 권하지 않고, GPIO를 다루는 길로 libgpiod를 권합니다
- **RPi.GPIO를 쓰던 코드**: 같은 API를 흉내 내면서 문자 장치 위에서 도는 rpi-lgpio가 있습니다
- **lgpio**: pigpio를 만든 이가 문자 장치를 쓰도록 새로 만든 라이브러리입니다. 백서는 pigpio보다 느리지만 모든 모델에서 될 것이라고 적습니다

## 옮겨 갈 곳

| 하던 일 | 지금의 길 |
| --- | --- |
| 핀을 켜고 끄고 읽기, 변화 기다리기 | libgpiod. 이 책입니다 |
| 밝기 조절과 서보 | 커널의 PWM. 이 서가의 「PWM」 |
| I2C, SPI, 시리얼을 핀으로 흉내 내기 | 커널의 버스 드라이버. 이 서가의 「I2C」, 「SPI」, 「시리얼 통신」 |
| 파이썬 | gpiozero와 lgpio, 또는 libgpiod의 바인딩([「파이썬 바인딩」](#/read/libgpiod/bn-python)) |

- **속도는 내준다**: 문자 장치는 값을 한 번 쓸 때마다 커널을 거칩니다. 백서도 레지스터를 직접 만지는 쪽이 빠르다고 적습니다. 얼마나 차이 나고 그것이 문제가 되는 일이 무엇인지는 [「사용자 공간에서 얼마나 정확한가」](#/read/libgpiod/tm-jitter)에서 봅니다
- **고장을 찾을 때는 남아 있다**: `pinctrl`은 지금도 레지스터를 직접 들여다봅니다. 백서는 이것을 개발할 때의 도구로만 쓰라고 적습니다([「pinctrl」](#/read/libgpiod/tl-pinctrl))

<Note>
라이브러리들의 사정과 권고는 라즈베리파이의 GPIO 백서(2025년 8월 판)에서 옮겼습니다. 레지스터의 자리는 리눅스 커널의 BCM2835 핀 드라이버에 적힌 값이고, 묶음의 주소는 보드별 주변 장치 주소에 0x200000을 더한 것입니다. `/dev/gpiomem`이 생긴 때는 RPi.GPIO의 문제 보고 115에서 봤습니다. 예제는 배열에 쓰기만 하고 진짜 레지스터는 건드리지 않습니다. x86-64와 aarch64에서 같은 출력을 냈습니다.
</Note>

## 정리

- 옛 라이브러리들은 `/dev/mem`이나 `/dev/gpiomem`을 `mmap`해서 SoC의 GPIO 레지스터를 직접 읽고 썼다
- 그 방식은 빠르지만 임자도 이벤트도 없고 칩에 묶여 있으며, RP1이 핀을 맡은 5에서는 통하지 않는다
- 핀은 libgpiod로, 파형과 버스는 커널의 PWM과 버스 드라이버로 옮긴다
