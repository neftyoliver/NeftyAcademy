5는 헤더의 핀을 SoC가 아니라 RP1이라는 다른 칩에 맡겼습니다. 그 결정 하나로 GPIO를 다루던 옛 길 셋이 한꺼번에 흔들렸습니다. 레지스터를 직접 만지던 라이브러리는 돌지 않게 됐고, sysfs의 번호는 믿을 수 없게 됐고, 문자 장치를 쓰던 프로그램도 칩의 번호 때문에 엉뚱한 칩을 열었습니다. 무엇이 왜 깨졌는지를 보면 어떤 코드가 오래 가는지가 보입니다. RP1이 어떤 칩인지는 「라즈베리파이 시작하기」의 [「라즈베리파이 5의 RP1」](#/read/sbc-start/hdr-rp1)에서 봤습니다.

## 깨진 길 셋

| 길 | 5에서 벌어진 일 | 까닭 |
| --- | --- | --- |
| 레지스터를 직접 만지기 | RPi.GPIO와 pigpio가 돌지 않는다 | GPIO의 레지스터가 RP1에 있고 생김새가 다르다 |
| sysfs의 번호 | 옛 번호를 믿을 수 없다 | 번호가 칩의 `base`에 달려 있고, 칩부터 다르다 |
| 문자 장치와 칩 번호 | `/dev/gpiochip0`이 헤더의 칩이 아니었다 | RP1의 칩이 다섯째여서 `gpiochip4`가 됐다 |

앞의 둘은 [「/dev/mem으로 레지스터를 만지던 라이브러리들」](#/read/libgpiod/hs-devmem)과 [「sysfs 방식과 그것이 사라진 이유」](#/read/libgpiod/hs-sysfs)에서 본 약점이 그대로 드러난 것입니다. 셋째는 libgpiod를 쓰는 코드에도 닿는 일이라 자세히 봅니다.

## 칩 번호의 소동

5가 처음 나왔을 때 `gpiodetect`는 이렇게 답했습니다.

```text
gpiochip0 [gpio-brcmstb@107d508500] (32 lines)
gpiochip1 [gpio-brcmstb@107d508520] (4 lines)
gpiochip2 [gpio-brcmstb@107d517c00] (17 lines)
gpiochip3 [gpio-brcmstb@107d517c20] (6 lines)
gpiochip4 [pinctrl-rp1] (54 lines)
```

- **앞의 넷은 SoC의 것**: 보드 안에서 쓰는 줄들입니다. 헤더의 핀은 다섯째인 `pinctrl-rp1`에 있습니다
- **4용 코드가 엉뚱한 칩을 열었다**: `/dev/gpiochip0`의 17번 줄을 요청하는 코드는 5에서 SoC의 첫 칩에 있는 17번 줄을 달라고 한 셈이 됩니다. 요청이 통하면 오류 없이 엉뚱한 줄이 움직이고, 헤더의 LED는 켜지지 않습니다
- **모든 모델을 받치는 라이브러리**: 보드가 5인지부터 알아낸 다음 칩을 골라야 했습니다

2024년 7월에 라즈베리파이는 커널과 디바이스 트리를 고쳐 번호를 바꿨습니다.

```text
gpiochip0 [pinctrl-rp1] (54 lines)
gpiochip10 [gpio-brcmstb@107d508500] (32 lines)
gpiochip11 [gpio-brcmstb@107d508520] (4 lines)
gpiochip12 [gpio-brcmstb@107d517c00] (17 lines)
gpiochip13 [gpio-brcmstb@107d517c20] (6 lines)
```

- **헤더의 칩이 0번이 됐다**: OS를 그 뒤의 것으로 올린 5에서는 다른 모델처럼 `/dev/gpiochip0`이 헤더입니다
- **SoC의 칩은 10번부터**: 고친 이는 까닭을 둘 들었습니다. 보드 안의 자원이라는 것이 번호에서 드러나고, `gpiochip4`가 비어서 5용으로 4번을 적어 둔 옛 코드가 엉뚱한 칩을 조용히 건드리지 않게 됩니다
- **그 사이에 나온 글**: 5용으로 `gpiochip4`를 적은 글과 코드가 남아 있습니다. 0으로 바꿔 읽습니다
- **4번이 남아 있을 수도 있다**: 그 변경을 다룬 글의 댓글에는 옛 코드를 위해 `gpiochip4`라는 이름을 `gpiochip0`으로 이어 주는 udev 규칙이 들어왔다는 말이 있습니다. 댓글은 그 때문에 `gpiodetect`에 같은 칩이 두 번 나온다고도 적었는데, libgpiod 2.2.4의 도구는 목록을 만들 때 심볼릭 링크를 건너뜁니다. 내 보드에서는 `ls -l /dev/gpiochip*`로 봅니다

## 번호를 믿지 않는 코드

칩의 정보에는 드라이버가 붙인 이름표가 있고, 이름표는 번호가 바뀌어도 그대로입니다. 아래 예제는 칩을 차례로 열어 이름표가 `pinctrl-`로 시작하는 것을 고릅니다. 번호를 바꾸기 전의 5로 돌린 결과입니다.

```c gpiosim board=pi5-old
// 헤더를 맡은 칩을 번호가 아니라 이름표로 찾는다
#include <gpiod.h>
#include <stdio.h>
#include <string.h>

// 이름표가 pinctrl-로 시작하는 칩을 찾아 연다. 없으면 nullptr
static struct gpiod_chip* open_header_chip(void) {
    for (int n = 0; n < 16; ++n) {
        char path[32];
        snprintf(path, sizeof path, "/dev/gpiochip%d", n);
        if (!gpiod_is_gpiochip_device(path)) continue;
        struct gpiod_chip* chip = gpiod_chip_open(path);
        if (!chip) continue;
        struct gpiod_chip_info* info = gpiod_chip_get_info(chip);
        const char* label = info ? gpiod_chip_info_get_label(info) : "";
        bool found = strncmp(label, "pinctrl-", 8) == 0;
        printf("  %s [%s]%s\n", path, label, found ? " ← 헤더의 칩" : "");
        gpiod_chip_info_free(info);
        if (found) return chip;
        gpiod_chip_close(chip);
    }
    return nullptr;
}

int main(void) {
    printf("칩을 차례로 열어 이름표를 본다\n");
    struct gpiod_chip* chip = open_header_chip();
    if (!chip) {
        fprintf(stderr, "헤더의 칩을 찾지 못했다\n");
        return 1;
    }
    int offset = gpiod_chip_get_line_offset_from_name(chip, "GPIO17");
    printf("연 칩은 %s, 이름이 GPIO17인 줄은 %d번\n", gpiod_chip_get_path(chip),
           offset);
    gpiod_chip_close(chip);
}
```

```text
칩을 차례로 열어 이름표를 본다
  /dev/gpiochip0 [gpio-brcmstb@107d508500]
  /dev/gpiochip1 [gpio-brcmstb@107d508520]
  /dev/gpiochip2 [gpio-brcmstb@107d517c00]
  /dev/gpiochip3 [gpio-brcmstb@107d517c20]
  /dev/gpiochip4 [pinctrl-rp1] ← 헤더의 칩
연 칩은 /dev/gpiochip4, 이름이 GPIO17인 줄은 17번
```

- **지금의 5와 4에서는**: 첫 칩에서 바로 찾습니다. 지금의 5는 `/dev/gpiochip0 [pinctrl-rp1]`, 4는 `/dev/gpiochip0 [pinctrl-bcm2711]`입니다
- **찾은 다음은 같다**: 어느 칩이 헤더인지만 가려내면 오프셋은 세 경우 모두 17입니다
- **`pinctrl-`로 가린 것**: 4와 5의 이름표가 둘 다 이 말로 시작한다는 데 기댄 이 책의 간단한 기준입니다. 다른 보드까지 받치려면 이름표를 통째로 견줍니다
- **라이브러리들도 이렇게 고쳤다**: `gpiochip4`를 박아 두었던 rpi-lgpio는 이름표를 보도록 바뀌었습니다
- **`gpiod_is_gpiochip_device`**: 그 경로가 GPIO 칩의 장치 파일인지 알려 줍니다. 없는 번호를 건너뛰는 데 썼습니다([「칩 열기」](#/read/libgpiod/ch-open))
- **언제 이렇게까지 하나**: 내 보드 하나에서만 돌 프로그램이면 `/dev/gpiochip0`을 상수로 두는 것으로 충분합니다. 남에게 건네거나 여러 보드에서 돌릴 코드에 이 방법을 씁니다

## 그 밖에 달라진 것

- **줄의 이름**: 5의 헤더는 `GPIO2`부터 `GPIO27`까지 번호로 불립니다. 4와 다릅니다([「핀 번호: 헤더, BCM, 줄 오프셋」](#/read/libgpiod/gp-numbering))
- **버스의 이름과 번호**: UART의 장치 이름, PWM의 채널 번호, 오버레이의 이름이 4와 다릅니다. 「라즈베리파이 시작하기」의 표에 있습니다
- **들여다보는 도구**: `raspi-gpio`의 자리를 `pinctrl`이 이어받았습니다([「pinctrl」](#/read/libgpiod/tl-pinctrl))

## 살아남은 것

- **커널을 거친 코드**: 문자 장치로 칩과 오프셋을 적은 프로그램은 칩의 경로만 고치면 됐습니다. 핀의 자리도 3.3V 논리도 그대로였습니다
- **남는 교훈**: 주소와 번호를 코드에 박아 넣은 것이 깨졌고, 커널이 내주는 이름을 물어서 쓴 것이 남았습니다

<Note>
두 번의 `gpiodetect` 출력과 2024년 7월이라는 때는 라즈베리파이의 GPIO 백서에서, 번호를 10부터로 한 까닭과 rpi-lgpio가 바뀐 일, udev 규칙에 대한 말은 그 변경을 담은 저장소의 글(raspberrypi/linux 6144)에서 옮겼습니다. udev 규칙은 댓글에 나온 말일 뿐 직접 확인하지 못했습니다. 예제는 흉내 칩에 백서의 칩 목록을 넣어 돌린 것이고, SoC 쪽 네 칩의 줄에 무엇이 달렸는지는 흉내 내지 않았습니다. 진짜 5에서 돌려 보지는 못했습니다.
</Note>

## 정리

- 5는 헤더를 RP1에 맡겨서, 레지스터를 직접 만지던 라이브러리와 sysfs의 번호와 칩 번호를 박아 둔 코드가 깨졌다
- 헤더의 칩은 처음에 `gpiochip4`였다가 2024년 7월부터 `gpiochip0`이고, SoC의 칩들은 10번부터다
- 번호를 믿지 못할 자리에서는 칩을 차례로 열어 이름표로 고른다. 오프셋은 보드가 달라도 같다
