아무리 조심해서 써도 프로그램에는 구멍이 남습니다. [「의도하지 않은 코드 실행」](#/read/c-mid/hack-code-exec)과 [「다른 프로그램을 띄우기」](#/read/c-mid/hack-launch)에서 본 실수들은 수십 년 된 큰 프로젝트에서도 해마다 새로 발견됩니다. 그래서 보안의 절반은 **나중에 발견된 구멍을 빨리, 빠짐없이 메우는 것**입니다. 이 쪽은 그 일이 어떻게 돌아가는지 봅니다.

## 구멍이 알려지는 길

누군가 구멍을 찾으면 보통 이런 순서를 밟습니다.

1. 찾은 사람이 만든 쪽에 몰래 알린다(책임 있는 공개)
2. 만든 쪽이 고친 버전을 준비하는 동안 구멍은 비밀로 한다
3. 고친 버전과 함께 구멍을 공개하고, **CVE 번호**를 붙인다
4. 배포판과 제품 회사들이 고친 버전을 사용자에게 보낸다

CVE(Common Vulnerabilities and Exposures)는 `CVE-2014-0160` 같은 꼴로 구멍마다 붙이는 공통 번호입니다. 같은 구멍을 여러 회사가 서로 다른 이름으로 부르는 혼란을 막습니다. 이 예는 2014년 OpenSSL의 "하트블리드"로, 서버 메모리를 64KB씩 읽어 갈 수 있던 구멍입니다. 길이를 확인하지 않은 `memcpy` 하나가 원인이었습니다.

<Note>
구멍이 공개되는 순간부터 공격자도 그 내용을 압니다. 공개된 지 며칠 만에 그 구멍을 노리는 공격이 퍼지는 일이 흔합니다. 그래서 "업데이트를 미루지 말라"는 말은 잔소리가 아니라, 공개된 구멍이 열린 채로 있는 시간을 줄이라는 뜻입니다.
</Note>

## 한 벌 고쳐서 모두 고치기

[「동적 라이브러리」](#/read/c-mid/lib-dynamic)에서 라이브러리 파일만 바꿔 끼우면 쓰는 프로그램이 다시 빌드 없이 고쳐지는 것을 봤습니다. 보안에서는 이것이 결정적입니다. 이 책의 검사 기계에서 `/usr/bin`의 프로그램 가운데 OpenSSL(`libssl.so`)을 불러오는 것을 세어 보니 **62개**였습니다.

```sh
for f in /usr/bin/*; do
    ldd "$f" 2>/dev/null | grep -q libssl.so && echo "$f"
done | wc -l
```

OpenSSL에 구멍이 나면 `libssl` 패키지 하나만 새로 깔면 62개가 한꺼번에 고쳐집니다. 이 프로그램들이 OpenSSL을 [정적으로](#/read/c-mid/lib-static) 넣었다면, 62개를 모두 다시 빌드해 다시 깔아야 하고 그중 하나라도 빠뜨리면 구멍이 남습니다. 리눅스 배포판이 라이브러리를 될 수 있는 한 동적으로 나눠 쓰게 하는 큰 까닭입니다.

## 배포판의 보안 패치

이 기계의 OpenSSL 버전을 보면 흥미로운 것이 있습니다.

```text nocheck
$ openssl version
OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024)
$ dpkg -l | grep libssl3
ii  libssl3t64:amd64  3.0.13-0ubuntu3.16
```

OpenSSL 자체 버전은 2024년 1월의 3.0.13인데, 우분투 패키지 버전은 `3.0.13-0ubuntu3.16`입니다. 우분투는 안정성을 위해 큰 버전을 올리지 않고, **그 뒤에 나온 보안 고침만 골라 옛 버전에 덧대어** 내보냅니다. 끝의 `ubuntu3.16`이 그렇게 덧댄 횟수를 나타냅니다. 그래서 `openssl version`의 숫자만 보고 "옛날 버전이라 위험하다"고 판단하면 틀릴 수 있습니다. 실제로 어떤 CVE가 고쳐졌는지는 패키지의 변경 기록(`apt changelog libssl3t64`)에 적혀 있습니다.

우분투와 라즈베리파이 OS에서 보안 업데이트를 받는 명령은 [「apt와 저장소」](#/read/basics/apt)에서 본 것 그대로입니다.

```sh
sudo apt update          # 새 목록 받기
sudo apt full-upgrade    # 고친 패키지 깔기
```

우분투는 `unattended-upgrades`라는 프로그램이 보안 업데이트를 매일 자동으로 깝니다. 라이브러리를 새로 깔아도 **이미 실행 중인 프로그램**은 메모리에 옛 라이브러리를 그대로 들고 있으므로, 그 프로그램을 다시 시작하거나 컴퓨터를 재부팅해야 고침이 적용됩니다.

## 작은 기기의 업데이트

PC는 사람이 업데이트를 누르지만, 공장에 붙은 센서나 집 안의 IoT 기기는 아무도 돌보지 않는 경우가 많습니다. 그래서 IoT 기기를 만들 때는 **처음부터 업데이트할 길을 설계에 넣어야** 합니다.

| 고민 | 흔한 답 |
| --- | --- |
| 업데이트 중에 전원이 나가면? | 파티션을 둘 두고(A/B), 안 쓰는 쪽에 새것을 쓴 뒤 다음 부팅에 바꾼다. 실패하면 옛쪽으로 돌아간다 |
| 가짜 업데이트를 받으면? | 업데이트 파일에 만든 회사의 디지털 서명을 붙이고, 기기가 서명을 확인한 뒤에만 깐다 |
| 어떤 기기가 무슨 버전인지? | 기기가 자기 버전을 서버에 알리게 한다 |

이 설계는 소형 기기 서가의 「장치 보안과 업데이트」에서 직접 다룹니다. 서명이 무엇인지는 [「TLS로 암호화하기」](#/read/c-mid/iot-tls)에서 봅니다.

<Note kind="tip">
내 프로그램이 쓰는 라이브러리에 알려진 구멍이 있는지 확인하는 습관을 들이세요. 깃허브의 Dependabot 같은 도구는 저장소가 쓰는 라이브러리 버전을 CVE 목록과 맞춰 보고 알려 줍니다. 직접 만든 C 프로그램이라면 쓰는 라이브러리와 버전을 README에 적어 두는 것만으로도 나중에 큰 도움이 됩니다.
</Note>

## 정리

- 구멍은 배포한 뒤에도 발견되고, 고친 버전과 함께 CVE 번호를 붙여 공개되는 순간부터 공격이 시작될 수 있다
- 동적 라이브러리를 쓰면 라이브러리 한 벌만 고쳐도 그것을 쓰는 프로그램이 모두 고쳐지며, 배포판은 고침만 골라 옛 버전에 덧대어 보낸다
- IoT 기기는 A/B 파티션과 서명 확인처럼 안전하게 업데이트할 길을 처음부터 설계에 넣어야 한다
