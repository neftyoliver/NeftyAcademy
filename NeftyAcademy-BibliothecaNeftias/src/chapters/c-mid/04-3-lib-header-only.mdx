[「정적 라이브러리」](#/read/c-mid/lib-static)와 [「동적 라이브러리」](#/read/c-mid/lib-dynamic)는 미리 컴파일해 두고 링크하는 방식이었습니다. 쓰는 사람은 `-L`, `-l`, 로더의 검색 경로까지 챙겨야 합니다. 그 수고를 아예 없앤 것이 **헤더만 있는 라이브러리**입니다. 파일 하나를 프로젝트에 복사해 `#include`하면 끝입니다. 이미지를 읽는 `stb_image.h`, JSON을 읽는 여러 라이브러리가 이 방식으로 널리 쓰입니다.

## 왜 그냥 헤더에 함수를 넣으면 안 될까

헤더에 함수 정의를 그대로 적으면 문제가 생깁니다. 그 헤더를 `#include`한 `.c` 파일마다 같은 함수의 정의가 하나씩 생기고, 링크할 때 정의가 여럿이라 실패합니다. [「헤더를 포함한 C 파일」](#/read/c-basic/headers)에서 본 대로 `#include`는 글을 그대로 붙여 넣는 것뿐이기 때문입니다. 헤더 라이브러리는 이것을 두 가지 방법으로 피합니다.

## 방법 1: static inline

작은 함수는 `static inline`을 붙여 헤더에 그대로 둡니다.

```c nocheck
static inline int clamp_max(int a, int b)
{
    return a > b ? a : b;
}
```

`static`은 "이 함수는 이 `.c` 파일 안에서만 보인다"는 뜻이라, 파일마다 자기만의 복사본을 가져도 이름이 부딪치지 않습니다. `inline`은 "부르는 자리에 몸체를 펼쳐 넣어도 좋다"는 힌트이고, 펼쳐 넣으면 함수 호출 비용도 사라집니다. 그 대가로 큰 함수를 이렇게 두면 쓰는 파일마다 기계어가 복사되어 프로그램이 커집니다.

## 방법 2: IMPLEMENTATION 매크로

큰 함수는 **선언은 모두에게, 정의는 한 파일에만** 보이게 합니다. stb 라이브러리들이 퍼뜨린 방식입니다.

```c nocheck
// clamp.h — 헤더 하나짜리 라이브러리
// 쓰는 법: 딱 한 .c 파일에서만 #include 앞에 #define CLAMP_IMPLEMENTATION
#ifndef CLAMP_H
#define CLAMP_H

int clamp(int v, int lo, int hi);

static inline int clamp_max(int a, int b)   // 작아서 헤더에 바로 둔다
{
    return a > b ? a : b;
}

#endif

#ifdef CLAMP_IMPLEMENTATION
int clamp(int v, int lo, int hi)
{
    return v < lo ? lo : v > hi ? hi : v;
}
#endif
```

헤더는 두 부분입니다. 위쪽은 보통의 헤더처럼 선언만 있고 [포함 가드](#/read/c-basic/headers)로 한 번만 읽히게 했습니다. 아래쪽 정의는 `CLAMP_IMPLEMENTATION`이 정의돼 있을 때만 컴파일됩니다.

`main.c`

```c nocheck
#include <stdio.h>
#define CLAMP_IMPLEMENTATION
#include "clamp.h"

void report(int v);

int main(void)
{
    printf("%d %d\n", clamp(250, 0, 100), clamp_max(3, 9));
    report(-7);
    return 0;
}
```

`report.c`

```c nocheck
#include <stdio.h>
#include "clamp.h"

void report(int v)
{
    printf("report: %d\n", clamp(v, 0, 10));
}
```

```text nocheck
$ gcc-14 -std=c23 -Wall -Wextra main.c report.c -o app
$ ./app
100 9
report: 0
```

`main.c`만 `CLAMP_IMPLEMENTATION`을 정의했으므로 `clamp`의 정의는 `main.o`에 하나만 생기고, `report.c`는 선언만 보고 그것을 부릅니다. 빌드 명령에 라이브러리 옵션이 하나도 없습니다.

## 정의가 둘이 되는 함정

`report.c`에도 `#define CLAMP_IMPLEMENTATION`을 적으면 이렇게 됩니다.

```text nocheck
report2.c:(.text+0x0): multiple definition of `clamp';
    main.c:(.text+0x17): first defined here
collect2: error: ld returned 1 exit status
```

정의가 두 목적 파일에 하나씩 생겨 링커가 멈췄습니다. 그래서 이런 라이브러리는 보통 정의를 켜는 일만 하는 `.c` 파일을 따로 하나 둡니다.

```c nocheck
// clamp_impl.c — 이 파일 하나에서만 정의를 만든다
#define CLAMP_IMPLEMENTATION
#include "clamp.h"
```

다른 파일들은 모두 `#include "clamp.h"`만 합니다. 이렇게 하면 어느 파일이 정의를 맡는지 헷갈리지 않습니다.

## 장단점

| | 헤더만 있는 라이브러리 |
| --- | --- |
| 좋은 점 | 복사 한 번이면 끝. 빌드 시스템, 컴파일러, OS를 가리지 않는다 |
| 좋은 점 | 컴파일러가 몸체를 보므로 펼쳐 넣기(inline) 최적화가 잘 된다 |
| 나쁜 점 | `#include`하는 곳마다 긴 헤더를 다시 읽어 컴파일이 느려진다 |
| 나쁜 점 | 라이브러리를 고치면 쓰는 파일을 모두 다시 컴파일해야 한다. 동적 라이브러리처럼 바꿔 끼울 수 없다 |

작고 자주 쓰는 도구에는 헤더 라이브러리가, 크고 여러 프로그램이 함께 쓰며 보안 업데이트가 중요한 것(OpenSSL, SQLite의 시스템 판)에는 동적 라이브러리가 잘 맞습니다. 이 책 뒤쪽의 [「자주 쓰이는 C 생태계 라이브러리」](#/read/c-mid/common-libraries)에서 세 방식의 라이브러리를 고루 만납니다.

<Note kind="tip">
SQLite는 소스 전체를 `sqlite3.c` 파일 하나(25만 줄이 넘습니다)로 합친 "합본"(amalgamation)도 배포합니다. 헤더 라이브러리는 아니지만, 파일 하나를 프로젝트에 넣고 함께 컴파일하면 된다는 생각은 같습니다. 이렇게 하면 컴파일러가 라이브러리 전체를 한꺼번에 보고 최적화할 수 있습니다.
</Note>

## 정리

- 헤더만 있는 라이브러리는 파일 하나를 `#include`하면 끝이라 링크 설정이 필요 없다
- 작은 함수는 `static inline`으로 파일마다 복사본을 두고, 큰 함수는 IMPLEMENTATION 매크로를 정의한 한 파일에서만 정의를 만든다
- 정의를 켜는 파일이 둘이 되면 `multiple definition` 링크 오류가 나므로, 정의만 담당하는 `.c` 파일을 따로 두는 것이 안전하다
