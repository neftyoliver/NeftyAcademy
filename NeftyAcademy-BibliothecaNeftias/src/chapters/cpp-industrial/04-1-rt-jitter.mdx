[「실시간이라는 요구」](#/read/cpp-industrial/land-realtime)에서 보통 리눅스의 주기 작업이 가끔 1ms 넘게 늦는 것을 보았습니다. 이 장에서는 그 늦음을 줄입니다. 먼저 늦음이 어디서 오는지 알아야 합니다. 이 쪽에서는 예정 시각과 실제로 코드가 다시 돌기 시작한 시각의 차이를 **지연**(latency), 그 지연이 주기마다 흔들리는 정도를 **지터**라고 부릅니다.

## 깨어나기까지의 사슬

`clock_nanosleep`으로 잠든 스레드가 다시 돌기까지는 여러 단계를 거칩니다. 하드웨어 타이머가 인터럽트를 내고, 커널이 그 스레드를 "실행할 수 있음"으로 바꾸고, 스케줄러가 CPU를 내주고, 그 CPU가 실제로 코드를 실행합니다. 단계마다 늦어질 까닭이 있습니다.

| 원인 | 어떻게 늦어지나 | 대책 |
| --- | --- | --- |
| 타이머 여유 | 보통 스레드의 깨어남을 기본 50µs 안에서 미뤄 다른 깨어남과 묶는다 | 실시간 우선순위 |
| 스케줄러 | 같은 CPU의 다른 스레드가 자기 몫을 쓸 때까지 기다린다 | 실시간 우선순위 |
| 커널의 긴 구간 | 선점할 수 없는 커널 코드나 인터럽트 처리가 끝나야 한다 | PREEMPT_RT |
| CPU 절전 | 깊이 잠든 코어가 깨어나는 데 시간이 든다 | 절전 상태 제한 |
| 메모리 | 처음 만지는 페이지의 폴트, 할당자의 잠금 | 메모리 잠금, 미리 할당 |
| 캐시 | 다른 일이 캐시를 밀어내 코드가 느려진다 | CPU 격리 |

## 네 조건에서 재기

1ms 주기로 5000번 깨어나며 지연을 쟀습니다. 부하는 CPU 수만큼의 스레드가 쉬지 않고 도는 상황입니다. 실시간 커널이 아닌 보통 리눅스(가상 기계, 2코어)에서 관리자 권한으로 잰 값입니다.

```cpp norun
// 1ms 주기로 깨어날 때의 늦음을 네 가지 조건에서 잰다
#include <pthread.h>
#include <sched.h>
#include <sys/prctl.h>
#include <algorithm>
#include <atomic>
#include <cstdio>
#include <ctime>
#include <thread>
#include <vector>

long long ns(const timespec& t) { return t.tv_sec * 1'000'000'000LL + t.tv_nsec; }

void measure(const char* name, bool fifo, bool load, bool slack1) {
    std::atomic<bool> stop{false};
    std::vector<std::thread> hogs;               // CPU를 쉬지 않고 쓰는 다른 일
    if (load)
        for (unsigned i = 0; i < std::thread::hardware_concurrency(); ++i)
            hogs.emplace_back([&] { while (!stop) {} });

    std::vector<long long> late;
    std::thread rt([&] {
        if (fifo) {                              // 실시간 우선순위(루트 권한 필요)
            sched_param p{};
            p.sched_priority = 80;
            pthread_setschedparam(pthread_self(), SCHED_FIFO, &p);
        }
        if (slack1) prctl(PR_SET_TIMERSLACK, 1); // 타이머 여유를 1ns로
        timespec next, now;
        clock_gettime(CLOCK_MONOTONIC, &next);
        for (int i = 0; i < 5000; ++i) {
            next.tv_nsec += 1'000'000;
            if (next.tv_nsec >= 1'000'000'000) {
                next.tv_nsec -= 1'000'000'000;
                ++next.tv_sec;
            }
            clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, nullptr);
            clock_gettime(CLOCK_MONOTONIC, &now);
            late.push_back(ns(now) - ns(next));
        }
    });
    rt.join();
    stop = true;
    for (auto& h : hogs) h.join();
    std::sort(late.begin(), late.end());
    long long sum = 0;
    for (long long v : late) sum += v;
    std::printf("%s\n    평균 %lldµs, 99%% %lldµs, 최대 %lldµs\n", name,
                sum / (long long)late.size() / 1000,
                late[late.size() * 99 / 100] / 1000, late.back() / 1000);
}

int main() {
    measure("보통 스레드", false, false, false);
    measure("보통 스레드, 여유 1ns", false, false, true);
    measure("보통 스레드 + 부하", false, true, false);
    measure("SCHED_FIFO 80 + 부하", true, true, false);
}
```

```text nocheck
보통 스레드
    평균 98µs, 99% 200µs, 최대 2988µs
보통 스레드, 여유 1ns
    평균 40µs, 99% 112µs, 최대 1276µs
보통 스레드 + 부하
    평균 73µs, 99% 124µs, 최대 3995µs
SCHED_FIFO 80 + 부하
    평균 21µs, 99% 48µs, 최대 289µs
```

- **타이머 여유**: 리눅스는 전력을 아끼려고 보통 스레드의 타이머를 조금씩 미뤄 묶습니다. `prctl(PR_SET_TIMERSLACK, 1)`로 여유를 없애자 평균이 60µs쯤 줄었습니다. 실시간 우선순위 스레드에는 이 여유가 적용되지 않습니다
- **부하가 오면 최대가 4ms**: 바쁜 스레드들과 같은 대우를 받는 보통 스레드는 그들이 자기 몫의 시간을 다 쓸 때까지 기다리기도 합니다. 최대 지연이 4ms 가까이 되었습니다. 1ms 주기라면 주기를 네 번 통째로 놓친 것입니다
- **실시간 우선순위**: 같은 부하에서 `SCHED_FIFO` 80을 주자 평균 21µs, 최대 289µs가 되었습니다. 바쁜 스레드가 있어도 이 스레드가 깨어나는 순간 CPU를 빼앗아 옵니다. 다만 최대값은 여전히 수백 마이크로초이고, 돌릴 때마다 꽤 달라집니다. 커널 안의 선점할 수 없는 구간 때문이며, 다음 쪽의 PREEMPT_RT가 이것을 다룹니다
- **쉬는 CPU가 더 늦다**: 부하가 없을 때의 평균(98µs)이 부하가 있을 때(73µs)보다 길었습니다. 아무 일도 없으면 CPU가 절전 상태로 들어가고, 깨어나는 데 시간이 들기 때문으로 보입니다. 실시간 시스템에서 깊은 절전 상태를 막아 두는 까닭입니다

<Note>
가상 기계에서 잰 값은 하이퍼바이저가 가상 CPU를 언제 실제 CPU에 올려 주는지에 따라서도 흔들리므로, 실제 장비의 값으로 생각하면 안 됩니다. 이 쪽에서 볼 것은 숫자 자체보다 조건에 따른 차이입니다. 실제 제어기를 고를 때는 그 하드웨어 위에서 [「측정」](#/read/cpp-industrial/rt-measure)의 방법으로 오래 재야 합니다.
</Note>

## 정리

- 지연은 예정 시각과 코드가 실제로 다시 돈 시각의 차이이며, 타이머, 스케줄러, 커널, 절전, 메모리, 캐시가 단계마다 늦음을 더한다
- 보통 스레드는 타이머 여유와 다른 스레드와의 경쟁 때문에 부하가 오면 수 밀리초까지 늦어진다
- 실시간 우선순위는 평균과 대부분의 지연을 크게 줄이지만, 최악의 값을 묶으려면 커널과 하드웨어까지 다루어야 한다
