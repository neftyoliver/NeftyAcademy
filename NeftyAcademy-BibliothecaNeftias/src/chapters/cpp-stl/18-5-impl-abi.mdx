export const summary = 'ABI가 정하는 것, 이름이 막아 주는 섞임과 못 막는 섞임, GLIBCXX 버전이 맞지 않을 때, 경계를 긋는 법';

소스가 같아도 [구현이 다르면](#/read/cpp-stl/impl-three) `std::string`의 크기가 다릅니다. 프로그램 전체를 한 번에 빌드하면 아무 문제가 없습니다. 문제는 **따로 빌드한 조각들을 붙일 때** 생깁니다. 미리 빌드된 라이브러리, 플러그인, 다른 기계에서 만든 실행 파일이 그렇습니다.

## ABI

| | API | ABI |
| --- | --- | --- |
| 무엇의 약속인가 | 소스 코드 | 기계어로 빌드된 결과 |
| 정하는 것 | 이름, 인자, 반환 타입 | 객체의 크기와 멤버의 자리, 함수 이름의 표기, 인자를 넘기는 방법, 예외와 가상 함수의 구조 |
| 어긋나면 | 컴파일 오류 | 링크 오류이거나, **조용히 틀린 동작** |
| 맞추는 법 | 소스를 고친다 | 같은 설정으로 다시 빌드한다 |

C++ 표준은 ABI를 정하지 않습니다. 컴파일러와 표준 라이브러리가 저마다 정합니다. `std::string`을 받는 함수를 가진 라이브러리와 그것을 부르는 프로그램으로 실제로 어긋나게 해 봅니다.

```cpp nocheck
// lib.h
#include <string>

struct Reading {
    std::string name;
    int value;
};

void greet(const std::string& who);
int name_length(const Reading& r);      // r.name.size() 를 돌려준다
```

## 이름이 막아 주는 섞임

컴파일러는 함수의 이름에 인자의 타입을 섞어 넣습니다(이름 맹글링). `greet`가 목적 파일에 어떤 이름으로 들어가는지 `nm`으로 봤습니다.

| 빌드한 방법 | `greet`의 이름 |
| --- | --- |
| GCC 14, 기본 | `_Z5greetRKNSt7__cxx1112basic_stringIc...EE` |
| GCC 14, `-D_GLIBCXX_USE_CXX11_ABI=0` | `_Z5greetRKSs` |
| Clang 20, `-stdlib=libc++` | `_Z5greetRKNSt3__112basic_stringIc...EE` |

세 가지 `std::string`이 **서로 다른 타입**으로 표기됩니다. libstdc++는 `std::__cxx11::`, libc++는 `std::__1::`이라는 숨은 네임스페이스를 끼워 넣었습니다. 그래서 섞으면 링크 단계에서 걸립니다.

```text nocheck
$ g++ -std=c++23 -D_GLIBCXX_USE_CXX11_ABI=0 -c lib.cpp
$ g++ -std=c++23 main.cpp lib.o
main.cpp:(.text+0x48): undefined reference to
`greet(std::__cxx11::basic_string<char, std::char_traits<char>,
std::allocator<char> > const&)'
```

오류 메시지에 <strong>`__cxx11`이나 `[abi:cxx11]`</strong>이 보이면 이 문제입니다. libstdc++는 2015년(GCC 5)에 C++11의 요구에 맞추려고 `std::string`과 `std::list`의 속을 바꿨고, 옛 것과 새 것을 한 라이브러리에 함께 넣어 두었습니다. `_GLIBCXX_USE_CXX11_ABI`가 그 둘을 고르는 스위치입니다. 오래전에 빌드된 서드파티 라이브러리나, 이 매크로를 0으로 두고 빌드하는 배포 패키지를 붙일 때 만납니다. 고치는 법은 한쪽을 다른 쪽과 같은 설정으로 다시 빌드하는 것뿐입니다.

[디버그 모드](#/read/cpp-stl/impl-debug)도 같은 방식으로 막혀 있습니다. `std::vector`가 `std::__debug::vector`라는 다른 이름이 됩니다.

## 이름이 막아 주지 못하는 섞임

`name_length`는 다릅니다. 인자가 `std::string`이 아니라 **내 구조체** `Reading`입니다.

| 빌드한 방법 | `name_length`의 이름 | `sizeof(Reading)` |
| --- | --- | --- |
| GCC 14 (libstdc++) | `_Z11name_lengthRK7Reading` | 40 |
| Clang 20 (libc++) | `_Z11name_lengthRK7Reading` | 32 |

이름이 같습니다. 구조체의 이름에는 그 안에 무엇이 들었는지가 적히지 않기 때문입니다. 그래서 **링크가 됩니다.** `main`은 libc++로, 라이브러리는 libstdc++로 빌드해 붙이고 돌려 봤습니다.

```text nocheck
$ ./mixed            # name 이 "temperature-of-the-kitchen" (26글자)
main 이 아는 길이 26, 라이브러리가 읽은 길이 26
$ ./mixed            # name 이 "kitchen" (7글자)
main 이 아는 길이 7, 라이브러리가 읽은 길이 0
```

긴 이름에서는 **우연히 맞았습니다.** 두 구현 모두 긴 문자열의 길이를 객체의 8바이트째에 두기 때문입니다. [짧은 이름](#/read/cpp-stl/impl-sso)에서는 libc++가 길이를 첫 바이트에 두므로 라이브러리가 엉뚱한 곳을 읽어 0을 냈습니다. 오류도 경고도 없고, 죽지도 않고, 시험에 쓴 자료의 길이에 따라 맞기도 틀리기도 합니다. ABI가 어긋났을 때 가장 무서운 모습이 이것입니다.

같은 일이 구현을 섞지 않아도 생깁니다. 구조체의 배치를 바꾸는 컴파일 옵션(`-fpack-struct`, `-fshort-enums`)이나 `#pragma pack`, 구조체에 멤버가 하나 추가된 헤더의 새 판을 **한쪽만** 쓰는 경우입니다. 헤더와 라이브러리 파일이 다른 판일 때 생기는 버그가 대개 이것입니다.

## 버전이 맞지 않을 때

같은 libstdc++끼리도 **새 판으로 빌드한 프로그램은 옛 판에서 돌지 않습니다.** 리눅스의 공유 라이브러리는 함수마다 "어느 판부터 있는가"를 달고 있고, 프로그램은 자기가 쓴 것 가운데 가장 새 것을 요구합니다.

```text nocheck
$ g++ -std=c++23 -O2 main.cpp -o app        # std::cout 으로 한 줄 찍는 프로그램
$ objdump -T app | grep -o 'GLIBCXX_[0-9.]*' | sort -uV | tail -1
GLIBCXX_3.4.32
$ LIB=/usr/lib/x86_64-linux-gnu/libstdc++.so.6
$ strings $LIB | grep '^GLIBCXX_3' | sort -V | tail -1
GLIBCXX_3.4.33
```

첫 명령은 이 프로그램이 **요구하는** 판이고, 둘째는 이 기계의 라이브러리가 **가진** 판입니다. 가진 것이 요구보다 낮은 기계로 실행 파일을 옮기면 시작하자마자 `version 'GLIBCXX_3.4.32' not found`라는 말과 함께 끝납니다(이 환경에는 옛 라이브러리가 없어 직접 내 보지는 못한 메시지입니다).

| GCC | libstdc++가 가진 가장 새 판 |
| --- | --- |
| 12 | `GLIBCXX_3.4.30` |
| 13.1, 13.2 | `GLIBCXX_3.4.31`, `GLIBCXX_3.4.32` |
| 14 | `GLIBCXX_3.4.33` |

PC에서 새 컴파일러로 빌드해 보드로 복사하는 흐름에서 흔히 만납니다. 보드의 OS가 한 세대 전이면 라이브러리도 그렇습니다. 길이 셋 있습니다.

| 방법 | 내용 |
| --- | --- |
| 대상에 맞춰 빌드한다 | 보드에서 직접 빌드하거나, 보드와 같은 OS의 컨테이너나 sysroot로 빌드한다. 가장 확실하다 |
| 표준 라이브러리를 실행 파일에 넣는다 | `-static-libstdc++ -static-libgcc`. 위 프로그램에서 `GLIBCXX` 요구가 0개가 됐고, 크기는 118KB에서 1.5MB가 됐다 |
| 통째로 정적 링크한다 | `-static`. C 라이브러리(glibc)의 판까지 맞지 않을 때. 네트워크 이름 풀이처럼 정적 링크에서 제약이 생기는 기능이 있다 |

둘째 방법을 써도 C 라이브러리의 요구(`GLIBC_2.34` 같은 것)는 남습니다. 같은 명령에서 `GLIBCXX`를 `GLIBC`로 바꿔 확인합니다.

## 경계를 긋는 법

따로 빌드되어 따로 배포되는 조각 사이에서는 지킬 것이 정해져 있습니다.

| 원칙 | 까닭 |
| --- | --- |
| 경계의 함수는 [`extern "C"`](#/read/cpp-advanced/iop-c-abi)로, 인자는 정수·포인터·길이·단순한 구조체로 | C의 ABI는 플랫폼마다 하나로 정해져 있고 안정적이다 |
| `std::string`, `std::vector`를 경계 너머로 넘기지 않는다 | 양쪽의 구현, 판, 옵션이 같다는 보장이 없다. `const char*`와 길이로 넘긴다 |
| 할당한 쪽이 해제한다 | 양쪽의 `malloc`이 다른 것일 수 있다. 해제 함수를 함께 내놓는다 |
| 예외가 경계를 넘지 않게 한다 | [넘어가면 안 되는 경계](#/read/cpp-stl/err-exceptions)다. 오류는 반환값으로 |
| 속을 숨긴다 | 구조체를 내놓지 않고 [불투명한 포인터](#/read/cpp-syntax/mod-pimpl)만 준다. 멤버를 늘려도 ABI가 그대로다 |

한 번에 함께 빌드하는 내 프로젝트의 **안쪽**에서는 이럴 필요가 없습니다. 모듈 사이에 `std::string`과 `std::vector`를 마음껏 넘깁니다. 지킬 것은 하나, **모든 조각을 같은 컴파일러, 같은 표준 라이브러리, 같은 옵션으로** 빌드하는 것입니다. CMake의 프리셋으로 옵션을 한곳에 모아 두는 까닭이 이것입니다.

<Note>
ABI는 라이브러리를 만드는 쪽도 묶습니다. `std::string`의 배치를 한 번 정하면, 그것을 쓰는 프로그램이 모두 다시 빌드되지 않는 한 바꿀 수 없습니다. 더 나은 구조가 알려져 있어도 표준 라이브러리의 어떤 부분이 그대로인 까닭이 대개 이것입니다. 무엇이 ABI를 깨고 무엇이 깨지 않는지, 깨지 않으면서 라이브러리를 키워 가는 법은 [「ABI 안정성」](#/read/cpp-advanced/iop-abi-stable)에서 다룹니다.
</Note>

## 정리

- ABI는 빌드된 결과끼리의 약속이다. 객체의 크기와 배치, 함수 이름의 표기가 구현과 옵션마다 다르다
- 표준 타입이 함수의 인자에 직접 있으면 이름이 달라 링크에서 걸린다. 내 구조체 안에 들어 있으면 걸리지 않고, 조용히 틀린 값을 읽는다
- 새 라이브러리로 빌드한 프로그램은 옛 라이브러리에서 돌지 않는다. 대상에 맞춰 빌드하거나 표준 라이브러리를 실행 파일에 넣고, 따로 배포되는 조각의 경계는 C의 꼴로 긋는다
