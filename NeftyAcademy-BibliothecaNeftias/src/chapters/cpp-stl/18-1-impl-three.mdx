표준은 `std::vector`가 **무엇을 해야 하는지**와 얼마나 빨라야 하는지만 정합니다. 속을 어떻게 만들지는 구현의 몫이고, 널리 쓰이는 구현이 셋 있습니다. 이 책의 수치가 "GCC 14에서"라는 단서를 달고 있던 까닭을 이 챕터에서 모아 봅니다.

## 세 구현

| 구현 | 만드는 곳 | 기본으로 쓰이는 곳 |
| --- | --- | --- |
| **libstdc++** | GNU (GCC와 함께) | 리눅스 대부분. 라즈베리 파이 OS, 우분투, 데비안. 리눅스의 Clang도 기본으로 이것을 쓴다 |
| **libc++** | LLVM (Clang과 함께) | macOS와 iOS, 안드로이드 NDK, FreeBSD. 리눅스에서는 `-stdlib=libc++`로 고른다 |
| **MSVC STL** | 마이크로소프트 | 윈도우의 Visual Studio. 윈도우의 Clang(`clang-cl`)도 이것을 쓴다 |

**컴파일러와 표준 라이브러리는 따로**라는 점이 눈에 띕니다. 리눅스에서 Clang으로 빌드해도 라이브러리는 대개 libstdc++입니다. 셋 다 소스가 공개되어 있어서, 궁금한 것은 헤더를 열어 읽을 수 있습니다. 리눅스에서는 `/usr/include/c++/14/` 아래에 있습니다.

내 프로그램이 어느 구현으로 빌드되는지는 매크로로 압니다.

```cpp
#include <print>
#include <version>

int main()
{
#if defined(_LIBCPP_VERSION)
    std::println("libc++ {}", _LIBCPP_VERSION);
#elif defined(__GLIBCXX__)
    std::println("libstdc++ {} (날짜 {})", _GLIBCXX_RELEASE, __GLIBCXX__);
#elif defined(_MSVC_STL_VERSION)
    std::println("MSVC STL {}", _MSVC_STL_VERSION);
#endif

    // 기능 하나하나는 기능 시험 매크로로 묻는다
#ifdef __cpp_lib_mdspan
    std::println("mdspan 있음 {}", __cpp_lib_mdspan);
#else
    std::println("mdspan 없음");
#endif
#ifdef __cpp_lib_generator
    std::println("generator 있음 {}", __cpp_lib_generator);
#else
    std::println("generator 없음");
#endif
}
```

```text
libstdc++ 14 (날짜 20240908)
mdspan 없음
generator 있음 202207
```

날짜는 설치된 판에 따라 다릅니다. `<version>` 헤더(C++20)가 이 매크로들을 모아 줍니다. "GCC 버전이 14 이상이면"처럼 컴파일러 버전으로 가르지 말고 **`__cpp_lib_...` 매크로로 기능을 직접** 묻습니다. 같은 GCC라도 리눅스 배포판마다 라이브러리 버전이 다를 수 있고, Clang은 어느 라이브러리와도 짝지어질 수 있기 때문입니다.

## 같은 코드, 다른 속

같은 프로그램을 GCC 14의 libstdc++와 Clang 20의 libc++로 빌드해 재어 본 것입니다(둘 다 x86-64 리눅스).

| 재어 본 것 | libstdc++ 14 | libc++ 20 |
| --- | --- | --- |
| `sizeof(std::string)` | 32 | 24 |
| 힙 없이 담기는 글자 수 | 15 | 22 |
| `string`이 자라는 용량 | 15, 30, 60, 120 | 22, 47, 95, 191 |
| `sizeof(std::deque<int>)` | 80 | 48 |
| 빈 `deque`를 만들 때의 할당 | 2번 (576바이트) | 0번 |
| `deque<int>`의 블록 하나 | 512바이트 | 4,096바이트 |
| `sizeof(std::map<int, int>)` | 48 | 24 |
| `unordered_map<int, int>`의 노드 | 16바이트 | 24바이트 |
| 버킷 수가 느는 순서 | 1, 13, 29, 59, 127 | 0, 2, 5, 11, 23, 47 |
| `sizeof(std::function<void()>)` | 32 | 48 |
| `function`이 힙 없이 담는 캡처 | 16바이트까지 | 24바이트도 담긴다 |
| `sizeof(std::any)` | 16 | 32 |
| `sizeof(std::shared_mutex)` | 56 | 144 |
| `make_shared<int>`의 할당 크기 | 24바이트 | 32바이트 |

같은 것도 많습니다. `vector`는 양쪽 모두 포인터 셋(24바이트)이고 용량이 두 배씩 늡니다. `list<int>`와 `map<int, int>`의 노드는 24바이트와 40바이트로 같았습니다. `unique_ptr`는 8, `shared_ptr`는 16, `mutex`는 40바이트입니다.

MSVC STL은 이 책을 쓰는 환경에서 돌려 보지 못했습니다. 문서와 공개된 소스로 알려진 차이만 적어 둡니다. `vector`가 두 배가 아니라 **1.5배**씩 자라고, `deque`의 블록이 아주 작아(원소가 8바이트를 넘으면 블록에 원소 하나) `deque`가 사실상 연결 리스트처럼 됩니다. 윈도우에서도 돌아야 하는 코드는 그쪽에서 직접 재어 봅니다.

이 표에서 가져갈 것은 숫자가 아니라 **무엇이 정해져 있지 않은가**입니다.

- 객체의 크기와 배치. 구조체에 `std::string`을 넣으면 그 구조체의 크기도 구현을 따릅니다
- 언제, 몇 번, 얼마나 할당하는가. "15글자까지는 할당이 없다"에 기대는 코드는 다른 구현에서 다르게 돕니다
- 자라는 비율과 버킷 수. 재할당이 일어나는 시점이 달라집니다
- [순서 없는 컨테이너를 도는 순서](#/read/cpp-stl/assoc-unordered), [난수 분포가 내는 값](#/read/cpp-stl/num-random), `what()`의 글, 해시 값

## 있는 기능과 없는 기능

새 표준의 기능이 들어오는 순서도 구현마다 다릅니다. 기능 시험 매크로가 정의되어 있는지를 두 구현에서 찍어 본 것입니다.

| 기능 | GCC 14 | Clang 20 + libc++ 20 |
| --- | --- | --- |
| `std::print`, `std::expected`, `std::ranges::to`, `std::jthread` | 있다 | 있다 |
| [`<mdspan>`](#/read/cpp-stl/num-linalg), [`<flat_map>`](#/read/cpp-stl/assoc-flat) | 없다 | 있다 |
| 레인지 서식(`{}`에 `vector` 넣기), `std::from_range` | 없다 | 있다 |
| `std::ranges::starts_with`, `ends_with` | 없다 | 있다 |
| [`<generator>`](#/read/cpp-advanced/co-generator), [`<stacktrace>`](#/read/cpp-stl/err-location), [`<spanstream>`](#/read/cpp-stl/io-string) | 있다 | 없다 |
| `std::move_only_function`, `views::zip`, `views::chunk` | 있다 | 없다 |
| [병렬 알고리즘](#/read/cpp-stl/alg-parallel), [특수 수학 함수](#/read/cpp-stl/num-numbers) | 있다 | 없다 |
| `<flat_set>`, `<inplace_vector>`, `<linalg>` | 없다 | 없다 |

어느 쪽이 앞서 있다고 말하기 어렵습니다. 서로 다른 것부터 만들었을 뿐입니다. 두 구현에서 다 돌아야 하는 코드는 **양쪽에 다 있는 것만** 쓰거나, 매크로로 갈라 한쪽에는 직접 만든 대용품을 둡니다.

```cpp nocheck
#include <version>

#ifdef __cpp_lib_flat_map
#include <flat_map>
template <typename K, typename V>
using SmallMap = std::flat_map<K, V>;
#else
#include <map>
template <typename K, typename V>
using SmallMap = std::map<K, V>;        // 인터페이스가 같은 것으로 대신한다
#endif
```

구현이 실제로 어디까지 지원하는지는 각 프로젝트의 지원 현황 표와 cppreference의 "compiler support" 표에 정리되어 있습니다. 그 표도 틀릴 때가 있어서, 마지막 판단은 **컴파일해 보는 것**입니다.

<Note>
구현의 속에 기대도 되는 때가 있습니다. 대상이 하나로 정해진 프로젝트입니다. 라즈베리 파이용 펌웨어를 그 보드의 GCC로만 빌드한다면 "libstdc++의 `string`은 15글자까지 힙을 쓰지 않는다"를 알고 설계에 쓰는 것은 정당합니다. 그럴 때는 그 가정을 [`static_assert`](#/read/cpp-syntax/ct-assert)나 시험으로 적어 두어, 컴파일러를 바꾸는 날 조용히 틀어지지 않고 걸리게 합니다.
</Note>

## 정리

- 표준 라이브러리의 구현은 libstdc++, libc++, MSVC STL 셋이다. 컴파일러와 라이브러리는 따로이고, 무엇을 쓰는지는 매크로로 안다
- 크기, 할당하는 시점과 횟수, 자라는 비율, 도는 순서는 표준이 정하지 않았다. 재어 보면 구현마다 다르다
- 기능이 있는지는 컴파일러 버전이 아니라 `__cpp_lib_...` 매크로로 묻는다
