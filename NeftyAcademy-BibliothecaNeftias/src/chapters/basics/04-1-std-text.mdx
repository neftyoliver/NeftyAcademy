컴퓨터는 수만 다룹니다([「2진수와 16진수」](#/read/basics/math-bases)). 그러니 글자를 저장하려면 **글자마다 번호를 붙이는 약속**이 있어야 합니다. 같은 약속을 쓰는 컴퓨터끼리만 글이 제대로 보이고, 약속이 다르면 글자가 깨집니다. 이 쪽은 그 약속이 어떻게 하나로 모여 왔는지를 봅니다.

## ASCII

1963년 미국에서 정한 ASCII는 영어 알파벳, 숫자, 문장 부호와 제어 문자에 0부터 127까지 번호를 붙였습니다. 7비트면 다 들어갑니다.

| 번호(10진) | 16진 | 글자 |
| --- | --- | --- |
| 0~31 | 00~1F | 제어 문자(줄바꿈 10, 탭 9 등). 화면에 찍히지 않는다 |
| 32 | 20 | 빈칸 |
| 48~57 | 30~39 | `0`~`9` |
| 65~90 | 41~5A | `A`~`Z` |
| 97~122 | 61~7A | `a`~`z` |
| 127 | 7F | 지우기(제어 문자) |

배치에 꾀가 들어 있습니다. 숫자 `0`~`9`는 0x30에 숫자를 더한 값이라, 글자 `'7'`에서 `'0'`을 빼면 수 7이 나옵니다. 대문자와 소문자는 정확히 32(0x20) 차이라서 비트 하나(`0010 0000`)만 바꾸면 대소문자가 뒤바뀝니다.

## 나라마다 다른 인코딩

ASCII에는 영어밖에 없습니다. 1바이트는 256가지를 담을 수 있으니, 나라마다 남는 128~255 자리에 자기 글자를 넣었습니다. 그런데 한글, 한자, 일본 가나는 수천 자라서 1바이트로 모자라 **2바이트**를 썼습니다.

| 인코딩 | 쓰던 곳 | '한'의 바이트 |
| --- | --- | --- |
| EUC-KR, CP949 | 한국(윈도우의 한국어 기본) | `C7 D1` |
| Shift_JIS | 일본 | 한글 없음 |
| Latin-1 | 서유럽 | 한글 없음 |

문제는 바이트에 "나는 어느 인코딩이다"라는 표시가 없다는 것입니다. CP949로 저장한 `C7 D1`을 다른 인코딩으로 읽으면 엉뚱한 글자가 나옵니다. 이것이 "글자가 깨진다"는 현상이고, 한국에서는 이메일, 웹페이지, 압축 파일 이름에서 오랫동안 흔했습니다.

## 유니코드

1991년에 나온 유니코드는 **세상의 모든 글자에 겹치지 않는 번호를 하나씩** 붙이는 표준입니다. 이 번호를 코드 포인트라고 하고 `U+` 뒤에 16진수로 적습니다.

| 글자 | 코드 포인트 |
| --- | --- |
| A | U+0041 |
| é | U+00E9 |
| 한 | U+D55C |
| 😺 | U+1F63A |

번호의 범위는 U+0000부터 U+10FFFF까지라서 110만 개 남짓을 담을 수 있고, 15만 자 넘게 정해졌습니다(2025년 9월의 17.0 기준 159,801자). 현대 한글 음절 11,172자는 U+AC00(가)부터 U+D7A3(힣)까지 한 덩어리로 들어 있습니다. 앞의 127자는 ASCII와 똑같습니다.

유니코드는 **번호**를 정할 뿐, 그 번호를 몇 바이트로 어떻게 저장할지는 따로 정합니다. 그 방법이 UTF-8, UTF-16 같은 인코딩입니다.

## UTF-8

UTF-8은 번호가 작은 글자는 짧게, 큰 글자는 길게 적습니다.

| 코드 포인트 범위 | 바이트 수 | 예 |
| --- | --- | --- |
| U+0000~U+007F | 1 | 영문, 숫자(ASCII와 같다) |
| U+0080~U+07FF | 2 | 라틴 문자의 악센트, 그리스 문자 |
| U+0800~U+FFFF | 3 | 한글, 한자 대부분 |
| U+10000~U+10FFFF | 4 | 이모지, 옛 한자 |

C 프로그램으로 실제 바이트를 찍어 봅니다. 소스 파일은 UTF-8로 저장했고, GCC는 문자열을 그 바이트 그대로 프로그램에 넣습니다.

```c
#include <stdio.h>
#include <string.h>

// 문자열이 메모리에 어떤 바이트로 들어 있는지 찍는다
static void dump(const char *label, const char *s)
{
    printf("%zu바이트 :", strlen(s));
    for (const unsigned char *p = (const unsigned char *)s; *p; p++)
        printf(" %02X", *p);
    printf("   ← %s\n", label);
}

int main(void)
{
    dump("A", "A");
    dump("Hi!", "Hi!");
    dump("é", "é");
    dump("한", "한");
    dump("한글", "한글");
    dump("😺", "😺");
    printf("'A' = %d, 'a' = %d, '0' = %d\n", 'A', 'a', '0');
    return 0;
}
```

```text
1바이트 : 41   ← A
3바이트 : 48 69 21   ← Hi!
2바이트 : C3 A9   ← é
3바이트 : ED 95 9C   ← 한
6바이트 : ED 95 9C EA B8 80   ← 한글
4바이트 : F0 9F 98 BA   ← 😺
'A' = 65, 'a' = 97, '0' = 48
```

`strlen`은 글자 수가 아니라 **바이트 수**를 셉니다. "한글"은 두 글자지만 6입니다. C에서 한글 문자열을 다룰 때 가장 먼저 부딪히는 일입니다.

UTF-8이 널리 쓰이게 된 까닭은 이렇습니다.

- **ASCII와 호환된다.** 영어로만 된 파일은 ASCII 파일과 바이트가 똑같다
- **경계를 알 수 있다.** 첫 바이트의 앞 비트가 이 글자가 몇 바이트인지 알려 주고, 이어지는 바이트는 모두 `10`으로 시작한다. 중간부터 읽어도 다음 글자의 시작을 찾을 수 있다
- **0 바이트가 끼지 않는다.** C는 0 바이트를 문자열의 끝으로 보는데, UTF-8은 글자 안에 0이 나오지 않아서 기존 C 함수에 그대로 넣을 수 있다

지금 웹페이지의 98% 넘게, 그리고 리눅스와 맥의 기본 인코딩이 UTF-8입니다.

<Note>
UTF-16은 대부분의 글자를 2바이트로, 이모지 같은 글자는 4바이트로 적습니다. '한'은 `D5 5C`, 😺는 `D8 3D DE 3A`입니다. 윈도우 내부와 자바, 자바스크립트의 문자열이 UTF-16이라, 윈도우 API를 쓰는 C 프로그램에서는 `wchar_t`와 함께 만나게 됩니다.
</Note>

<Note kind="tip">
윈도우의 메모장이나 터미널에서 한글이 깨지면 대개 UTF-8과 CP949가 섞인 것입니다. 소스 파일과 터미널을 모두 UTF-8로 맞추는 것이 가장 쉽습니다. 윈도우 10부터는 "Beta: 세계 언어 지원을 위해 Unicode UTF-8 사용"이라는 설정으로 시스템 전체를 UTF-8로 바꿀 수도 있습니다.
</Note>

## 정리

- ASCII는 영문과 숫자, 제어 문자에 0~127을 붙인 약속이고, 대소문자는 비트 하나 차이로 배치됐다
- 나라마다 다른 인코딩을 쓰던 시절에는 바이트에 인코딩 표시가 없어 글자가 자주 깨졌다
- 유니코드는 모든 글자에 번호를 붙였고, UTF-8은 그 번호를 1~4바이트로 적으며 한글은 3바이트다
