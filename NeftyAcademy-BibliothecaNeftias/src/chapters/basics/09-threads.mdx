## 프로세스와 스레드

**스레드**는 프로세스 안에서 진행되는 실행 흐름 하나입니다. 프로그램을 실행하면 스레드가 하나(메인 스레드) 있는 프로세스가 생기고, 프로그램이 원하면 스레드를 더 만들 수 있습니다.

| | 프로세스 | 스레드 |
| --- | --- | --- |
| 무엇 | 실행 중인 프로그램 하나 | 프로세스 안의 실행 흐름 하나 |
| 메모리 | 프로세스마다 따로 | 같은 프로세스의 스레드끼리 **함께** 쓴다 |
| 각자 가진 것 | 메모리, 열린 파일, 권한 | 레지스터, 프로그램 카운터, 스택 |
| 만드는 비용 | 크다 | 작다 |
| 하나가 죽으면 | 다른 프로세스는 멀쩡하다 | 대개 프로세스 전체가 끝난다 |

[「프로세스와 메모리 관리」](#/read/basics/os-process-memory)의 `fork` 예제에서 자식 프로세스가 변수를 고쳐도 부모의 변수는 그대로였습니다. 프로세스는 메모리가 따로이기 때문입니다. 스레드는 정반대입니다. 한 스레드가 전역 변수를 고치면 다른 스레드에게 곧바로 보입니다.

## 스레드를 쓰는 까닭

- **여러 코어를 쓰려고.** 계산을 나눠 맡기면 코어 수만큼 빨라질 수 있다([「코어와 스레드」](#/read/basics/terms-core-thread))
- **기다리는 동안 다른 일을 하려고.** 파일을 내려받는 스레드가 네트워크를 기다리는 동안 화면을 그리는 스레드는 계속 반응한다. 게임이 로딩 중에도 멈추지 않는 까닭이다
- **함께 쓰는 메모리가 편해서.** 프로세스끼리는 자료를 주고받으려면 OS를 거쳐야 하지만, 스레드는 같은 변수를 그냥 읽고 쓰면 된다

마지막 장점이 그대로 위험이 됩니다.

## 경쟁 상태를 일으켜 보기

두 스레드가 같은 변수에 1을 백만 번씩 더합니다. 끝나면 200만이어야 합니다. 보통 변수와 C11의 원자적 변수(`atomic_long`)를 함께 세어 봅니다.

```c
#include <stdatomic.h>
#include <stdio.h>
#include <threads.h>

enum { TIMES = 1000000 };

static long plain = 0;              // 보통 변수
static atomic_long safe = 0;        // 원자적 변수

static int work(void *arg)
{
    (void)arg;
    for (int i = 0; i < TIMES; i++) {
        plain++;                    // 읽고, 1 더하고, 쓰기가 따로따로
        atomic_fetch_add(&safe, 1); // 한 덩어리로
    }
    return 0;
}

int main(void)
{
    thrd_t a, b;
    thrd_create(&a, work, NULL);
    thrd_create(&b, work, NULL);
    thrd_join(a, NULL);
    thrd_join(b, NULL);
    printf("기대한 값 %d\n", 2 * TIMES);
    printf("보통 변수 %ld\n", plain);
    printf("원자적    %ld\n", atomic_load(&safe));
    return 0;
}
```

검사 기계에서 세 번 돌린 결과입니다.

```text nocheck
기대한 값 2000000
보통 변수 1487357
원자적    2000000

기대한 값 2000000
보통 변수 1651028
원자적    2000000

기대한 값 2000000
보통 변수 1634527
원자적    2000000
```

보통 변수는 돌릴 때마다 다른 값이 나오고, 50만 번 가까이 더하기가 **사라졌습니다.** 원자적 변수는 늘 정확히 200만입니다.

## 더하기가 사라지는 까닭

`plain++`는 C에서는 한 줄이지만 CPU에게는 세 단계입니다. 램에서 레지스터로 읽고, 1을 더하고, 램에 다시 씁니다([「CPU와 레지스터」](#/read/basics/arch-cpu)). 두 스레드가 이 세 단계를 동시에 하면 이런 일이 생깁니다.

| 차례 | 스레드 A | 스레드 B | 램의 값 |
| --- | --- | --- | --- |
| 1 | 읽는다: 5 | | 5 |
| 2 | | 읽는다: 5 | 5 |
| 3 | 1 더해 6을 쓴다 | | 6 |
| 4 | | 1 더해 6을 쓴다 | 6 |

둘 다 1씩 더했는데 값은 1만 늘었습니다. 둘이 같은 옛 값을 읽었기 때문입니다. 이렇게 **실행 순서에 따라 결과가 달라지는** 상황을 경쟁 상태(race condition)라고 합니다. 순서는 OS의 스케줄러와 코어의 사정에 따라 매번 바뀌므로, 오류가 나왔다 안 나왔다 합니다. 그래서 찾기도 고치기도 어려운 버그입니다.

`atomic_fetch_add`는 CPU가 제공하는 특별한 명령으로 "읽고, 더하고, 쓰기"를 **끊기지 않는 한 덩어리**로 합니다. 그 사이에 다른 코어가 끼어들 수 없습니다. 더 큰 덩어리(여러 변수를 함께 고치기)를 지키려면 뮤텍스라는 자물쇠를 씁니다. 한 번에 한 스레드만 들어가게 하는 것입니다. 이 둘은 [「뮤텍스와 경쟁 상태」](#/read/c-mid/thr-mutex), [「원자적 연산」](#/read/c-mid/thr-atomics)에서 직접 써 봅니다.

<Note kind="warn">
C에서 여러 스레드가 보호 없이 같은 변수를 읽고 쓰는 것(데이터 경쟁)은 정의되지 않은 동작입니다. 값이 틀리는 데서 그치지 않고, 컴파일러가 최적화하면서 더 이상한 일이 생길 수 있습니다. GCC와 Clang의 `-fsanitize=thread`(스레드 새니타이저)로 컴파일하면 실행 중에 데이터 경쟁을 찾아 줍니다.
</Note>

<Note>
스레드는 편리하지만 함께 쓰는 자료를 하나씩 지켜야 하는 부담이 따릅니다. 그래서 자료를 함께 쓰지 않고 메시지로 주고받게 하거나(채널), 아예 프로세스를 여러 개 쓰는 설계도 많이 씁니다. 크롬 브라우저가 탭마다 프로세스를 따로 두는 것도, 한 탭이 망가져도 다른 탭은 멀쩡하게 하려는 선택입니다.
</Note>

## 정리

- 스레드는 프로세스 안의 실행 흐름이고, 같은 프로세스의 스레드끼리는 메모리를 함께 쓰며 레지스터와 스택만 각자 가진다
- 스레드는 여러 코어를 쓰고 기다리는 동안 다른 일을 하는 데 쓰지만, 함께 쓰는 변수를 동시에 고치면 경쟁 상태가 생긴다
- `x++` 같은 읽기-고치기-쓰기는 끊길 수 있으므로, 원자적 연산이나 뮤텍스로 한 덩어리로 만들어 지켜야 한다
