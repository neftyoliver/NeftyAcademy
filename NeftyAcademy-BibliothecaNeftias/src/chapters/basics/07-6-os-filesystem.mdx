[「C 드라이브」](#/read/basics/terms-c-drive)에서 파일 시스템을 "파티션 안에 파일과 폴더를 정리하는 방식"이라고 했습니다. 디스크는 사실 번호가 붙은 블록(보통 4KiB)이 늘어선 것일 뿐이고, 파일이나 폴더라는 개념은 없습니다. 이 쪽은 파일 시스템이 그 위에 어떻게 파일을 만들어 내는지를 리눅스의 ext4를 예로 봅니다.

## 파일 시스템이 적어 두는 것

| 적어 두는 것 | 내용 |
| --- | --- |
| 파일의 내용 | 디스크 블록 여러 개에 나눠 담는다 |
| 메타데이터 | 크기, 주인, 권한, 만든 시각, 고친 시각, 내용이 든 블록의 위치 |
| 폴더 | "이름 → 메타데이터 번호" 목록. 폴더도 이런 목록을 담은 특별한 파일이다 |
| 빈 블록 표 | 어느 블록이 비어 있는지 |

ext4 같은 유닉스 계열 파일 시스템은 파일 하나의 메타데이터를 **아이노드**(inode)라는 칸에 담고, 번호를 붙입니다. 놀라운 점은 아이노드에 **파일 이름이 없다**는 것입니다. 이름은 폴더의 목록에 있고, 폴더는 "이 이름은 몇 번 아이노드"라고만 적어 둡니다.

## 직접 보기

리눅스의 `stat` 명령은 파일의 아이노드에 적힌 것을 보여 줍니다. 검사 기계에서 "안녕"을 담은 `a.txt`를 만들고 살펴봤습니다.

```text nocheck
$ printf '안녕\n' > a.txt
$ stat a.txt
  File: a.txt
  Size: 7               Blocks: 8          IO Block: 4096   regular file
Device: 254,0   Inode: 1213328     Links: 1
Access: (0644/-rw-r--r--)  Uid: (    0/    root)   Gid: (    0/    root)
Modify: 2026-11-21 18:16:31.036009959 +0900
```

- 크기는 7바이트지만 디스크에서는 4KiB 블록 하나(`Blocks: 8`은 512바이트 단위로 센 값)를 차지합니다. 아무리 작은 파일도 블록 하나는 씁니다
- `Inode: 1213328`이 이 파일의 아이노드 번호입니다
- `Links: 1`은 이 아이노드를 가리키는 이름이 하나라는 뜻입니다
- `0644`는 [8진수](#/read/basics/math-bases)로 적은 권한, 곧 주인은 읽고 쓰기, 나머지는 읽기만입니다

## 하드 링크와 심볼릭 링크

이름과 내용이 따로라서, **한 내용에 이름을 여러 개** 붙일 수 있습니다.

```text nocheck
$ ln a.txt b.txt          # 하드 링크: 같은 아이노드에 이름 하나 더
$ ln -s a.txt c.txt       # 심볼릭 링크: "a.txt를 보라"는 쪽지
$ ls -li
1213328 -rw-r--r-- 2 root root 7 Nov 21 18:16 a.txt
1213328 -rw-r--r-- 2 root root 7 Nov 21 18:16 b.txt
1213375 lrwxrwxrwx 1 root root 5 Nov 21 18:16 c.txt -> a.txt
$ rm a.txt
$ cat b.txt
안녕
$ cat c.txt
cat: c.txt: No such file or directory
```

- **하드 링크** `b.txt`는 `a.txt`와 아이노드 번호가 같습니다. 같은 파일에 이름이 둘이 됐고, 링크 수가 2로 올랐습니다
- **심볼릭 링크** `c.txt`는 자기 아이노드를 가진 작은 파일이고, 내용은 `a.txt`라는 **경로 글자**(5바이트)입니다
- `a.txt`를 지워도 `b.txt`로 내용을 읽을 수 있습니다. `rm`은 이름 하나를 지우고 링크 수를 줄일 뿐이고, 링크 수가 0이 될 때 비로소 블록을 비웁니다. 반면 `c.txt`는 가리키던 이름이 사라져서 빈 쪽지가 됐습니다

윈도우의 "바로 가기"는 심볼릭 링크와 비슷한 쪽지이고, NTFS도 하드 링크와 심볼릭 링크를 지원합니다.

## 전원이 나가도 망가지지 않게

파일 하나를 쓰는 데도 내용 블록, 아이노드, 빈 블록 표, 폴더 목록을 함께 고쳐야 합니다. 그 중간에 전원이 나가면 표들이 서로 맞지 않게 됩니다. 그래서 ext4, NTFS, APFS는 고치기 전에 "이제 이것들을 고칠 것"이라고 **일지**(저널)에 먼저 적어 둡니다. 다시 켜졌을 때 일지를 보고 하다 만 일을 마무리하거나 되돌립니다. 이런 파일 시스템을 저널링 파일 시스템이라고 합니다.

<Note kind="warn">
USB 메모리를 "안전하게 제거" 없이 뽑으면 안 되는 까닭이 여기에 있습니다. OS는 쓰기를 램에 모아 두었다가 나중에 한꺼번에 디스크로 보내므로, 복사가 끝난 것처럼 보여도 아직 다 쓰지 않았을 수 있습니다. 리눅스에서는 `sync` 명령으로 모아 둔 쓰기를 내보낼 수 있습니다. FAT32와 exFAT은 저널이 없어서 특히 잘 망가집니다.
</Note>

## 리눅스의 폴더 지도

[「C 드라이브」](#/read/basics/terms-c-drive)에서 리눅스는 `/` 아래 나무 하나라고 했습니다. 그 나무의 큰 가지들은 이름이 정해져 있습니다.

| 폴더 | 담는 것 |
| --- | --- |
| `/home` | 사용자마다의 폴더. 윈도우의 `C:\Users` |
| `/etc` | 설정 파일 |
| `/usr` | 설치된 프로그램과 라이브러리 (`/usr/bin`, `/usr/lib`) |
| `/var` | 계속 바뀌는 자료: 로그(`/var/log`), 캐시 |
| `/tmp` | 임시 파일. 재부팅하면 지워질 수 있다 |
| `/dev` | 장치. 디스크도 `/dev/sda` 같은 파일로 보인다 |
| `/proc`, `/sys` | 디스크에 없는 가짜 파일들. 커널의 상태를 파일처럼 보여 준다 |

`/proc`와 `/sys`는 "모든 것은 파일"이라는 유닉스의 생각을 끝까지 밀고 간 것입니다. [「버스와 입출력」](#/read/basics/arch-bus-io)에서 읽은 `/proc/iomem`, [「램과 저장 공간」](#/read/basics/terms-ram-storage)의 `/proc/meminfo`가 모두 커널이 그때그때 만들어 주는 글입니다.

## 정리

- 파일 시스템은 번호 붙은 디스크 블록 위에 내용, 메타데이터, 폴더 목록, 빈 블록 표를 적어 파일과 폴더를 만든다
- 유닉스 계열에서 파일의 메타데이터는 아이노드에 있고 이름은 폴더에 있어서, 하드 링크로 한 내용에 이름을 여러 개 붙일 수 있다
- 저널링 파일 시스템은 고칠 일을 먼저 일지에 적어 전원이 나가도 망가지지 않게 하며, 리눅스의 폴더 이름에는 정해진 쓰임이 있다
