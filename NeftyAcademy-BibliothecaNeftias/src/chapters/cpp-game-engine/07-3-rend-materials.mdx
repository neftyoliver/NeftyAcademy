화면의 모든 물체는 **머티리얼**로 그려집니다. 머티리얼은 "어떤 셰이더로, 어떤 값과 텍스처를 넣어서 그리나"를 묶은 에셋입니다. 셰이더 하나로 모든 경우를 처리하면 느리고, 경우마다 셰이더를 따로 쓰면 수가 폭발합니다. 이 쪽은 그 사이의 균형과, CPU와 GPU가 매개변수를 주고받을 때의 배치 규칙을 봅니다.

## 기능 비트와 조합의 폭발

셰이더 하나에 기능 스위치를 여러 개 두고(`#ifdef NORMAL_MAP` …), 필요한 조합마다 따로 컴파일하는 것이 흔한 방법입니다. 조합 하나를 비트 묶음(**셰이더 키**)으로 나타냅니다.

```cpp
#include <cstdint>
#include <map>
#include <print>
#include <string>
#include <vector>

// 셰이더 기능 하나 = 비트 하나
const std::vector<std::string> kFeatures = {
    "NORMAL_MAP", "SKINNING", "ALPHA_TEST", "SHADOWS", "FOG", "VERTEX_COLOR"};

std::string defines(std::uint32_t key)
{
    std::string s;
    for (std::size_t i = 0; i < kFeatures.size(); ++i)
        if (key & (1u << i)) s += "#define " + kFeatures[i] + " 1\n";
    return s;
}

// std140 규칙으로 유니폼 블록의 칸 위치를 계산한다
struct Field { std::string name; std::string type; };
void layout_std140(const std::vector<Field>& fields)
{
    auto align_of = [](const std::string& t) {
        if (t == "float") return 4;
        if (t == "vec2") return 8;
        return 16;                                    // vec3, vec4, mat4는 16
    };
    auto size_of = [](const std::string& t) {
        if (t == "float") return 4;
        if (t == "vec2") return 8;
        if (t == "vec3") return 12;
        if (t == "vec4") return 16;
        return 64;                                    // mat4
    };
    int offset = 0;
    for (const auto& f : fields) {
        int a = align_of(f.type);
        offset = (offset + a - 1) / a * a;
        std::println("  {:<6} {:<10} 위치 {:3}", f.type, f.name, offset);
        offset += size_of(f.type);
    }
    std::println("  블록 크기 {}바이트(16의 배수로 {})", offset,
                 (offset + 15) / 16 * 16);
}

int main()
{
    std::println("기능 {}개 -> 가능한 조합 {}가지", kFeatures.size(),
                 1u << kFeatures.size());

    // 실제 머티리얼들이 쓰는 조합만 모은다
    struct Mat { std::string name; std::uint32_t key; };
    std::vector<Mat> mats = {{"바위", 1 | 8},      {"풀", 4 | 8 | 16},
                             {"캐릭터", 1 | 2 | 8}, {"바위2", 1 | 8},
                             {"물", 8 | 16},        {"캐릭터2", 1 | 2 | 8}};
    std::map<std::uint32_t, int> compiled;           // 조합 -> 쓰는 머티리얼 수
    for (auto& m : mats) ++compiled[m.key];
    std::println("머티리얼 {}개가 쓰는 조합 {}가지만 컴파일", mats.size(),
                 compiled.size());
    std::print("캐릭터 셰이더의 머리:\n{}", defines(1 | 2 | 8));

    std::println("머티리얼 매개변수 블록(std140):");
    layout_std140({{"base_color", "vec3"}, {"roughness", "float"},
                   {"uv_scale", "vec2"}, {"emissive", "vec3"}, {"world", "mat4"}});
}
```

```text
기능 6개 -> 가능한 조합 64가지
머티리얼 6개가 쓰는 조합 4가지만 컴파일
캐릭터 셰이더의 머리:
#define NORMAL_MAP 1
#define SKINNING 1
#define SHADOWS 1
머티리얼 매개변수 블록(std140):
  vec3   base_color 위치   0
  float  roughness  위치  12
  vec2   uv_scale   위치  16
  vec3   emissive   위치  32
  mat4   world      위치  48
  블록 크기 112바이트(16의 배수로 112)
```

- 기능이 6개면 조합은 2⁶ = 64가지, 20개면 100만 가지가 넘습니다. 게다가 조합마다 그림자 패스용, 깊이만 그리는 패스용 같은 **패스별 판**이 곱해집니다. 대형 엔진이 수만~수십만 개의 셰이더를 컴파일하고, 셰이더 캐시를 따로 관리하는 까닭입니다
- 그래서 **실제로 쓰는 조합만** 컴파일합니다. 위의 머티리얼 6개는 조합 4가지만 썼습니다. 굽는 단계([「에셋 파이프라인」](#/read/cpp-game-engine/res-pipeline))에서 모든 머티리얼을 훑어 필요한 키를 모으고, 키의 해시로 결과를 캐시합니다
- 조합 수를 줄이는 다른 방법도 함께 씁니다. 자주 바뀌지 않는 기능은 셰이더 안의 `if`로(요즘 GPU는 모든 스레드가 같은 쪽으로 가는 분기를 싸게 처리합니다), 조합이 꼭 필요한 기능만 비트로 둡니다

## 실행 중에 처음 만나는 조합

미리 굽지 못한 조합을 게임 중에 처음 만나면, 그 자리에서 셰이더를 컴파일하고 파이프라인을 만드느라 한 프레임이 수십~수백 ms 멈춥니다. PC 게임에서 처음 가는 곳마다 잠깐씩 끊기는 현상이 흔히 이것입니다. 대처는 로딩 화면에서 그 레벨이 쓸 파이프라인을 미리 만들어 두기, 드라이버의 파이프라인 캐시를 저장해 두었다 다음 실행에 다시 쓰기, 그리고 [「그래픽 API 감싸기」](#/read/cpp-game-engine/rend-abstraction)의 RHI에서 파이프라인 생성을 [「비동기 로딩」](#/read/cpp-game-engine/res-async)처럼 다른 스레드로 돌리기입니다.

## 매개변수 블록과 std140

머티리얼의 값(색, 거칠기, 크기)은 GPU 버퍼에 담아 셰이더로 넘깁니다. 이때 **C++의 구조체 배치와 셰이더의 배치가 다를 수 있습니다**. GLSL의 유니폼 블록에 흔히 쓰는 std140 규칙에서는 `vec3`가 16바이트 경계에서 시작하고, `vec2`는 8바이트, `mat4`는 16바이트 경계입니다.

- `vec3 base_color` 뒤의 `float roughness`는 남은 4바이트(위치 12)에 딱 들어갑니다
- 그다음 `vec2 uv_scale`은 8의 배수인 16에서 시작합니다
- `vec3 emissive`는 16의 배수여야 해서 24가 아니라 **32**에서 시작합니다. C++에서 `float[3]`과 `float[2]`를 그냥 이어 붙인 구조체로 쓰면 이 자리부터 값이 밀려, 셰이더가 엉뚱한 색을 읽습니다

그래서 엔진은 C++ 쪽 구조체에 채움 칸을 직접 넣고 `static_assert(offsetof(MatParams, emissive) == 32)` 같은 검사를 두거나, 셰이더의 반사 정보(SPIR-V를 읽어 칸 위치를 알아내는 도구)로 C++ 쪽 배치를 자동으로 만듭니다. 매개변수 블록은 머티리얼마다 하나를 만들어 두고, 같은 셰이더·다른 값의 **머티리얼 인스턴스**는 블록만 바꿔 끼웁니다.

<Note>
std140 말고도 std430(저장 버퍼에서 쓰는 더 촘촘한 규칙), HLSL의 상수 버퍼 규칙, Metal의 규칙이 저마다 조금씩 다릅니다. 같은 구조체를 여러 API에 넘기는 엔진은 가장 까다로운 규칙에 맞춰(`vec3` 대신 `vec4`만 쓰기 등) 하나로 통일하기도 합니다. 셰이더 언어와 SPIR-V는 「벌칸, GLSL, SPIR-V」 책에서 깊이 다룹니다.
</Note>

## 정리

- 셰이더는 기능 비트의 조합(셰이더 키)마다 컴파일하되, 조합이 폭발하므로 굽는 단계에서 실제로 쓰는 조합만 모아 캐시한다
- 처음 만나는 조합의 컴파일·파이프라인 생성은 프레임을 멈추게 하므로 미리 만들거나 캐시하거나 다른 스레드로 돌린다
- 머티리얼 매개변수는 std140 같은 GPU 배치 규칙을 따라 C++ 구조체에 채움을 넣고 위치를 검사하며, 인스턴스는 블록만 바꿔 끼운다
