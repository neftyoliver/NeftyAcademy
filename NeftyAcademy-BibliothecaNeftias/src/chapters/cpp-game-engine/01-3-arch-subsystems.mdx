렌더러는 창이 있어야 하고, 창은 플랫폼 층이 있어야 하며, 자원 시스템은 메모리와 파일 시스템이 있어야 합니다. 엔진의 **서브시스템**은 서로 기대고 있어서, 켜는 순서와 끄는 순서를 틀리면 시작하자마자, 또는 끝나는 순간 프로그램이 쓰러집니다. 이 쪽은 그 순서를 안전하게 정하는 방법들을 봅니다.

## 전역 싱글턴의 함정

가장 손쉬운 방법은 서브시스템마다 전역 객체(싱글턴)를 두는 것입니다. 하지만 C++에서 **서로 다른 번역 단위의 전역 객체가 만들어지는 순서는 정해져 있지 않습니다**. 「C++ 문법」의 [「정적 초기화 순서 문제」](#/read/cpp-syntax/life-static-init)에서 본 문제가 그대로 생깁니다. 렌더러의 전역 생성자가 아직 만들어지지 않은 메모리 관리자를 부를 수 있고, 끝날 때는 반대로 이미 부서진 로거에 기록하려다 쓰러질 수 있습니다.

함수 안의 `static`(처음 부를 때 만들어짐)으로 바꾸면 켜는 순서는 저절로 맞지만, 부서지는 순서는 "만들어진 반대 순서"라서 여전히 통제하기 어렵고, 언제 켜지는지가 코드에 드러나지 않습니다. 그래서 대부분의 엔진은 서브시스템을 **명시적으로** 켜고 끕니다.

## 의존 순서로 켜고, 거꾸로 끄기

서브시스템마다 "먼저 켜져 있어야 하는 것"을 적어 두면, 켜는 순서는 **위상 정렬**로 구할 수 있습니다. 끄는 순서는 그 정확한 반대입니다.

```cpp
#include <map>
#include <print>
#include <queue>
#include <stdexcept>
#include <string>
#include <vector>

struct Subsystem {
    std::string name;
    std::vector<std::string> needs;   // 먼저 켜져 있어야 하는 것
    bool fail_on_start = false;
};

// 칸 알고리즘: 들어오는 화살표가 없는 것부터 차례로 꺼낸다
std::vector<std::string> start_order(const std::vector<Subsystem>& subs)
{
    std::map<std::string, int> indeg;
    std::map<std::string, std::vector<std::string>> users;
    for (const auto& s : subs) {
        indeg[s.name] += 0;
        for (const auto& n : s.needs) {
            users[n].push_back(s.name);
            ++indeg[s.name];
        }
    }
    std::queue<std::string> ready;
    for (const auto& [name, d] : indeg)
        if (d == 0) ready.push(name);
    std::vector<std::string> order;
    while (!ready.empty()) {
        auto n = ready.front();
        ready.pop();
        order.push_back(n);
        for (const auto& u : users[n])
            if (--indeg[u] == 0) ready.push(u);
    }
    if (order.size() != indeg.size())
        throw std::runtime_error("의존에 고리가 있다");
    return order;
}

void boot(const std::vector<Subsystem>& subs)
{
    std::map<std::string, const Subsystem*> by_name;
    for (const auto& s : subs) by_name[s.name] = &s;

    std::vector<std::string> started;
    std::print("  켬:");
    try {
        for (const auto& n : start_order(subs)) {
            if (by_name[n]->fail_on_start)
                throw std::runtime_error(n + " 시작 실패");
            std::print(" {}", n);
            started.push_back(n);
        }
        std::println("\n  -- 게임 루프 --");
    } catch (const std::exception& e) {
        std::println("\n  !! {}", e.what());
    }
    std::print("  끔:");
    for (auto it = started.rbegin(); it != started.rend(); ++it)
        std::print(" {}", *it);              // 켠 것만, 거꾸로
    std::println();
}

int main()
{
    std::vector<Subsystem> subs = {
        {"render", {"window", "memory", "resource"}},
        {"window", {"platform"}},
        {"platform", {}},
        {"memory", {"platform"}},
        {"resource", {"memory", "filesystem"}},
        {"filesystem", {"platform"}},
        {"audio", {"memory", "resource"}},
        {"physics", {"memory"}},
    };
    std::println("정상:");
    boot(subs);

    subs[6].fail_on_start = true;            // audio 장치가 없다
    std::println("소리 장치가 없을 때:");
    boot(subs);
}
```

```text
정상:
  켬: platform window memory filesystem physics resource render audio
  -- 게임 루프 --
  끔: audio render resource physics filesystem memory window platform
소리 장치가 없을 때:
  켬: platform window memory filesystem physics resource render
  !! audio 시작 실패
  끔: render resource physics filesystem memory window platform
```

- **위상 정렬**(칸 알고리즘): 기대는 것이 없는 서브시스템부터 꺼내고, 꺼낼 때마다 그것에 기대던 것들의 "남은 의존 수"를 줄입니다. 의존에 고리가 있으면 끝까지 꺼내지 못한 것이 남으므로 바로 알 수 있습니다
- **끄기는 거꾸로**: 렌더러를 끄는 동안 메모리 관리자와 창이 아직 살아 있어야 하므로, 켠 순서의 정반대로 끕니다
- **실패하면 켠 것만 되돌린다**: 소리 장치가 없어 `audio`가 실패하면, 그때까지 켠 것만 거꾸로 끄고 빠져나옵니다. 켜지도 않은 것을 끄려다 쓰러지는 일이 없습니다

## RAII로 같은 일을

C++에서는 같은 규칙을 언어가 대신 지켜 주게 할 수도 있습니다. 클래스의 **멤버는 선언된 순서대로 만들어지고, 거꾸로 부서지며**, 생성자가 예외를 던지면 이미 만들어진 멤버만 거꾸로 부서집니다.

```cpp
#include <print>
#include <stdexcept>
#include <string>

struct Sub {
    std::string name;
    explicit Sub(std::string n, bool fail = false) : name(std::move(n))
    {
        if (fail)
            throw std::runtime_error(name + " 시작 실패");
        std::println("켬 {}", name);
    }
    ~Sub() { std::println("끔 {}", name); }
    Sub(const Sub&) = delete;
    Sub& operator=(const Sub&) = delete;
};

// 멤버는 적힌 순서대로 만들어지고, 거꾸로 부서진다
struct Engine {
    Sub platform{"platform"};
    Sub memory{"memory"};
    Sub resource{"resource"};
    Sub audio;
    explicit Engine(bool no_audio) : audio("audio", no_audio) {}
};

int main()
{
    try {
        Engine e(true);
    } catch (const std::exception& ex) {
        std::println("잡음: {}", ex.what());
    }
}
```

```text
켬 platform
켬 memory
켬 resource
끔 resource
끔 memory
끔 platform
잡음: audio 시작 실패
```

`audio`의 생성자가 실패하자 앞의 셋이 거꾸로 정리되었습니다. 의존이 단순하면 이 방법이 가장 짧고 안전합니다. 멤버의 선언 순서가 곧 켜는 순서이므로, 순서를 바꿀 때는 선언 순서를 바꾸면 됩니다. 「C++ 고급」의 [「예외에 안전한 코드 쓰기」](#/read/cpp-advanced/res-exception)에서 본 RAII를 엔진 전체에 적용한 것입니다.

| 방법 | 좋은 점 | 아쉬운 점 |
| --- | --- | --- |
| 전역 싱글턴 | 어디서나 바로 쓴다 | 순서가 정해지지 않는다 |
| main에서 손으로 차례대로 | 단순하고 눈에 보인다 | 서브시스템이 늘면 순서를 사람이 관리한다 |
| 의존을 적고 위상 정렬 | 플러그인처럼 늘어나도 순서가 저절로 | 의존 목록을 바르게 적어야 한다 |
| RAII 멤버 | 실패·정리를 언어가 보장 | 순서가 선언 순서에 묶인다 |

<Note>
끝낼 때 모든 것을 정성껏 정리하지 않는 엔진도 많습니다. 게임을 끌 때 수만 개의 객체를 하나하나 해제하면 종료가 몇 초씩 걸리기 때문입니다. 저장해야 할 것(설정, 세이브 파일)과 꼭 닫아야 할 것(장치, 파일, 네트워크 연결)만 순서대로 처리하고, 나머지 메모리는 운영체제가 프로세스와 함께 거둬 가게 둡니다. 다만 개발 중에는 [「새니타이저」](#/read/cpp-advanced/tool-sanitizers)로 새는 곳을 찾기 위해 전부 정리하는 모드를 남겨 둡니다.
</Note>

## 정리

- 서브시스템은 서로 기대므로, 순서가 정해지지 않는 전역 싱글턴 대신 명시적으로 켜고 끈다
- 의존을 적어 두고 위상 정렬로 켜는 순서를 구하며, 끄기는 정확히 거꾸로, 실패하면 켠 것만 되돌린다
- 의존이 단순하면 RAII 멤버의 선언 순서로 같은 일을 언어가 보장하게 할 수 있다
