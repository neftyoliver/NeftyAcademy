게임 엔진은 창을 띄우는 코드부터 그림자를 계산하는 코드, 에디터의 버튼까지 수십만 줄이 한 프로그램에 들어갑니다. 이것을 버티게 하는 첫 번째 설계가 **층**입니다. 이 책은 엔진을 아래층부터 하나씩 쌓아 올리며, 이 쪽은 그 전체 모양을 먼저 그립니다. 「C++ 고급」의 [「의존성 주입」](#/read/cpp-advanced/des-injection)에서 본 원칙들이 여기서 큰 규모로 쓰입니다.

## 흔한 층의 모양

| 층 | 하는 일 | 이 책에서 |
| --- | --- | --- |
| 플랫폼 | 창, 입력, 파일, 시간, 스레드를 운영체제마다 감싼다 | 2장 |
| 코어 | 할당자, 컨테이너, 로그, 수학, 핸들 | 3·4장 |
| 자원 | 에셋을 읽고, 굽고, 나눠 쓰고, 해제한다 | 6장 |
| 엔진 서브시스템 | 렌더러, 물리, 애니메이션, 소리, 작업 큐 | 7·9~11·13장 |
| 게임 틀 | 장면, ECS, 스크립트, 네트워크 복제 | 5·8·12·15장 |
| 게임 | 이 게임만의 규칙과 내용 | 1.4 |
| 도구 | 에디터, 프로파일러, 에셋 굽는 프로그램 | 14장 |

규칙은 하나입니다. **위층은 아래층을 알지만, 아래층은 위층을 모른다.** 렌더러는 "플레이어"라는 말을 몰라야 하고, 파일 시스템 감싸개는 렌더러를 몰라야 합니다. 같은 층끼리는 서로 쓸 수 있지만, 고리(A가 B를, B가 A를)는 만들지 않습니다.

## 왜 나누나

- **옮기기**: 윈도에서 콘솔이나 리눅스로 옮길 때 플랫폼 층만 다시 쓰면 됩니다. 위층이 `CreateWindowEx`를 직접 부르고 있으면 그 모든 곳을 찾아야 합니다
- **시험**: 아래층은 위층 없이 돌릴 수 있으니, 수학 라이브러리나 할당자는 렌더러를 띄우지 않고 단위 시험을 할 수 있습니다
- **빌드 시간**: 아래층 헤더가 위층을 끌어오지 않으니, 게임 코드를 고쳐도 엔진 전체가 다시 컴파일되지 않습니다
- **책임**: "이 버그는 어느 층의 것인가"가 분명해집니다. 큰 팀에서는 층이 곧 팀의 경계가 되기도 합니다

## 의존 방향 검사하기

규칙은 말로만 두면 깨집니다. 모듈마다 층 번호를 매기고, 각 모듈이 쓰는 모듈의 층이 자기보다 높지 않은지 검사해 봅니다.

```cpp
#include <map>
#include <print>
#include <string>
#include <vector>

// 엔진을 이루는 모듈과 층(숫자가 작을수록 아래)
struct Module {
    std::string name;
    int layer;
    std::vector<std::string> uses;   // 이 모듈이 #include 하는 모듈들
};

int main()
{
    const std::vector<Module> modules = {
        {"platform", 0, {}},
        {"core", 1, {"platform"}},
        {"math", 1, {}},
        {"resource", 2, {"core", "platform"}},
        {"render", 3, {"resource", "math", "core"}},
        {"physics", 3, {"math", "core"}},
        {"scene", 4, {"render", "physics", "core"}},
        {"game", 5, {"scene", "render"}},
        // 실수: 렌더러가 게임 코드의 플레이어 정보를 직접 본다
        {"render_debug", 3, {"render", "game"}},
    };

    std::map<std::string, int> layer_of;
    for (const auto& m : modules)
        layer_of[m.name] = m.layer;

    int bad = 0;
    for (const auto& m : modules) {
        for (const auto& u : m.uses) {
            if (layer_of.at(u) > m.layer) {   // 위층을 보면 위반
                std::println("위반: {}(층 {}) -> {}(층 {})", m.name, m.layer,
                             u, layer_of.at(u));
                ++bad;
            }
        }
    }
    std::println("모듈 {}개, 위반 {}개", modules.size(), bad);
}
```

```text
위반: render_debug(층 3) -> game(층 5)
모듈 9개, 위반 1개
```

실제 엔진에서는 `uses` 목록을 손으로 적지 않고, 빌드 시스템이 이미 알고 있는 의존을 씁니다. CMake라면 모듈마다 라이브러리 타깃을 만들고 `target_link_libraries(render PRIVATE core resource math)`처럼 아래층만 적어 두면, 위층 헤더를 `#include`했을 때 그 경로가 없어서 **컴파일이 실패**합니다. 「C++ 고급」의 [「CMake 깊이」](#/read/cpp-advanced/tool-cmake)에서 본 대로 `PRIVATE`·`PUBLIC`으로 의존이 새어 나가는 범위까지 정할 수 있습니다. 규칙은 사람의 기억보다 도구가 지키게 하는 편이 낫습니다.

## 거꾸로 뒤집기

위 예제의 위반은 흔한 바람에서 나옵니다. 디버그 화면에 "플레이어의 속도"를 선으로 그리고 싶은데, 렌더러가 게임을 알면 안 됩니다. 해결은 **의존을 뒤집는 것**입니다. 아래층은 "그릴 것을 주는 쪽"의 모양(인터페이스, 콜백)만 정하고, 위층이 자기 정보를 거기에 등록합니다.

```cpp
#include <functional>
#include <print>
#include <string>
#include <vector>

// ---- render 층: 게임을 모른다. "그릴 것을 주는 쪽"의 모양만 정한다 ----
namespace render {
struct DebugLine {
    float x0, y0, x1, y1;
    std::string label;
};

class DebugDraw {
public:
    using Provider = std::function<void(std::vector<DebugLine>&)>;
    void add_provider(Provider p) { providers_.push_back(std::move(p)); }
    void frame()
    {
        std::vector<DebugLine> lines;
        for (auto& p : providers_)
            p(lines);                 // 누가 주는지 모른 채 모은다
        for (const auto& l : lines)
            std::println("선 ({},{})-({},{}) {}", l.x0, l.y0, l.x1, l.y1,
                         l.label);
    }

private:
    std::vector<Provider> providers_;
};
}  // namespace render

// ---- game 층: 아래의 render를 알고, 자기 정보를 등록한다 ----
namespace game {
struct Player {
    float x = 3, y = 4;
    float vx = 1, vy = 0;
};
}  // namespace game

int main()
{
    render::DebugDraw debug;
    game::Player player;
    debug.add_provider([&player](std::vector<render::DebugLine>& out) {
        out.push_back({player.x, player.y, player.x + player.vx,
                       player.y + player.vy, "플레이어 속도"});
    });
    debug.frame();
}
```

```text
선 (3,4)-(4,4) 플레이어 속도
```

`render::DebugDraw`는 `game::Player`라는 이름을 한 번도 쓰지 않습니다. 등록하는 쪽(`main`, 곧 게임 층)이 둘을 잇습니다. 같은 모양이 엔진 곳곳에 나옵니다. 물리 엔진이 충돌을 알릴 때, 자원 시스템이 "파일이 바뀌었다"고 알릴 때, 플랫폼 층이 창 크기 변화를 알릴 때 모두 아래층이 콜백·이벤트의 모양을 정하고 위층이 듣습니다. 이벤트는 [「이벤트와 메시지」](#/read/cpp-game-engine/ecs-events)에서 더 봅니다.

<Note>
`std::function`은 편하지만 호출마다 간접 호출이 하나 끼고, 큰 람다를 담으면 할당이 생길 수 있습니다([「타입 지우기 구현하기」](#/read/cpp-advanced/te-implement)). 디버그 그리기처럼 프레임에 몇 번 부르는 곳에는 상관없고, 프레임에 수만 번 부르는 곳에서는 다른 모양(함수 포인터 + 사용자 데이터, 가상 함수 한 번, 데이터를 모아 한 번에 넘기기)을 고릅니다.
</Note>

## 층을 너무 많이 만들지 않기

층은 많을수록 좋은 것이 아닙니다. 층마다 감싸개를 두면 "파일 하나 읽는" 데 다섯 겹의 함수를 지나게 되고, 각 층이 자기만의 문자열·컨테이너 타입을 만들면 변환 코드가 늘어납니다. 이 책은 위 표의 일곱 층 정도로 시작하고, 필요가 보일 때 나눕니다. 처음부터 "언젠가 필요할" 추상화를 만들지 않는 것도 엔진 설계의 중요한 기술입니다.

## 정리

- 게임 엔진은 플랫폼, 코어, 자원, 서브시스템, 게임 틀, 게임, 도구의 층으로 나누고, 위층만 아래층을 안다
- 층은 옮기기·시험·빌드 시간·책임을 쉽게 하며, 의존 방향은 빌드 시스템의 타깃 의존으로 도구가 지키게 한다
- 아래층이 위층의 정보를 필요로 하면 아래층이 콜백·인터페이스의 모양을 정하고 위층이 등록하도록 의존을 뒤집는다
