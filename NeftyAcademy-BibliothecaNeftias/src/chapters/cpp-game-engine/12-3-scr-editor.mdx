[「리플렉션 만들기」](#/read/cpp-game-engine/scr-reflection)에서 만든 필드 정보는 결국 두 손님을 위한 것입니다. 하나는 파일로 저장하고 불러오는 직렬화, 다른 하나는 편집기입니다. 이 장에서는 같은 필드 목록으로 둘을 한꺼번에 해결하고, 개발 중에 형식이 바뀌어도 옛 파일이 깨지지 않게 하는 방법과 편집기 안에서 게임을 돌렸다가 되돌리는 방법을 봅니다.

## 같은 목록, 세 가지 쓰임

이번에는 필드 위치 대신 **멤버 포인터**(`float T::*`)를 저장해서 [「리플렉션 만들기」](#/read/cpp-game-engine/scr-reflection) 노트의 `offsetof` 문제를 피했습니다.

```cpp
#include <map>
#include <print>
#include <sstream>
#include <string>
#include <vector>

// 12.1의 리플렉션을 줄인 것: 필드마다 읽기·쓰기 함수와 옛 이름
template <class T> struct FieldT {
    const char* name;
    const char* old_name;                  // 이름을 바꾼 필드의 예전 이름
    const char* label;                     // 속성 창에 보일 이름
    float T::*member;
    float min, max;
};
struct Enemy { float hp = 100, speed = 3, sight = 10; };
const std::vector<FieldT<Enemy>> enemy_fields = {
    {"hp", nullptr, "체력", &Enemy::hp, 1, 999},
    {"speed", "spd", "이동 속도", &Enemy::speed, 0, 20},
    {"sight", nullptr, "시야 거리", &Enemy::sight, 0, 100},
};

// ---- 리플렉션으로 만든 범용 저장/불러오기: "이름 값" 줄들 ----
template <class T>
std::string save(const T& obj, const std::vector<FieldT<T>>& fs) {
    std::ostringstream o;
    for (auto& f : fs) o << f.name << " " << obj.*f.member << "\n";
    return o.str();
}
template <class T>
void load(T& obj, const std::vector<FieldT<T>>& fs, const std::string& text) {
    std::istringstream in(text);
    std::string key; float v;
    while (in >> key >> v) {
        bool found = false;
        for (auto& f : fs)
            if (key == f.name || (f.old_name && key == f.old_name)) {
                obj.*f.member = v; found = true;
            }
        if (!found) std::println("  모르는 필드 '{}' 건너뜀", key);
    }
}

// ---- 속성 창: 필드 목록만 보고 그린다 ----
template <class T>
void panel(const T& obj, const std::vector<FieldT<T>>& fs) {
    for (auto& f : fs) {
        float v = obj.*f.member;
        int bar = int(10 * (v - f.min) / (f.max - f.min) + 0.5f);
        std::println("  [{}{}] {:5} {}", std::string(bar, '#'),
                     std::string(10 - bar, '.'), v, f.label);
    }
}

int main() {
    std::println("-- 옛 파일 읽기 (spd는 옛 이름, sight 없음, color는 지운 필드)");
    Enemy e;
    load(e, enemy_fields, "hp 250\nspd 7\ncolor 3\n");
    std::print("{}", save(e, enemy_fields));

    std::println("-- 속성 창");
    panel(e, enemy_fields);

    std::println("-- 편집기에서 플레이 누르기: 장면을 찍어 두고 실행");
    std::vector<Enemy> scene = {e, Enemy{}};
    std::vector<std::string> snapshot;
    for (auto& x : scene) snapshot.push_back(save(x, enemy_fields));
    for (int frame = 0; frame < 3; ++frame)          // 게임이 돌며 값을 바꾼다
        for (auto& x : scene) x.hp -= 40;
    std::println("  실행 중 체력: {} {}", scene[0].hp, scene[1].hp);
    for (std::size_t i = 0; i < scene.size(); ++i)   // 정지: 찍어 둔 것으로 복원
        load(scene[i], enemy_fields, snapshot[i]);
    std::println("  정지 후 체력: {} {}", scene[0].hp, scene[1].hp);
}
```

## 형식이 바뀌어도 읽히게

[「저장과 불러오기」](#/read/cpp-game-engine/scene-serialize)에서는 버전 번호로 옛 파일을 구분했습니다. 리플렉션이 있으면 대부분의 변화를 버전 없이 견딜 수 있습니다. 비결은 값을 **이름과 함께** 저장하고, 읽을 때 이름으로 찾는 것입니다.

- **없는 필드**: 옛 파일에는 `sight`가 없었지만, 객체의 기본값 10이 그대로 남았습니다. 새 필드를 추가해도 옛 파일이 읽힙니다
- **모르는 필드**: 지워진 `color`는 경고만 남기고 건너뛰었습니다. 오류로 멈추면 필드 하나를 지울 때마다 모든 파일을 고쳐야 합니다
- **바뀐 이름**: `speed`의 예전 이름 `spd`를 필드 정보에 적어 두어서, 옛 파일의 `spd 7`이 `speed`로 들어갔습니다. 다시 저장하면 새 이름으로 쓰이므로, 파일은 열고 저장할 때마다 조금씩 최신 형식으로 옮겨 갑니다

타입이 바뀌는 것(정수를 실수로, 한 값을 두 값으로)처럼 이름만으로 안 되는 변화에는 여전히 버전과 변환 함수가 필요합니다. 그래도 대부분의 일상적인 변화는 이 세 규칙으로 해결됩니다.

## 속성 창

`panel`은 `Enemy`를 모르고 필드 목록만 보고 화면을 그립니다. 표시 이름과 범위도 목록에 있으니 슬라이더가 저절로 생깁니다. 실제 편집기는 [「즉시 모드 GUI」](#/read/cpp-game-engine/ed-imgui)로 이런 창을 그리고, 값 종류마다 위젯(실수는 끌기, 색은 색 고르기, 에셋 참조는 끌어다 놓기)을 정해 둡니다. 새 컴포넌트를 만들면 별도의 편집기 코드 없이 속성 창에 바로 나타나는 것, 이것이 리플렉션을 만드는 가장 큰 이유입니다. 값을 바꾸는 일은 [「실행 취소」](#/read/cpp-game-engine/ed-undo)가 기록할 수 있도록 명령 객체를 통해 합니다.

## 플레이 모드와 복원

편집기 안에서 플레이를 누르면 게임이 돌면서 장면의 값을 마구 바꿉니다. 실행 중 체력이 130과 -20이 되었습니다. 정지를 누르면 편집하던 상태로 돌아와야 하므로, 플레이 직전에 장면 전체를 **직렬화해 찍어 두고** 정지할 때 그것으로 되돌립니다. 저장 코드를 그대로 쓰므로 따로 만들 것이 없습니다.

<Note>
찍어 두기 대신 플레이용 장면을 통째로 복사해 따로 돌리는 엔진도 있고, 아예 게임을 별도 프로세스로 띄워 편집기와 소켓으로 통신하는 엔진도 있습니다. 별도 프로세스는 게임이 죽어도 편집기가 살아남고 콘솔이나 휴대폰 같은 다른 기기에서 돌리는 게임에도 연결할 수 있지만, 장면과 변경 사항을 계속 직렬화해 주고받아야 합니다. 어느 쪽이든 그 통신의 바탕은 같은 리플렉션 기반 직렬화입니다.
</Note>

## 정리

- 리플렉션 하나로 저장, 불러오기, 속성 창, 플레이 모드 복원을 모두 만든다
- 값을 이름과 함께 저장하면 없는 필드는 기본값, 모르는 필드는 건너뛰기, 바뀐 이름은 옛 이름 기록으로 버전 없이 견딘다
- 플레이 직전 장면을 직렬화해 찍어 두고 정지할 때 되돌리며, 별도 프로세스 방식도 같은 직렬화 위에 선다
