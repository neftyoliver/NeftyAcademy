[「비동기 로딩」](#/read/cpp-game-engine/res-async)으로 에셋을 올렸다면, 언제 내릴까요? 바위 텍스처는 바위 백 개가 함께 쓰고, 그 바위들이 하나씩 사라지다 마지막 하나가 사라질 때에야 내려도 됩니다. 또 아티스트가 텍스처를 고쳐 저장하면, 게임을 다시 켜지 않고 바로 바뀌어 보이면 좋겠습니다. 이 쪽은 에셋의 **수명**과 **다시 불러오기**를 다룹니다.

## 같은 것은 한 번만, 아무도 안 쓰면 내린다

```cpp
#include <cstdint>
#include <map>
#include <print>
#include <string>
#include <vector>

struct Texture { std::string data; std::uint32_t version = 0; };

class TextureCache {
public:
    std::uint32_t acquire(const std::string& path)      // 이미 있으면 같은 것을
    {
        auto id = static_cast<std::uint32_t>(slots_.size());
        auto [it, fresh] = by_path_.try_emplace(path, id);
        if (fresh) {
            slots_.push_back({path, {"<" + path + " v1>", 1}, 0, -1});
            std::println("  읽음 {}", path);
        }
        auto& s = slots_[it->second];
        ++s.refs;
        s.release_frame = -1;                           // 다시 쓰이면 내리기 취소
        return it->second;
    }
    void release(std::uint32_t id, int frame)
    {
        if (--slots_[id].refs == 0) slots_[id].release_frame = frame;
    }
    const Texture& get(std::uint32_t id) const { return slots_[id].tex; }

    // 파일이 바뀌었다: 같은 칸에서 내용만 바꾼다. 핸들을 든 쪽은 그대로
    void reload(const std::string& path)
    {
        auto& s = slots_[by_path_.at(path)];
        ++s.tex.version;
        s.tex.data = "<" + path + " v" + std::to_string(s.tex.version) + ">";
        std::println("  다시 읽음 {} -> 판 {}", path, s.tex.version);
    }
    // 아무도 안 쓴 지 2프레임 지난 것만 내린다(GPU가 아직 쓸 수 있다)
    void end_frame(int frame)
    {
        for (auto& s : slots_)
            if (s.refs == 0 && s.release_frame >= 0 &&
                frame - s.release_frame >= 2) {
                std::println("  내림 {} (프레임 {})", s.path, frame);
                s.release_frame = -1;
                s.tex.data.clear();
            }
    }

private:
    struct Slot {
        std::string path;
        Texture tex;
        int refs;
        int release_frame;
    };
    std::vector<Slot> slots_;
    std::map<std::string, std::uint32_t> by_path_;
};

struct Material {                 // 텍스처를 쓰는 쪽: 판이 바뀌면 다시 만든다
    std::uint32_t tex;
    std::uint32_t built_version = 0;
    void update(const TextureCache& c)
    {
        if (c.get(tex).version != built_version) {
            built_version = c.get(tex).version;
            std::println("  머티리얼 다시 만듦: {}", c.get(tex).data);
        }
    }
};

int main()
{
    TextureCache cache;
    std::println("프레임 1");
    auto a = cache.acquire("rock.tex");
    auto b = cache.acquire("rock.tex");               // 두 번째는 읽지 않는다
    Material mat{a};
    mat.update(cache);
    std::println("  같은 텍스처인가: {}", a == b);

    std::println("프레임 2");
    cache.reload("rock.tex");                         // 아티스트가 저장했다
    mat.update(cache);

    std::println("프레임 3");
    cache.release(a, 3);
    cache.release(b, 3);                              // 이제 아무도 안 쓴다
    cache.end_frame(3);
    std::println("프레임 4");
    cache.end_frame(4);
    std::println("프레임 5");
    cache.end_frame(5);
}
```

```text
프레임 1
  읽음 rock.tex
  머티리얼 다시 만듦: <rock.tex v1>
  같은 텍스처인가: true
프레임 2
  다시 읽음 rock.tex -> 판 2
  머티리얼 다시 만듦: <rock.tex v2>
프레임 3
프레임 4
프레임 5
  내림 rock.tex (프레임 5)
```

- **같은 경로는 한 번만**: `rock.tex`를 두 번 달라고 했지만 읽기는 한 번이었고, 두 핸들이 같은 칸을 가리킵니다. 대신 **참조 수**가 2가 됩니다
- **0이 되어도 바로 내리지 않는다**: 3프레임에 둘 다 놓아 참조 수가 0이 되었지만, 실제로 내린 것은 2프레임 뒤인 5프레임입니다. CPU가 다음 프레임을 준비하는 동안 GPU는 아직 지난 프레임을 그리고 있을 수 있어서, 방금 놓은 텍스처를 그리는 명령이 GPU에 남아 있을 수 있기 때문입니다. 그 사이에 누가 다시 달라고 하면 내리기를 취소하고 그대로 씁니다
- 참조 세기는 「C++ 고급」의 [「shared_ptr의 제어 블록」](#/read/cpp-advanced/sp-shared)과 같은 생각이지만, 엔진은 보통 `shared_ptr` 대신 정수 핸들과 칸마다의 수를 씁니다. 해제 시점을 위처럼 엔진이 정해야 하고, 원자적 증감이 필요 없는 곳(한 스레드에서만 다루는 곳)에서는 그 비용도 아낄 수 있기 때문입니다

## 다시 불러오기: 같은 핸들, 새 내용

파일이 바뀌면 캐시는 **같은 칸**에서 내용만 바꾸고 판 번호를 올립니다. 핸들을 들고 있는 쪽은 아무것도 바꿀 필요가 없습니다. 이것이 핸들(한 번 거쳐 가는 번호)을 쓰는 큰 이유 중 하나입니다. 포인터를 직접 나눠 줬다면 새 텍스처의 주소를 모든 곳에 다시 알려야 합니다.

에셋을 **쓰는 쪽**은 판 번호를 기억해 두었다가, 바뀌면 자기가 만든 것을 다시 만듭니다. 위의 머티리얼은 텍스처가 판 2가 되자 스스로 다시 만들어졌습니다. 텍스처 → 머티리얼 → 프리팹처럼 의존이 이어지면, [「에셋 파이프라인」](#/read/cpp-game-engine/res-pipeline)의 의존 정보로 다시 구울 것과 다시 불러올 것을 함께 정합니다.

## 바뀐 것 알아채기

| 방법 | 장단점 |
| --- | --- |
| 운영체제의 파일 감시(inotify, ReadDirectoryChangesW, FSEvents) | 바로 알지만 운영체제마다 다르고, 저장 한 번에 알림이 여러 번 오기도 한다 |
| 주기적으로 수정 시각 보기 | 단순하고 어디서나 되지만 늦고, 파일이 많으면 느리다 |
| 에디터·굽기 도구가 직접 알림(소켓, 파이프) | 굽기가 끝난 뒤에 정확히 한 번 알 수 있다 |

[「동적 라이브러리와 핫 리로드」](#/read/cpp-game-engine/plat-hot-reload)에서처럼, 쓰는 도중의 파일을 읽지 않도록 "굽기가 끝났다"를 확인하고 다시 불러오는 것이 중요합니다. 그래서 큰 엔진은 에디터나 굽기 도구가 게임에게 직접 알려 주는 마지막 방법을 많이 씁니다.

<Note>
메모리가 정해진 기기에서는 참조 수가 0인 에셋을 바로 버리지 않고 **예산** 안에서 캐시로 들고 있다가, 자리가 모자랄 때 가장 오래 안 쓴 것부터 내리는(LRU) 방법을 함께 씁니다. 방금 지나온 방을 돌아갔을 때 다시 읽지 않아도 됩니다. 반대로 예산을 넘었는데 모두 쓰이는 중이라 내릴 수 없다면, 그 장면은 기기에 비해 너무 무거운 것이니 경고를 띄웁니다([「성능 예산」](#/read/cpp-game-engine/ship-budget)).
</Note>

## 정리

- 같은 에셋은 한 번만 읽고 참조 수를 세며, 0이 되어도 GPU가 아직 쓸 수 있으므로 몇 프레임 뒤에 내리고 그 사이 다시 쓰이면 취소한다
- 다시 불러오기는 같은 칸에서 내용만 바꾸고 판 번호를 올려, 핸들을 든 쪽은 그대로 두고 쓰는 쪽이 판을 보고 다시 만든다
- 바뀐 것은 파일 감시, 수정 시각, 도구의 직접 알림으로 알아채고, 굽기가 끝난 뒤에만 다시 불러오며, 메모리 예산 안에서 LRU 캐시를 함께 쓴다
