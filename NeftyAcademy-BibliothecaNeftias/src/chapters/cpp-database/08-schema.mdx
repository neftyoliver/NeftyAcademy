프로그램이 자라면 테이블도 바뀝니다. 열이 늘고, 이름이 바뀌고, 인덱스가 생깁니다. 개발자의 기계, 테스트 서버, 운영 서버의 스키마가 저마다 다르면 같은 코드가 어디서는 돌고 어디서는 깨집니다. **마이그레이션**은 스키마의 변경을 번호 붙은 작은 단계로 적어 두고, 각 데이터베이스가 어디까지 적용했는지 기록해 두었다가 남은 단계만 차례대로 적용하는 방식입니다. 이미 배포한 단계는 고치지 않고, 바꿀 것이 있으면 새 단계를 더합니다.

## 작은 마이그레이터

SQLite에는 데이터베이스 파일 머리에 정수 하나를 적어 두는 `PRAGMA user_version`이 있어서, 적용한 마지막 번호를 담기에 알맞습니다. 아래 `migrate`는 프로그램이 시작할 때 부르는 것을 가정합니다.

```cpp flags=-lsqlite3
#include <sqlite3.h>
#include <cstdio>
#include <string>
#include <vector>

struct Migration {
    int version;
    const char* name;
    const char* sql;
};

std::string one(sqlite3* db, const char* sql) {   // 첫 행의 첫 칸
    sqlite3_stmt* st;
    sqlite3_prepare_v2(db, sql, -1, &st, nullptr);
    std::string v;
    if (sqlite3_step(st) == SQLITE_ROW && sqlite3_column_text(st, 0))
        v = reinterpret_cast<const char*>(sqlite3_column_text(st, 0));
    sqlite3_finalize(st);
    return v;
}

// 아직 적용하지 않은 것만 순서대로, 하나씩 트랜잭션 안에서 적용한다
void migrate(sqlite3* db, const std::vector<Migration>& ms) {
    int applied = 0;
    for (const Migration& m : ms) {
        if (m.version <= std::stoi(one(db, "PRAGMA user_version"))) continue;
        std::string sql = std::string("BEGIN IMMEDIATE; ") + m.sql +
                          "; PRAGMA user_version = " + std::to_string(m.version) +
                          "; COMMIT";
        char* err = nullptr;
        if (sqlite3_exec(db, sql.c_str(), nullptr, nullptr, &err) != SQLITE_OK) {
            std::printf("  v%d %s 실패: %s → 되돌림\n", m.version, m.name, err);
            sqlite3_free(err);
            sqlite3_exec(db, "ROLLBACK", nullptr, nullptr, nullptr);
            break;                               // 뒤의 것도 적용하지 않는다
        }
        std::printf("  v%d %s\n", m.version, m.name);
        ++applied;
    }
    if (applied == 0) std::printf("  할 일 없음\n");
    std::printf("  → 버전 %s, 열 %s\n", one(db, "PRAGMA user_version").c_str(),
                one(db, "SELECT group_concat(name, ', ') "
                        "FROM pragma_table_info('products')").c_str());
}

int main() {
    sqlite3* db;
    sqlite3_open(":memory:", &db);
    Migration v1{1, "상품 테이블",
                 "CREATE TABLE products (id INTEGER PRIMARY KEY, "
                 "name TEXT NOT NULL, price INTEGER)"};
    Migration v2{2, "title 열을 더하고 name 값으로 채움",   // 넓히기(expand)
                 "ALTER TABLE products ADD COLUMN title TEXT; "
                 "UPDATE products SET title = name"};
    Migration v3{3, "title 인덱스",
                 "CREATE INDEX products_title ON products (title)"};
    Migration v4_bad{4, "name 열 지우기",                 // 좁히기(contract), 실수
                     "ALTER TABLE products DROP COLUMN name; "
                     "CREATE INDEX products_name ON products (name)"};
    Migration v4{4, "name 열 지우기", "ALTER TABLE products DROP COLUMN name"};

    std::printf("1차 배포\n");
    migrate(db, {v1});
    sqlite3_exec(db, "INSERT INTO products (name, price) VALUES ('볼트', 120)",
                 nullptr, nullptr, nullptr);
    std::printf("2차 배포\n");
    migrate(db, {v1, v2, v3, v4_bad});
    std::printf("3차 배포 (v4를 고쳐서)\n");
    migrate(db, {v1, v2, v3, v4});
    std::printf("  데이터: %s\n",
                one(db, "SELECT title || ' ' || price FROM products").c_str());
    std::printf("다시 시작\n");
    migrate(db, {v1, v2, v3, v4});
    sqlite3_close(db);
}
```

```text
1차 배포
  v1 상품 테이블
  → 버전 1, 열 id, name, price
2차 배포
  v2 title 열을 더하고 name 값으로 채움
  v3 title 인덱스
  v4 name 열 지우기 실패: no such column: name → 되돌림
  → 버전 3, 열 id, name, price, title
3차 배포 (v4를 고쳐서)
  v4 name 열 지우기
  → 버전 4, 열 id, price, title
  데이터: 볼트 120
다시 시작
  할 일 없음
  → 버전 4, 열 id, price, title
```

- **한 번씩, 차례대로**: 2차 배포는 이미 적용된 v1을 건너뛰고 v2부터 적용했고, 다시 시작했을 때는 할 일이 없었습니다. 그래서 매번 시작할 때 불러도 됩니다
- **단계마다 트랜잭션**: v4는 열을 지운 뒤 두 번째 문장에서 실패했습니다. SQLite와 PostgreSQL은 DDL도 트랜잭션 안에서 되돌리므로, 지운 열과 버전 번호가 함께 돌아와 버전 3인 스키마가 그대로 남았습니다. 실패한 단계 뒤의 단계도 적용하지 않습니다
- **넓히기와 좁히기**: `name`을 `title`로 바꾸면서 열 이름을 한 번에 바꾸지 않았습니다. v2에서 새 열을 더해 채우고(넓히기), 모든 프로그램이 새 열을 쓰게 된 뒤 v4에서 옛 열을 지웁니다(좁히기). 배포하는 동안 옛 판과 새 판의 프로그램이 함께 돌아도 둘 다 동작합니다. 그 사이의 새 판은 두 열에 모두 쓰게 합니다
- **SQLite의 ALTER TABLE**: 열 더하기, 이름 바꾸기(3.25부터), 지우기(3.35부터)는 바로 되지만, 열의 형이나 제약을 바꾸려면 새 테이블을 만들어 옮기고 바꿔치는 절차를 밟아야 합니다

## 서버형 데이터베이스에서

PostgreSQL에서 `ALTER TABLE`은 테이블에 가장 강한 잠금을 겁니다. 오래 도는 쿼리 하나 뒤에서 이 잠금을 기다리는 동안, 그 뒤에 온 평범한 SELECT들까지 모두 줄을 서서 서비스가 멈춘 것처럼 보입니다. 그래서 마이그레이션에서는 `SET lock_timeout = '2s'`처럼 기다림에 끝을 두고, 실패하면 잠시 뒤 다시 합니다. 큰 테이블의 인덱스는 `CREATE INDEX CONCURRENTLY`로 쓰기를 막지 않고 만드는데, 이 문장은 트랜잭션 안에서 실행할 수 없어서(25001) 혼자 따로 도는 단계로 둡니다. PostgreSQL 11부터 바뀌지 않는 기본값을 가진 열은 테이블을 다시 쓰지 않고 바로 더해집니다. MySQL과 MariaDB는 DDL 문장이 그 자리에서 암묵적으로 커밋하므로 여러 문장짜리 단계는 중간에 실패하면 반만 남습니다. 단계 하나에 DDL 하나를 두고, `IF NOT EXISTS`처럼 다시 실행해도 되게 씁니다.

손으로 짠 마이그레이터 대신 도구를 쓰는 경우가 많습니다. Flyway는 `V3__add_title.sql`처럼 번호 붙은 SQL 파일을 차례대로 적용하고, 적용 기록과 체크섬을 `flyway_schema_history` 테이블에 남겨 이미 적용한 파일이 바뀌면 알려 줍니다. Liquibase는 변경 묶음(changeset)을 XML, YAML, SQL로 적고 `DATABASECHANGELOG` 테이블에 기록합니다. Sqitch는 번호 대신 변경 사이의 의존 관계로 순서를 정하고, 변경마다 적용(deploy), 되돌리기(revert), 확인(verify) 스크립트를 둡니다.

<Note>
되돌리기 스크립트를 두더라도, 데이터를 지운 단계는 되돌려도 데이터가 돌아오지 않습니다. 그래서 운영에서는 문제가 생기면 이전 판으로 되돌리기보다, 고친 새 단계를 앞으로 더하는 쪽이 보통입니다. 위험한 단계 전에는 백업을 떠 둡니다([「백업」](#/read/cpp-database/dbops-backup)).
</Note>

## 정리

- 스키마 변경은 번호 붙은 단계로 적고, 데이터베이스마다 적용한 번호를 기록해 남은 단계만 차례대로 한 번씩 적용하며, 배포한 단계는 고치지 않는다
- SQLite와 PostgreSQL은 단계마다 트랜잭션으로 감쌀 수 있지만 MySQL의 DDL은 암묵적으로 커밋하고, PostgreSQL의 CREATE INDEX CONCURRENTLY는 트랜잭션 밖에서 돌린다
- 이름 바꾸기 같은 변경은 넓히기와 좁히기로 나눠 옛 판과 새 판이 함께 돌게 하고, 테이블 잠금이 필요한 DDL에는 lock_timeout을 둔다
