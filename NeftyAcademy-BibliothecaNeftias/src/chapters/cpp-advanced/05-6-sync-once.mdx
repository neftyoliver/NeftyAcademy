"처음 필요할 때, **한 번만**" 만들고 싶은 것이 있습니다. 읽는 데 오래 걸리는 표, 연결, 로그 파일입니다. 스레드가 하나일 때는 `if (!ready) { 만들기; ready = true; }`면 되지만, 둘이 동시에 오면 둘 다 만듭니다. C++에는 이것을 맞게 해 주는 도구가 둘 있고, 하나는 이미 쓰고 있었습니다.

## 정적 지역 변수

```cpp
#include <atomic>
#include <latch>
#include <mutex>
#include <print>
#include <stdexcept>
#include <string>
#include <thread>
#include <vector>

std::atomic<int> catalogs = 0;
std::atomic<int> builds = 0;

struct Catalog {
    Catalog() { ++catalogs; }           // 비싼 준비라고 치자
};

Catalog& catalog()
{
    // 여러 스레드가 동시에 와도 한 번만 만들어진다
    static Catalog instance;
    return instance;
}

// 객체마다 한 번: 정적 변수가 아니라 멤버를 늦게 채운다
class Report {
public:
    const std::string& text() const
    {
        std::call_once(built_, [this] {
            ++builds;
            text_ = "summary";
        });
        return text_;
    }

private:
    mutable std::once_flag built_;
    mutable std::string text_;
};

int attempts = 0;

int& flaky()
{
    static int value = [] {
        if (++attempts == 1) throw std::runtime_error("첫 시도는 실패");
        return 7;
    }();
    return value;
}

int main()
{
    Report report;
    std::latch start(1);
    {
        std::vector<std::jthread> workers;
        for (int i = 0; i < 8; ++i) {
            workers.emplace_back([&] {
                start.wait();           // 여덟이 한꺼번에 출발한다
                catalog();
                report.text();
            });
        }
        start.count_down();
    }
    std::println("Catalog 생성 {}번, Report 채우기 {}번", catalogs.load(),
                 builds.load());

    try {
        flaky();
    } catch (const std::exception& e) {
        std::println("flaky: {}", e.what());
    }
    int value = flaky();
    std::println("다시 부르면 {} (시도 {}번)", value, attempts);
}
```

```text
Catalog 생성 1번, Report 채우기 1번
flaky: 첫 시도는 실패
다시 부르면 7 (시도 2번)
```

함수 안의 `static` 변수는 [처음 지나갈 때 초기화됩니다](#/read/cpp-syntax/life-storage). C++11부터는 그 초기화가 **스레드에 안전**합니다. 한 스레드가 만드는 동안 온 다른 스레드는 끝날 때까지 기다렸다가 만들어진 것을 씁니다. 컴파일러가 변수 옆에 "만들었는가"를 적는 바이트를 두고, 함수의 첫머리에서 그것을 봅니다.

```text
from_static_local():
        movzbl 0x169d5(%rip), %eax      # "만들었는가" 바이트를 읽는다
        test   %al, %al
        je     ...                      # 아직이면 잠그고 만드는 느린 길로
        lea    0x169d2(%rip), %rax      # 만들어졌으면 주소만 돌려준다
        ret
```

만든 뒤에는 읽기 한 번과 비교 한 번입니다. 느린 길에서는 `__cxa_guard_acquire`가 잠급니다.

| 초기화하는 도중에 | 일어나는 일 |
| --- | --- |
| 다른 스레드가 같은 줄에 온다 | 끝날 때까지 기다린다 |
| 예외가 나온다 | "아직 안 한 것"으로 남는다. 다음에 지나갈 때 다시 한다(`flaky`) |
| 같은 스레드가 그 줄에 다시 온다(초기화식이 그 함수를 부른다) | 정의되지 않은 동작. GCC와 Clang 모두 프로그램을 끝냈다 |
| 두 스레드가 서로의 정적 변수가 만들어지기를 기다린다 | [교착](#/read/cpp-advanced/sync-deadlock) |

## call_once

정적 지역 변수는 프로그램에 하나입니다. **객체마다** 한 번씩 해야 하는 일은 `std::once_flag`를 멤버로 두고 `std::call_once`에 맡깁니다. 위의 `Report`가 그 꼴입니다. `text()`가 `const`인데 안을 채우므로 두 멤버는 `mutable`이고, `call_once`가 그 수정을 한 번으로, 한 스레드로 묶어 줍니다.

예외를 다루는 방식은 같습니다. 넘긴 함수가 예외로 끝나면 깃발은 서지 않고, 다음에 온 호출이 다시 시도합니다. 깃발 하나는 4바이트(libc++는 8바이트)입니다. 깃발은 복사도 이동도 되지 않으므로, 깃발을 멤버로 둔 클래스도 그렇게 됩니다.

## 방법마다의 값

| 이미 만들어진 뒤에 한 번 부르는 값 | GCC 14 | Clang 20 |
| --- | --- | --- |
| 정적 지역 변수 | 1.2 ns | 1.1 ns |
| `std::call_once` | 3.6 ns | 1.2 ns |
| 원자적 포인터를 보고, 없으면 잠그고 다시 본다 | 1.4 ns | 1.2 ns |
| 매번 `std::mutex`를 잠근다 | 19 ns | 18 ns |

x86-64 서버 VM에서 `-O2`로, 인라인되지 않는 함수를 2억 번 불러 잰 값입니다. 함수를 부르는 값 1 ns쯤이 들어 있으므로 앞의 셋은 사실상 공짜입니다. 셋째 줄은 "이중 확인 잠금"이라 불리는 손으로 쓰는 방법입니다.

```cpp
struct Config {
    int level = 3;
};

std::atomic<Config*> cached{nullptr};
std::mutex making;

Config& config()
{
    Config* p = cached.load(std::memory_order_acquire);    // 잠그지 않고 먼저 본다
    if (p == nullptr) {
        std::lock_guard lock(making);
        p = cached.load(std::memory_order_relaxed);         // 잠근 뒤에 다시 본다
        if (p == nullptr) {
            p = new Config;
            cached.store(p, std::memory_order_release);
        }
    }
    return *p;
}
```

포인터를 `std::atomic`으로 두지 않으면 [경합](#/read/cpp-advanced/atm-atomic)이고, 맞게 써도 정적 지역 변수보다 빠르지 않습니다. 컴파일러가 넣어 주는 확인이 바로 이 방법이기 때문입니다. 손으로 쓸 까닭은 없습니다.

## 늦추지 않아도 되는 것

가장 싼 초기화는 **실행 중에 하지 않는** 것입니다. [`constinit`](#/read/cpp-syntax/ct-consteval)이 붙는 전역 변수는 실행 파일에 값이 이미 들어 있어서 확인도, 순서 문제도 없습니다. `std::mutex`, `std::atomic`, `std::once_flag`의 생성자는 `constexpr`입니다. 그래서 전역 뮤텍스는 프로그램이 시작하기 전에 이미 쓸 수 있는 상태이고, 늦춰 만들 까닭이 없습니다.

## 사라지는 순서

정적 지역 변수는 `main`이 끝난 뒤 **만들어진 순서의 반대로** 사라집니다. 그때까지 돌고 있는 스레드가 있으면 사라진 객체를 건드립니다.

| 지킬 것 | 방법 |
| --- | --- |
| `main`이 끝나기 전에 스레드를 모두 끝낸다 | [`jthread`를 `main`의 지역 변수나 그 멤버로](#/read/cpp-advanced/res-ownership) 둔다. `detach`하지 않는다 |
| 정적 객체의 소멸자에서 다른 정적 객체를 쓰지 않는다 | 먼저 사라졌을 수 있다 |
| 끝까지 살아 있어야 하는 것 | `static Logger& log = *new Logger;`로 만들고 지우지 않는다 |

마지막 줄은 일부러 소멸자를 부르지 않는 방법입니다. 메모리는 프로세스가 끝날 때 운영체제가 거둬 가지만, 소멸자가 하던 일(버퍼 비우기)은 따로 챙겨야 합니다. 로그처럼 다른 소멸자들이 마지막까지 쓰는 객체에만 씁니다.

<Note>
"처음 쓸 때 한 번"은 [전역 객체의 초기화 순서 문제](#/read/cpp-syntax/life-static-init)를 푸는 방법이기도 합니다. 다른 파일의 전역 객체가 아직 만들어지지 않았을 수 있다면, 그것을 정적 지역 변수로 바꾸고 함수로 꺼내 쓰게 합니다. 부르는 순간 만들어지므로 순서가 저절로 맞습니다.
</Note>

## 정리

- 함수 안의 `static` 변수는 여러 스레드가 동시에 와도 한 번만 만들어진다. 만든 뒤의 확인은 읽기 한 번이다
- 객체마다 한 번 할 일은 `once_flag`와 `call_once`로 한다. 둘 다 예외가 나면 다음에 다시 시도한다
- 정적 객체는 `main` 뒤에 거꾸로 사라진다. 그 전에 스레드를 모두 끝낸다
