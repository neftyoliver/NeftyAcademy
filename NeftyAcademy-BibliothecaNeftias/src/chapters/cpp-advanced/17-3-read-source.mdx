코드는 쓰는 시간보다 읽는 시간이 깁니다. 남이 쓴 큰 코드를 처음부터 끝까지 읽을 수는 없으므로 들어가는 순서가 필요합니다. 두 곳에서 해 봅니다. 하나는 이 책이 내내 써 온 `std::println`의 원형인 `fmt` 라이브러리의 저장소이고, 하나는 이미 내 컴퓨터에 있는 표준 라이브러리의 헤더입니다.

## 먼저 크기를 잰다

GitHub의 `fmtlib/fmt`를 내려받아 2026년 11월 16일의 커밋에서 쟀습니다.

| 물은 것 | 명령 | 답 |
| --- | --- | --- |
| 얼마나 큰가 | `git ls-files` | 파일 148개. `test`에 69, `include`에 16 |
| 어디가 본체인가 | `wc -l include/fmt/*.h` | 헤더가 19,139줄이고 `format.h` 하나가 5,815줄 |
| 얼마나 오래됐나 | `git rev-list --count HEAD` | 2012년 12월부터 커밋 8,101개 |
| 누가 썼나 | `git shortlog -sn` | 이름 675개. 가장 많은 이름 하나가 5,895개 |

10분이면 나오는 숫자들이 읽을 곳을 정해 줍니다. 본체는 헤더 몇 개이고, 테스트 파일이 본체보다 네 배 많고, 커밋의 대부분을 한 사람이 썼습니다.

## 역사에 묻는다

저장소에는 코드만이 아니라 **그렇게 된 까닭**이 들어 있습니다.

| 물은 것 | 명령 | 답 |
| --- | --- | --- |
| 어디가 자주 바뀌나 | `git log --name-only --format=`을 세기 | `format.h`가 1,621번, `test/format-test.cc`가 785번 |
| 이 함수는 언제 생겼나 | `git log -S'void println(' -- include/fmt` | 2023년 1월 24일의 커밋 "Implement `println` (#3267)" |
| 이 줄은 왜 이렇게 됐나 | `git blame -L 시작,끝 파일` | 그 줄을 마지막으로 고친 커밋 |

- **자주 바뀌는 파일이 중심입니다.** 가장 많이 고쳐진 곳이 가장 중요하고, 가장 조심해서 건드릴 곳입니다.
- **`-S`는 글자가 늘거나 준 커밋을 찾습니다.** 함수가 처음 들어온 커밋의 메시지와 `#3267` 같은 번호를 따라가면 그때의 토론이 나옵니다. 코드에는 없는 "왜"가 거기 있습니다.

## 끝에서 거꾸로 따라간다

`std::println("{:>6}", 42)`가 화면에 닿기까지를 알고 싶습니다. `<format>`은 libstdc++ 14에서 4,586줄입니다. 위에서부터 읽지 않고, **결과가 나오는 곳에 중단점을 걸어** 거기까지 온 길을 봅니다.

```text nocheck
$ g++ -std=c++23 -g hello.cpp -o hello
$ gdb -batch -ex 'break fwrite' -ex run -ex bt ./hello      # 인자와 주소는 지웠다
#0  fwrite                    libio/iofwrite.c:31
#1  std::vprint_nonunicode    /usr/include/c++/14/print:60
#2  std::vprint_unicode       /usr/include/c++/14/print:70
#3  std::print<std::string>   /usr/include/c++/14/print:108
#4  std::println<int>         /usr/include/c++/14/print:122
#5  std::println<int>         /usr/include/c++/14/print:129
#6  main                      hello.cpp:5
```

읽을 곳이 4,586줄에서 여섯 줄로 줄었습니다. 그런데 4번과 3번이 이상합니다. `int`를 넘겼는데 `print`는 `string`을 받았습니다. 122번 줄을 열어 보면 까닭이 있습니다. 이 구현의 `println`은 먼저 `std::format`으로 문자열을 만들고, 그 문자열을 `"{}\n"`에 넣어 `print`를 한 번 더 부릅니다. **서식을 두 번 합니다.** 그렇다면 할당도 한 번 더 있을 것입니다.

```cpp
#include <cstdlib>
#include <new>
#include <print>

int allocations = 0;
void* operator new(std::size_t n)
{
    ++allocations;
    if (void* p = std::malloc(n)) return p;
    throw std::bad_alloc();
}
void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }

int main()
{
    int before = allocations;
    std::println("{:>40}", 42);
    const int with_println = allocations - before;

    before = allocations;
    std::print("{:>40}\n", 42);
    const int with_print = allocations - before;

    std::println("println {}번, print {}번", with_println, with_print);
}
```

```text
                                      42
                                      42
println 1번, print 0번
```

읽은 대로입니다. `/dev/null`에 200만 번 쓰며 쟀더니 `println`이 103 ns, 줄바꿈을 서식에 넣은 `print`가 65 ns였습니다. 짧아서 [문자열 안에 들어가는](#/read/cpp-advanced/perf-copies) 출력에서는 할당 없이 71 ns와 46 ns였습니다.

<Note kind="warn">
이것은 GCC 14의 libstdc++라는 **한 구현의 사정**이지 `println`의 성질이 아닙니다. Clang 20의 libc++에서는 둘 다 할당 한 번에 160 ns였습니다. 소스에서 읽은 것은 [그 버전의 답](#/read/cpp-advanced/read-reference)입니다.
</Note>

## 읽는 버릇

- **질문 하나를 들고 들어갑니다.** 이 장비의 libstdc++ 헤더는 802개 파일에 40만 줄입니다. "`println`은 어디서 쓰는가"가 그것을 여섯 줄로 줄였습니다.
- **이름의 규칙을 먼저 익힙니다.** libstdc++는 멤버에 `_M_`, 지역 이름에 `__`, 매크로에 `_GLIBCXX_`를 붙입니다. 사용자의 매크로와 부딪히지 않도록 구현에만 허락된 이름을 쓰는 것이고, 규칙을 알면 눈에 걸리지 않습니다.
- **읽은 것을 가설로 두고 돌려 봅니다.** 위에서 한 일입니다. 읽기만 하면 틀린 줄을 따라가고도 모릅니다.
- **도구에 맡깁니다.** 정의로 건너뛰기는 [`compile_commands.json`](#/read/cpp-advanced/tool-cmake)을 읽는 편집기가, 기계어는 [`objdump`](#/read/cpp-advanced/read-reference)가, 실행 중의 길은 디버거가 보여 줍니다.

이 책은 처음부터 끝까지 같은 일을 했습니다. 재고, 돌려 보고, 원문을 확인했습니다. 남의 코드 앞에서도, 다음 표준 앞에서도 할 일은 같습니다.

## 정리

- 큰 코드는 크기와 역사부터 본다. 파일 수, 가장 큰 파일, 자주 바뀌는 파일, 커밋의 수와 사람이 읽을 곳을 정해 준다
- 위에서부터 읽지 않는다. 결과가 나오는 곳에 중단점을 걸고 호출 경로를 거꾸로 읽으면 수천 줄이 몇 줄이 된다. 테스트는 돌아가는 설명서다
- 읽은 것은 가설이다. `println`이 서식을 두 번 한다는 것을 소스에서 읽고, 할당 한 번과 103 ns 대 65 ns로 확인했다. 그것도 그 버전의 답이다
