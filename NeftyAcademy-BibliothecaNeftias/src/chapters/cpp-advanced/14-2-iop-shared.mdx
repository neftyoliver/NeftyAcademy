공유 라이브러리(리눅스의 `.so`, 윈도우의 `.dll`)는 실행할 때 프로그램에 이어집니다. [앞 페이지](#/read/cpp-advanced/iop-c-abi)에서 경계에 둘 타입을 골랐으니, 여기서는 두 가지를 봅니다. 라이브러리의 **무엇이 밖으로 보이는가**, 그리고 프로세스 안에 같은 것이 **몇 벌 생기는가**입니다.

## 이름이 겹치면

```cpp nocheck
// liba.cpp → liba.so: 온도 라이브러리
#include <print>

const char* unit() { return "섭씨"; }       // 안에서만 쓰려던 도우미
void a_report(double value) { std::println("A: {} {}", value, unit()); }
```

```cpp nocheck
// libb.cpp → libb.so: 남이 만든 압력 라이브러리. 우연히 같은 이름을 썼다
#include <print>

const char* unit() { return "헥토파스칼"; }
void b_report(double value) { std::println("B: {} {}", value, unit()); }
```

```cpp nocheck
// main.cpp
void a_report(double value);
void b_report(double value);

int main()
{
    a_report(21.5);
    b_report(1013.0);
}
```

```text nocheck
$ g++ -fPIC -shared liba.cpp -o liba.so && g++ -fPIC -shared libb.cpp -o libb.so
$ g++ main.cpp -L. -la -lb -o app && LD_LIBRARY_PATH=. ./app
A: 21.5 섭씨
B: 1013 섭씨
$ g++ main.cpp -L. -lb -la -o app && LD_LIBRARY_PATH=. ./app
A: 21.5 헥토파스칼
B: 1013 헥토파스칼
```

압력이 섭씨로 찍혔습니다. 리눅스의 공유 라이브러리는 표시하지 않은 함수를 **모두 내보이고**, 같은 이름은 프로세스 전체에서 먼저 올라온 것 하나로 통합니다. `libb.so`가 제 안의 `unit()`을 부르는 것조차 그 규칙을 따릅니다. 경고도 오류도 없고, 링크 순서를 바꾸면 반대쪽이 틀립니다.

## 내보일 것만 내보인다

`-fvisibility=hidden`으로 기본을 뒤집고, 내놓을 것에만 표시를 답니다. 윈도우는 처음부터 이 방식이어서 매크로 하나로 둘을 맞춥니다.

```cpp
// thermo_api.h
#if defined(_WIN32)
#  if defined(THERMO_BUILD)                  // 라이브러리를 빌드하는 중
#    define THERMO_API __declspec(dllexport)
#  else                                      // 라이브러리를 쓰는 쪽
#    define THERMO_API __declspec(dllimport)
#  endif
#else
#  define THERMO_API __attribute__((visibility("default")))
#endif

THERMO_API void a_report(double value);      // 내보인다
const char* unit();                          // 표시가 없으면 안에만 있다
```

두 라이브러리를 이렇게 다시 빌드하자 `B: 1013 헥토파스칼`이 됐습니다. 파일 20개짜리 라이브러리에 해 보면 숫자로도 보입니다(GCC 14 `-O2`).

| | 그냥 | `-fvisibility=hidden`, 함수 20개만 표시 |
| --- | --- | --- |
| 내보인 이름 | 183개 | 46개 |
| 파일 크기 | 234 KB | 213 KB |
| 올릴 때 이어 줄 자리 | 220곳 | 97곳 |

남은 46개 가운데 26개는 표준 라이브러리의 템플릿과 타입 정보입니다. 내보인 이름은 곧 [지켜야 할 약속](#/read/cpp-advanced/iop-abi-stable)이므로 적을수록 좋습니다.

## 하나인 줄 알았던 것이 여럿

숨기면 생기는 일도 있습니다. 헤더에 이런 함수를 두고 프로그램과 라이브러리 둘이 한 번씩 올렸습니다.

```cpp
// counter.h: 어디서 불러도 같은 변수를 준다고 믿었다
inline int& counter()
{
    static int value = 0;
    return value;
}
```

| 빌드 | 프로그램이 본 `counter()` |
| --- | --- |
| 그냥 | 3 |
| 셋 다 `-fvisibility=hidden` | 1 |

숨기자 `static` 변수가 모듈마다 한 벌씩 생겼습니다. 싱글턴, 등록부, 캐시가 이렇게 갈라집니다. 여러 모듈이 함께 쓸 상태는 **한 라이브러리의 `.cpp`에 두고, 내보인 함수로만** 닿게 합니다.

타입의 정체도 갈라집니다. 헤더에 정의한 예외 `SensorError`를 라이브러리가 던지고 프로그램이 잡게 했습니다. libstdc++에서는 숨겨도 잡혔고, libc++에서는 `catch (const SensorError&)`를 지나쳐 `std::exception`으로만 잡혔습니다. 타입에 `struct THERMO_API SensorError`처럼 표시를 달자 잡혔습니다. 경계를 넘어 던지거나 `dynamic_cast`할 타입은 내보입니다.

## 실행 중에 올리기

플러그인은 프로그램이 뜬 뒤에 이름으로 찾아 올리는 공유 라이브러리입니다. 찾을 이름이 망가지지 않도록 들머리는 [C 함수](#/read/cpp-advanced/iop-c-abi)로 둡니다.

```cpp nocheck
// filter.h: 프로그램과 플러그인이 함께 읽는 약속
#pragma once

struct Filter {
    virtual ~Filter() = default;
    virtual double apply(double sample) = 0;
};

// 플러그인이 C 이름으로 내놓아야 하는 함수 둘
extern "C" {
typedef Filter* (*create_filter_fn)(void);
typedef void (*destroy_filter_fn)(Filter*);
}
```

```cpp nocheck
// smooth.cpp → libsmooth.so
#include "filter.h"

#define EXPORT __attribute__((visibility("default")))

namespace {
class Smooth : public Filter {
public:
    double apply(double sample) override
    {
        value_ = started_ ? value_ * 0.5 + sample * 0.5 : sample;
        started_ = true;
        return value_;
    }

private:
    double value_ = 0;
    bool started_ = false;
};
}

extern "C" {
EXPORT Filter* create_filter() { return new Smooth; }
EXPORT void destroy_filter(Filter* f) { delete f; }
}
```

```cpp nocheck
// host.cpp: 실행 중에 파일 이름으로 찾아 올린다
#include "filter.h"

#include <dlfcn.h>
#include <memory>
#include <print>

int main()
{
    void* library = dlopen("./libsmooth.so", RTLD_NOW);
    if (library == nullptr) {
        std::println("올리지 못함: {}", dlerror());
        return 1;
    }
    const auto create =
        reinterpret_cast<create_filter_fn>(dlsym(library, "create_filter"));
    const auto destroy =
        reinterpret_cast<destroy_filter_fn>(dlsym(library, "destroy_filter"));
    if (create == nullptr || destroy == nullptr) {
        std::println("약속한 함수가 없다");
        return 1;
    }
    {
        std::unique_ptr<Filter, destroy_filter_fn> filter(create(), destroy);
        for (double sample : {10.0, 20.0, 20.0})
            std::println("{}", filter->apply(sample));
    }                    // 객체를 먼저 없애고
    dlclose(library);    // 그다음에 내린다
}
```

```text nocheck
$ g++ -std=c++23 -fPIC -fvisibility=hidden -shared smooth.cpp -o libsmooth.so
$ g++ -std=c++23 host.cpp -o host && ./host
10
15
17.5
```

`Filter`는 가상 함수가 있는 C++ 타입입니다. 이 꼴은 프로그램과 플러그인을 **같은 컴파일러와 표준 라이브러리로** 빌드할 때만 씁니다. 그렇지 않다면 [핸들과 C 함수](#/read/cpp-advanced/iop-c-abi)로 내려갑니다. 만든 쪽이 없애도록 `destroy_filter`를 함께 내놓은 것도 같은 까닭입니다.

<Note kind="warn">
내리는 순서를 지킵니다. 객체가 살아 있는데 `dlclose`를 하고 `filter->apply()`를 불렀더니 `Segmentation fault`로 죽었습니다. 가상 함수의 코드가 메모리에서 사라졌기 때문입니다. 플러그인이 준 객체, 콜백, 그 안에서 돌던 스레드가 모두 끝난 뒤에 내립니다.
</Note>

## 리눅스와 윈도우

| | 리눅스 (`.so`) | 윈도우 (`.dll`) |
| --- | --- | --- |
| 표시하지 않은 함수 | 내보인다 | 내보이지 않는다 |
| 두 라이브러리에 같은 이름 | 먼저 올라온 것 하나로 통한다 | 라이브러리마다 제 것을 쓴다 |
| 헤더의 `inline` 함수 속 `static` | 숨기지 않으면 하나로 합쳐진다 | 모듈마다 한 벌 |
| `new`와 `delete` | 보통 프로세스에 힙 하나 | 모듈이 다른 런타임을 쓰면 힙도 따로다 |

윈도우 쪽은 이 책의 환경에서 돌려 보지 못했고, 널리 알려진 동작을 적었습니다. 두 칸을 함께 만족하는 규칙은 하나입니다. **리눅스에서도 숨기고 빌드하고, 윈도우에서 될 것만 한다.**

## 정리

- 리눅스는 다 내보이고 같은 이름을 하나로 통한다. 두 라이브러리의 `unit()`이 겹쳐 압력이 섭씨로 찍혔다
- `-fvisibility=hidden`과 표시 매크로로 내놓을 것만 내놓는다. 대신 헤더의 `static`과 타입의 정체가 모듈마다 갈라진다
- 플러그인의 들머리는 C 함수로 두고, 만든 쪽이 없애며, 객체가 다 사라진 뒤에 내린다
