[「수명이 끝난 객체 쓰기」](#/read/cpp-syntax/ubc-lifetime)와 [「임시 객체의 수명」](#/read/cpp-syntax/life-temporary)에서 사라진 객체를 가리키게 되는 길과 도구가 잡아 주는 것을 봤습니다. 여기서는 컴파일러가 그것을 **어떻게** 찾는지를 보고, 그 검사를 내 코드까지 넓힙니다.

## 두 컴파일러, 두 방식

```cpp nocheck
struct NameView {                                   // 내가 만든 뷰
    const char* data;
    NameView(const std::string& s) : data(s.c_str()) {}
};
const std::string& longer(const std::string& a, const std::string& b);
struct Config {
    std::string name_;
    const std::string& name() const { return name_; }
};

NameView v = std::string("temporary");              // 1
const std::string& r = longer(s, "temporary");      // 2
const std::string& n = load().name();               // 3
std::string_view w;
w = make();                                         // 4. make는 string을 돌려준다
```

네 줄 모두 문장이 끝나면 사라지는 임시 객체를 붙듭니다. `-Wall`로 컴파일했습니다.

| 줄 | GCC 14 | Clang 20 |
| --- | --- | --- |
| 1 | `-O2`일 때만 경고 | 조용하다 |
| 2 | 경고 | 조용하다 |
| 3 | 경고 | 조용하다 |
| 4 | 조용하다 | 경고 |

- **GCC는 짐작합니다.** 임시 객체를 참조로 받아 참조를 돌려주는 함수의 결과를 참조에 묶으면 `possibly dangling reference to a temporary`라고 합니다. 함수의 속은 보지 않습니다. 1번은 다른 길로 잡혔습니다. 최적화가 생성자를 펼친 뒤에야 죽은 메모리를 읽는 것이 보여서, `-O0`에서는 조용했습니다.
- **Clang은 표시를 읽습니다.** 표준 라이브러리의 `string`에는 주인, `string_view`에는 가리키는 것이라는 표시가 붙어 있어서 4번을 압니다. 표시가 없는 내 타입과 함수에는 조용합니다.

짐작은 틀리기도 합니다.

```cpp nocheck
const std::string& lookup(const std::string& key);  // 표에 든 값을 돌려준다
const std::string& mode = lookup("mode");           // 옳은 코드
```

돌려준 참조는 인자와 상관없는데도 GCC는 같은 경고를 냈습니다. 선언에 `[[gnu::no_dangling]]`을 붙이자 조용해졌습니다. GCC에는 "이것은 괜찮다"를, Clang에는 "이것은 묶인다"를 적어 주는 셈입니다.

## 표시를 붙인다

```cpp
#include <print>
#include <string>
#include <string_view>
#include <vector>

#if __has_cpp_attribute(clang::lifetimebound)
#define LIFETIMEBOUND [[clang::lifetimebound]]
#else
#define LIFETIMEBOUND
#endif
#if __has_cpp_attribute(clang::lifetime_capture_by)
#define CAPTURED_BY(x) [[clang::lifetime_capture_by(x)]]
#else
#define CAPTURED_BY(x)
#endif

// 돌려준 참조는 두 인자가 살아 있는 동안만 쓸 수 있다
const std::string& longer(const std::string& a LIFETIMEBOUND,
                          const std::string& b LIFETIMEBOUND)
{
    return a.size() >= b.size() ? a : b;
}

struct Config {
    std::string name_;
    // 돌려준 참조는 이 객체가 살아 있는 동안만 쓸 수 있다
    const std::string& name() const LIFETIMEBOUND { return name_; }
};

// s가 가리키는 것은 out보다 오래 살아야 한다
void add(std::vector<std::string_view>& out, std::string_view s CAPTURED_BY(out))
{
    out.push_back(s);
}

int main()
{
    const std::string a = "kitchen", b = "hall";
    const Config config{"living room"};
    std::vector<std::string_view> names;
    add(names, longer(a, b));
    add(names, config.name());
    for (std::string_view name : names) std::println("{}", name);
}
```

```text
kitchen
living room
```

`main`의 끝에 틀린 줄 셋을 넣어 봤습니다.

```cpp nocheck
    const std::string& r = longer(a, "temporary");       // 43번 줄
    const std::string& n = Config{"hall"}.name();        // 44
    add(names, std::string("temporary"));                // 45
```

```text nocheck
$ clang++ -std=c++23 -Wall main.cpp
main.cpp:43:38: warning: temporary bound to local reference 'r' will be destroyed
      at the end of the full-expression [-Wdangling]
main.cpp:44:28: warning: temporary bound to local reference 'n' will be destroyed
      at the end of the full-expression [-Wdangling]
main.cpp:45:16: warning: object whose reference is captured by 'names' will be
      destroyed at the end of the full-expression [-Wdangling-capture]
```

GCC는 앞의 둘만 짐작으로 잡았고 45번 줄은 지나쳤습니다.

- **매개변수에 붙인 `lifetimebound`.** 돌려주는 것이 그 인자에 묶인다는 뜻입니다. 멤버 함수의 뒤에 붙이면 `this`에 묶입니다. 생성자의 인자에 붙이면 위의 `NameView`도 잡힙니다.
- **`lifetime_capture_by(x)`.** 그 인자가 `x` 안에 붙잡혀 남는다는 뜻입니다.
- **타입에 붙이는 표시.** `[[gsl::Owner]]`와 `[[gsl::Pointer]]`입니다. 주인의 임시 객체로 가리키는 쪽을 만들면 `-Wdangling-gsl`이 나옵니다.
- **컴파일러마다 다른 표시.** Clang의 표시를 GCC에 주면 `-Wattributes` 경고가, GCC의 것을 Clang에 주면 `-Wunknown-attributes` 경고가 납니다. 그래서 `__has_cpp_attribute`로 감쌌습니다.

<Note kind="warn">
Clang 20은 표시를 믿을 뿐 본문과 맞춰 보지 않습니다. 전역 객체를 돌려주는 함수에 `lifetimebound`를 잘못 붙이자 옳은 코드에 경고가 났고, 인자를 그대로 돌려주는 함수에 붙이지 않자 틀린 코드가 조용히 지나갔습니다. 표시는 문서이고, 문서는 틀릴 수 있습니다.
</Note>

## 끝내 못 잡는 것

두 컴파일러와 [clang-tidy](#/read/cpp-advanced/tool-static)의 `bugprone-`, `clang-analyzer-` 검사가 모두 조용했던 코드 넷입니다.

| 코드 | 보통 빌드 | ASan |
| --- | --- | --- |
| 표시 없는 `add`에 임시 `string`을 넘긴다 | 깨진 글자를 찍고 0으로 끝남 | `heap-use-after-free` |
| `v.front()`의 참조를 쥔 채 `push_back`하고 읽는다 | 실행마다 다른 쓰레기 값 | `heap-use-after-free` |
| 지역 변수를 참조로 캡처한 람다를 `std::function`으로 돌려준다 | `1`, `2`. 맞아 보인다 | `stack-use-after-return` |
| 생성자가 임시 객체의 뷰를 멤버에 넣는다 | 깨진 글자 | `heap-use-after-free` |

첫째와 넷째는 위의 표시를 붙이면 컴파일할 때 잡힙니다. 둘째와 셋째는 Clang 20에 적을 표시가 없습니다. 셋째는 람다를 `auto`로 그대로 돌려줄 때만 Clang이 `-Wreturn-stack-address`로 잡았습니다. 넷 다 [ASan](#/read/cpp-advanced/tool-sanitizers)이 잡았지만 그 줄이 [테스트에서 실행돼야](#/read/cpp-advanced/tool-testing) 합니다.

<Note>
2026년의 Clang 문서에는 함수 안의 흐름을 따라가는 새 분석(`-Wlifetime-safety`)이 올라와 있고, `push_back` 뒤의 사용을 찾는 검사도 실험 단계로 적혀 있습니다. Clang 20은 이 옵션을 모른다고 답해서 이 책에서는 돌려 보지 못했습니다.
</Note>

## 프로파일

경고는 꺼져 있을 수도 있고 컴파일러마다 다릅니다. **프로파일**은 [Core Guidelines의 묶음](#/read/cpp-advanced/safe-guidelines)을 언어로 올리자는 제안입니다. 번역 단위에 프로파일을 걸면, 그 보장을 깨는 코드를 어느 컴파일러든 같은 기준으로 거절합니다.

```cpp nocheck
// 제안의 문법. 이 번역 단위에 초기화 프로파일을 건다
[[profiles::enforce(std::init)]];
```

어쩔 수 없는 곳은 이름을 대고 그 자리에서만 끕니다. 2026년 11월 현재 C++26 초안에는 들어 있지 않고, 다음 표준을 목표로 틀과 프로파일 하나하나가 따로 논의되고 있습니다. 실험용 Clang이 있다고 하지만 이 책의 컴파일러에는 없어서 돌려 보지 못했습니다. 지금은 가까운 것을 켜서 씁니다.

| 프로파일 | 오늘 쓸 수 있는 가까운 것 |
| --- | --- |
| 타입 | `cppcoreguidelines-pro-type-` 검사들, `-Wold-style-cast` |
| 범위 | Clang의 `-Wunsafe-buffer-usage`와 [경화된 라이브러리](#/read/cpp-advanced/safe-hardening) |
| 수명 | 이 페이지의 경고와 표시, 실행 중에는 ASan |

`-Wunsafe-buffer-usage`는 포인터에 번호를 붙여 읽는 곳마다 경고합니다. [앞 페이지의 옛 코드](#/read/cpp-advanced/safe-guidelines)에서 셋이 나왔고 고친 코드에서는 없었습니다. 이런 경고를 `-Werror=dangling`처럼 오류로 올려 두면 그 프로젝트 안에서는 규칙이 됩니다.

## 정리

- GCC는 함수의 꼴로 짐작하고 Clang은 표시를 읽는다. 같은 코드에 두 컴파일러가 내는 경고가 다르므로 둘 다 돌린다
- `lifetimebound`와 `lifetime_capture_by`로 내 함수의 수명 약속을 적으면 Clang이 부르는 쪽을 검사한다. 표시가 맞는지는 검사하지 않는다
- 무효가 된 참조와 돌려준 람다의 캡처는 컴파일할 때 잡히지 않았다. 프로파일은 아직 제안이고, 그 자리는 ASan과 테스트가 메운다
